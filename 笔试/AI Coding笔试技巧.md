## 先别让 AI 写代码
第一句不要说“帮我实现全部功能”。这类题面很长，AI 一旦直接开写，通常会把字段名、状态枚举、时间规则、账务流转混在一起，最后看起来代码很多，但基础契约都不稳。

第一轮建议这样问：
```
先只阅读题面和现有代码，不要修改任何文件。
 
请帮我整理：
1. 这题有哪些核心对象；
2. 每个对象有哪些状态；
3. 哪些字段名、枚举值、ID 规则是硬契约；
4. 哪些接口是基础分，哪些接口是复杂业务分；
5. 哪些动作会产生连锁副作用；
6. 当前代码大概缺什么；
7. 建议按什么顺序实现，先保基础分。
 
不要写代码，只输出做题地图。
```

这一步的作用是让 AI 先进入题目语境。你也能顺手检查它有没有读歪题。如果它连“这是额度批次 + 单据状态 + 虚拟时钟 + 流水对账”都没说出来，后面直接让它写代码大概率会偏。

## 每轮只让 AI 做一类事
AI Coding 工程题最怕一句话塞太多要求。比如“实现请假、销假、加班、离职、结转，并保证账务正确”，这基本就是让 AI 自由发挥。

更稳的节奏是：
```
现在只做基础骨架。
目标是服务能启动，reset 干净，clock 正确，创建和查询接口能跑。
 
不要处理复杂业务。
不要重构无关文件。
完成后列出修改文件和自测命令。
```

等基础骨架能跑，再进入下一轮：
```
现在只做主流程。
目标是让一条正常业务路径从创建到完成能走通。
 
先保证字段名、状态和返回格式完全按题面。
不要处理特殊情况。
不要修改已经通过的基础接口。
完成后给正常路径和非法请求无副作用的测试。
```

再下一轮才补复杂规则：
```
现在只补异常和边界规则。
请先说明每条规则会影响哪些对象和哪些字段，再改代码。
 
限制：
- 不要扩大修改范围；
- 不要为了修一个边界重写主流程；
- 每个失败请求都必须无副作用；
- 重复请求不能重复生效。
```
这种对话方式的核心是“范围控制”。你不是让 AI 展示能力，而是在让它按你的验收顺序搬砖。

## 这题要一直提醒 AI：账务不能只看余额
这题最容易被 AI 写错的地方，是把假期额度当成一个简单余额。题面真正关心的是每个批次的流转：发放、占用、使用、退回、到期、作废、结转，每一步都要能查到。

所以提示词里要反复强调：
```
不要只维护一个总余额。
所有额度变化都要落到具体批次。
每次变化都要追加流水。
不要覆盖旧流水，不要删除历史记录。
余额查询要能从批次和流水解释得通。
```
这个提醒非常重要。因为 AI 很擅长把当前结果凑对，但隐藏测试往往会查历史、查流水、查重复操作后的结果。当前余额看起来对，不代表账是对的。

时间规则要单独拿出来说
只要题目出现“虚拟时钟”，就不要相信 AI 会自动处理好。很多模型会顺手用真实时间，或者只在推进时钟时处理一次，查询时又忘了刷新状态。

可以这样压：
```
现在只审计时间逻辑。
 
要求：
1. 全系统禁止使用真实时间；
2. 所有 created_at、approved_at、closed_at 都取虚拟 now；
3. 到期和超时只随 clock advance 或查询刷新发生；
4. 时间只能向前；
5. 重复推进时钟不能重复产生流水或状态变化；
6. 给我覆盖刚好到边界、超过边界、重复推进的测试。
```
时间题的坑不在“会不会加秒数”，而在边界和幂等。刚好到期算不算、重复推进会不会重复扣账、查询时是否已经体现超时，都是要盯的点。

### 让 AI 先写测试，再让它改代码
当业务越来越复杂时，不要继续让 AI 直接修。更好的提示是：
```
先不要改代码。
 
请根据题面设计 6 个最小自测场景：
1. 正常路径；
2. 非法请求无副作用；
3. 重复操作幂等；
4. 时间边界；
5. 多批次账务；
6. 终态后禁止继续修改。
 
每个场景写清楚请求顺序、预期状态、预期余额或流水变化。
```
测试写出来后再说：
```
现在根据上面的自测，只修第一个失败场景。
先解释失败对应哪条题面规则，再给最小补丁。
不要改测试，不要重构其他模块。
```
这样能避免 AI 看到失败就开始大改。AI Coding 里最贵的不是它不会写，而是它修 A 的时候把 B、C、D 都改坏了。

### 失败反馈不要过度解读
如果平台只告诉你某类用例没过，不要让 AI 反推出隐藏输入。可以这样问：

```
根据当前公开反馈，只判断可能是哪一类规则没覆盖。
不要猜隐藏用例的具体输入输出。
请列出 3 个最可能的题面规则缺口，并给本地可复现的最小测试。
```
这比“帮我修隐藏用例”靠谱。隐藏反馈只能说明方向，不等于告诉你具体 bug。让 AI 猜得越细，越容易把代码改偏。

### 每轮都要加的护栏
我会在每轮提示词后面固定加这段：
```
只处理本轮范围，其他模块不要重构。
不要修改测试。
不要删除已有接口。
字段名、枚举值、返回结构必须按题面。
非法请求必须无副作用。
重复操作必须幂等。
所有时间只用虚拟时钟。
完成后列出：修改文件、影响接口、自测命令、需要回归的旧路径。
```
这几句看起来啰嗦，但很有用。AI 需要明确边界，不然它会为了“更优雅”去重构，为了“更方便”改返回格式，为了“修 bug”清空历史数据。

### 最后要做一次合同审计
临提交前，不要只问“还有什么问题吗”。要让 AI 按题面逐项审计：
```
请做一次提交前合同审计。
 
只检查并修复明确违反题面的地方：
1. 服务启动和端口；
2. reset、ID、自增；
3. 字段名和状态枚举；
4. 所有接口是否存在；
5. 非法请求是否无副作用；
6. 重复操作是否幂等；
7. 虚拟时钟是否没有使用真实时间；
8. 账务字段和流水是否能对账；
9. sample_testcases 和我写的自测是否通过。
 
不要做大重构。
不要引入新依赖。
不要猜隐藏用例。
```
这一步本质是防守。AI Coding 工程题不是代码越多越好，而是题面契约越稳越好。

### 最容易踩的坑
第一，第一轮就让 AI 全量实现。这样最容易得到一坨“看似完整”的代码，但基础字段、状态和返回格式都不稳。

第二，只跑样例。样例通常只覆盖服务连通和最短路径，不能证明账务、时间、幂等、非法请求都对。

第三，让 AI 直接猜隐藏测试。平台反馈只能当方向，不要当题面。正确做法是回到公开规则，构造本地最小场景。

第四，AI 为了修一个点顺手重构。每轮都要限制“只改本轮范围”，否则旧路径很容易被改坏。

第五，忽略无副作用。工程题里非法请求不是“返回错了就算了”，而是不能留下半截对象、半截流水、半截状态。

第六，忽略幂等。同一个审批、撤回、结转、时钟推进重复调用，如果重复扣减或重复退款，隐藏分会掉得很明显。

第七，把历史覆盖掉。账务类题最怕直接改当前值。更稳的是保留历史，用新流水表达变化。
