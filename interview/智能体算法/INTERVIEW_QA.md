# 多任务医学视觉 Agent — 面试问答（真实进度版）

> 口径原则：重点讲已经完成的工程与训练链路；没有稳定日志支撑的最终指标不要写死。

---

## 1. 项目定位

### Q1：一句话介绍这个项目。

**参考回答：**
这是一个基于 `Qwen3-VL` 的医学影像多任务 Agent。我没有把分类、检测、分割写成固定流水线，而是把三类视觉能力封装成工具，让 VLM 根据任务指令自主决定调哪个工具、是否继续交互以及何时停止。

### Q2：这个项目里，你的核心增量是什么？

**参考回答：**
我的工作不是从零写一个全新论文框架，而是基于现有 `MedSAM-Agent` / `verl` 代码做二次开发，重点补齐四部分：
1. 把项目从偏分割任务扩展到`分类 + 检测 + 分割`多任务；
2. 把数据从单一场景扩到 6 个数据集、5 种模态；
3. 增加三后端微服务和多任务 Agent loop；
4. 打通 SFT 数据生成、RL 数据构建和 AMD/ROCm 训练兼容。

### Q3：为什么这算 Agent，而不是普通多模型串联？

**参考回答：**
普通串联一般是固定顺序，比如先检测再分割再分类，模型本身不做决策。这个项目里，VLM 负责“决策层”：它会根据当前任务和上一步反馈，选择调用 `detect`、`classify`、`add_bbox`、`add_point` 或 `stop_action`。也就是说，视觉模型是工具，VLM 是调度者，这就是 Agent 化的核心。

## 2. 架构设计

### Q4：为什么不直接训练一个统一的多任务模型？

**参考回答：**
主要有三个原因：
1. `分类 / 检测 / 分割` 的输出空间差异很大，统一建模成本高；
2. 这个项目想验证的是“VLM 调度工具”的能力，而不是再训练一个更大的端到端视觉模型；
3. 工程上拆成工具后更容易替换后端，比如分割模型以后可以从 `IMISNet` 切到 `MedSAM2`，对 Agent 层影响很小。

### Q5：三个后端服务分别做什么？为什么拆成三个 API？

**参考回答：**
- `segmentation_api.py`：统一封装 `IMISNet / MedSAM2`，支持 bbox、点提示和会话式交互分割；
- `detection_api.py`：封装 `Grounding DINO`，做开放词汇检测；
- `classification_api.py`：封装 `BioMedCLIP`，做零样本文本引导分类。

拆分的好处是：
1. 每个模型依赖不同，单独部署更稳定；
2. 显存和 CPU/GPU 资源可以独立分配；
3. 某个服务故障时不会拖垮整个系统；
4. 更换单个后端模型时，不需要重写整个 Agent。

### Q6：你怎么避免接口被某个数据集写死？

**参考回答：**
我专门把接口从“数据集专用”改成了“调用方传参”。例如分类服务不再内置某个乳腺超声标签映射，而是要求调用方传 `text_prompts`；检测服务也不再默认写死 `breast tumor` 之类的 caption，而是要求调用方显式传入目标描述。这样接口就能被不同模态、不同解剖部位复用。

## 3. 数据工程

### Q7：你这个项目支持哪些数据？

**参考回答：**
当前工程链路支持 6 个数据集：`BUSI`、`Kvasir-SEG`、`COVID-19`、`TN3K`、`AbdomenCT`、`AbdomenMR`。对应 5 种模态：`ultrasound`、`endoscopy`、`xray`、`ct`、`mr`。我把它们统一整理成带 `image_path / mask_path / bbox / label / modality / anatomy / sample_id` 的结构，便于后续 SFT 和 RL 共用。

### Q8：CT/MR 这类 3D 数据怎么接到 VLM 流程里？

**参考回答：**
我新增了 `3D NIfTI -> 2D` 的切片流程。做法是：
1. 读取 3D volume 和 label；
2. 自动找有目标的代表性切片；
3. 生成 2D PNG 图像；
4. 按器官拆成独立 mask，并计算 bbox；
5. 最后再写成 parquet。

这样做的意义是，VLM 和现有工具接口都更适合处理 2D 图像，但又保留了 CT/MR 多器官监督信息。

### Q9：为什么 SFT 用“直接扫图片目录”，RL 用 parquet？

**参考回答：**
这是为了分别优化两类训练的瓶颈：
- `SFT` 更像监督学习，核心是把图像和多轮对话组织成 `ShareGPT` 样式；直接从图片目录生成更直观，也避免先转 parquet 再回读图片的额外开销。
- `RL` 更依赖统一字段和批量采样，`parquet` 更适合 `verl` 的 dataset 读取和多数据集合并。

所以我把两条链路拆开：SFT 偏“图片直扫”，RL 偏“结构化 parquet”。

### Q10：`combined parquet` 的作用是什么？

**参考回答：**
它是把各数据集的 `train/val/test.parquet` 合并成统一总集，方便 RL 直接从一个入口采样多数据源。工程上这比在训练脚本里手写多个路径更清晰，也便于后续做采样比例控制或 ablation。

## 4. Agent Loop 与训练

### Q11：多任务 Agent loop 是怎么工作的？

**参考回答：**
核心逻辑在 `multi_task_agent_loop.py`。流程是：
1. 模型先生成 tool call；
2. Agent loop 执行对应工具；
3. 根据工具类型把结果重新喂回模型；
4. 模型再决定下一步动作。

这里最关键的是“反馈形式因工具而异”：
- `classify` 只回文本；
- `detect` 回检测框 overlay + 文本；
- `add_bbox / add_point` 回 mask overlay + 文本；
- `stop_action` 终止当前 episode。

这让模型每一轮看到的是“更新后的视觉状态”，而不只是静态文本日志。

### Q12：什么叫工具实例持久化复用？

**参考回答：**
在一个 episode 内，我不会每轮都重新初始化工具实例。`multi_task_agent_loop.py` 会为每个工具维护持久化实例 ID，同一条样本的多轮交互复用这个实例，结束时再统一释放。这样能减少重复初始化和状态丢失，尤其对交互式分割更重要，因为同一张图的上下文需要被连续保留。

### Q13：SFT 和 RL 两阶段分别解决什么问题？

**参考回答：**
- `SFT` 负责让模型学会基本的多轮对话格式和工具调用格式，比如 `<tool_call>` 怎么写、什么时候该输出工具参数；
- `RL` 负责优化“策略”，也就是在多种工具之间如何选、何时停止、怎样减少无效步骤。

简单理解：SFT 教会模型“会用工具”，RL 再优化它“用得更合理”。

### Q14：奖励函数是怎么设计的？

**参考回答：**
当前项目里我主要实现了规则版的过程奖励脚本，例如 `cpr_reward.py`。它不是额外训练一个 reward model，而是直接利用 GT 的 mask、bbox、label 来计算：
- 步骤级定位质量；
- 信息增益；
- 跨任务协同；
- 安全惩罚；
- 最终结果分。

这样做的优点是实现快、可解释、且不额外引入训练成本。

## 5. 工程难点与排障

### Q15：这个项目最难的工程问题是什么？

**参考回答：**
最难的不是单点代码，而是“多框架兼容”：`Qwen3-VL`、`LlamaFactory`、`verl`、`vllm/sglang`、三套视觉后端，再加上 AMD/ROCm 环境。很多问题不是业务逻辑错，而是版本兼容、依赖导入、推理引擎不匹配。我实际做了不少脚本和依赖层修补，先把链路跑通，再逐步追求稳定性。

### Q16：为什么 AMD/ROCm 环境特别麻烦？

**参考回答：**
因为很多多模态训练和推理生态默认优先适配 NVIDIA CUDA。到了 ROCm 环境，常见问题包括：
- 某些算子或依赖版本不兼容；
- `vllm` / `sglang` / `verl` 的组合在 AMD 上更容易出问题；
- 不同 wheel、不同 PyTorch/torchvision 版本之间可能连 import 都过不了。

我这里的处理思路是：先保证 SFT 可跑，再让 RL 至少能在 fallback 配置下启动，最后再逐步恢复更高性能的 rollout 方案。

### Q17：如果面试官问“你现在这个项目做到什么程度了”，怎么回答最稳妥？

**参考回答：**
最稳妥的回答是：
- 多任务数据工程已打通；
- 三后端 API 已可独立运行；
- SFT 数据生成与配置已可用；
- `verl` 侧多任务 dataset、agent loop、reward 和训练脚本已补齐；
- AMD 环境兼容做了较多排查；
- 但 RL 的大规模稳定收敛和最终量化指标仍在持续验证。

这样既体现工作量，也不会过度承诺。

## 6. 面试中的高频追问

### Q18：如果不用 Agent，直接人工写一个固定流程不行吗？

**参考回答：**
可以，但那样扩展性差。固定流程适合已知任务，而 Agent 的价值在于：输入只给自然语言目标，它自己决定是先检测、先分类，还是直接交互分割。这种“决策层”更适合多任务和复杂场景，也更容易继续接新的工具。

### Q19：为什么检测用 `Grounding DINO`，分类用 `BioMedCLIP`，分割用 `IMISNet/MedSAM2`？

**参考回答：**
因为三者各自覆盖一个明确能力：
- `Grounding DINO` 适合文本驱动检测；
- `BioMedCLIP` 适合零样本图文匹配分类；
- `IMISNet/MedSAM2` 适合交互式分割。

我更看重的是“工具之间能力互补”，而不是勉强让一个模型做完所有事情。

### Q20：如果现在让你继续推进，下一个优先级是什么？

**参考回答：**
我会优先做三件事：
1. 稳定 RL 训练配置，先拿到可重复的收敛日志；
2. 把 reward 和评估脚本对齐，形成可靠的指标面板；
3. 继续补多数据集 prompt 策略和采样策略，避免不同模态之间互相干扰。

## 8. 30 道高频必问题（精简参考答案版）

> 适合面试前快速过一遍，每题控制在 20-40 秒回答。

### Q1：请你用 2 分钟介绍一下这个项目

**参考回答：** 这是一个基于 `Qwen3-VL` 的医学影像多任务 Agent，目标是把`分类、检测、交互式分割`统一到一个自然语言驱动的决策框架里。我把 `Grounding DINO`、`BioMedCLIP`、`IMISNet/MedSAM2` 封装成工具，让 VLM 根据任务和中间反馈自主决定调用哪个工具、是否继续交互以及何时停止。

### Q2：这个项目解决的核心问题是什么

**参考回答：** 它解决的是医学视觉任务之间割裂的问题。传统做法通常是每个任务一个独立模型、固定串联；这个项目希望让一个 VLM 作为决策层，统一调度不同视觉工具完成多任务分析。

### Q3：为什么这是 Agent，而不是普通多模型流水线

**参考回答：** 因为这里不是预先写死 `detect -> segment -> classify`。VLM 会根据当前任务和上一步结果，动态决定下一步调哪个工具，这种“感知-决策-执行-反馈”的闭环就是 Agent 的核心。

### Q4：Agent 和固定流水线最大的区别是什么

**参考回答：** 固定流水线的顺序是人工预设的，遇到中间结果不好时没有自主调整能力。Agent 可以根据检测框、分割 mask、分类结果这些中间反馈重新规划下一步，所以更适合复杂和复合任务。

### Q5：你在这个项目里的核心贡献是什么

**参考回答：** 我主要做了四块：多任务工具化、6 数据集多模态数据工程、三后端 API 服务，以及 SFT 到 RL 的训练链路打通。重点不是单独训练一个视觉模型，而是把“工具调度能力”真正落到系统里。

### Q6：目前项目做到什么程度了

**参考回答：** 目前已经完成多任务数据工程、三后端服务、SFT 数据生成与配置、RL 训练骨架和 reward 脚本。当前还在持续验证 RL 的稳定收敛和最终量化指标，这部分我会实话实说。

### Q7：这个系统的整体架构是怎样的

**参考回答：** 上层是 `Qwen3-VL` 作为策略模型，中间是 Agent loop，底层是三个工具服务：检测、分类、分割。Agent 生成 tool call，工具执行后把文本或 overlay 图回灌给模型，模型再决定下一步动作。

### Q8：为什么要拆成三个后端 API，而不是一个大服务

**参考回答：** 因为三个模型依赖不同、资源需求不同、故障模式也不同。拆开后更容易独立部署、独立扩缩容、独立替换模型，工程上更稳。

### Q9：为什么检测选 `Grounding DINO`

**参考回答：** 因为它支持文本驱动的开放词汇检测，和 Agent 的自然语言指令形式天然匹配。我不需要为每个医学数据集单独训练检测头，而是让 Agent 直接给出目标描述。

### Q10：为什么分类选 `BioMedCLIP`

**参考回答：** 因为它本质上是图文对齐模型，适合零样本分类。只要给定候选文本描述，就能做不同数据集、不同模态下的分类判断，接口复用性比较强。

### Q11：为什么分割选 `IMISNet/MedSAM2`

**参考回答：** 因为这个项目强调的是交互式分割，不是一次性静态分割。`bbox + point` 这类交互提示非常适合 Agent 多轮决策，也更接近真实使用场景。

### Q12：多任务 Agent loop 是怎么工作的

**参考回答：** 先由模型生成工具调用，再执行工具，再把结果回灌给模型，循环直到 `stop_action`。其中分类回文本，检测回框的 overlay，分割回 mask overlay，不同工具的反馈形式不一样。

### Q13：为什么一定要有 `stop_action`

**参考回答：** 因为 Agent 不仅要学会“怎么做”，还要学会“什么时候该停”。没有显式停止动作，模型容易反复调用工具，导致效率低，甚至出现无意义交互。

### Q14：什么是工具实例持久化复用

**参考回答：** 就是在一个 episode 内复用同一个工具实例，而不是每一轮都重新初始化。这样能减少重复加载和状态丢失，尤其对交互式分割很重要，因为同一张图的会话状态需要连续保留。

### Q15：这个项目支持哪些数据

**参考回答：** 当前支持 6 个数据集：`BUSI`、`Kvasir-SEG`、`COVID-19`、`TN3K`、`AbdomenCT`、`AbdomenMR`。对应 5 种模态：`ultrasound`、`endoscopy`、`xray`、`ct`、`mr`。

### Q16：为什么要扩到 6 个数据集、5 种模态

**参考回答：** 因为如果只在单一数据集里做，很难体现 Agent 的泛化和工具复用价值。多数据集、多模态能更好地验证这个框架是不是一个真正可扩展的系统。

### Q17：CT/MR 这类 3D 数据是怎么处理的

**参考回答：** 我把 `3D NIfTI` 先转成 2D 切片，再生成对应的器官 mask、bbox 和 parquet。这样既能保留监督信息，又能复用现有的 2D VLM 和工具接口。

### Q18：为什么要把 3D 转成 2D

**参考回答：** 因为当前 VLM、检测和交互式分割工具都更适合处理 2D 图像。直接上 3D 会显著增加建模和部署复杂度，所以先做 2D 化是更现实的工程方案。

### Q19：为什么 SFT 用直接扫图片目录，而 RL 用 parquet

**参考回答：** SFT 更关注图像和对话样本的组织，直接从图片生成 `ShareGPT` 数据最直观，也更快。RL 更需要统一字段、批量采样和多数据集合并，所以 parquet 更适合。

### Q20：`combined parquet` 的作用是什么

**参考回答：** 它是把每个数据集的 `train/val/test.parquet` 合并成统一总入口。这样 RL 可以直接在一个数据源里采样多种任务和多种模态，管理起来更清晰。

### Q21：SFT 阶段到底在教模型什么

**参考回答：** SFT 主要教模型学会正确的工具调用格式和多轮交互结构。简单说，就是先让模型“会用工具”，而不是一上来就追求最优策略。

### Q22：为什么选 `LlamaFactory + LoRA` 做 SFT

**参考回答：** `LlamaFactory` 对多模态 SFT 配置比较方便，数据格式和训练流程也比较成熟。LoRA 的好处是显存友好、迭代快，适合先快速验证 Agent 工具调用能力。

### Q23：为什么 SFT 之后还要做 RL

**参考回答：** 因为 SFT 只能让模型学会“调用格式”，不一定学会“决策最优”。RL 的作用是进一步优化策略，比如少走无效步骤、合理选择工具、在合适的时候停止。

### Q24：为什么用 `verl` 和 `GRPO`

**参考回答：** `verl` 更适合做大模型的多轮 RL 和工具交互训练。`GRPO` 不需要单独训练 critic，在这种多轮工具调用场景下实现成本和显存压力都更可控。

### Q25：你的 reward 是怎么设计的

**参考回答：** 我做的是规则版过程奖励，综合看定位质量、信息增益、跨任务协同、安全惩罚和最终结果。核心思路是：不仅看最后对不对，也看每一步操作有没有价值。

### Q26：为什么 reward 要看“过程”，不能只看最终结果

**参考回答：** 因为 Agent 场景里，过程本身就是学习目标。如果只看最终结果，模型可能通过很多无效步骤才碰巧答对，但这不是真正好的策略。

### Q27：你怎么避免接口被某个数据集写死

**参考回答：** 我的原则是把数据集语义放到调用参数，而不是写死在服务里。比如分类服务要求调用方传 `text_prompts`，检测服务要求显式传 `caption`，这样接口才能跨数据集复用。

### Q28：如果某个工具调用失败了怎么办

**参考回答：** 工具层会把错误信息回传给 Agent，而不是直接让整个流程崩掉。这样模型至少能看到失败反馈，后续可以重试、换工具，或者终止当前路径。

### Q29：这个项目最难的工程问题是什么
