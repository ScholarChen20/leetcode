# AI Agent 方向面试题及参考答案

## Q2. ReAct 流程如何实现，Agent 如何完成规划和执行

**核心原理：** ReAct = Reasoning + Acting 交替执行。LLM 先推理当前状态（Thought），决定调用哪个工具（Action），获取工具返回（Observation），再进入下一轮推理，循环直到任务完成。

**执行流程：**
1. 将用户任务和可用工具列表注入 System Prompt
2. LLM 输出 Thought（分析）+ Action（工具调用）
3. 解析 Action，执行对应工具，获取 Observation
4. 将结果追加到上下文，进入下一轮
5. 当 LLM 输出 Final Answer 时结束

**常见问题及解决：**
- LLM 输出格式不稳定 → 改用 Function Call 原生接口替代文本解析
- 无限循环反复调同一工具 → 加重复检测 + 最大步数限制
- 工具参数错误 → Schema 校验 + 自动重试
- 上下文膨胀 → 步骤摘要压缩
- 幻觉调用不存在的工具 → 严格匹配工具列表

**适用场景：** 探索性强、不确定需要几步的任务，如信息检索、简单问答。

## Q3. 为什么使用 Workflow 进行任务编排，而不是直接采用 ReAct

**核心原因：** ReAct 每步都让 LLM 动态决策，在确定性强、步骤多的任务中存在三个问题——Token 消耗高（每步都要推理）、可控性差（随时可能偏航）、容易陷入循环。Workflow 把已知流程固化下来，只在分支点让 LLM 决策，大幅减少不必要的 LLM 调用。

**两者区别：**

| 维度 | ReAct | Workflow |
|---|---|---|
| 决策方式 | 每步 LLM 动态决策 | 流程预定义，分支点才决策 |
| Token 消耗 | 高（每步完整推理） | 低（固定步骤免推理） |
| 可控性 | 低，容易偏航 | 高，流程可审计 |
| 灵活性 | 高，能处理未知任务 | 低，只覆盖预定义流程 |
| 适合场景 | 探索性、开放性任务 | 确定性强、步骤固定的任务 |

**实际选择：** 简单任务用 ReAct 即可；多步骤固定流程用 Workflow；复杂任务用混合模式——Workflow 做整体编排，关键节点内嵌 ReAct 处理不确定性。

## Q4. Plan Mode 具体设计，任务拆解和执行流程

**整体流程：** 规划 → 执行 → 反思 → 输出。

**规划阶段：** LLM 将用户任务拆解为有序子任务列表，每个子任务包含描述、依赖关系、预期工具和预期输出。限制最大子任务数（5-8 个），过细则合并。

**执行阶段：** 按依赖关系拓扑排序，无依赖的子任务可并行。每个子任务执行时注入前置任务的结果作为上下文。子任务内部可用 ReAct 执行。

**反思阶段：** 每个子任务完成后检查结果是否符合预期。不符合则重试或重新规划剩余部分。重要决策节点可暂停等用户确认。

**关键设计：**
- 每个子任务独立上下文，不共享全部历史，控制 Token
- 计划可动态调整，某步失败触发重新规划
- 与 ReAct 的关系：Plan Mode 是全局编排，ReAct 是子任务内的执行引擎

## Q5. 多 Agent 场景下子 Agent 如何分配和协同

**三种常见编排模式：**

1. **中心编排（Hub-and-Spoke）：** 主 Agent 负责分析和分配任务，子 Agent 执行后结果回传主 Agent 综合。最常见，解耦性好。
2. **流水线（Pipeline）：** Agent 串联，前一个的输出是后一个的输入。适合有明确先后顺序的任务。
3. **并行+合并（Parallel+Merge）：** 多个子 Agent 同时执行独立任务，最后由 Merge Agent 汇总。适合可并行的场景。

**任务分配策略：** 主 Agent 通过 LLM 推理，根据子 Agent 的能力描述匹配任务；或基于 Embedding 相似度匹配。

**子 Agent 间信息传递：** 最常用的是主 Agent 中转——子 Agent 结果先摘要再传给下一个，避免上下文膨胀。复杂场景可用共享存储（Blackboard 模式），所有 Agent 读写同一共享状态。

**失败处理：** 子 Agent 失败时重试 + 降级换策略，主 Agent 可动态重新分配任务。

## Q6. 上下文压缩策略及实际 Token 节省

**为什么需要：** ReAct 多轮执行后上下文持续增长，10 轮可能 5000-10000 Token，20 轮可能超过 20000，导致触发窗口限制、成本飙升、延迟增加。

**四种压缩策略：**

1. **步骤摘要：** 保留最近 3 轮完整内容，更早的轮次用 LLM 压缩成一句话。如 800 Token 的工具返回压缩成 30 Token 的摘要。
2. **滚动摘要：** 每 N 轮做一次摘要，摘要不断累积合并，始终只保留最新版本。
3. **结构化提取：** 不做文本摘要，而是提取关键信息为结构化 KV 存储，不占用对话上下文。如天气、航班号、价格等。
4. **工具结果裁剪：** 搜索返回 2000 Token 截取 Top-3 相关段落约 200 Token。

**实际效果：** 组合使用后，20 轮对话从约 12000 Token 降到约 2500 Token，节省约 79%。

**触发条件：** 上下文 Token 超过阈值时触发；每完成 N 轮自动压缩；工具返回结果超长时立即裁剪。

## Q7. 压缩后关键信息保留的评估方法和指标

**三种评估方法：**

1. **任务完成率对比：** 同一批任务分别跑压缩前和压缩后版本，对比完成率。如从 85% 降到 82%，3% 的损失换来 79% 的 Token 节省，可接受。
2. **人工抽样评估：** 抽样 50 个对话，对比压缩前后上下文，人工标注关键信息是否丢失，计算保留率。
3. **LLM-as-Judge：** 用 LLM 自动评估压缩后上下文是否保留了完成任务所需的关键信息，输出保留率、丢失内容和是否仍可完成。

**核心指标：**

| 指标 | 目标 |
|---|---|
| 任务完成率损失 | < 5% |
| 关键信息保留率 | > 90% |
| 信息失真率（压缩引入错误） | < 3% |
| Token 压缩比 | < 30% |
| 回答质量评分差 | < 0.5（满分 5） |

**评估流程：** 准备 100 个多轮 Agent 对话测试集 → 分别跑压缩前/后版本 → 对比任务完成率、答案质量、关键信息保留 → 统计指标决定压缩参数。

## Q8. 项目中涉及的指标数据是如何统计和验证的

**指标体系分三层：**

1. **任务级指标：** 任务完成率、完成准确率（人工标注 + LLM Judge）、平均执行步数、平均耗时。
2. **效率指标：** 平均 Token 消耗、平均延迟（TTFT/TPOT）、工具调用成功率、循环终止率。
3. **业务指标：** 用户满意度、采纳率、人工干预率、错误率。

**评测集来源：**
- 线上真实用户对话脱敏后筛选，覆盖典型场景和边缘 case
- 人工构造复杂任务，确保覆盖多步骤、多工具组合
- Badcase 回流，把线上失败的 case 加入评测集持续迭代

**保证可靠性：**
- 评测集和训练集严格隔离，避免数据泄漏
- 每次改动后在同一评测集上回归测试，保证可比性
- 同时用人工标注和 LLM-as-Judge 双重验证，人工抽检比例不低于 20%
- 多次运行取平均值，排除 LLM 随机性影响
- 建立版本化评测报告，每次改动记录指标变化

## Q9. Agent 开发中遇到的典型问题和踩坑

**踩坑一：LLM 输出格式不稳定**
- 问题：ReAct 中 LLM 经常输出格式不符的 Action，解析失败率约 15%
- 解决：迁移到 Function Call 原生接口；加 fallback 二次修正；Schema 校验补默认值
- 效果：失败率降到 1% 以下

**踩坑二：Agent 无限循环**
- 问题：复杂任务中反复调用同一工具不收敛，循环率约 8%
- 解决：重复 Action 检测（相同工具+参数超过阈值即终止）；每 3 步 Reflection 检查是否有进展；历史摘要注入让 LLM 意识到重复
- 效果：循环率降到 1% 以下

**踩坑三：多 Agent 上下文膨胀**
- 问题：子 Agent 间传递大段结果导致上下文爆炸
- 解决：结果先摘要再传递；结构化提取关键字段；大文件存外部只传引用
- 效果：Token 消耗降低约 60%

**踩坑四：偏好提取误判**
- 问题：LLM 从对话提取的偏好不准确，误提取率约 12%
- 解决：置信度阈值过滤；同一偏好信号出现 2 次以上才持久化；用户可查看修正
- 效果：误提取率降到 3% 左右

**总结的优化方法论：** 问题定位先看数据（日志、指标），再定方案；每个优化必须有前后对比的量化数据；Badcase 持续回流形成闭环。

## Q10. 如何理解 Agent 中的长短期记忆

**短期记忆：** 当前对话/任务执行过程中的上下文，包括用户输入、中间步骤、工具结果。特点是时效性强、实时读写、随会话结束而清除。存在于 LLM 的上下文窗口中，受 Token 限制需要压缩管理。

**长期记忆：** 跨会话持久化的信息，包括用户偏好、历史结论、知识积累。特点是持久存储、可检索、需要更新和淘汰机制。

**短期记忆实现：**
- 上下文窗口内管理：保留最近 N 轮完整内容 + 历史摘要
- 压缩策略：步骤摘要、滚动摘要、结构化提取（详见 Q6）
- 超长时触发压缩，保证关键信息不丢

**长期记忆实现：**
- 向量数据库存储历史对话和知识，用 Embedding 检索召回相关记忆
- 结构化存储用户偏好（Redis + DB），每次对话注入
- 记忆更新：新信息覆盖旧信息，过时信息定期淘汰
- 记忆检索：根据当前任务语义召回相关历史记忆，注入上下文

**两者的关系：** 长期记忆通过检索注入短期记忆发挥作用。即：从长期存储中检索相关内容 → 注入当前上下文 → 作为短期记忆参与推理。

## Q11. 是否了解 KV Cache，它在大模型推理中起什么作用

**是什么：** Transformer 自回归生成时，前面所有 Token 的 Key 和 Value 计算结果不变。KV Cache 把这些中间结果缓存下来，避免每生成一个新 Token 就重新计算全部历史。

**为什么能加速：** Decode 阶段每步只需计算新 Token 的 K/V 追加到 Cache，不需要重复计算历史。时间复杂度从 O(n²) 降到 O(n)，生成速度大幅提升。

**显存占用：** KV Cache 显存 = 2 × 层数 × KV 头数 × 头维度 × 序列长度 × Batch × 数据类型字节数。模型越大、上下文越长、并发越多，KV Cache 占用越大，甚至超过模型权重本身。

**带来的挑战和优化：**
- 显存碎片严重 → vLLM 的 PagedAttention 按块分页管理，利用率从约 20% 提升到约 96%
- 并发受限 → GQA/MQA 减少 KV 头数，降低 Cache 体积
- 多请求前缀重复 → Prefix Cache 共享相同前缀的 KV
- Prefill 阶段不受益 → Prefill 是计算密集型，KV Cache 主要优化 Decode 阶段

**一句话总结：** KV Cache 是 LLM 推理加速的核心机制，用空间换时间，但也带来显存管理挑战。

## Q12. Skill 机制了解多少，渐进式加载如何实现

**Skill 是什么：** Agent 的能力插件，封装了特定领域的工具集、Prompt 指引和工作流程。比 Tool 粒度更大——一个 Skill 可包含多个 Tool 和多步骤工作流。

**Skill vs Tool：** Tool 是单一函数（如搜索），Skill 是一组相关能力（如「PDF 处理」含文本提取、图片识别、表格解析）。Tool 无状态，Skill 可有内部状态。

**为什么需要渐进式加载：**

如果把所有 Skill 的完整信息（工具定义、Prompt、示例）一次性加载到上下文，几十个 Skill 可能占用数千 Token，导致：
- 上下文窗口浪费在 Skill 描述上
- LLM 注意力被分散，选择准确率下降
- 每次请求成本增加

**渐进式加载实现：**
1. **注册阶段：** 所有 Skill 注册到 Registry，只维护名称 + 简短描述（每个约 20-30 Token）
2. **匹配阶段：** 用户输入任务后，用 Embedding 相似度或 LLM 判断哪个 Skill 最相关
3. **加载阶段：** 只把匹配到的 Skill 的完整信息（工具定义、详细 Prompt、示例）动态注入上下文
4. **执行阶段：** Skill 内部按需加载子工具，用完即卸载

**效果：** 上下文只包含当前需要的 Skill，Token 开销降低约 70%，Skill 选择准确率反而提升（候选少了，LLM 判断更准）。

## Q13. 用户偏好信息如何处理和存储，为何异步

**偏好类型：** 显式偏好（用户主动设置的 语言、格式、风格）和隐式偏好（从交互行为推断的 常用工具、提问习惯、技术深度）。

**存储方案：**
- 热数据存 Redis，读取延迟 < 1ms，每次对话注入用
- 冷数据存 PostgreSQL，持久化、可分析
- 更新流程：用户交互 → 提取偏好变化 → 写入 Redis + DB

**为什么异步：** 偏好提取可能涉及 LLM 调用，耗时 1-3 秒。如果同步处理，用户每次发消息都要等偏好提取完才能收到回复，体验差。

**异步方案：** 主流程读已有偏好 → LLM 生成回复 → 立即返回用户（< 200ms）；同时异步任务提取新偏好 → 写入 Redis + DB。偏好更新失败不影响当前对话，下次对话时生效即可。

**异步的额外好处：** 不阻塞用户、容错（偏好更新失败不影响对话）、可批量写入降低 DB 压力、最终一致即可（偏好不需要实时生效）。

**偏好准确性保障：** 置信度阈值过滤（低置信度不更新）、多轮确认（同一信号出现 2 次以上才持久化）、用户可查看和修正。

## Q15. 团队协作和沟通困难的解决

**场景一：业务团队不配合**
- 问题：推动 Agent 框架接入客服团队，对方觉得成本高、效果不确定
- 解决：先了解对方痛点，做小场景 Demo 让效果说话，提供标准 SDK 降低接入成本，找同盟者先试点再推广
- 结果：从"要我接"变成"我要接"

**场景二：需求频繁变更**
- 问题：产品频繁调整需求，架构反复返工
- 解决：推动需求评审会，变更需说明理由和影响；核心架构预留扩展点；建立优先级机制；每周同步进度
- 结果：返工率降低约 50%

**场景三：跨团队技术对齐**
- 问题：前后端对接口设计有分歧，阻塞开发
- 解决：拉技术对齐会，不争"谁对"而是对比方案优劣势列表；引入第三方做技术决策；确定后写文档双方确认
- 结果：1 天内对齐，后续无返工

**总结方法论：** 换位思考理解对方顾虑；用效果和数据说话而非口头说服；降低对方接入门槛；用流程机制减少摩擦；先找同盟者试点再推广。

## Q16. 循环链表算法题

**核心特点：** 尾节点的 next 指回头节点，形成环。

**关键设计：**
1. 维护 tail 指针，尾插 O(1)
2. 遍历终止条件是回到 head（而非 next 为 None）
3. 删除时需特殊处理 head 和 tail 指针更新

**操作复杂度：** append O(1)、prepend O(1)、delete O(n)、traverse O(n)。

**思路讲解：**
- 插入：空链表时 head 和 tail 都指向新节点，节点 next 指向自己；非空时 tail.next 指向新节点，新节点 next 指向 head，更新 tail
- 删除：从 tail 开始遍历一圈，找到目标后 prev.next = curr.next，同时更新 head/tail 指针
- 遍历：从 head 出发，curr = curr.next，回到 head 时停止

**快慢指针检测环：** 快指针每次走 2 步，慢指针每次走 1 步。有环则快指针一定追上慢指针（差距每轮缩小 1，最多走环长度步相遇）；无环则快指针先到达 None。

**约瑟夫环应用：** n 个人围一圈，每数到 k 淘汰一个。用循环链表模拟，走 k-1 步后删除下一个节点，重复直到只剩一个。复杂度 O(n×k)。
