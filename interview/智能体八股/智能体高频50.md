### Agent 基础与核心范式

**1. 什么是 ReAct？它的思考-行动-观察循环和工具调用流程是怎样的？**

ReAct（Reasoning + Acting）是一种将推理与行动相结合的Agent范式。其核心是让LLM交替生成推理轨迹（Thought）与任务操作（Action），再利用环境反馈（Observation）更新后续推理。这打破了传统语言模型“输入-输出”的单向链路，使其从“被动应答者”升级为“主动问题解决者”。

其循环流程为：**思考（Thought）** → **行动（Action）** → **观察（Observation）** → **重复（Repeat）**。具体地，Agent基于当前状态与历史信息进行推理；然后执行工具调用或生成最终答案；接着接收工具执行的结果；最后基于观察结果继续思考和行动，直到任务完成。

**2. RAG 中长文档切片的粒度和分块策略如何设计与优化？**

文档分块策略是决定RAG效果的决定性因素，业界共识是80%的RAG失败可追溯到切块决策。

设计与优化需从以下几个方面考虑：
- **切块策略选择**：有固定大小切块、基于分隔符切块、递归字符切块、语义切块和父子层级切块等。通用场景推荐LangChain的递归字符切块；对检索质量要求极高时，可用语义切块。
- **切块大小**：推荐 **300～500 tokens** 是企业级RAG的最佳区间。过大会导致信息密度不足，过小会切碎语义。
- **重叠区域**：相邻切块间保留 **10%-20%** 的重叠区域，确保跨切块信息不丢失。

**3. RAG 系统评测的维度和常用指标如何设计？**

RAG系统评测主要分为两大维度：
- **检索评估**：评估检索到相关文档的能力。常用指标包括**命中率（Hit Rate）** 、**精度（Precision）** 和**召回率（Recall）**。
- **生成评估**：评估LLM基于检索结果生成的答案质量。常用指标包括**忠实度（Faithfulness）** ——答案是否忠实于检索到的文档、**答案相关性（Answer Relevance）** 和**上下文利用率**等。

此外，还需关注**系统性能**，如成本和延迟。

**4. RAG 系统中的文档分块策略如何设计？chunk 大小、父子分块和不同文档格式要怎么取舍？**

分块策略需根据文档格式和场景灵活取舍：
- **chunk大小**：推荐 **300-500 tokens** 作为起点。结构化文档可适当增大，非结构化文本可适当减小。
- **父子分块（Parent-Child Chunking）** ：这是解决“检索精度”与“生成上下文”矛盾的最佳实践。小块（Child Chunk，100-200 token）用于高精度检索；大块（Parent Chunk，500-1500 token）包含完整上下文，当小块被命中后，真正喂给LLM的是其对应的父块。这种方式兼顾了召回率和上下文完整性。
- **不同文档格式**：对于Markdown、HTML等结构化文档，适合按标题层级切块；对于PDF、Word等非结构化文档，可使用语义切块。

**5. 多 Agent 协作有哪些常见模式、适用场景和主要挑战？**

常见模式包括：
- **串行模式（Pipeline）** ：Agent A的输出是Agent B的输入，适用于有强依赖关系的任务流。
- **并行模式（Parallel）** ：多个互不依赖的子任务同时进行，以缩短总执行时间。
- **编排模式（Orchestrator-Workers）** ：一个“总控Agent”负责任务拆解、调度和结果整合。
- **辩论模式（Debate）** ：多个Agent对同一问题进行辩论和交叉验证，以提高答案质量。

适用场景：多Agent协作像一个“专家团队”，能有效应对复杂任务挑战。**主要挑战**包括：调度架构复杂，易出现死循环或任务冲突；通信不可控、故障易扩散；以及运维成本高。

**6. Agent 的上下文管理和记忆机制通常如何设计，如何避免上下文过长或信息污染？**

设计上，通常将记忆分为：
- **短期记忆**：维护当前会话的即时上下文。
- **长期记忆**：存储跨会话的事实、用户偏好等。

避免上下文过长和信息污染的常用策略有：
- **自动摘要**：token超阈值时，自动将旧消息压缩成摘要。
- **上下文修剪**：只保留最近N轮对话。
- **针对性检索**：不批量加载所有上下文，只检索最相关的片段。
- **轮数限制**：设置最大对话轮数，超出则强制结束或重启。

**7. 在开发工作中如何使用 AI 工具辅助编程和提效？**

可以从“被动问答”转向“让AI主动干活”。具体模式包括：
- **Vibe Coding（氛围编程）** ：用自然语言描述意图，让AI生成代码。
- **囤积已知技巧**：把所有解决过的问题存档，供AI参考复用。
- **红绿TDD（测试驱动开发）** ：先让AI写测试，再写实现代码。
- **线性演练**：让AI按步骤执行复杂任务，便于调试。

**8. 大模型长上下文场景下，如何进行上下文压缩与优化？**

核心方法包括：
- **KV Cache压缩**：通过量化、剪枝等技术减少KV Cache内存占用。
- **语义保留压缩**：以语义块而非孤立token为压缩单元。
- **摘要压缩**：用辅助模型对中间轮次对话进行摘要。
- **两级摘要**：将原始对话压缩为单任务摘要和宏观摘要两层。

**9. 在 LLM 或 RAG 应用中，如何减少和规避幻觉问题？**

可通过多层防护体系来压制幻觉：
- **检索层**：做Query Rewrite、Hybrid Search + Rerank，确保检索到的上下文准确。
- **生成层**：RAG的核心逻辑是模型不记忆知识、只检索知识，让模型做阅读理解总结而非原创事实编造。
- **校验层**：用**忠实度（Faithfulness）** 等指标评估生成内容是否忠实于检索文档。
- **工程层**：多轮检索验证、零温度生成等。

**10. 在 RAG 中，既然向量检索已经计算了相似度，为什么还需要引入交叉编码器进行重排？**

根本原因在于**向量检索（双编码器/Bi-Encoder）缺乏Query与文档之间精细的交叉注意力交互**。向量检索将Query和文档独立编码为向量再计算相似度，速度快但精度有限。而**交叉编码器（Cross-Encoder）** 将Query和单个文档拼接成一个输入对，共同输入到一个完整的Transformer模型中进行处理，能同时分析两者之间的模式、上下文和共享信息，提供更细致、更准确的相关性评估。

**11. 如何评估 Rerank 的有效性，常用哪些指标？**

评估Rerank有效性的常用指标包括：
- **NDCG@k（归一化折损累计增益）** ：衡量排序质量，考虑相关性的等级。
- **Recall@k**：对比Rerank前后的召回率，评估是否保留了召回能力。
- **MRR（平均倒数排名）** ：衡量第一个相关结果的位置。
- **Precision@K（精确率）** 。
- **Latency（延迟）** ：评估Rerank带来的时间成本。

**12. GRPO 和 PPO 的核心区别是什么？在信用分配、优势估计和方差控制上分别有什么差异？**

- **信用分配（Credit Assignment）** ：PPO支持**细粒度的token级信用分配**，而GRPO仅提供**整条轨迹（episode）级别的信用**，同一轨迹中的每个token获得相同的优势值。
- **优势估计（Advantage Estimation）** ：PPO依赖**广义优势估计（GAE）** ，需要训练一个价值模型（Value Model/Critic）；GRPO**无需Critic模型**，通过组内归一化来估计优势。
- **方差控制（Variance Control）** ：GRPO的**组内归一化天然引入了基线，方差更低**；PPO则依赖GAE中的折扣因子来平衡偏差与方差。

**13. 工具调用的安全控制与敏感接口限制如何实现？**

实现安全控制的核心原则是**将提示理解与系统决定分离**，不能用自然语言描述替代确定性权限控制。具体措施包括：
- **策略化访问控制**：为Agent工具使用实施基于策略的访问控制。
- **工具调用防火墙**：每次调用前做安全评估，输出allow、warn、block、review四类决策。
- **最小权限原则**：动态注入最小权限，避免Agent滥用高危操作。
- **人工介入（HITL）** ：对敏感操作暂停执行，等待人工审批。

**14. ReAct 与 Plan-and-Execute 有什么区别，分别适用于什么场景，为什么在项目中会选择 ReAct？**

- **ReAct**：**边想边做**，每一步都是“思考→行动→观察”的循环。适合**开放式探索、工具调用不确定**的场景，如FAQ问答、客服Agent、调试型Agent。
- **Plan-and-Execute**：**先全局规划，再逐步执行**。适合**流程型任务、步骤有强先后依赖**的复杂长任务。

选择ReAct的原因：它是**一步一想**的灵活模式，对于路径未知的排查任务非常适用。在构建多工具智能体时，ReAct往往是**第一选择**。

**15. 如何自建一个 Agent 系统，并将其做到生产级落地？**

从原型到生产级落地，需关注：
- **架构选型与标准化**：从本地原型开发走向标准化架构。
- **工程化保障**：做好工具执行的可靠性、错误处理和可观测性。
- **云原生部署**：使用Docker、Kubernetes进行容器化部署和编排。
- **状态管理**：对长时任务的会话状态进行持久化。
- **测试与评估**：建立完善的测试体系和评估基准。

**16. 向量数据库检索到的历史信息即使语义相关但时间过久，还能直接使用吗？**

不能直接使用。需要引入**时间维度过滤**，在检索时结合语义相似度和时间新鲜度。向量数据库应支持按时间范围过滤，或对记忆元数据加入时间戳并进行时效性评分。在混合检索中，可将**向量相似度、关键词匹配和时间新鲜度**三者结合起来评分。

**17. 单 Agent 和多 Agent 分别适用于哪些场景，如何判断是否需要多 Agent？**

- **单Agent**：适合**问题边界清晰、任务链路短、确定性高**的场景。实现简单、可控性强、运维成本低。
- **多Agent**：适合**复杂拆解型、跨领域**的任务，在上下文保护等场景下能产生持续正向收益。

判断是否需要多Agent的准则是：**默认先做单Agent**。只有**同时满足两个条件**才考虑拆分成多Agent：**存在稳定、可描述的任务边界**；**拆分带来的收益经过评估能覆盖协调成本**。

**18. Rerank 的 Top-k 数量通常如何确定？**

Rerank的Top-k数量需在**召回率、延迟和成本**之间权衡。典型配置为：
- **召回阶段（粗排）** ：取 **Top 20-50** 个候选文档。
- **精排阶段（Rerank）** ：用Rerank模型重新打分后，取 **Top 5-10** 个文档喂给LLM。

具体数值取决于**延迟预算**和**初检检索器的噪声水平**。也可采用**动态TopK + 断崖检测算法**，根据分数分布自适应调整。

**19. 工具调用超时或返回空值时，如何设计 Prompt 让 Agent 进行用户反馈？**

Prompt中应加入**工具回退（Tool Fallback）规则**：当一个工具返回空结果或无意义内容时，模型应**先尝试替代工具**，而不是直接告诉用户“做不到”。同时，Prompt应要求Agent在工具失败时向用户提供**清晰的解释**，包括失败原因和已尝试的补救措施。

**20. MCP 和 Skills 有什么区别？它们分别解决什么问题？**

MCP和Skills**解决完全不同的问题，且互为补充**：
- **MCP（Model Context Protocol）** ：是AI连接外部系统的 **“USB-C协议”** ，解决 **“能不能连”** 的问题。它在架构层面解决AI能否触达外部世界的问题。
- **Skills**：是AI执行任务的 **“操作手册”** ，解决 **“会不会做”** 的问题。它在应用层面解决AI具体会做什么、怎么做的问题。

**21. LLM 是如何实现工具调用的？Function Calling 的底层机制与执行流程是什么？**

Function Calling的完整流程分为五步：
1. **工具注册**：系统预先注册所有可用函数，每个函数包含名称、描述和参数Schema。
2. **模型决策**：LLM根据用户意图判断是否需要调用工具、调用哪个工具以及传什么参数。
3. **工具调用**：系统解析LLM输出的工具调用请求。
4. **函数执行**：传入LLM生成的参数，执行实际函数。
5. **结果返回**：将执行结果返回给LLM，进入下一轮推理。

LLM在此过程中扮演的是 **“调度员”** 的角色，并非直接运行代码。

**22. 你做过的 AI 项目中最困难的技术挑战是什么，你是如何解决的？**

（开放式问题，参考答案框架）常见的技术挑战及解决思路：
- **可靠性问题**：Agent在受限场景下产生不可预期的输出。解决：引入**零信任工具链**，做Schema强校验。
- **状态同步失效**：多Agent之间的状态同步失效。解决：建立**结构化任务图**精准记录任务节点、执行顺序与核心状态。
- **概率级联故障**：中间一次计算错误导致后续全部错误。解决：引入**检查点（Checkpoint）** 机制，长时任务可恢复。

**23. 当 Agent 需要调用多个工具或工具之间存在依赖关系时，调度引擎应该如何设计？**

调度引擎的核心设计思路是**将任务规划与工具执行解耦**，可采用**双层架构**：
- **规划层**：LLM-based Agent决定是否直接响应、澄清意图或检索并执行工具链。
- **执行层**：使用**工具关系图**来决定使用哪些工具以及执行顺序。

具体机制包括：
- **并行执行**：无依赖关系的工具可并行执行。
- **串行执行**：有依赖关系的工具按顺序执行，通过**动态变量注入**传递中间结果。

**24. 开源模型的 Function Calling 能力较弱时，如何通过微调或 Prompt 设计来提升其工具调用能力？**

开源模型（如Qwen、Llama）原生工具调用能力薄弱，存在不会判需调用、格式错乱、参数提取错误等问题。
- **微调（Fine-tuning）** ：使用**QLoRA**等技术对模型进行微调。训练模型在输出结构化工具调用之前先产生**思维链推理轨迹**。
- **Prompt设计**：在系统提示中提供**简洁的函数描述**而非详细规格；使用**结构化的输出格式**要求；配合**Toolshim模型**作为后处理器，将开源模型输出转换为标准化的工具调用。

**25. Agentic RAG 与传统 RAG 的核心区别是什么？**

- **传统RAG**：**被动匹配、线性执行**，单次检索-生成流程。如同“查阅百科的助手”。
- **Agentic RAG**：**主动规划、循环推理**。基于**Agent Loop框架**，实现智能体自主反思、智能切换检索策略、多轮迭代检索。支持**多轮自适应检索、深度意图分析、工具动态调用与结果多维评估**。如同“能动手解决问题的工程师”。

**26. 在项目中是如何进行 LLM 模型选择的？是支持多模型切换、统一使用某家模型，还是自研模型？**

（开放式问题，参考答案框架）实践中通常采用**多模型路由（Model Routing）** 策略：
- **统一使用**：适合场景单一、对成本和延迟敏感的项目。
- **多模型切换**：通过**LLM Router**自动为不同任务选择最优模型，在性能、成本与延迟间灵活权衡。
- **自研模型**：适合有深厚AI研发实力、对数据安全和定制化有极高要求的企业。

路由策略包括：将简单请求路由到快速低成本模型，将困难请求升级到更强模型。

**27. 在多 Agent 协作中，如何解决冲突、分歧以及争议无法收敛的问题？**

冲突解决需先区分冲突类型：
- **事实冲突**（两个Agent数据不一致）：检查**数据源、时间和范围**。
- **目标冲突**（Agent目标相悖）：由**Planner提前定义优先级**，不让模型临时争论。

核心机制包括：
- **角色契约**：定义每个Agent的责任边界。
- **仲裁机制**：引入仲裁者或协调者进行最终决策。
- **冲突通知**：发现冲突时通知当事Agent，让其自己判断并修正。

**28. 基于强化学习的 Agent 与传统基于 Prompt 的 Agent 有什么区别？**

- **传统Prompt-based Agent**（如ReAct）：**静态推理**，模型仅根据输入文本生成输出，缺乏与环境的深度交互。Prompt能增强上下文学习能力，但无法实现**内部适应**。
- **强化学习Agent**：**动态决策**，通过 **“试错-反馈-优化”** 的闭环机制自主发现新策略。能在动态变化的真实场景中**自适应**，传统方法在同样场景下常因缺乏自适应能力而失效。

**29. 如何评估 Agent 的执行效果和项目效果？**

需从多维度、多层次评估：
- **评估维度**：**功能准确性**、**服务性能**（延迟、并发、成功率）、**运行安全性**、**成本损耗**。
- **评估方法**：**LLM-as-Judge**（用LLM评判）、**人工标注**、**A/B测试**三位一体。
- **评估层次**：从**单元测试**（单步决策）到**端到端测试**（完整任务）。

**30. 什么是 Multi-Agent 系统？它与单 Agent 系统相比有哪些特点和适用场景？**

**Multi-Agent系统**是将职责分配给多个专业Agent的系统。

| 维度 | 单Agent系统 | 多Agent系统 |
|------|------------|------------|
| 特点 | 所有逻辑整合到一个Agent中，实现简单 | 模块化、职责分离、可扩展性高 |
| 适用场景 | 任务边界清晰、不涉及多系统流转 | 跨部门、跨领域的复杂决策链 |
| 成本 | 链路短、可控性强、运维简单 | 引入协调成本、链路变长 |

**31. 在多轮工具调用中，如何判断下一步是继续调用工具还是直接结束流程？**

判断依据来自**Agent Loop的核心逻辑**：
- **继续调用**：LLM返回的响应中包含 `tool_calls`。
- **结束流程**：LLM直接返回文本（无 `tool_calls`）；或达到最大步数（`maxSteps`）限制；或LLM输出 `end_turn` 或 `stop_sequence`。

**32. Agent 项目通常如何进行测试与评估？**

需建立分层测试体系：
- **单元测试（Unit Test）** ：测试单步决策是否正确。
- **工具测试（Tool Test）** ：测试每个工具调用的正确性。
- **Agent测试**：测试多轮交互和状态管理。
- **集成测试（Integration Test）** ：测试端到端流程。
- **端到端测试（E2E Test）** ：模拟真实用户场景。
- **生产测试（Production Test）** ：线上灰度、A/B测试。

需维护**版本化的黄金数据集（Golden Dataset）** ，并用**多种Grader组合**（代码型、模型型、人工型）进行评估。

**33. 为什么 Agent 需要 Memory 系统来维持任务连贯性？**

因为Agent的**上下文窗口有限**，无法承载长周期任务的所有信息。Memory系统的价值在于：
- **保障长任务稳定性**：卸载冷数据，仅保留关键状态。
- **跨会话连贯性**：切换终端或重开对话时不会“失忆”。
- **降低Token消耗**：实测可降低最高61%的Token使用量。
- **经验沉淀**：从对话中提取可复用的知识和技能。

**34. 长上下文场景下如何做摘要压缩，既控制上下文长度又尽量避免关键信息丢失和语义扭曲？**

关键策略包括：
- **增量摘要**：LLM参考“旧摘要”和“新消息”生成涵盖全量历史的新摘要，避免信息在多次压缩中丢失。
- **保留最近消息**：始终保留最近的N条消息（默认10条）不被压缩，维持短期记忆和对话连贯性。
- **两级摘要**：将原始对话压缩为单任务摘要和宏观摘要两层。
- **外部存储**：被移出上下文的原始内容保存在外部存储中，Agent需要时可回查。

**35. 在 RAG 场景中，什么时候适合使用静态知识库，什么时候适合使用动态网页检索？**

- **静态知识库**：适合需要检索**私有或内部文档**的场景，如客户合同、内部Wiki、机密研究等。这些数据不能通过外部API传输。
- **动态网页检索**：适合用户询问**时事、竞品价格、公开信息**等知识库中没有的内容时。

**最佳实践是两者结合**：用静态检索处理专有数据，用实时网页搜索获取当前信息。

**36. RAG 中长文本应该如何切分，如何选择合适的切分策略？**

切分策略应根据文档类型和需求选择：
- **通用文档**：用**固定大小切块**（如512 tokens）。
- **长文档**：用**层次切片**（父子分块）。
- **高精度场景**：用**语义切片**，基于嵌入相似度在话题跳变点切割。
- **结构化文档**（Markdown、HTML）：适合**递归切块**或按标题层级切块。
- **非结构化文档**（PDF、Word）：可使用**语义切块**。

块大小建议在 **256-512 tokens** 之间。

**37. 请详细讲解 ReAct 框架的原理。**

ReAct（Reasoning + Acting）由Yao等人于2022年提出，核心原理是**将链式推理与环境行动有机结合**。它让LLM交替生成**推理轨迹（Thought）** 与**特定任务行动（Action）** ，模拟人类解决问题时的“思考-行动-观察”循环。

具体原理：
1. **思考（Thought）** ：LLM分析当前状态，决定下一步做什么。
2. **行动（Action）** ：执行工具调用或生成最终答案。
3. **观察（Observation）** ：接收工具执行的结果。
4. **迭代**：基于观察结果继续思考和行动，直到任务完成。

ReAct的核心创新在于让模型在推理过程中与外部世界交互，从“被动应答者”升级为“主动问题解决者”。

**38. 如何解决 Agent 工具调用时的幻觉问题，例如编造 API 或传错参数？**

行业共识是从 **“信任模型输出”转向“零信任工具链”** 。具体防御体系包括：
- **Schema强校验**：用Pydantic等工具对参数进行校验，确保参数合法才调用API。
- **工具网关**：在工具调用前增加一层网关，进行统一的安全检查和参数验证。
- **Mock契约测试**：模拟工具调用场景进行测试，提前发现参数幻觉问题。
- **强制校验**：开启 `tool_use_enforcement` 强制校验工具调用。
- **结构化反馈**：当参数错误时，向模型返回结构化的错误信息，帮助其自我纠正。

**39. 为什么要使用 RAG（检索增强生成）技术？**

RAG技术诞生的核心背景是**让大模型能够借助外部知识库来回答问题**。其优势包括：
- **解决幻觉问题**：让模型基于检索到的事实生成答案，而非凭空编造。
- **知识实时更新**：无需重新训练模型即可更新知识库。
- **接入私有数据**：让LLM能够回答原本不包含在训练数据中的专属领域问题。
- **成本效益高**：相比重新训练或微调模型，RAG的实施成本微乎其微。
- **结果可追溯**：生成答案可追溯至检索到的具体文档片段。

**40. 为什么工具描述中“什么时候该用”比“能做什么”更重要？工具描述设计有哪些关键原则？**

因为工具描述是**给LLM看的，不是给用户看的**。LLM需要通过描述来**理解何时该调用**哪个工具。只写“能做什么”会导致模型不知道该在什么场景下触发调用；而写明“什么时候该用”能**直接提升工具的触发率**。

关键原则：
- **做什么（What）** ：工具的功能是什么。
- **何时用（When）** ：触发条件和使用场景。
- **何时不用（When NOT）** ：明确禁止的误用路径。
- **参数格式和示例**：不要让LLM猜测。
- **参数边界条件**：required/optional/default/range。

**41. 如何让 Agent 具备自我学习和经验沉淀的能力？**

核心思路是让Agent从自己的成功和失败轨迹中**自动蒸馏出可复用的“经验”** 。具体机制包括：
- **学习循环（Learning Loop）** ：Agent从执行过程中自动提炼技能、持续优化决策策略。
- **反思（Reflexion）** ：先让Agent针对单次失败进行反思。
- **经验蒸馏**：从多条轨迹中提炼可跨任务迁移的规律。
- **Skill沉淀**：将提炼的规律进一步组织成Workflow或Skill。
- **经验检索**：在后续任务中检索、使用和强化这些经验。

**42. Rerank 之后的 TopK 截断如何实现，截断值怎么确定？**

Rerank之后的TopK截断通过**对Rerank后的文档按分数重新排序，然后取TopK个最高分文档**来实现。

截断值的确定方法包括：
- **固定数量策略**：根据业务经验设定固定值（如取Top 5-10）。
- **动态阈值策略**：采用**绝对硬阈值**（分数低于某值直接丢弃）、**相对动态落差**（分数断崖处截断）或**软硬双阈值分流**。
- **断崖检测算法**：根据分数分布自适应调整截取数量。

典型配置：粗排取Top 20-50，精排后取Top 5-10。

**43. 什么是 Memory？短期记忆在对话轮次增加时如何持续处理上下文爆炸和重复压缩？**

**Memory（记忆）** 是存储过去用户交互和上下文信息的组件，让Agent能在时间维度上做出更准确的响应。

处理上下文爆炸和重复压缩的机制包括：
- **分层记忆**：分为**短期记忆**（当前会话的逐轮交互）和**长期记忆**（跨会话的关键洞察）。
- **窗口记忆（WindowMemory）** ：只保留最近N轮对话。
- **摘要记忆（SummaryMemory）** ：当超出预算时，用运行摘要替换最旧的对话，同时保留最近的对话原文。
- **增量压缩**：将对话视为交织的上下文线程，存储每个线程的可修订压缩状态。

**44. Agent 的 Planning 模块有哪些主流实现方式，Step-by-step 和 Plan-and-execute 有什么区别？**

Planning模块的主流实现方式包括：

| 对比维度 | Step-by-Step（ReAct） | Plan-and-Execute |
|---------|----------------------|------------------|
| 思考模式 | 单步思考-行动循环 | 两阶段分离：先规划后执行 |
| 执行流程 | Thought→Action→Observation（循环） | Plan→Execute Step 1→Execute Step 2→... |
| 规划时机 | 动态规划，边走边看 | 先生成完整计划，再逐步执行 |
| 适用场景 | 路径未知的开放式任务 | 步骤有强先后依赖的复杂长任务 |

Plan-and-Execute可将**规划和高性能模型解耦**，用Planner做规划，用便宜的Executor执行。一旦任务超过五六个步骤，Plan-and-Execute会更便宜、更易调试。

**45. Agent 开发中常见的系统安全风险有哪些，例如 Prompt Injection、沙箱逃逸和越权执行？应如何防范？**

常见安全风险包括：
- **提示词注入（Prompt Injection）** ：攻击者通过恶意输入操控Agent行为。
- **沙箱逃逸（Sandbox Escape）** ：Agent突破隔离环境，访问主机资源。
- **越权执行**：Agent调用超出权限的敏感接口。

防范措施：
- **纵深防御**：从外围防护转向全链路安全工程化。
- **输入净化**：对用户输入进行过滤和校验。
- **最小权限沙箱**：将Agent置于Docker等沙箱中，以独立用户身份运行。
- **权限控制**：实施基于策略的访问控制，动态注入最小权限。
- **网络出口控制**：阻止对任意站点的网络访问。

**46. Agent 耗时过长时，工程侧和基座侧分别有哪些优化手段？**

**工程侧优化**：
- **减少LLM调用次数**：Qwen的实测数据显示，LLM调用占78%的耗时。
- **并行化**：对无依赖关系的子任务并行执行。
- **缓存复用**：缓存计划、摘要、检索到的上下文和工具输出等中间产物。
- **检查点**：对长时任务设置检查点，可恢复执行。
- **流式传输**：使用WebSocket或SSE支持流式推送中间结果。

**基座侧优化**：
- **模型选型**：为不同子任务匹配合适大小的模型。
- **KV Cache优化**：通过量化、卸载等技术减少内存占用。
- **动态模型路由**：简单请求用低成本模型，困难请求升级到更强模型。

**47. 请介绍 MCP（Model Context Protocol）的作用、原理，以及你是否有过相关实践？**

**MCP（Model Context Protocol）** 是由Anthropic于2024年11月开源的开放标准协议。

- **作用**：为AI大模型与外部数据源、工具和服务之间建立**统一、安全、高效的双向通信通道**。旨在替换碎片化的Agent代码集成。
- **原理**：MCP在LLM和外部服务之间建立了一层隔离，Client可对所有工具调用进行**权限控制和审计**。其执行流程本质上与Function Calling类似，但工具的获取和执行变得更加灵活，可动态注册和更新。

**48. 如何设计 Agent 的流式输出，以提升用户体验，尤其是在包含工具调用和多轮大模型交互的场景下？**

流式输出设计需实现**三层流式**以提升用户体验：
- **Token流**：逐字输出最终答案，解决“等待感”问题。
- **步骤流**：实时展示Agent当前的执行步骤（如“正在思考...”、“正在调用工具...”）。
- **动作流**：展示工具调用的具体事件和参数。

技术实现上，使用**SSE（Server-Sent Events）** 作为底层通信机制。关键设计要点包括：
- **推理细分**：将推理片段、工具调用事件和请求元数据随回合展开实时返回。
- **可打断设计**：用户可随时中断Agent的执行。
- **生产级保障**：实现重连、背压控制和幂等性。

**49. Agent 长期记忆的 FIFO 淘汰策略有哪些问题，如何优化？**

**FIFO（先进先出）淘汰策略的核心问题是“重要性无关”（importance-blind）** ——它只按时间顺序淘汰，不考虑记忆内容的重要性。这会导致**关键信息被过早淘汰**，而无关信息却被保留。

优化方案包括：
- **基于分数的优先级淘汰**：用时效性衰减等分数来决定淘汰优先级。
- **记忆分级**：临时约束类记忆设置短生存时间，事实类记忆永久保存但不参与实时检索。
- **抽象摘要替代原始记忆**：检索3-5条高质量摘要和模式，而非20条原始记录。
- **TraceRetain等先进算法**：实验显示FIFO在长任务中准确率大幅下降，而TraceRetain-CEM几乎不变。

**50. 什么是 Self-Reflection 机制？它在代码生成或故障排查 Agent 中如何应用？**

**Self-Reflection（自我反思）** 机制让Agent对自己的输出进行**批判性审视和修正**。在代码生成或故障排查中，Self-Reflection将“自我反思”从事后补丁提升为Agent推理过程中的**一等控制循环**。

应用流程为：
1. **生成**：Agent生成代码或诊断方案。
2. **评估**：通过编译器、测试或自我批判来评估结果。
3. **批判**：分析失败原因（控制流错误、边界情况遗漏、API理解错误等）。
4. **存储与复用**：将经验教训存储为可检索的教训，防止跨会话重复犯错。

在代码生成场景中，可强制Agent在执行编辑工具前先问自己三个关键问题。在故障排查中，Self-Reflection帮助将原始诊断转化为可操作的假设。
