### 业务背景：为什么要做这个统一投放平台

这个项目的业务起点很典型：**代理商投放渠道多、平台接口不统一、运营重复操作多、数据分散难监控。**

比如华为、vivo、OPPO 等渠道，虽然都有广告投放能力，但各自有独立的营销平台、API 规范、权限体系、报表口径和素材规则。 运营如果要在多个渠道上创建计划、分组、创意，再分别看消耗、ROI、转化数据，效率很低，也很容易出现预算超支、低效计划没及时关停、优质计划没及时扩量等问题。

所以这个平台的核心价值不是“简单封装几个 API”，而是把**多平台投放能力抽象成统一模型**，再用 AgentScope 智能体把“创建—监控—优化”串成闭环。

### 平台整体架构

可以按四层来描述：

| 层级 | 职责 | 关键实现 |
|---|---|---|
| 接入层 | 接收运营指令、告警回调、报表数据 | Webhook、API Gateway、消息队列 |
| Agent 层 | 意图识别、任务拆解、策略生成 | AgentScope ReActAgent + Tool Calling |
| 适配层 | 屏蔽华为、vivo、OPPO 等平台差异 | ChannelAdapter + 统一投放模型 |
| 数据层 | 存储账户、计划、素材、消耗、ROI | MySQL/ClickHouse + 缓存 + 报表库 |

AgentScope 在这里主要承担**智能体编排、工具调用、消息流转和会话状态管理**。 它不是简单替代后台服务，而是负责把自然语言指令转成可执行任务，再调用内部工具完成投放操作。

### 多端集成：如何统一华为、vivo、OPPO 等代理商渠道

这里最关键是做一个**渠道适配器层**。每个渠道有自己的 API 差异，比如：

- 认证方式不同：OAuth、Token、AppKey/Secret；
- 资源层级不同：Campaign / AdGroup / Ad / Creative 的命名和字段不完全一致；
- 报表口径不同：消耗、转化、ROI、归因窗口可能不同；
- 限流规则不同：接口 QPS、批量创建上限、素材审核机制不同。

所以我会设计一个统一接口：

```python
class AdChannelAdapter(ABC):
    @abstractmethod
    def create_campaign(self, account_id: str, payload: dict) -> dict: ...

    @abstractmethod
    def create_ad_group(self, campaign_id: str, payload: dict) -> dict: ...

    @abstractmethod
    def create_creative(self, ad_group_id: str, payload: dict) -> dict: ...

    @abstractmethod
    def get_report(self, account_id: str, metrics: list, date_range: dict) -> dict: ...

    @abstractmethod
    def update_budget(self, entity_id: str, budget: float) -> dict: ...

    @abstractmethod
    def pause_entity(self, entity_id: str) -> dict: ...
```

然后分别实现：

```python
class HuaweiAdapter(AdChannelAdapter): ...
class VivoAdapter(AdChannelAdapter): ...
class OppoAdapter(AdChannelAdapter): ...
```

Agent 不需要知道底层是哪家渠道，只需要操作统一模型，比如：

```python
{
  "channel": "vivo",
  "account_id": "xxx",
  "campaign_name": "双十一_电商拉新",
  "objective": "app_install",
  "budget": 5000,
  "ad_groups": [...],
  "creatives": [...]
}
```

### 意图识别：如何解析“一句话创建广告”

运营输入类似：

> 帮我在 vivo 和华为各建一个拉新计划，预算各 5000，定向 18-35 岁安卓用户，用最近点击率最高的 3 套素材。

LLM 会先做意图识别，再输出结构化参数。这里不要直接让 LLM 调渠道 API，而是让它输出一个**中间任务对象**，由后端校验后再执行。

```python
intent = llm.parse_intent(user_message)

# 输出类似
{
  "intent": "batch_create_campaign",
  "channels": ["vivo", "huawei"],
  "objective": "app_install",
  "budget_per_channel": 5000,
  "targeting": {
    "age_min": 18,
    "age_max": 35,
    "os": "android"
  },
  "creative_strategy": "top_ctr_3"
}
```


这样可以避免 LLM 幻觉直接落到渠道 API 上。

### 批量创建：计划 → 分组 → 创意

创建流程可以做成流水线：

```python
for channel in channels:
    adapter = adapter_factory.get(channel)

    campaign_id = adapter.create_campaign(account_id, campaign_payload)

    for ad_group in ad_groups:
        ad_group_id = adapter.create_ad_group(campaign_id, ad_group)

        for creative in select_creatives(ad_group):
            adapter.create_creative(ad_group_id, creative)
```

这里可以加几个工程细节：

- **幂等性**：用 `request_id` 或 `campaign_key` 防止重复创建；
- **批量限流**：按渠道 QPS 做令牌桶控制；
- **失败重试**：对临时网络错误重试，对参数错误直接告警；
- **部分成功回写**：即使部分计划失败，也要把成功/失败结果分别回写数据库，并通知运营。

### 实时监控：如何聚合多平台消耗和 ROI

监控层不建议只靠轮询。更合理的做法是：

- 报表数据通过**定时任务 + 渠道 API**拉取；
- 转化回传通过**渠道 Webhook**接收；
- 统一写入数据仓库后，再计算 CTR、CVR、CPA、ROI；
- 关键指标异常通过规则引擎触发告警。

```python
metrics = report_service.aggregate(
    channels=["huawei", "vivo", "oppo"],
    metrics=["spend", "impressions", "clicks", "conversions", "roi"],
    granularity="hourly"
)
```
```text
广告投放指标：
ROI（投资回报率）、
CVR（转化率）、CPA（转化成本）、
CTR（点击率）、CPC（平均点击成本）、
OCPX（智能转化成本优化）
eCPM（预估千次曝光收益）= 出价 × 预估转化率 (pCVR) × 1000
pCVR（广告转化率预估）
```
广告投放的内部流程
> 用户触发广告位，前端发起广告请求；平台先根据定向召回一批候选广告；模型计算每条广告 eCPM，按 eCPM 排序竞价，一般采用次价结算；经过频控、风控过滤后，返回胜出广告进行展示；后续点击、转化事件回传平台做归因，同时扣预算、扣费，模型用转化样本持续迭代预估。

### 规则引擎：预算、告警、自动优化

规则引擎可以设计成“条件 + 动作 + 频率 + 安全阈值”。

例如：

| 触发条件 | 执行动作 | 安全约束 |
|---|---|---|
| ROI < 0.7 且消耗 > 500 | 降低预算 30% | 单次降幅不超过 50% |
| CPA 连续 2 小时超标 | 暂停低效创意 | 不自动删除，只暂停 |
| ROI > 1.5 且转化稳定 | 提高预算 20% | 单日预算不超过上限 |
| 消耗突增 200% | 推送告警 | 需人工确认后扩量 |


### 面试时可以这样讲

> 这个平台主要解决的是多代理商渠道投放割裂的问题。华为、vivo、OPPO 等平台在账号体系、API 接口、报表口径和素材规则上都不一样，运营需要反复切换后台。我们基于 AgentScope 搭建了一个广告投放智能体，上层通过 LLM 做意图识别，把运营的自然语言指令解析成结构化投放任务；中间通过渠道适配器屏蔽各平台差异，统一成计划、分组、创意模型；下层接报表数据和转化回传，做实时监控。规则引擎负责触发预算调整、异常告警和素材优化建议，最终形成从创建到监控再到优化的闭环。

如果面试官追问技术亮点，可以重点说三点：

1. **统一投放模型**：把多平台广告结构抽象成标准实体，避免每个渠道各写一套业务逻辑；
2. **LLM 不直接操作 API**：LLM 只负责意图识别和策略建议，真正执行前会经过校验、规则引擎和权限控制；
3. **自动化有边界**：自动调价、暂停、扩量都带安全阈值和人工兜底，避免智能体误操作导致预算风险。

### 智能优化换素材、调预算策略
> 设计了一个六层闭环：数据聚合层统一拉取多平台报表；检测层用硬规则+统计异常发现机会和问题；诊断层让 LLM 做归因分析，输出根因和置信度；策略层生成结构化的调价、换素材、扩量等候选动作；执行层通过规则引擎做安全校验，按风险分级执行——低风险自动跑，中高风险推给运营确认；最后效果回写形成反馈闭环。核心原则是 LLM 只负责诊断和建议，真正执行必须经过校验，避免误操作导致预算风险
