下面我按**业务背景 → 平台架构 → 核心能力实现 → 智能策略优化闭环（含 RAG 经验库 / 素材库多模态检索） → 面试表达口径**帮你整理一版，尽量贴近真实项目复盘。

### 业务背景：为什么要做这个统一投放平台

这个项目的业务起点很典型：**代理商投放渠道多、平台接口不统一、运营重复操作多、数据分散难监控。**

比如华为、vivo、OPPO 等渠道，虽然都有广告投放能力，但各自有独立的营销平台、API 规范、权限体系、报表口径和素材规则。 运营如果要在多个渠道上创建计划、分组、创意，再分别看消耗、ROI、转化数据，效率很低，也很容易出现预算超支、低效计划没及时关停、优质计划没及时扩量等问题。

所以这个平台的核心价值不是“简单封装几个 API”，而是把**多平台投放能力抽象成统一模型**，再用 AgentScope 智能体把“创建—监控—优化”串成闭环。

### 平台整体架构

可以按四层来描述：

| 层级 | 职责 | 关键实现 |
|---|---|---|
| 接入层 | 接收运营指令、告警回调、报表数据 | Webhook、API Gateway、消息队列 |
| Agent 层 | 意图识别、任务拆解、策略生成 | AgentScope ReActAgent + Tool Calling |
| 适配层 | 屏蔽华为、vivo、OPPO 等平台差异 | ChannelAdapter + 统一投放模型 |
| 数据层 | 存储账户、计划、素材、消耗、ROI、经验案例 | MySQL / ClickHouse + 向量库 + 缓存 + 报表库 |

AgentScope 在这里主要承担**智能体编排、工具调用、消息流转和会话状态管理**。 它不是简单替代后台服务，而是负责把自然语言指令转成可执行任务，再调用内部工具完成投放操作。

### 多端集成：如何统一华为、vivo、OPPO 等代理商渠道

这里最关键是做一个**渠道适配器层**。每个渠道有自己的 API 差异，比如：

- 认证方式不同：OAuth、Token、AppKey/Secret；
- 资源层级不同：Campaign / AdGroup / Ad / Creative 的命名和字段不完全一致；
- 报表口径不同：消耗、转化、ROI、归因窗口可能不同；
- 限流规则不同：接口 QPS、批量创建上限、素材审核机制不同。

所以我会设计一个统一接口：

```python
class AdChannelAdapter(ABC):
    @abstractmethod
    def create_campaign(self, account_id: str, payload: dict) -> dict: ...

    @abstractmethod
    def create_ad_group(self, campaign_id: str, payload: dict) -> dict: ...

    @abstractmethod
    def create_creative(self, ad_group_id: str, payload: dict) -> dict: ...

    @abstractmethod
    def get_report(self, account_id: str, metrics: list, date_range: dict) -> dict: ...

    @abstractmethod
    def update_budget(self, entity_id: str, budget: float) -> dict: ...

    @abstractmethod
    def pause_entity(self, entity_id: str) -> dict: ...
```

然后分别实现：

```python
class HuaweiAdapter(AdChannelAdapter): ...
class VivoAdapter(AdChannelAdapter): ...
class OppoAdapter(AdChannelAdapter): ...
```

Agent 不需要知道底层是哪家渠道，只需要操作统一模型，比如：

```python
{
  "channel": "vivo",
  "account_id": "xxx",
  "campaign_name": "双十一_电商拉新",
  "objective": "app_install",
  "budget": 5000,
  "ad_groups": [...],
  "creatives": [...]
}
```

### 意图识别：如何解析“一句话创建广告”

运营输入类似：

> 帮我在 vivo 和华为各建一个拉新计划，预算各 5000，定向 18-35 岁安卓用户，用最近点击率最高的 3 套素材。

LLM 会先做意图识别，再输出结构化参数。这里不要直接让 LLM 调渠道 API，而是让它输出一个**中间任务对象**，由后端校验后再执行。

```python
intent = llm.parse_intent(user_message)

# 输出类似
{
  "intent": "batch_create_campaign",
  "channels": ["vivo", "huawei"],
  "objective": "app_install",
  "budget_per_channel": 5000,
  "targeting": {
    "age_min": 18,
    "age_max": 35,
    "os": "android"
  },
  "creative_strategy": "top_ctr_3"
}
```


这样可以避免 LLM 幻觉直接落到渠道 API 上。

### 批量创建：计划 → 分组 → 创意

创建流程可以做成流水线：

```python
for channel in channels:
    adapter = adapter_factory.get(channel)

    campaign_id = adapter.create_campaign(account_id, campaign_payload)

    for ad_group in ad_groups:
        ad_group_id = adapter.create_ad_group(campaign_id, ad_group)

        for creative in select_creatives(ad_group):
            adapter.create_creative(ad_group_id, creative)
```

这里可以加几个工程细节：

- **幂等性**：用 `request_id` 或 `campaign_key` 防止重复创建；
- **批量限流**：按渠道 QPS 做令牌桶控制；
- **失败重试**：对临时网络错误重试，对参数错误直接告警；
- **部分成功回写**：即使部分计划失败，也要把成功/失败结果分别回写数据库，并通知运营。

### 实时监控：如何聚合多平台消耗和 ROI

监控层不建议只靠轮询。更合理的做法是：

- 报表数据通过**定时任务 + 渠道 API**拉取；
- 转化回传通过**渠道 Webhook**接收；
- 统一写入数据仓库后，再计算 CTR、CVR、CPA、ROI；
- 关键指标异常通过规则引擎触发告警。

```python
metrics = report_service.aggregate(
    channels=["huawei", "vivo", "oppo"],
    metrics=["spend", "impressions", "clicks", "conversions", "roi"],
    granularity="hourly"
)
```
```text
广告投放指标：
ROI（投资回报率）、
CVR（转化率）、CPA（转化成本）、
CTR（点击率）、CPC（平均点击成本）、
OCPX（智能转化成本优化）
eCPM（预估千次曝光收益）= 出价 × 预估转化率 (pCVR) × 1000
pCVR（广告转化率预估）
```
广告投放的内部流程
> 用户触发广告位，前端发起广告请求；平台先根据定向召回一批候选广告；模型计算每条广告 eCPM，按 eCPM 排序竞价，一般采用次价结算；经过频控、风控过滤后，返回胜出广告进行展示；后续点击、转化事件回传平台做归因，同时扣预算、扣费，模型用转化样本持续迭代预估。

### 规则引擎：预算、告警、自动优化

规则引擎可以设计成“条件 + 动作 + 频率 + 安全阈值”。

例如：

| 触发条件 | 执行动作 | 安全约束 |
|---|---|---|
| ROI < 0.7 且消耗 > 500 | 降低预算 30% | 单次降幅不超过 50% |
| CPA 连续 2 小时超标 | 暂停低效创意 | 不自动删除，只暂停 |
| ROI > 1.5 且转化稳定 | 提高预算 20% | 单日预算不超过上限 |
| 消耗突增 200% | 推送告警 | 需人工确认后扩量 |

规则引擎覆盖的是**已知的确定性规则**，但它回答不了两件事：一是“为什么变差”（归因），二是“这个账户该怎么投才最好”（个性化策略）。这两件事交给下面的智能策略优化闭环。

---

### 智能策略优化：换素材、调预算、扩量的六层闭环

> 一句话总览：**数据聚合层**统一拉取多平台报表；**检测层**用硬规则 + 统计异常发现机会和问题；**诊断层**让 LLM 做归因分析，输出根因和置信度；**策略层**生成结构化的调价、换素材、扩量等候选动作，并通过 RAG 检索该账户的历史成功经验做个性化增强；**执行层**通过规则引擎做安全校验，按风险分级执行——低风险自动跑，中高风险推给运营确认；最后**效果回写**形成反馈闭环。
>
> 核心原则：**LLM 只负责诊断和建议，真正执行必须经过校验**，避免误操作导致预算风险。

#### 1. 六层闭环总览

| 层 | 输入 | 处理 | 输出 | 技术选型 |
|---|---|---|---|---|
| ① 数据聚合层 | 多渠道报表 API + 转化 Webhook | 口径归一、小时级聚合 | 统一的指标宽表 | 定时任务 + ClickHouse |
| ② 检测层 | 指标宽表（含环比窗口） | 硬规则命中 + 3σ/环比统计异常 | Signal（信号 + 证据） | 规则配置表 + 滑动窗口 |
| ③ 诊断层 | Signal + 上下文（同账户其他计划、素材、人群包） | LLM 归因，判断是素材/人群/出价/预算哪一类问题 | 根因 + 置信度 + 证据链 | LLM + 结构化输出 |
| ④ 策略层 | 根因 + 当前投放配置 + **RAG 检索的历史成功案例** | 生成候选动作，Few-shot 注入 Prompt | 结构化动作 JSON（含风险等级） | LLM + 经验案例库 |
| ⑤ 执行层 | 动作 JSON | 安全阈值校验 → 风险分级 → 执行/推送 | 执行结果 + 操作审计日志 | 规则引擎 + 渠道适配器 |
| ⑥ 反馈层 | 执行前后的指标对比 | 效果评估、经验沉淀、规则/权重调优 | 新经验案例、策略命中率报表 | 定时评估任务 |

#### 2. 检测层：硬规则 + 统计异常

规则不写死在代码里，放配置表，运营可调；统计异常用来兜住“规则没覆盖到的突发”。

```python
class AnomalyDetector:
    def detect(self, window: list[dict]) -> list[Signal]:
        signals = []
        for rule in rule_repo.list_enabled():          # 硬规则：ROI < 0.7 且消耗 > 500
            if rule.evaluate(window):
                signals.append(Signal(
                    rule_id=rule.id, level="hard",
                    evidence=rule.hit_evidence(window)
                ))
        signals += self.zscore_detect(window)          # 统计异常：消耗/CTR 环比超 3σ
        return self.dedup(signals)                     # 同一实体短时间窗口内去重，避免重复触发策略
```

#### 3. 诊断层：LLM 归因分析

把 Signal 连同上下文一起给 LLM，强制结构化输出，并且**必须给置信度**——低置信度不进入策略层，直接推运营人工看。

```json
{
  "root_cause": "素材点击率衰减",
  "confidence": 0.82,
  "evidence": [
    "近 3 小时 CTR 由 3.1% 降至 1.4%",
    "同人群包其他计划 CTR 稳定，排除人群问题"
  ],
  "scope": "creative",
  "suggestion_hint": "换素材优先于调价"
}
```

#### 4. 策略层：候选动作生成

输出统一动作 schema，方便执行层做校验，也避免 LLM 直接产出渠道 API 参数：

```json
{
  "actions": [
    {"type": "replace_creative", "target_id": "ad_123",
     "candidates": ["素材A", "素材B"], "reason": "同主题历史高 ROI 素材"},
    {"type": "adjust_budget", "target_id": "campaign_456",
     "delta_pct": -20, "reason": "CPA 连续超标"}
  ],
  "risk_level": "low",
  "expected_roi": 1.35,
  "reference_cases": ["case_8821", "case_9014"]
}
```

`reference_cases` 是关键的可解释性字段：这条建议参考了哪几条历史案例，运营可以在推送卡片里直接点开看。策略层的个性化能力由下面的 **RAG + Few-shot 经验库**提供。

#### 5. 执行层：安全校验与风险分级

```python
AUTO_WHITELIST = {"adjust_budget_small", "replace_creative"}

def execute(action: dict, risk_level: str) -> str:
    if not safety_guard.check(action):        # 单次降幅 <= 50%、单日预算上限、只暂停不删除、频控
        return "rejected"
    if risk_level == "low" and action["type"] in AUTO_WHITELIST:
        adapter_factory.get(action["channel"]).apply(action)
        audit_log.write(action, mode="auto")
        return "auto_executed"
    notify_ops(action)                         # 中高风险：推送运营确认，附带根因、证据、参考案例
    return "pending_confirm"
```

风险分级参考：预算小幅调整、换素材 → 低风险自动执行；关停计划、大额调价、新人群包 → 中风险需确认；跨账户预算搬运、批量操作 → 高风险强制人工。

#### 6. 反馈层：效果回写

执行后按固定观察窗口（如 2h / 24h）对比执行前后的 ROI、CPA、CTR，写入效果表；达标动作沉淀为新的经验案例，未达标的动作降权并反哺检测规则阈值，形成闭环。

### 策略层增强：基于 RAG + Few-shot 的个性化学习方案

> 把每个账户历史表现好的广告沉淀成经验库，运营问新计划怎么投时，智能体先检索该账户的相似成功案例，用 Few-shot 方式注入 Prompt，让 LLM 基于真实数据给出建议。这样智能体是“跟着这个账户的历史成功经验学”，而不是凭通用知识给模板化建议。

#### RAG 在这里的定位：解决“个性化”问题
规则引擎和 LLM 默认只能给“通用策略”（ROI 低就降预算），RAG 的价值是让策略带上**这个账户自己的成功经验**——每个行业、每个账户的打法差异很大，把该账户历史上真实跑出效果的做法检索出来喂给 LLM，让它基于事实而非通用经验给建议。它接入的是优化闭环里的**策略层**：只改变“建议的质量”，不改变“执行的安全边界”（输出照旧走规则引擎校验）。

#### 1. 经验数据从哪来（三类数据源）
| 数据 | 存储 | 内容 |
|---|---|---|
| 报表数据 | ClickHouse | spend / impressions / clicks / conversions / ROI / CTR / CVR / CPA，campaign / adgroup / creative 三个粒度 × 小时级 |
| 投放配置 | MySQL | 定向（年龄、性别、OS、人群包 ID）、出价、预算、时段、渠道、投放目标（拉新/召回） |
| 素材数据 | 企业素材库（多模态向量） | 素材 ID、文本主题标签、图像的 CLIP 类向量，支持“文本主题 → 图像”检索 |

#### 2. 怎么沉淀成“经验案例”（离线 ETL，定时任务）
- **打标**：规则引擎筛选成功广告，如 ROI > 1.5 且消耗 > 500 且连续 N 天稳定 → 该 campaign/adgroup 标记为成功案例；
- **生成 Case**：一条经验 = 结构化上下文（渠道、目标、定向、素材主题、预算、出价）+ 效果指标（ROI/CTR/CVR/CPA）+ 可选归因备注；
- **双写存储**：
  - MySQL 经验案例表：存结构化字段，用于**硬过滤**（account_id、channel、objective、时间窗）；
  - 向量库（Milvus / ES）：存 case 描述文本的 embedding，用于**语义召回**；
- **Embedding 的内容是拼好的自然语言描述，不是裸指标**。例如：“vivo 渠道，电商 App 拉新，定向 18-35 岁安卓，使用'A 主题'素材，日预算 5000，OCPM 出价，7 天 ROI 1.8、CTR 3.2%、CVR 4.1%”——文本化让检索按“场景相似”召回，而不是只按数字匹配。

#### 3. 在线检索链路（运营提问 / 策略生成时）
1. **意图识别**：LLM 从“新计划怎么投”中抽取查询条件（账户、渠道、目标、题材、人群），而不是拿原始问句直接检索；
2. **混合检索**：
   - 先元数据硬过滤：限 account_id + channel + objective + 近 90 天（保证个性化且新鲜）；
   - 再向量召回 top-k 相似 case；
   - 重排：相似度 × 时效衰减 × ROI 加权；
3. **素材推荐支路**：查询文本主题 → 素材库多模态向量检索 → 召回同主题历史高 ROI 的图像素材，直接作为推荐素材（这就是简历上“素材推荐”的出处，具体实现见下一节）。

#### 4. Few-shot 注入 Prompt
把 top-k case 格式化成示例块：

```text
【历史成功案例】
案例1：vivo / 拉新 / 18-35安卓 / 素材主题A / 预算5000 → ROI 1.8, CTR 3.2%, CVR 4.1%
案例2：vivo / 拉新 / 25-40安卓 / 素材主题C / 预算8000 → ROI 1.6, CTR 2.9%
【当前任务】新计划：vivo / 拉新 / 18-35安卓 / 预算6000
【输出要求】JSON：{预算分配、定向建议、素材推荐、预估ROI、风险提示}
```

- 让 LLM 做的是“从真实案例中归纳差异化打法”，而不是凭通用知识幻觉；
- 输出仍是结构化 JSON，照旧走规则引擎安全校验 + 风险分级执行（低风险自动跑，中高风险推运营确认）。

#### 5. 数据表设计（经验案例表）

```sql
CREATE TABLE experience_case (
  case_id       BIGINT PRIMARY KEY,
  account_id    VARCHAR(64) NOT NULL,   -- 账户隔离，保证个性化
  channel       VARCHAR(32) NOT NULL,
  objective     VARCHAR(32) NOT NULL,   -- 拉新 / 召回
  industry      VARCHAR(32),
  targeting     JSON,                    -- 年龄、OS、人群包 ID
  creative_tags JSON,                    -- 文本主题标签
  budget        DECIMAL(12,2),
  bid           DECIMAL(12,2),
  metrics       JSON,                    -- ROI / CTR / CVR / CPA
  case_text     TEXT,                    -- 用于 embedding 的自然语言描述
  embedding_id  VARCHAR(64),            -- 向量库中的对应 ID
  source_id     VARCHAR(64),            -- 来源 campaign / adgroup，可溯源
  decay_weight  FLOAT DEFAULT 1.0,     -- 时效衰减权重
  valid_from    DATETIME,
  created_at    DATETIME
);
CREATE INDEX idx_case_filter ON experience_case(account_id, channel, objective, valid_from);
```

规则配置表同理：`rule_config(rule_id, condition_expr, action_expr, frequency, safety_threshold, enabled)`，检测层与执行层共用一份配置。

#### 6. 反馈闭环（经验库怎么持续进化）
- 建议被执行的计划，效果数据回写 ClickHouse；
- 定时任务评估：达标 → 沉淀为新 case 入库；不达标 → 不入库；
- 时效管理：case 带 `decay_weight` 随时间衰减，热点素材类案例过期自动降权，防止“过期经验”污染建议。

#### 7. 面试追问预案
- **为什么 RAG 不直接 fine-tune？** 单账户数据量小、账户间差异大、经验需随投放实时更新、建议需可解释（能指出“参考了哪条历史案例”），RAG 全占优；
- **冷启动？** 账户无历史时降级检索“同行业 + 同渠道 + 同目标”的全局成功案例；
- **检索不准怎么办？** 混合检索（BM25 + 向量）+ 重排，查询条件来自 LLM 结构化抽取而非原始问句；
- **为什么 Few-shot 而不是全量数据塞 context？** token 成本、噪声干扰、输出可控性（案例格式统一，LLM 输出更稳定）；
- **怎么证明策略有效？** 用策略命中率、执行前后 ROI 提升幅度、人工采纳率三个指标做 A/B 对比，避免“只推送不评估”。

### 素材库多模态检索：文本主题 → 图像

> 一句话：用 CLIP 类双塔模型把「图像」和「文本主题」编码到**同一个向量空间**，文本 query 直接与图像向量算余弦相似度即可文搜图；工程上再叠加**语义增强、混合召回、效果加权**三件事，才能在投放场景真正可用。

#### 1. 为什么不是「人工打标签 + 关键词检索」
- 标签覆盖不全、维护成本高，“科技感”“高级感”“构图”这类抽象语义没法枚举；
- 运营的主题 query 是开放的（随口一句），需要零样本能力才能接住；
- 但纯向量检索也有短板：**强关键词**（“双十一”logo、品牌名）不一定准、**合规硬条件**（素材尺寸、审核状态、渠道规格）过不了、**结果不可解释**。所以真实方案是混合，不是二选一。

#### 2. 核心原理：双塔 + 共享向量空间（对比学习）
- Image Encoder / Text Encoder 分别输出 d 维向量（512 / 768），L2 归一化后用余弦相似度；
- 训练目标 InfoNCE：batch 内配对图文拉近、不配对推远；
- 中文广告场景用 **Chinese-CLIP / AltCLIP**，不要用原生 CLIP；
- **一个容易讲错的认知**：文搜图本身**不需要**给每张图配文本标签（两个 encoder 天然共享空间）；工程上仍然补 caption / tags，是为了拿**硬过滤、关键词召回、可解释性**——这三件事向量检索本身给不了。这个点讲出来很显功力。

#### 3. 离线：素材向量化建库
1. **接入**：创意 Agent 生成图、历史投放素材、设计上传图 → 对象存储（OSS / MinIO），元数据进 MySQL；
2. **预处理**：pHash 近重复去重、视频抽关键帧、缩略图生成、尺寸归一；
3. **语义增强（关键步骤）**：
   - VLM 生成图片描述 caption（“一对年轻情侣在明亮客厅看手机”）；
   - OCR 抽海报上的营销文案 / logo 文字（广告图的文字信息量很大，不能丢）；
   - LLM 结合投放上下文抽结构化标签：主题、风格、色调、人群、卖点、适用渠道 / 规格；
4. **编码**：`img_vec = CLIP.encode_image(image)`；`txt_vec = CLIP.encode_text(caption + ocr + tags)`，两份向量都存（或加权融合成一份）；
5. **入库**：Milvus / ES `dense_vector`，HNSW 索引；**向量与标量字段同库存**（tags、channel、size、status、hist_roi），让「ANN 召回 + 条件过滤」一次完成，避免先召回再内存过滤导致 top-k 不足；
6. **版本化**：embedding 模型升级需全量重刷，用 collection 别名灰度切换；新素材走流式增量写入。

```python
class MaterialIndexer:
    def ingest(self, material: Material) -> None:
        image = oss.get(material.file_key)
        caption = vlm.caption(image)                       # 图像语义描述
        ocr_text = ocr.extract(image)                      # 海报文字
        tags = llm.extract_tags(caption, ocr_text, material.context)
        img_vec = l2_norm(clip.encode_image(image))
        txt_vec = l2_norm(clip.encode_text(f"{caption} {ocr_text} {tags}"))
        vector_db.upsert(
            id=material.id,
            vectors={"img": img_vec, "txt": txt_vec},
            payload={"tags": tags, "caption": caption,
                     "channel": material.channel, "size": material.size,
                     "status": "approved", "hist_roi": material.hist_roi}
        )
```

#### 4. 在线：混合检索 + 效果加权
1. **Query 理解**：LLM 把“给我几套双十一拉新、年轻女性、科技感的素材”改写成规范检索描述，并抽出硬过滤条件（渠道规格、尺寸、审核状态、禁用品牌）；
2. **混合召回**：
   - 向量 ANN top-N（HNSW，带标量过滤）；
   - BM25 关键词 top-N（标签 / caption，兜住强关键词与专有名词）；
   - 硬过滤：规格合规、审核通过、未下架；
3. **融合精排**：RRF 融合两路结果 → cross-encoder 重排模型精排；
4. **效果感知加权（本项目差异点）**：
   `final = α·语义相关度 + β·历史ROI分位 + γ·新鲜度 − δ·素材疲劳度`
   把素材上线后的 CTR / ROI 回写作为排序特征，让「检索」直接对齐「投放效果」，而不是只对齐语义；
5. **MMR 多样性去重**：避免 top-k 返回五张高度相似的图；
6. **输出**：top-k 素材 ID + 命中理由，交给策略层填进 `replace_creative` 动作的 `candidates` 字段。

```python
class MaterialRetriever:
    def search(self, topic: str, filters: dict, top_k: int = 5) -> list[Material]:
        q = llm.rewrite_query(topic)                       # 改写 + 抽过滤条件
        q_vec = l2_norm(clip.encode_text(q.text))
        ann = vector_db.search(q_vec, field="img", filter=filters, top_n=50)
        kw  = bm25.search(q.keywords, filter=filters, top_n=30)
        cands = rrf_fuse(ann, kw)                          # 融合两路召回
        cands = reranker.rank(q.text, cands)               # cross-encoder 精排
        cands = effect_boost(cands)                        # ROI / 新鲜度 / 疲劳度
        return mmr_diversify(cands, top_k)
```

#### 5. 与 RAG 经验库的分工（面试常问，容易讲混）
| | 经验案例库 | 企业素材库 |
|---|---|---|
| 检索对象 | 历史投放案例（文本 Case） | 可用素材（图像 / 视频） |
| 向量类型 | 文本 embedding | 图文共享空间的多模态 embedding |
| 回答的问题 | “这类计划该怎么投 / 该用什么主题” | “这个主题有哪些具体图可用” |
| 输出去向 | Few-shot 示例注入 Prompt | `replace_creative` 的素材候选列表 |

两条支路在**策略层汇合**：经验库给方向，素材库给弹药。

#### 6. 面试追问预案
- **领域偏移怎么办？** 通用 CLIP 对广告海报（含营销文案、商品图、中文文字）理解弱 → 用内部「素材图 + 主题 / 文案」配对数据做对比学习微调（LoRA），并把 OCR 文本一起编码；
- **中文语义？** Chinese-CLIP / AltCLIP，别用原生 CLIP；
- **规模与延迟？** 百万级 HNSW 单机够用，调 `efSearch` 平衡召回率与延迟；更大规模上 IVF_PQ 压缩；控制 top-N 召回量，把耗时留给精排；
- **为什么还要补 caption / tags？** 硬过滤、关键词召回、可解释，纯向量给不了；
- **冷启动？** 先用 VLM 自动生成 caption 跑零样本检索，再逐步用投放数据微调；
- **效果闭环？** 素材 CTR 回写素材表作为排序特征，同时沉淀“主题 × 人群 × 渠道”的高 ROI 组合进经验案例库，与 RAG 链路打通；
- **安全合规？** 审核状态做硬过滤，未过审素材不进召回池；品牌 / 版权黑名单在过滤阶段拦截。

### 面试时可以这样讲

> 这个平台主要解决的是多代理商渠道投放割裂的问题。华为、vivo、OPPO 等平台在账号体系、API 接口、报表口径和素材规则上都不一样，运营需要反复切换后台。我们基于 AgentScope 搭建了一个广告投放智能体，上层通过 LLM 做意图识别，把运营的自然语言指令解析成结构化投放任务；中间通过渠道适配器屏蔽各平台差异，统一成计划、分组、创意模型；下层接报表数据和转化回传，做实时监控。规则引擎负责触发预算调整、异常告警和素材优化建议，最终形成从创建到监控再到优化的闭环。

如果面试官追问“优化策略具体怎么生成”，可以展开讲六层闭环：

> 优化不是一个大模型端到端出结果，而是拆成六层：先聚合多平台报表，检测层用硬规则加统计异常发现问题，诊断层让 LLM 输出根因和置信度，策略层生成结构化的调价、换素材、扩量候选动作，执行层做安全校验并按风险分级——低风险自动执行，中高风险推送运营确认，最后效果回写形成闭环。策略层上还叠加了 RAG + Few-shot 的个性化学习：把每个账户历史跑得好的广告沉淀成经验案例库，检索相似案例注入 Prompt，让建议跟着这个账户的真实成功经验走，而不是给通用模板。

如果面试官追问技术亮点，可以重点说四点：

1. **统一投放模型**：把多平台广告结构抽象成标准实体，避免每个渠道各写一套业务逻辑；
2. **LLM 不直接操作 API**：LLM 只负责意图识别、归因诊断和策略建议，真正执行前会经过校验、规则引擎和权限控制；
3. **自动化有边界**：自动调价、暂停、扩量都带安全阈值和人工兜底，避免智能体误操作导致预算风险；
4. **策略可个性化、可解释、可进化**：RAG 检索账户历史成功案例，Few-shot 注入让建议带上真实数据依据，输出里带 `reference_cases` 可溯源，效果回写后经验库持续更新。
