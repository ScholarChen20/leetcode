## 一、"网络监测助手"是怎么做到自动化的？

结合你在深信服的项目经历，这个"网络监测助手"本质上是**基于 FastGPT 工作流编排 + 后端服务 + 数据仓库**三位一体的自动化闭环系统。自动化主要体现在以下几个层面：

### 1. 工作流驱动的阶段自动流转

核心架构是"告警→检测→诊断→修复→工单"五阶段流水线，每个阶段都是一个独立节点，由 FastGPT 的工作流引擎自动串联：

- **告警接入节点**：自动从监控平台（如 Zabbix、Prometheus、深信服自研监控）拉取原始告警事件，做标准化处理（统一告警格式、提取关键指标如源IP、目标IP、端口、告警等级）
- **检测节点**：自动调用检测工具/脚本（如 ping 探测、端口扫描、日志检索），对目标系统进行健康检查，返回结构化检测结果
- **诊断节点**：将检测结果输入 LLM，做根因分析（是网络抖动？磁盘故障？还是配置错误？），生成诊断结论和修复建议
- **修复节点**：根据诊断建议，自动执行修复脚本（如重启服务、清理磁盘、切换备用链路）或生成修复工单
- **工单节点**：自动创建工单并流转给对应运维人员，附带完整的诊断报告和修复记录

**自动化的关键**：整个链路无需人工干预，告警一旦产生就自动流经全流程。只有当 LLM 诊断置信度低于阈值时，才触发人工审核节点（人机协同兜底）。

### 2. 数据仓库与 ETL 调度自动化

- 打通各监控平台的数据孤岛，通过 ETL 任务自动抽取、清洗、加载各源数据到统一数据仓库
- 优化数据仓库模型（如构建统一的告警事实表、网络设备维度表），让上层分析查询更快
- ETL 调度任务自动触发（如每小时增量同步、每天全量快照），保证数据时效性

### 3. 告警通知链路自动化

- 构建"告警→消息→电话"三级通知链路
- 根据告警等级自动路由通知渠道：P0 级直接打电话、P1 级发企业微信/钉钉消息、P2 级写入工单系统
- 关键告警触达时效从分钟级降至秒级

### 4. 闭环反馈自动化

- 修复结果自动回写监控系统，更新设备健康状态
- 工单状态自动同步到告警平台，形成"发现→处理→关闭"的完整闭环
- 定期生成运维报告（告警趋势、故障根因分布、MTTR 统计），驱动持续优化

## 二、如何提取不同子系统的 IP 地址？

这是一个非常具体的技术追问，面试官想考察的是你对**企业 IT 运维中多源异构数据治理**的实际经验。以下是基于真实场景的可行方案：

### 1. 数据来源有哪些？

企业里 IP 地址分散在多个子系统：

| 子系统 | IP 数据来源形式 | 提取方式 |
|--------|----------------|----------|
| **CMDB**（配置管理数据库） | 结构化数据库表（服务器表、网络设备表） | SQL 查询，提取 hostname → IP 映射 |
| **监控系统**（Zabbix/Prometheus） | API 接口或数据库 | 调用 Discovery API 获取所有监控主机及其 IP |
| **日志系统**（ELK/Splunk） | 非结构化日志文本 | 正则匹配 IP 地址模式（如 `(\d{1,3}\.){3}\d{1,3}`） |
| **网络扫描工具**（Nessus/OpenVAS） | 扫描报告（CSV/XML/PDF） | 解析报告文件中的主机列表 |
| **云平台 API**（阿里云/腾讯云/AWS） | REST API | 调用 DescribeInstances 等接口获取实例 IP |
| **DNS 系统** | DNS 记录数据库 | 查询 A 记录反向解析 IP |
| **工单系统** | 工单文本描述 | NLP/正则提取工单中提到的 IP 地址 |

### 2. 统一 IP 提取管道设计

实际工程中不会每个源写一套代码，而是设计一个**统一的 IP 提取管道**：

```
各子系统数据源 → 适配器层（Adapter） → 标准化 IP 实体 → 去重/融合 → 统一 IP 资产库
```

- **适配器层**：为每个子系统编写独立的适配器（Adapter），统一输出标准格式：
  ```
  {ip_address, hostname, subsystem_source, last_seen, device_type, location}
  ```
- **去重与融合**：同一 IP 可能出现在多个系统中（如 CMDB 有一条记录、监控系统有一条记录），需要按 IP 地址做去重，取最新更新时间作为权威来源
- **IP 资产库**：最终写入统一的数据库表（或图数据库 Neo4j），供上层检测/诊断节点查询

### 3. 具体提取技术细节

**CMDB 提取**：
```sql
-- 直接查询配置数据库
SELECT ip_address, hostname, asset_type, department 
FROM cmdb_server 
WHERE status = 'running';
```

**日志中提取 IP**：
```python
import re
# 匹配IPv4地址（含基本校验）
ip_pattern = re.compile(
    r'\b(?:(?:25[0-5]|2[0-4]\d|[01]?\d\d?)\.){3}'
    r'(?:25[0-5]|2[0-4]\d|[01]?\d\d?)\b'
)
# 从日志行中提取所有IP
ips = ip_pattern.findall(log_line)
```

### 4. 面试中可能的追问及应对

- **"如果不同系统对同一台服务器的IP记录不一致怎么办？"**
  → 设计权威数据源策略：CMDB 作为主机基础信息的权威源，监控系统作为运行状态的权威源，工单系统作为事件记录的权威源。冲突时按权威源优先级覆盖，并记录差异日志供人工核查。

- **"IP 地址会动态变化（如云主机弹性伸缩），怎么保证时效性？"**
  → 设置定期同步任务（如每5分钟增量同步）+ 事件驱动同步（云平台发送实例变更事件时实时触发更新）+ 过期告警（超过24小时未更新的 IP 记录标记为"待确认"）。

- **"怎么区分内网IP和公网IP？"**
  → 在标准化阶段增加 IP 类型标记字段，根据 RFC1918 私有地址范围（10.x.x.x、172.16-31.x.x、192.168.x.x）自动标记为内网/公网，方便后续安全策略区分。

# 钱财务监控平台

## 一、大数据平台怎么监测订单信息
分两套路线：**离线监测（Hive为主） + 实时监测（Flink为主）**
1. **离线监测（T+1/小时级，对账、指标异常）**
多业务系统订单数据通过Canal同步Binlog、Sqoop同步、Kafka入湖（Hudi/Iceberg），Hive建分层数仓：ODS原始层 → DWD订单明细层 → DWS汇总宽表。
写Hive SQL做监测规则：
- 订单量突增突降：同比/环比波动超过阈值（比如环比下降30%）
- 跨系统不一致：下单表有订单、支付系统无支付记录、状态不一致
- 异常订单：超时未支付、重复下单、金额非法
SQL跑出异常明细、异常指标，写入结果表（如异常订单表、指标结果表）。

2. **实时监测（秒/分钟级，适合即时异常）**
Flink消费Kafka订单流，在流里写规则：连续大量失败订单、短时间同一用户高频下单、支付回调超时。实时匹配规则，直接产出异常消息。


## 二、异常告警信息采集、推送到数字化工单后台（管理工单系统）
完整流转链路：
1. 大数据侧识别异常后，统一封装告警报文：
告警内容包含：告警类型（订单量下跌/支付不一致）、异常订单明细、发生时间、所属系统、阈值、数据来源、等级（P0/P1/P2）
2. 告警汇聚层（两种常用方案）
- 方案A（轻量）：监测脚本里直接调用**工单平台开放HTTP接口**，POST告警JSON；工单平台收到后自动创建工单，分配责任人
- 方案B（解耦，生产推荐）：把告警消息推送到Kafka告警Topic；单独一个告警服务消费这个Topic，做去重、降噪、合并风暴告警、路由，再调用工单后台接口生成工单
✅ 降噪很重要：防止短时间大量相同异常刷屏，生成几百条重复工单，可以设置告警静默期、告警聚合
3. 工单平台能力：
自动生成工单、记录告警原始数据、支持流转、指派、回复、闭环、查看历史告警；也可以同时多渠道推送：企业微信/短信/电话，辅助通知。
4. 回执闭环：工单处理完成后，工单平台可以回调接口，回写给大数据平台，标记告警已处理。

## 三、高频追问预备（你后面大概率会被问到）
1. 问：怎么避免重复生成相同告警工单？
答：告警增加唯一标识，Kafka消费端做幂等，设置静默窗口、相同告警合并。
2. 问：Hive跑出来的异常，怎么判断要不要告警？
答：SQL计算指标，和配置中心里的阈值对比，阈值支持后台配置，不要硬编码。
3. 问：如果工单平台接口挂了怎么办？
答：告警消息持久化，重试队列，失败告警落地备份表，后续补推。

## 一、AI 智能体运维助手是怎么做到自动化的？

这个助手本质上是 **“FastGPT 工作流编排 + Java 状态机裁决 + 工具网关执行 + 长期记忆进化”** 的四层自动化闭环系统。自动化不是“一个脚本跑通”，而是六层自动化叠加，每层替代一类人工介入点。

### 1. 六层自动化总览

| 自动化层次 | 解决的人工动作 | 技术方案 |
|---|---|---|
| **编排自动化** | 人工切换系统、手动触发下一步 | FastGPT 五阶段工作流：告警接入→检测→诊断→修复→验证/工单，节点间 HTTP 工具调用 + 条件分支自动流转 |
| **检测自动化** | 人工登录机器 ping、看磁盘、翻日志 | Java 工具网关封装 ICMP/TCP/traceroute、磁盘四层检测、日志指标查询；FastGPT 按结构化检测对象自动调用 |
| **决策自动化** | 人工判断“是什么故障、要不要修、谁来修” | LLM 诊断根因 + 风险分级；Java 状态机按转移表裁决放行；低风险自动修、高风险转审批/工单 |
| **执行与闭环自动化** | 人工执行修复、手动关单、手动通知 | 幂等修复执行器 + 独立验证 + 自动回滚；终态自动触发工单创建、告警恢复、三级通知 |
| **经验自动化** | 人工复盘、靠老员工经验 | 闭环结束自动写入长期记忆案例库，下次诊断混合召回相似案例 |
| **可观测自动化** | 人工排查“为什么没闭环” | 每次状态转移落 `transition_log`，OpenTelemetry 链路追踪，Prometheus 指标看板 |

### 2. 工作流驱动的阶段自动流转（双层工作流）

核心架构是“告警→检测→诊断→修复→验证→工单”六环节流水线。与普通工作流不同，这里采用 **FastGPT 工作流 + Java 状态机** 双层设计：

- **FastGPT 工作流**：负责 AI 节点编排、LLM 推理、变量传递、条件分支、HTTP 工具调用。每个阶段节点末尾调用 Java 的 `transition` 接口提交证据。
- **Java 状态机**：业务状态的唯一持有者和裁决者。定义 9 个状态：`DETECTING / DIAGNOSING / AWAITING_APPROVAL / REPAIRING / VERIFYING / COMPLETED / ROLLING_BACK / ROLLED_BACK / MANUAL`。所有阶段跳转必须经过状态机校验，FastGPT 的“建议目标状态”只是输入，不是裁决结果。

**关键约定**：FastGPT 节点只负责“算”和“建议”，不直接改状态、不直接操作生产；状态机负责“判”，工具网关负责“做”。FastGPT 节点超时由 Java 定时扫描兜底推进到 `MANUAL`，业务状态不悬空。

### 3. 检测自动化：IP 资产解析 + 分级探测

**（1）统一 IP 提取管道**（详见第二节）：  
CMDB / 监控 API / 日志正则 / 扫描报告 / 云平台 API / DNS / 工单文本 → 适配器层统一输出 `{ip, hostname, subsystem, source, last_seen, type}` → 去重融合 → 统一 IP 资产库。权威源策略：CMDB 管基础信息，监控系统管运行状态，工单系统管事件记录；冲突按优先级覆盖并记录差异日志。动态 IP 通过定时增量同步（5 分钟）+ 云平台事件驱动 + 超 24 小时未更新标记“待确认”保证时效性。

**（2）网络连通性分级探测**（不裸调 ping，全部走 Java 工具网关）：

| 层级 | 探测手段 | 输出 evidence | 用途 |
|---|---|---|---|
| L1 | ICMP ping / ping_sweep | 可达性、丢包率、RTT | 快速面扫 |
| L2 | TCP 端口探测 | 端口 open/closed、连接耗时 | 确认服务可用性 |
| L3 | traceroute / mtr | 逐跳延迟与丢包 | 定位链路断点 |

**（3）磁盘检测四层覆盖**：

| 层级 | 命令/手段 | 输出 | 注意 |
|---|---|---|---|
| L1 | `df -hP` + `df -iP` | 容量使用率、inode 使用率 | inode 耗尽时容量可能正常，必须并行检查 |
| L2 | `du -xhd1` 下钻 | 占用来源目录 | 定位日志/临时文件/业务数据 |
| L3 | `lsof +L1` | 已删未释放文件及进程 | 暗坑：`df` 满但 `du` 小 |
| L4 | `mount` 只读标志、`dmesg` I/O error | 文件系统健康 | 只读/硬件错误**不自动修复**，直接工单 |

**（4）安全边界**：凭证、SSH 密钥、SNMP community 全部留在 Java 侧；FastGPT 只拿结构化结果；网关层做并发限流和超时控制，防探测风暴。

### 4. 决策自动化：状态机裁决 + 风险分流

**状态转移表（配置化，Java 侧持有）**：

| 当前状态 | 目标状态 | 条件 | 异常路径 |
|---|---|---|---|
| DETECTING | DIAGNOSING | 检测对象有效、故障类型可处理 | 无效/超时→MANUAL |
| DIAGNOSING | REPAIRING | 有可执行建议且风险=低 | 无建议→MANUAL |
| DIAGNOSING | AWAITING_APPROVAL | 命中高风险白名单（改权限/删数据/批量变更） | 审批超时→MANUAL |
| DIAGNOSING | MANUAL | 无可自动修复动作（如链路中间跳丢包、FS只读） | — |
| REPAIRING | VERIFYING | 执行回执返回（无论成败） | 确定性失败→ROLLING_BACK |
| VERIFYING | COMPLETED | 业务指标满足验收条件 | 不达标→ROLLING_BACK；无法判定→MANUAL |
| VERIFYING | ROLLING_BACK | 故障特征仍存在 | 补偿不可用→MANUAL |
| ROLLING_BACK | ROLLED_BACK | 补偿成功且幂等校验通过 | 回滚失败→MANUAL |
| 任意非终态 | MANUAL | 超时/重试耗尽/权限拒绝 | 人工处置后可重触发 |

**四道硬约束**（保证状态扭转合理）：
1. **版本 CAS**：`UPDATE ... WHERE run_id=? AND status=? AND version=?`，影响行数 0 即冲突，挡旧状态覆盖新状态。
2. **幂等键**：`runId + actionType + targetObject`，Redis SETNX 占位 + effects 表回填，挡重复副作用。
3. **独立验证**：`VERIFYING` 查业务指标（磁盘可用空间/inode、TCP 连通性、服务健康接口），不读修复脚本返回码，挡虚假自愈。
4. **租约隔离**：进入 `MANUAL` 原子转移 `lease_owner` 给人工，自动链路后续写入被拒，挡人机并发写。

**风险分流示例**：

| 检测结论 | 动作 | 风险 | 去向 |
|---|---|---|---|
| TCP 端口不可达、ICMP 可达 | 重启服务（先查状态，已运行跳过） | 低 | 自动修复→验证 |
| 链路中间跳丢包 | 无安全自动动作 | — | 直接工单（附 mtr 证据） |
| 日志目录容量超阈值 | 清理 N 天前日志（幂等） | 低 | 自动修复→验证 |
| inode 耗尽、临时文件堆积 | 清理过期文件（幂等） | 低 | 自动修复→验证 |
| 已删未释放大文件 | 重启进程/截断（影响面大） | 中/高 | 预览方案→审批/工单 |
| FS 只读 / 硬件 I/O 错误 | 不自动修复 | — | 直接工单（附 dmesg） |

### 5. 执行与闭环自动化：幂等执行 + 三级通知 + 工单回执

- **修复执行**：FastGPT 修复节点调 `POST /workflow/{runId}/action/repair`，透传 `Idempotency-Key`；执行器先查状态再执行，执行前快照，失败可补偿；执行回执作为 `REPAIRING→VERIFYING` 的 evidence。
- **验证查询**：`POST /workflow/{runId}/action/verify` 查真实业务状态，返回快照，不返回布尔值。
- **告警三级通知**：P0 电话、P1 企微/钉钉、P2 工单；Java `AlertNotifyService` 统一封装，告警→消息→电话链路秒级触达。
- **工单闭环**：工单不由 FastGPT 直接调接口，而由状态机进入 `MANUAL` 时触发工单适配器，附件带 `transition_log` 证据引用；告警汇聚生产推荐方案 B（Kafka 告警 Topic + 告警服务去重/降噪/合并/路由后调工单）；告警唯一标识 + 消费端幂等 + 静默窗口 + 相同告警合并防工单风暴；工单接口故障时消息持久化 + 重试队列 + 失败落备份表补推；工单处理完成回调状态机，`COMPLETED` 终态触发告警平台恢复接口，真正闭合“告警→处置→恢复”。

### 6. 经验自动化：长期记忆替代数仓沉淀

数仓适合统计“过去 30 天磁盘告警多少次”，但 Agent 诊断需要回答“和当前故障最像的历史案例怎么处置、结果如何”。因此经验沉淀放在**长期记忆案例库**，而非数仓聚合表。

**记忆结构（案例，非聚合表）**：

```json
{
  "case_id": "disk-inode-var-spool-20261105",
  "fault_signature": {
    "type": "disk", "subtype": "inode_exhaustion",
    "symptom": "df -h正常但df -i超90%，/var/spool膨胀",
    "subsystem": "order-service",
    "environment_tags": ["prod","k8s-node","log-agent-v3"]
  },
  "diagnosis": "会话文件堆积导致inode耗尽",
  "remediation": {"action":"清理/var/spool/sessions下7天前文件","risk":"low","rollback":"快照恢复"},
  "outcome": {"verified":true,"mttr_seconds":45,"rollback_triggered":false},
  "embedding_ref": "vec_0x..."
}
```

- **写入时机**：状态机进入 `COMPLETED/ROLLED_BACK` 终态后异步写入；失败案例同样写入（回滚案例价值不低于成功案例）；相似签名合并更新 `occurrence_count` 和最近 outcome，防膨胀。
- **召回方式**：诊断节点生成建议前做混合召回——先按 `type + subsystem + environment_tags` 标量过滤，再按症状文本向量相似度 Top-K；召回结果作为参考证据注入诊断上下文，不照抄。
- **与数仓分工**：记忆库存“个体经验”服务诊断召回；数仓（ClickHouse/Doris）存“群体统计”（故障趋势、自动闭环率、MTTR 分布）服务运营看板。Agent 诊断读记忆，不读数仓。

### 7. 可观测自动化

- 每次转移写 `workflow_transition_log`：`run_id、from、to、trigger_event、actor、evidence_ref、version_before、version_after`；
- OpenTelemetry 追踪 FastGPT 节点 → Java transition → 工具网关 → 外部系统耗时；
- Prometheus 指标：自动闭环率、验证通过率、回滚率、工单转人工率、记忆召回命中率。

## 二、如何提取不同子系统的 IP 地址？

这是面试高频追问，考察多源异构数据治理经验。企业里 IP 分散在多个子系统，实际工程不会每个源写一套代码，而是设计**统一 IP 提取管道**。

### 1. 数据来源与提取方式

| 子系统 | IP 数据来源形式 | 提取方式 |
|---|---|---|
| **CMDB** | 结构化数据库表 | SQL 查询，提取 hostname → IP 映射 |
| **监控系统**（Zabbix/Prometheus） | API 或数据库 | 调用 Discovery API 获取监控主机及 IP |
| **日志系统**（ELK/Splunk） | 非结构化日志文本 | 正则匹配 IP 模式 |
| **网络扫描工具**（Nessus/OpenVAS） | CSV/XML/PDF 报告 | 解析报告主机列表 |
| **云平台 API**（阿里云/腾讯云/AWS） | REST API | `DescribeInstances` 等接口获取实例 IP |
| **DNS 系统** | DNS 记录数据库 | 查询 A 记录反向解析 |
| **工单系统** | 工单文本描述 | NLP/正则提取 IP |

### 2. 统一 IP 提取管道

```
各子系统数据源 → 适配器层（Adapter） → 标准化 IP 实体 → 去重/融合 → 统一 IP 资产库
```

- **适配器层**：每个子系统独立适配器，统一输出 `{ip_address, hostname, subsystem_source, last_seen, device_type, location}`。
- **去重与融合**：同一 IP 多系统出现时按 IP 去重，取最新更新时间作为权威来源；权威源策略：CMDB 管基础信息、监控系统管运行状态、工单系统管事件记录，冲突按优先级覆盖并记录差异日志。
- **IP 资产库**：写入统一数据库表（或图数据库 Neo4j），供检测/诊断节点查询。

### 3. 技术细节示例

**CMDB 提取**：
```sql
SELECT ip_address, hostname, asset_type, department
FROM cmdb_server
WHERE status = 'running';
```

**日志中提取 IP**：
```python
import re
ip_pattern = re.compile(
    r'\b(?:(?:25[0-5]|2[0-4]\d|[01]?\d\d?)\.){3}'
    r'(?:25[0-5]|2[0-4]\d|[01]?\d\d?)\b'
)
ips = ip_pattern.findall(log_line)
```

### 4. 高频追问应对

- **不同系统 IP 记录不一致怎么办？**  
  → 权威数据源策略：CMDB 主机基础信息权威，监控系统运行状态权威，工单系统事件记录权威；冲突按优先级覆盖并记录差异日志供人工核查。
- **IP 动态变化（云主机弹性伸缩）怎么保证时效性？**  
  → 定期增量同步（如 5 分钟）+ 云平台事件驱动实时更新 + 过期告警（超 24 小时未更新标记“待确认”）。
- **怎么区分内网 IP 和公网 IP？**  
  → 标准化阶段增加 IP 类型标记字段，按 RFC1918 私有地址范围（10.x.x.x、172.16-31.x.x、192.168.x.x）自动标记内网/公网，供安全策略区分。

## 三、OTC 钱财务监控平台方案

> 整体思路：**大数据平台负责订单数据计算、识别异常；调度系统负责定时/实时触发任务；告警模块识别异常后推送到工单数字化后台，生成管理工单**。分四块讲：订单监测方案、任务调度执行、告警流转到工单平台、核心风险点。

### 1. 大数据平台怎么监测订单信息

分两套路线：**离线监测（Hive 为主）+ 实时监测（Flink 为主）**。

**（1）离线监测（T+1/小时级，对账、指标异常）**  
多业务系统订单数据通过 Canal 同步 Binlog、Sqoop 同步、Kafka 入湖（Hudi/Iceberg），Hive 建分层数仓：ODS 原始层 → DWD 订单明细层 → DWS 汇总宽表。  
写 Hive SQL 做监测规则：
- 订单量突增突降：同比/环比波动超过阈值（如环比下降 30%）；
- 跨系统不一致：下单表有订单、支付系统无支付记录、状态不一致；
- 异常订单：超时未支付、重复下单、金额非法。  
SQL 跑出异常明细、异常指标，写入结果表（异常订单表、指标结果表）。

**（2）实时监测（秒/分钟级，适合即时异常）**  
Flink 消费 Kafka 订单流，在流里写规则：连续大量失败订单、短时间同一用户高频下单、支付回调超时。实时匹配规则，直接产出异常消息。

### 2. 异常告警采集、推送到数字化工单后台

完整流转链路：

1. **大数据侧识别异常后统一封装告警报文**：告警类型（订单量下跌/支付不一致）、异常订单明细、发生时间、所属系统、阈值、数据来源、等级（P0/P1/P2）。
2. **告警汇聚层（两种常用方案）**：
   - 方案 A（轻量）：监测脚本直接调用工单平台开放 HTTP 接口，POST 告警 JSON；工单平台收到后自动创建工单、分配责任人。
   - 方案 B（解耦，生产推荐）：告警消息推送到 Kafka 告警 Topic；单独告警服务消费该 Topic，做去重、降噪、合并风暴告警、路由，再调用工单后台接口生成工单。
   - **降噪很重要**：防止短时间大量相同异常刷屏生成几百条重复工单，可设置告警静默期、告警聚合。
3. **工单平台能力**：自动生成工单、记录告警原始数据、支持流转/指派/回复/闭环/查看历史告警；可同时多渠道推送企业微信/短信/电话辅助通知。
4. **回执闭环**：工单处理完成后，工单平台回调接口，回写大数据平台，标记告警已处理。

### 3. 高频追问预备

- **怎么避免重复生成相同告警工单？**  
  → 告警增加唯一标识，Kafka 消费端做幂等，设置静默窗口、相同告警合并。
- **Hive 跑出来的异常，怎么判断要不要告警？**  
  → SQL 计算指标，与配置中心阈值对比，阈值支持后台配置，不要硬编码。
- **如果工单平台接口挂了怎么办？**  
  → 告警消息持久化，重试队列，失败告警落地备份表，后续补推。

## 四、与 AI 智能体运维助手的关联

钱财务监控平台的“离线+实时监测 → 告警汇聚 → 工单闭环”链路，与 AI 智能体运维助手在**告警接入、降噪、工单流转、回执闭环**上共用同一套设计思想：

- 告警汇聚层的去重/静默/合并策略，可直接复用到智能体助手的告警入口；
- 工单平台回调接口，对应智能体状态机进入 `MANUAL`/`COMPLETED` 时的工单创建与恢复上报；
- 两者的差异在于：钱财务平台侧重“大数据计算识别异常”，智能体助手侧重“AI 推理 + 状态机裁决 + 自动修复验证”。前者解决“发现异常”，后者解决“自动处置并证明闭环”。

## 五、技术栈总结（偏 Workflow）

| 层 | 选型 | 职责 |
|---|---|---|
| AI 工作流编排 | FastGPT（工作流 + 知识库 + HTTP 节点 + 条件分支 + 变量） | 六环节节点编排、LLM 推理、结构化输出 |
| 业务工作流裁决 | Java 17 + Spring Boot + 自研状态机（MySQL 转移表 + CAS） | 状态生命周期、转移合法性、幂等、租约、超时兜底 |
| 调度与异步 | XXL-JOB / Spring Scheduling；可选 Temporal | 超时扫描、重试、长流程异步 |
| 工具网关 | Spring Boot REST + Redis 分布式锁 + Resilience4j | 修复/验证/工单/通知统一入口，限流超时 |
| 检测工具 | Java 封装 ICMP/TCP/traceroute；sshj/JSch；Prometheus/Loki/ELK API | 网络分级探测、磁盘四层检测、日志指标查询 |
| 数据与记忆 | PostgreSQL/MySQL + pgvector（或 Qdrant/Milvus）+ ClickHouse/Doris | run/日志/案例元数据、向量召回、离线统计 |
| 消息与告警 | Kafka（可选）+ 告警平台 + 短信/电话 + 企微/钉钉 | 告警接入、去重降噪、三级通知 |
| 工单 | Jira / 自研工单 + 回调接口 | 工单创建、流转、回执闭环 |
| 可观测 | OpenTelemetry + Prometheus + Grafana + 审计日志 | 链路追踪、状态审计、指标看板 |

**最小可行**：FastGPT + Spring Boot + 自研状态机 + MySQL + Redis + pgvector + XXL-JOB + Prometheus/Loki + 工单/通知通道。  
**进阶可选**：Temporal（复杂人工任务）、Kafka（事件解耦）、Qdrant/Milvus（大规模案例）、ClickHouse（统计）。
