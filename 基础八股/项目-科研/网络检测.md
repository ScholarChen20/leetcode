## 一、"网络监测助手"是怎么做到自动化的？

结合你在深信服的项目经历，这个"网络监测助手"本质上是**基于 FastGPT 工作流编排 + 后端服务 + 数据仓库**三位一体的自动化闭环系统。自动化主要体现在以下几个层面：

### 1. 工作流驱动的阶段自动流转

核心架构是"告警→检测→诊断→修复→工单"五阶段流水线，每个阶段都是一个独立节点，由 FastGPT 的工作流引擎自动串联：

- **告警接入节点**：自动从监控平台（如 Zabbix、Prometheus、深信服自研监控）拉取原始告警事件，做标准化处理（统一告警格式、提取关键指标如源IP、目标IP、端口、告警等级）
- **检测节点**：自动调用检测工具/脚本（如 ping 探测、端口扫描、日志检索），对目标系统进行健康检查，返回结构化检测结果
- **诊断节点**：将检测结果输入 LLM，做根因分析（是网络抖动？磁盘故障？还是配置错误？），生成诊断结论和修复建议
- **修复节点**：根据诊断建议，自动执行修复脚本（如重启服务、清理磁盘、切换备用链路）或生成修复工单
- **工单节点**：自动创建工单并流转给对应运维人员，附带完整的诊断报告和修复记录

**自动化的关键**：整个链路无需人工干预，告警一旦产生就自动流经全流程。只有当 LLM 诊断置信度低于阈值时，才触发人工审核节点（人机协同兜底）。

### 2. 数据仓库与 ETL 调度自动化

- 打通各监控平台的数据孤岛，通过 ETL 任务自动抽取、清洗、加载各源数据到统一数据仓库
- 优化数据仓库模型（如构建统一的告警事实表、网络设备维度表），让上层分析查询更快
- ETL 调度任务自动触发（如每小时增量同步、每天全量快照），保证数据时效性

### 3. 告警通知链路自动化

- 构建"告警→消息→电话"三级通知链路
- 根据告警等级自动路由通知渠道：P0 级直接打电话、P1 级发企业微信/钉钉消息、P2 级写入工单系统
- 关键告警触达时效从分钟级降至秒级

### 4. 闭环反馈自动化

- 修复结果自动回写监控系统，更新设备健康状态
- 工单状态自动同步到告警平台，形成"发现→处理→关闭"的完整闭环
- 定期生成运维报告（告警趋势、故障根因分布、MTTR 统计），驱动持续优化

## 二、如何提取不同子系统的 IP 地址？

这是一个非常具体的技术追问，面试官想考察的是你对**企业 IT 运维中多源异构数据治理**的实际经验。以下是基于真实场景的可行方案：

### 1. 数据来源有哪些？

企业里 IP 地址分散在多个子系统：

| 子系统 | IP 数据来源形式 | 提取方式 |
|--------|----------------|----------|
| **CMDB**（配置管理数据库） | 结构化数据库表（服务器表、网络设备表） | SQL 查询，提取 hostname → IP 映射 |
| **监控系统**（Zabbix/Prometheus） | API 接口或数据库 | 调用 Discovery API 获取所有监控主机及其 IP |
| **日志系统**（ELK/Splunk） | 非结构化日志文本 | 正则匹配 IP 地址模式（如 `(\d{1,3}\.){3}\d{1,3}`） |
| **网络扫描工具**（Nessus/OpenVAS） | 扫描报告（CSV/XML/PDF） | 解析报告文件中的主机列表 |
| **云平台 API**（阿里云/腾讯云/AWS） | REST API | 调用 DescribeInstances 等接口获取实例 IP |
| **DNS 系统** | DNS 记录数据库 | 查询 A 记录反向解析 IP |
| **工单系统** | 工单文本描述 | NLP/正则提取工单中提到的 IP 地址 |

### 2. 统一 IP 提取管道设计

实际工程中不会每个源写一套代码，而是设计一个**统一的 IP 提取管道**：

```
各子系统数据源 → 适配器层（Adapter） → 标准化 IP 实体 → 去重/融合 → 统一 IP 资产库
```

- **适配器层**：为每个子系统编写独立的适配器（Adapter），统一输出标准格式：
  ```
  {ip_address, hostname, subsystem_source, last_seen, device_type, location}
  ```
- **去重与融合**：同一 IP 可能出现在多个系统中（如 CMDB 有一条记录、监控系统有一条记录），需要按 IP 地址做去重，取最新更新时间作为权威来源
- **IP 资产库**：最终写入统一的数据库表（或图数据库 Neo4j），供上层检测/诊断节点查询

### 3. 具体提取技术细节

**CMDB 提取**：
```sql
-- 直接查询配置数据库
SELECT ip_address, hostname, asset_type, department 
FROM cmdb_server 
WHERE status = 'running';
```

**日志中提取 IP**：
```python
import re
# 匹配IPv4地址（含基本校验）
ip_pattern = re.compile(
    r'\b(?:(?:25[0-5]|2[0-4]\d|[01]?\d\d?)\.){3}'
    r'(?:25[0-5]|2[0-4]\d|[01]?\d\d?)\b'
)
# 从日志行中提取所有IP
ips = ip_pattern.findall(log_line)
```

### 4. 面试中可能的追问及应对

- **"如果不同系统对同一台服务器的IP记录不一致怎么办？"**
  → 设计权威数据源策略：CMDB 作为主机基础信息的权威源，监控系统作为运行状态的权威源，工单系统作为事件记录的权威源。冲突时按权威源优先级覆盖，并记录差异日志供人工核查。

- **"IP 地址会动态变化（如云主机弹性伸缩），怎么保证时效性？"**
  → 设置定期同步任务（如每5分钟增量同步）+ 事件驱动同步（云平台发送实例变更事件时实时触发更新）+ 过期告警（超过24小时未更新的 IP 记录标记为"待确认"）。

- **"怎么区分内网IP和公网IP？"**
  → 在标准化阶段增加 IP 类型标记字段，根据 RFC1918 私有地址范围（10.x.x.x、172.16-31.x.x、192.168.x.x）自动标记为内网/公网，方便后续安全策略区分。

# 钱财务监控平台

## 一、大数据平台怎么监测订单信息
分两套路线：**离线监测（Hive为主） + 实时监测（Flink为主）**
1. **离线监测（T+1/小时级，对账、指标异常）**
多业务系统订单数据通过Canal同步Binlog、Sqoop同步、Kafka入湖（Hudi/Iceberg），Hive建分层数仓：ODS原始层 → DWD订单明细层 → DWS汇总宽表。
写Hive SQL做监测规则：
- 订单量突增突降：同比/环比波动超过阈值（比如环比下降30%）
- 跨系统不一致：下单表有订单、支付系统无支付记录、状态不一致
- 异常订单：超时未支付、重复下单、金额非法
SQL跑出异常明细、异常指标，写入结果表（如异常订单表、指标结果表）。

2. **实时监测（秒/分钟级，适合即时异常）**
Flink消费Kafka订单流，在流里写规则：连续大量失败订单、短时间同一用户高频下单、支付回调超时。实时匹配规则，直接产出异常消息。


## 二、异常告警信息采集、推送到数字化工单后台（管理工单系统）
完整流转链路：
1. 大数据侧识别异常后，统一封装告警报文：
告警内容包含：告警类型（订单量下跌/支付不一致）、异常订单明细、发生时间、所属系统、阈值、数据来源、等级（P0/P1/P2）
2. 告警汇聚层（两种常用方案）
- 方案A（轻量）：监测脚本里直接调用**工单平台开放HTTP接口**，POST告警JSON；工单平台收到后自动创建工单，分配责任人
- 方案B（解耦，生产推荐）：把告警消息推送到Kafka告警Topic；单独一个告警服务消费这个Topic，做去重、降噪、合并风暴告警、路由，再调用工单后台接口生成工单
✅ 降噪很重要：防止短时间大量相同异常刷屏，生成几百条重复工单，可以设置告警静默期、告警聚合
3. 工单平台能力：
自动生成工单、记录告警原始数据、支持流转、指派、回复、闭环、查看历史告警；也可以同时多渠道推送：企业微信/短信/电话，辅助通知。
4. 回执闭环：工单处理完成后，工单平台可以回调接口，回写给大数据平台，标记告警已处理。

## 三、高频追问预备（你后面大概率会被问到）
1. 问：怎么避免重复生成相同告警工单？
答：告警增加唯一标识，Kafka消费端做幂等，设置静默窗口、相同告警合并。
2. 问：Hive跑出来的异常，怎么判断要不要告警？
答：SQL计算指标，和配置中心里的阈值对比，阈值支持后台配置，不要硬编码。
3. 问：如果工单平台接口挂了怎么办？
答：告警消息持久化，重试队列，失败告警落地备份表，后续补推。
