## 一、项目概述

### 1. 请介绍一下这个项目

这是一个从美食点评业务持续迭代的本地生活平台。原有功能包括商家查询、附近商家、优惠券秒杀、探店笔记、关注点赞、签到统计和智能客服；本次新增“用户侧智能导购＋商家预约后台＋平台知识与会话管理”，围绕餐厅到店预约形成业务闭环。

原点评模块使用 MySQL 保存用户、商家、优惠券、订单和笔记等数据；Redis 处理缓存、登录 Session、秒杀资格、地理位置与社交关系，Caffeine 构建本地缓存，RabbitMQ 异步处理秒杀订单。原智能客服采用 Qwen＋LangChain4j、Redis 记忆与 Function Calling 查询商家和处理到家服务预约。

**新增功能：** 新导购提取预算、人数、日期等结构化条件，通过 Elasticsearch BM25＋向量 kNN 与 RRF 融合检索已发布知识，提供带来源的推荐；实时桌位和预约结果由数据库业务接口提供。用户核对草稿并明确提交后，事务自动分配适配桌位并立即确认，商家可签到、完成或取消，平台可审核知识和追踪会话。

**当前实现边界：** 新平台会话与请求持久化在数据库，模型按受控流程参与条件提取和证据选择；并非沿用旧客服的自主工具调用模式。新旧账号和预约领域独立，旧模块默认未启用，需配置后运行。

### 2. 项目中最有挑战的地方是什么

原有挑战是秒杀防超卖/一人一单、商家缓存一致性、大模型安全调用业务。新增挑战主要体现在：

1. **预约库存：** 真实桌位与固定时段建模，重复点击、超时重试和关售并发时保证订单与库存一致。
2. **推荐依据：** 将实时价格/余位与文本知识分开获取，融合召回后检查来源归属，避免跨店资料和无依据回答。
3. **知识更新：** 新版索引尚未就绪时继续使用旧版，撤回后即使 ES 尚未清理也不能再用于新检索。
4. **异步恢复：** 预约提交与 Outbox 同事务保存，通知和索引失败后能够重试，后台能看到原因。

面试时可以概括为：原有模块关注热点访问与秒杀，新平台进一步明确了模型理解、知识检索、业务查询、事务确认和后台履约之间的责任。

## 二、Spring Boot 与项目架构

### 1. 项目采用什么分层结构

原点评模块采用 Controller、Service、Mapper、Entity 分层：

- Controller：接收请求、参数校验和返回统一结果。
- Service：编排业务流程，处理事务和业务规则。
- Mapper：通过 MyBatis-Plus 访问数据库。
- Entity/DTO：分别表示数据库实体和接口传输对象。
- Config/Interceptor：处理 Redis、RabbitMQ、鉴权和 Web 配置。

业务逻辑尽量集中到 Service，依赖注入优先使用构造器注入。

**新增平台的实际结构：** 按 auth、restaurant、reservation、guide、knowledge、search、ops 组织业务模块，核心流程采用 Controller → Service → Db（JdbcTemplate）的参数化 SQL。部分管理接口仍直接在 Controller 中调用 Db，DTO/Repository 分离是后续改进，不能笼统说所有代码均严格采用 Mapper 分层。当前为模块化单体，Java 17＋Spring Boot 3，原 javax 相关代码已迁移至 Jakarta。

### 2. 为什么使用统一的 Result 返回结果

统一返回结构可以让前端稳定处理接口结果，通常包含成功标识、错误信息、业务数据和总数等字段。这样可以减少不同接口返回格式不一致的问题，也方便统一异常处理和接口文档维护。

**新增平台：** 原点评接口沿用 Result；新 API 成功返回 DTO/数据，异常返回 code/message/traceId 等字段并设置 HTTP 状态。401/403 用于身份和权限，409 用于业务冲突，429 用于限流。两套返回约定需要区分，不是所有接口都包装 Result。

### 3. Spring 事务主要用在哪些地方

事务主要用于涉及多步数据库操作、且必须保证原子性的业务，例如创建秒杀订单、更新业务数据后处理关联记录等。

需要注意：Spring 事务默认基于代理实现，同一个类内部直接调用另一个事务方法时，可能不会经过代理，导致事务注解不生效。事务边界应该尽量放在 Service 对外方法上。

**新增事务场景：** 餐厅确认预约将订单、库存、草稿消费、状态事件和 Outbox 一起提交；知识审核将状态与索引任务一起提交。异步线程不自动继承请求事务，会话后台任务按需要使用 TransactionTemplate。模型调用和 ES 网络请求不放入预约库存事务。

## 三、商家缓存与一致性

### 1. 商家详情使用什么缓存策略

使用 Cache Aside，也叫旁路缓存：

1. 查询时先查 Redis。
2. Redis 命中则直接返回。
3. Redis 未命中时查询 MySQL。
4. 查询到数据后写入 Redis。
5. 更新时先更新 MySQL，成功后删除 Redis 缓存。

数据库是最终数据源，缓存只是加速访问。

**当前项目补充：** 上述是 Redis 层的基本流程，原商家详情入口还会先读 Caffeine，详见本章第 6 问。新平台的余位与确认直接检查业务数据库，不依赖缓存占桌。

### 2. 为什么更新时选择“先更新数据库，再删除缓存”

因为数据库保存的是最终数据。更新数据库成功后删除缓存，下一次请求会重新从数据库加载最新值。

如果采用“更新数据库后更新缓存”，并发场景下可能发生旧数据覆盖新数据：一个线程读取旧数据后，另一个线程更新数据库并写入新缓存，前一个线程又把旧数据写回缓存，最终缓存反而变旧。

“先删缓存再更新数据库”也存在问题：删除缓存后，其他线程可能在数据库更新完成前读到旧数据，并把旧数据重新写入缓存。

### 3. 什么是缓存穿透、缓存击穿和缓存雪崩

缓存穿透：请求的数据缓存和数据库中都不存在，请求每次都打到数据库。

常见解决方案：缓存空对象、布隆过滤器、参数校验、接口限流。

缓存击穿：一个热点 Key 在某一时刻过期，大量请求同时访问数据库。

常见解决方案：互斥锁、逻辑过期、热点数据不过期、后台异步重建。

缓存雪崩：大量 Key 在同一时间集中失效，导致大量请求同时访问数据库。

常见解决方案：TTL 增加随机值、热点数据不过期、限流熔断、多级缓存和 Redis 高可用。

布隆过滤器由一个位数组和多个哈希函数组成。插入元素时，通过多个哈希函数计算出多个下标，并将对应位置设为 1；查询时，如果任意一个位置为 0，说明元素一定不存在，如果所有位置都为 1，只能说明元素可能存在。它的优点是空间占用小、查询速度快，适合防止缓存穿透；缺点是存在误判，不能直接删除，也不能保存原始数据。

### 4. 项目中如何解决缓存穿透

当数据库查询不到商家时，在 Redis 中缓存一个空字符串，并设置较短的过期时间。后续相同的非法请求命中空值后直接返回，不再反复访问数据库。

需要注意空值 TTL 不能设置太长，否则商家刚新增时可能因为缓存空值而短时间查不到；同时还要限制非法参数，避免大量随机 ID 请求。

### 5. 互斥锁和逻辑过期有什么区别

互斥锁是在缓存重建期间只允许一个线程查询数据库，其他线程等待或重试，数据一致性相对更好，但可能增加响应时间。

逻辑过期是在缓存中保存数据和逻辑过期时间。数据逻辑过期后，先返回旧数据，再由后台线程异步重建缓存，性能更好，但允许短时间返回旧数据。

### 6. Caffeine 和 Redis 如何构建二级缓存

查询顺序是 Caffeine、Redis、MySQL：

1. 先查本机 Caffeine，速度最快。
2. Caffeine 未命中再查 Redis。
3. Redis 未命中查询 MySQL。
4. 查询到数据后回填 Redis 和 Caffeine。

当前原点评模块在数据库事务 afterCommit 中先清理本机 Caffeine、删除 Redis，再通过 Redis Pub/Sub 广播 shopId，其他实例监听并清理本地缓存。该机制已经实现，不再列为“未来才增加”。

**边界：** Pub/Sub 不保存离线消息。Caffeine 当前为 expireAfterAccess(10 分钟)，持续访问的热 key 会刷新访问过期时间；漏收失效消息时，不能承诺最多 10 分钟必然更新。可改写后过期、版本校验或可靠失效事件以约束陈旧窗口。

### 7. 缓存一致性是否能做到绝对一致

通常只能做到最终一致，而不是严格强一致。项目中通过“先更新数据库，再删除缓存”降低不一致窗口；对一致性要求更高的场景，可以使用延迟双删、消息通知、Binlog 订阅或缓存更新重试。

**以下保留一致性方案对比：** 延迟双删、Binlog 订阅属于可选改进；当前已经使用提交后失效和 Pub/Sub 广播。

### 8. 延迟双删

执行流程：

1. 第一次删除缓存；
2. 更新数据库；
3. 延迟一段时间后再次删除缓存。

它主要用于解决并发读写时，旧数据被重新写入缓存的问题。第一次删除缓存，第二次删除可以清理并发线程写入的旧数据。
优点是实现简单、改造成本低；缺点是延迟时间不好确定，仍然需要配合失败重试或消息补偿。

### 9. 消息通知

数据库更新成功后，发送缓存失效消息，由其他服务实例或缓存节点消费消息并删除缓存。
常见流程：

```text
更新数据库 → 发送缓存失效消息 → 删除 Redis / 本地缓存
```

这种方式适合多实例和多级缓存场景，例如通知各服务实例清理本地 Caffeine 缓存。
优点是解耦、便于扩展；缺点是需要保证消息可靠投递、失败重试和消费幂等。

### 10. Binlog 订阅

应用更新 MySQL 后，Canal、Debezium 等组件订阅 MySQL Binlog，监听数据库的新增、修改和删除事件，再根据变更内容删除或更新缓存。
典型流程：

```text
更新 MySQL → 写入 Binlog → Canal / Debezium 解析 → 删除或更新缓存
```

它适合多个服务、后台任务或脚本都可能修改同一份数据的场景，可以统一监听数据库变更，减少业务代码漏删缓存的问题。
优点是数据变更入口统一；缺点是需要额外组件，并且存在一定的异步延迟。


### 11. 三种方案如何选择

| 方案 | 主要解决的问题 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 先更新数据库再删缓存 | 普通缓存更新 | 简单、成本低 | 删除失败需要补偿 |
| 延迟双删 | 并发读写时旧数据回填 | 改造成本低 | 延迟时间难确定，不能绝对一致 |
| 消息通知 | 多实例、多级缓存同步 | 解耦，适合广播缓存失效 | 需要保证消息可靠和消费幂等 |
| Binlog 订阅 | 多数据入口导致缓存漏更新 | 以数据库变更为统一触发源 | 需要额外组件，存在异步延迟 |

### 12. 面试总结回答

> 普通商家缓存可以采用 Cache Aside，查询时先查缓存，未命中查数据库并回填；更新时先更新数据库，成功后删除缓存。
> 并发读写较多时，可以增加延迟双删，降低旧数据重新写回缓存的概率。
> 多实例或 Caffeine + Redis 多级缓存场景，可以通过 RabbitMQ 或 Redis 发布订阅发送缓存失效消息，通知所有实例清理本地缓存。
> 如果系统存在多个服务、后台任务或脚本都可能修改同一份数据，可以通过 Canal 或 Debezium 订阅 MySQL Binlog，统一触发缓存失效。以上方案主要保证最终一致，关键业务仍然要以 MySQL 为准。


### 13. ThreadLocal 面试总结回答

> ThreadLocal 的优点是线程隔离、使用方便，适合保存当前请求的轻量用户上下文。

> 它的弊端主要有几个：第一，线程池线程会被复用，如果请求结束后没有 remove，可能导致用户信息残留和用户串号；第二，ThreadLocalMap 的 Key 是弱引用、Value 是强引用，ThreadLocal 对象被回收后可能造成 Value 长时间挂在线程上，引发内存泄漏；第三，ThreadLocal 数据不能自动传递到 @Async、线程池和 RabbitMQ 消费线程；第四，它不能跨服务使用，也不适合保存登录状态。

> 解决方案是在 Filter 或拦截器中通过 finally 或 afterCompletion 统一清理，只保存轻量数据，异步场景优先显式传递 userId，确实需要在线程池传递上下文时使用 TaskDecorator，并且在订单、优惠券等关键业务中重新校验用户权限。

## 四、Redis 高频场景

### 1. 为什么登录信息放到 Redis

如果 Session 只保存在单机内存中，请求被负载均衡到其他实例后可能无法识别用户。将 Token 对应的用户信息存入 Redis，可以让多个实例共享登录状态，并通过 TTL 控制登录有效期。

原点评模块的 RefreshTokenInterceptor 负责校验 Token 和刷新有效期，LoginInterceptor 负责判断接口是否需要登录。

**新平台登录：** 使用 Spring Security＋SessionFilter，密码经 BCrypt 保存；随机 Bearer Token 的哈希在 Redis 中关联 userId，8 小时有效，演示模式存在数据库。每请求重新查账号状态与角色，没有实现滑动续期。不要把原拦截器流程描述为新平台当前鉴权实现。

### 2. 为什么使用 ThreadLocal 保存当前用户

请求经过鉴权后，将用户信息放入 ThreadLocal，Service 层可以直接获取当前用户，不需要每一层都传递 userId。

请求结束后必须调用 remove 清理，否则线程池复用时可能出现用户信息串号，也可能造成内存泄漏。

### 3. 附近商家为什么使用 Redis GEO

Redis GEO 适合根据经纬度查询附近数据。项目中可以只把商家 ID 和坐标放进 GEO，商家详情仍然保存于 MySQL 或 Redis：

1. 通过 GEO 查询附近商家 ID 和距离。
2. 根据 ID 批量查询商家详情。
3. 按 GEO 返回的顺序组装结果。

这样既能利用 Redis 的地理位置能力，也能避免把完整商家对象重复放到 GEO 中。

**新增平台补充：** 当前附近餐厅对候选坐标用 Haversine 计算距离并按半径过滤，尚未使用旧 Redis GEO 路径；ES 有 geo_point mapping，但完整前置地理过滤仍可后续优化。

### 4. 用户签到为什么使用 Bitmap

签到只有“签了”和“没签”两种状态，非常适合用 Bitmap 表示。Key 可以设计为 `sign:{userId}:{yyyyMM}`，日期对应 Bit 的 offset。

- SETBIT：签到。
- GETBIT：判断当天是否签到。
- BITCOUNT：统计当月签到天数。
- 位运算：可以辅助计算连续签到。

Bitmap 占用空间小，一个用户一个月只需要几十个 Bit。

**新增预约的签到不同：** 到店核验依据预约码和时间窗口更新预约状态，不使用 Bitmap 代替业务履约记录。

### 5. UV 统计为什么使用 HyperLogLog

HyperLogLog 适合统计独立访客数量，内存占用很小，适合大规模数据。缺点是结果是估算值，不能得到具体访问用户，也不能替代精确去重。

**项目结合：** 新平台近期热度采用数据库内按用户/日去重的访问和非取消预约进行 log1p 加权，并未用 HLL 实现。样本不足展示评分参考；同城归一化和测试流量过滤尚待完善。

### 6. 关注关系为什么使用 Set

Set 适合保存关注用户 ID，支持快速判断是否关注、添加关注、取消关注和查询共同关注。共同关注可以通过两个用户关注集合的交集实现。

### 7. 点赞排行榜为什么使用 Sorted Set

Sorted Set 同时保存成员和分数，可以保存用户 ID 与点赞时间或点赞数量。这样既能判断用户是否点赞，也能按时间或热度排序。

## 五、优惠券秒杀

### 1. 秒杀场景的核心问题是什么

核心问题包括：

- 高并发请求瞬间涌入。
- 多线程同时扣库存导致超卖。
- 同一用户重复下单。
- 数据库和消息队列承受突发压力。

### 2. Redis Lua 脚本解决了什么问题

Lua 脚本可以把多个 Redis 操作合并成一个原子操作，项目中可以一次完成：

1. 判断库存是否大于 0。
2. 判断用户是否已经购买。
3. 扣减 Redis 库存。
4. 记录用户购买资格。
5. 返回执行结果。

这样可以避免“先查库存、再扣库存”之间被其他线程插入，降低超卖和一人多单风险。

### 3. 为什么不能先查询库存，再扣减库存

因为查询和扣减是两个独立操作。多个线程可能同时读到库存为 1，然后都执行扣减，最终库存可能变成负数或产生多笔订单。Lua 脚本可以保证判断和扣减整体执行。

### 4. 如何保证一人一单

Redis 层使用 Lua 脚本记录用户购买资格，快速拦截重复请求；MySQL 层建立 `(user_id, voucher_id)` 唯一索引作为最终兜底。即使因为重试或消息重复消费再次创建订单，唯一索引也能避免重复数据。

### 5. 为什么使用 RabbitMQ 异步下单

如果秒杀请求同步完成数据库扣库存、创建订单和事务提交，数据库会承受瞬时高并发压力。项目采用：

1. 生成订单 ID。
2. Redis Lua 原子完成库存预扣、资格校验并记录预扣状态。
3. 发送秒杀订单消息到 RabbitMQ，等待发布确认。
4. 返回受理结果，最终订单状态仍由持久化结果决定。
5. 消费者异步创建数据库订单。

这样可以削峰填谷，缩短接口响应时间，也能将秒杀入口和订单创建解耦。

### 6. Redis 预扣库存后，消息发送失败怎么办

这是秒杀系统需要重点考虑的一致性问题。可以采用：

- 生产者 Confirm 确认机制。
- 发送失败重试。
- 本地消息表或补偿记录。
- 定时任务扫描未成功投递的订单并补发。
- 订单超时或创建失败时回补 Redis 库存。

实际方案需要明确“预扣库存”和“订单消息”之间的补偿关系，不能只依赖接口返回成功。

**当前已有：** 原秒杀脚本保存 PENDING 预扣记录与超时索引，服务配置 Confirm/Return 和补偿扫描。Confirm 超时属于结果未知，保留预扣等待查询/补偿；不能一超时就直接回补，否则迟到消息可能继续落单。该流程仍需验证消费、提交、回补竞态，不等同新平台的事务 Outbox。

### 7. RabbitMQ 如何保证消息可靠性

生产者方面开启 Confirm，检查 Broker 发布确认；配合 mandatory Return 检查无法路由，Exchange、Queue 和消息的持久化配置提高重启后的可恢复性。消费端在业务处理成功或可靠记录补偿任务后确认，可由容器自动 ACK，也可手动 ACK，具体取决于监听器配置。

如果消费失败，可以重试；使用死信队列时要正确配置路由与拒绝策略，超过次数后交给补偿任务或人工处理。

**新平台补充：** 新知识/通知监听器采用容器 AUTO ACK，普通异常写入 Outbox 重试状态后返回，后续由扫描器再次投递；失败耗尽保存在 Outbox FAILED，DLQ 虽已声明，不能说所有业务失败都会自动进入死信队列。详见第十五章。

### 8. 如何保证消息幂等

RabbitMQ 可能因为消费者处理成功但 ACK 丢失而重复投递，所以消费端必须幂等：

- 订单 ID 或 `(user_id, voucher_id)` 建立唯一约束。
- 消费前查询订单是否已经创建。
- 通过业务状态判断是否已经处理。
- 重复消息直接确认并忽略。

幂等的关键不是保证消息只投递一次，而是保证消息重复处理也不会产生错误结果。

## 六、分布式锁与并发控制

### 1. 为什么需要分布式锁

Java 的 synchronized 或本地 Lock 只能锁住当前 JVM。服务部署多个实例后，同一个业务可能同时在不同机器执行，因此需要 Redis 或 Redisson 实现跨实例互斥。

常见场景包括缓存重建、同一用户重复下单、定时任务抢占和热点资源更新。

### 2. Redis 分布式锁如何实现

核心命令是：

```text
SET lockKey requestId NX EX 10
```

NX 表示只有 Key 不存在时才设置，EX 设置过期时间，requestId 用来标识锁的持有者。

释放锁时不能直接 DEL，因为锁可能已经过期并被其他线程重新获取。正确做法是通过 Lua 脚本判断 Value 是否等于自己的 requestId，只有相等时才删除。

### 3. Redisson 相比手写 Redis 锁有什么优势

Redisson 封装了可重入锁、自动续期 Watch Dog、公平锁、读写锁、信号量和闭锁等能力，可以减少手写锁时出现的误删、死锁和锁过期问题。

使用分布式锁时仍然要设置合理的锁粒度、超时时间和异常释放逻辑，不能因为用了 Redisson 就忽略业务幂等。

**项目结合：** Redisson Watchdog 通常用于未指定固定 leaseTime 的加锁方式；旧订单处理中 tryLock(2,30,SECONDS) 指定 30 秒租期，不能称为自动无限续期。新餐厅预约主要使用数据库行锁和事务，不将 Redis 锁作为库存正确性的唯一保证。

## 七、MySQL 与 MyBatis-Plus

### 1. 商家查询如何优化

- 商家类型、关联字段建立合适索引。
- 热门商家详情使用 Redis 缓存。
- 附近商家查询使用 Redis GEO。
- 分页查询限制单页数量。
- 只查询实际需要的字段。
- 避免大数据量下的深分页。
- 原名称模糊搜索可扩展到 Elasticsearch；新平台已实现 ES 餐厅关键词与知识双路检索。

需要注意，`LIKE '%关键词%'` 通常无法使用普通 B+ Tree 索引。数据量较大时可以改为前缀匹配、全文搜索或接入 Elasticsearch。

### 2. MySQL 为什么使用 B+ Tree 索引

B+ Tree 的非叶子节点只保存索引，能容纳更多索引项，树高度较低；数据集中在叶子节点，叶子节点之间有链表连接，适合范围查询和排序。

### 3. 数据库如何防止秒杀库存变成负数

可以使用带条件的原子更新：

```sql
UPDATE tb_seckill_voucher
SET stock = stock - 1
WHERE voucher_id = ? AND stock > 0;
```

通过返回影响行数判断是否扣减成功。Redis 负责高并发快速拦截，数据库条件更新负责最终兜底。

### 4. MyBatis-Plus 的优点和局限是什么

优点是简化常见 CRUD，提供条件构造器、分页插件、逻辑删除和通用 Service，能够减少 Mapper 样板代码。

局限是复杂查询、聚合统计和性能敏感 SQL 仍然需要手写 SQL；不能因为使用 ORM 框架就忽略索引、执行计划和事务设计。

**新增预约相关索引：** (table_id,slot_id) 唯一约束库存单元，(user_id,idempotency_key) 和 (draft_id,draft_version) 约束重复确认，预约列表按 (user_id,created_at)、(restaurant_id,starts_at) 访问。锁查询和批量筛选需要结合实际 SQL/执行计划优化。

**实现边界：** 新平台主要使用 JdbcTemplate 手写参数化 SQL；候选上限 50，部分热度和详情查询仍有 N+1 开销，后续优先改批量查询和分页。

## 八、智能客服与大模型

### 1. 为什么使用 LangChain4j

LangChain4j 面向 Java 应用封装了 Chat Model、AI Service、会话记忆和 Function Calling 等能力，可以把大模型接入到已有 Spring Boot 业务中。

**新平台实际使用：** ModelGateway 实现 ChatLanguageModel，使用其消息、Response 和 TokenUsage 抽象；底层通过 JDK HttpClient 明确控制超时。RAG 融合、知识发布和会话编排由应用实现，不能说全部由框架自动完成。

### 2. Qwen 如何接入项目

可以通过 DashScope 的 OpenAI 兼容接口接入：配置 API Key、Base URL 和模型名称。新平台使用自定义 ModelGateway 适配 LangChain4j 模型接口，同时提供聊天与 Embedding 调用、超时、错误处理和 Token 记录。

API Key 不应写死在代码或提交到 Git，可以使用环境变量或配置中心注入。

### 3. Function Calling 是什么

Function Calling 的流程是：

1. 后端向模型声明可用工具和参数结构。
2. 用户提出问题。
3. 模型判断是否需要调用工具。
4. 模型返回工具名称和参数。
5. 后端校验参数并真正执行方法。
6. 后端把工具结果交给模型。
7. 模型根据真实结果组织自然语言回复。

模型只负责理解意图和生成参数，不能直接访问数据库。商家查询、预约创建等动作必须由后端工具执行。

**新旧实现区别：** 原智能客服使用 AI Service 与工具调用。新智能导购采用“条件提取 → 受控查询/检索 → 证据选择”的固定流程，当前没有开放式自主 tool_calls 循环；写预约必须通过用户确认接口。

### 4. 如何防止智能客服编造商家信息

不能让模型凭训练记忆回答商家地址、价格和营业时间。应通过 Function Calling 查询 MySQL 或缓存，并在系统提示词中要求只基于工具结果回答。

如果工具查询不到数据，要明确告诉用户没有找到，不能让模型自行补全。返回给模型的商家信息也应控制字段，避免暴露无关数据。

**新增方案：** 实时价格/余位由业务查询提供，环境/菜品通过 RAG 获取已发布知识，模型只选择来源片段与原文引文。后端校验版本、店铺和引文确实存在。原文匹配不等于语义完全正确，仍需审核和效果评测，详见第十三章。

### 5. Redis 如何保存会话记忆

可以按用户或会话 ID 设计 Key，例如：

```text
chat:memory:{userId}
```

Value 保存最近一段对话消息，设置过期时间并限制最大消息数。每次请求读取历史消息，调用模型后再保存用户消息和 AI 回复。

**当前范围：** 上述是 Redis 会话记忆通用做法与原客服路线。新平台改用 guide_conversation/guide_request/guide_event 持久化约束、请求和执行事件，便于幂等、恢复、删除及追溯预约来源；不应说新平台仍把全部会话存 Redis。

生产环境需要考虑：

- 消息窗口限制，防止上下文无限增长。
- Redis TTL，避免长期占用内存。
- 多设备同时聊天时的并发更新。
- 敏感信息脱敏和会话清理。

### 6. Function Calling 如何保证安全

模型传入的参数不能直接信任，后端必须重新校验：

- 当前用户是否登录。
- 商家是否真实存在。
- 预约时间格式和时间范围是否合法。
- 联系电话和地址是否有效。
- 用户 ID 必须从登录上下文获取，不能由模型传入。
- 业务写操作是否需要幂等控制。

### 7. 大模型服务失败如何处理

- 设置连接、读取和整体调用超时。
- 捕获模型异常并返回友好提示。
- 对单用户和全局调用进行限流。
- 记录 traceId、模型名称和耗时。
- API Key 使用环境变量或密钥管理服务。
- 对模型不可用场景提供有限规则/FAQ 与手动查询入口；当前没有人工客服接管系统。
- 对输入和输出进行敏感信息过滤。

### 8. 新增导购如何支持多轮修改？

会话保存结构化条件，模型只提取本轮明确变化的字段，后端按白名单合并并校验。例如“改成 4 人”只改人数，预算与商圈继续保留；影响候选或预约的条件变化会使旧选择/确认卡失效。历史不是每次原样全部传入模型。

### 9. “第二家”“换一批”“周末”怎么处理？

“第二家”从上一轮持久化推荐列表中取稳定 ID；“换一批”排除上一轮候选；日期按 Asia/Shanghai 解释，“周末”不擅自确定日期，由用户进一步选择。精确时段最终在预约卡中核对。

### 10. 同一会话重复请求和并发怎么处理？

消息使用 clientMessageId，(conversation_id,client_message_id) 唯一，并校验内容摘要；同 key 不同内容拒绝。一个会话只允许一个 RUNNING 请求，执行声明持久化，防止重试重复调度。后台任务显式传身份并重新检查所有权，不自动继承 ThreadLocal。

### 11. 为什么使用 SSE？断流怎么恢复？

用户提交消息后得到 requestId，再用带 Bearer Header 的 fetch 订阅 SSE。服务端发送 status/done/error，最终结果落库；断流后前端按 requestId 查询，避免重新创建消息。当前推送阶段进度和结构化结果，没有逐 Token 流式输出，也没有完整 Last-Event-ID 回放。

### 12. 如何限制模型成本和后台任务？

新平台按用户/IP/全局固定分钟窗口限流，并限制用户每日请求数；执行器最多 4 个线程、队列 16，满时拒绝新任务。单次模型调用有超时和输出限制，记录 Token；缺少单价时费用显示未知。线程上限是单实例的，尚无分布式并发信号量或每日 Token 配额；评测与交互任务隔离可继续完善。

## 九、常见追问与标准回答

### 1. Redis 和 MySQL 数据不一致怎么办

先明确一致性目标。一般缓存场景追求最终一致：更新时先提交数据库，再删除缓存；删除失败时通过重试、消息补偿或定时任务再次删除。对强一致要求高的业务，不能只依赖缓存，需要以数据库或事务消息为准。

### 2. Redis 挂了会怎样

需要区分业务：商家查询可以降级到数据库，但要限流，避免数据库被打垮；秒杀场景不能简单放行，应暂停秒杀或走保护逻辑；登录业务可以暂时不可用，避免把权限判断降级为默认放行。

生产环境还应使用 Redis 主从、哨兵或集群，并配置连接池、超时和监控。

### 3. RabbitMQ 消息积压怎么处理

先监控队列深度、消费者数量和消费耗时，判断是流量突增、消费者故障还是单条消息处理变慢。然后可以临时增加消费者、优化慢 SQL、拆分耗时任务或降低生产速度。不能直接无脑增加消费者，还要确认数据库和下游服务能够承受。

### 4. 接口重复提交怎么处理

读请求一般不需要特殊处理，写请求可以使用幂等 Token、业务唯一索引或状态机。秒杀订单通过 (user_id,voucher_id) 唯一约束和订单状态控制。

**新预约已经实现：** (user_id,idempotency_key) 核对重复提交，payload hash 防 key 被用于其他内容，草稿 version 和 consumed_id 防旧确认卡和换 key 重复消费；取消同时匹配预约状态与库存归属。详见第十四章。

### 5. 如何定位线上接口慢

先通过监控和链路追踪拆分耗时：网关、Controller、Redis、MySQL、第三方服务或消息队列。再查看慢 SQL、连接池、线程池、GC、Redis 命中率和外部服务响应时间。项目中可以用 traceId 串联请求日志和消息日志。

### 6. 预约提交成功但通知失败，应该回滚预约吗？

不需要。预约和 Outbox 已同事务提交，用户可在列表查看确认状态。通知失败由 Outbox 重试；回滚预约会破坏已经承诺的桌位结果。数据库提交失败时则不能返回确认，也不会留下同事务的通知事件。

### 7. 商家能通过修改路径 ID 越权操作吗？

角色检查之后还要核验 merchant_member 归属，处理预约时使用数据库中的店铺 ID 再授权，用户只能访问自己的会话和预约。模型与客户端传入的身份均不可信；后台查看完整联系方式单独记录审计。

## 十一、面试速记版

### 缓存

Cache Aside：读缓存，未命中查库并回填；写库成功后删缓存。穿透用空值或布隆过滤器，击穿用互斥锁或逻辑过期，雪崩用随机 TTL 和限流。

### 秒杀

Lua 原子完成库存判断、扣减和一人一单校验；RabbitMQ 异步创建订单；MySQL 唯一索引和条件更新做最终兜底；消费者必须幂等。

### 分布式锁

`SET NX EX` 获取锁，Value 使用唯一请求 ID；释放锁要校验持有者，不能直接删除；复杂场景使用 Redisson。

### 登录

原点评拦截器校验并刷新 Redis Session；新平台使用 Spring Security、8 小时随机 Token，无滑动续期。请求结束清理身份上下文，异步显式传递并再授权。

### Redis 数据结构

GEO 做附近商家，Bitmap 做签到，Set 做关注关系，Sorted Set 做点赞排行，HyperLogLog 做 UV 估算。

### 智能客服

原客服：Qwen＋LangChain4j、Redis 记忆、Function Calling。

新导购：数据库保存约束与请求，受控流程查询商家/余位，RAG 检索已发布证据，SSE 返回进度和最终结果，预约由用户显式确认。

### 新增 RAG

BM25＋kNN 各 Top20，RRF 常数60，最终最多8段、每文档2段；两路相同范围过滤，发布版本与原文引用复核。

### 新增预约

桌位×固定时段；草稿10分钟不占桌；事务锁＋条件占用；幂等键＋草稿版本；取消只释放仍属于自己的库存。

### 新增知识与后台

审核后先索引再切发布指针；撤回先禁用再清索引；Outbox 同库事务、异步重试、通知去重；商家店铺范围授权与审计。

### 最后一句总结

> 这个项目的核心思路是：用 MySQL 保证业务数据可靠，用 Redis 承接高频访问和并发控制，用 RabbitMQ 做异步削峰和解耦，再通过大模型和后端工具把自然语言交互接入真实业务流程。

## 十二、滑动窗口限流（简历追问）

### 1. 项目里的限流现在是怎么做的？能称为滑动窗口吗？

当前仍是固定分钟窗口，需要区分原客服和新增平台：

| 实现 | 默认用户/IP/全局阈值 | 计数与响应 |
| --- | --- | --- |
| 原 AiRateLimiter | 20/60/600 | 原客服 Redis 分钟计数，异常由 Result.fail 返回 |
| 新 GuideRateLimiter | 20/60/120 | Lua 对单 key 原子 INCR＋首次 EXPIRE，超限 HTTP 429，Redis 异常 503 |

新平台三个维度在 Java 中依次检查，前面维度可能已计数、后面才拒绝；没有实现三维度一起判断/一起写入的严格滑动窗口，也不是 AOP 切面限流。AOP 相关代码主要用于原 AI 审计。

面试可说“Redis 多维度固定窗口限流”，下面保留的 ZSET＋Lua 滑动窗口是进一步改造方案，未作为当前已落地成果。

### 2. 为什么要用滑动窗口？

固定窗口在分钟交界处可能放过短时间内的双倍流量。例如单用户每分钟最多 20 次，在 12:00:59 连续请求 20 次，12:01:00 又请求 20 次，固定窗口认为两分钟各 20 次，但实际 2 秒内来了 40 次。滑动窗口每次都统计“当前时刻往前 60 秒”的请求，能消除这个边界突刺。

### 3. 如果改成 Redis 滑动窗口，具体怎么实现？

可以用 Redis **Sorted Set（ZSET）+ Lua 脚本**。用户、IP、全局各一个 Key；ZSET 的 score 是请求时间戳（毫秒），member 是“时间戳 + 唯一请求 ID”，避免同一毫秒内请求相互覆盖。以窗口 60 秒、阈值 `limit` 为例，每次请求在同一段 Lua 脚本中执行：

1. 用 Redis `TIME` 取得当前时间，统一各应用实例的时间基准。
2. 对三个 Key 分别执行 `ZREMRANGEBYSCORE key -inf cutoff`（`cutoff = now - 60000`），删除时间戳小于等于 `cutoff` 的记录；执行 `ZCARD` 得到窗口内次数。统计区间为 `(now - 60000, now]`。
3. 只要任一维度的次数 `>= limit`，立即拒绝，**三个维度都不写入本次请求**；全部未达阈值才分别 `ZADD` 本次请求，并用 `PEXPIRE` 设置略长于窗口的 TTL（例如 61 秒）。

判断和写入必须放在**同一个 Lua 脚本**里，由 Redis 原子执行；否则两个并发请求可能同时读到未超限，然后都放行。三个维度也要一起判断和写入，避免用户维度已计数、IP 维度却拒绝导致“被拒请求占用前一维度配额”。如果只为某个维度限流，可跳过阈值 `<= 0` 的维度。Redis Cluster 下，同一个脚本访问的 Key 必须位于同一 hash slot，可以用共同的 hash tag；但全局 Key 容易形成热点，需要结合实际流量评估。

### 4. 面试官追问性能、异常和验证时怎么答？

- 精确滑动窗口需要保存窗口内每次请求，内存约随请求量增长；清理和 ZSET 操作也有开销。高流量下可以改用按秒分桶的滑动计数器，减少内存，但精度会下降。
- IP 维度要使用可信网关传入的客户端 IP，不能直接信任任意请求头；用户维度使用登录态中的用户 ID。全局维度保护模型调用成本和下游容量。
- Redis 不可用时要有明确策略，不能无限放行模型请求。新增 GuideRateLimiter 超限已返回 HTTP 429、Redis 异常返回 503；Retry-After 与严格滑动窗口仍可完善，原客服接口返回语义需单独区分。
- 升级后的验证重点是窗口边界突刺、多线程并发下不超发、任一维度拒绝时其他维度不增加、Key 到期回收和 Redis 故障保护。当前固定窗口不具备全部这些性质。原 AI 有 hmdp_ai_rate_limited_total 指标，新平台细分限流指标可继续补齐。

**面试速答：**“项目当前对智能客服做了 Redis 用户、IP、全局三级限流，代码是固定分钟窗口。严格滑动窗口会改为 ZSET 记录请求时间，用 Lua 一次完成过期记录清理、三个维度计数判断和全部维度写入，解决分钟边界突刺及并发超发；Redis 故障时保护模型调用并降级。”

## 十三、RAG 混合检索与回答依据（新增）

### 1. 新增的 RAG 导购整体流程是什么？

用户输入需求后，先提取城市、商圈、人均预算、人数和日期等条件，后端进行字段校验，再筛选餐厅与实时余位。环境、菜品、停车等问题从当前已发布知识中检索；服务端整理候选卡和来源，模型选择有依据的资料片段，最后由用户选择时段并确认预约。

```text
用户需求 → 结构化条件 → 商家/余位筛选
                     → 已发布知识：BM25 + kNN → RRF 融合
                     → 推荐卡、引用来源 → 用户核对 → 预约事务
```

**项目结合：** `GuideService` 负责受控流程，`RestaurantService` 和 `ReservationService` 提供业务事实，`KnowledgeService` 与 `ElasticGateway` 提供证据。预约库存和确认结果不能通过 RAG 文本推断。

### 2. 为什么关键词召回从 MySQL 扩展到 Elasticsearch？

MySQL 保留业务事务和结构化过滤职责。它也有全文检索，但当需求包含中文分析、字段权重、相关性排序与向量召回时，Elasticsearch 提供了更统一的实现方式。当前用 ES 同时承载 BM25 和向量，减少同时维护两套检索服务的成本。

**取舍：** ES 增加索引延迟、内存与运维成本，不是数据量小也必须使用。当前选择也服务于知识检索、版本更新和效果对比的完整工程链路。

### 3. BM25 和向量检索为什么要结合？

BM25 通过词项匹配、词频饱和、逆文档频率和长度归一化衡量相关性，适合明确的餐厅名、菜品名和服务术语。向量检索更适合口语与同义表达，例如“适合聊事情”与“音乐轻柔、环境安静”。

两者各有盲区：关键词可能漏掉同义表达，向量相似可能只是主题相关。双路召回提供互补候选，但召回结果仍要经过店铺范围、发布版本和引用校验。

### 4. 为什么用 RRF？为什么不把两个分数相加？

BM25 分数和向量相似度不在同一尺度，直接相加会导致某一路不稳定地主导排序。RRF 用排名融合：

```text
RRF(d) = Σ 1 / (60 + rank_i(d))
```

排名从 1 开始，未召回的不计分。同一片段在两路都靠前时得到更高分。当前每路 Top 20，融合后按 chunkId 去重，每篇文档最多 2 段、最终最多 8 段。RRF 简单且不需要标定原始分数，但会丢失分数差距信息；常数 60 是初始配置，后续通过真实评测调整。

### 5. 中文分析器与知识切分怎么选？

当前 ES 使用内置 ngram 1～2 分析器与 lowercase，无需额外安装 IK 插件。它能匹配中文单字、相邻双字，但噪声和索引体积可能更大，后续应与词典分析器和同义词配置比较。

知识目前按 Java 字符串长度 500 切分，相邻重叠 60，保留文档 ID、版本 ID、店铺 ID、片段序号和来源说明。重叠减少边界信息丢失；该方案不是按 Token 或语义段落切分。菜单/FAQ 后续可按标题、问答条目分段。当前未实现 PDF/OCR 导入。

### 6. 怎么避免跨店知识混用与模型编造引用？

1. 服务端先计算允许的店铺和当前发布版本。
2. BM25 与 kNN 使用相同的 shopId、versionId、PUBLIC 过滤。
3. 融合后再次与数据库有效知识核对，响应前检查版本与店铺状态。
4. 模型返回 `chunkId + quote`，后端核验 quote 是该片段内的连续原文，再展示来源。
5. 价格、店名、余位和操作按钮由后端业务数据构建，模型没有预约写权限。

**注意：** 原文匹配证明“来源里有这句话”，不等于资料真实或确实回答了问题；否定上下文、资料过时、跨店语义归属仍需审核和效果评测。

### 7. 模型、Embedding、Elasticsearch 分别失败时怎么办？

| 故障 | 当前降级方式 |
| --- | --- |
| Qwen 请求失败 | 规则提取与资料节选，保留手动筛选 |
| Query Embedding 或 kNN 分支失败 | 保留已成功的 BM25 检索结果 |
| Elasticsearch 整体失败 | 无 RAG 证据，退回数据库基础查询与预约 |
| 新知识生成向量失败 | 保留原已发布版本，索引任务重试 |

ES 全故障时不能继续宣称拥有 ES BM25 能力。规则模式只覆盖有限问法，不能代替真实模型效果验证。

### 8. 怎么证明 RAG 效果？72/72 代表什么？

需要分别评估硬条件正确性、证据召回、排序、引用支持和无答案拒答。当前固定集有 72 条合成资料案例，本地词面检索 72/72 满足预期；指标是指定店铺范围内前 5 个来源是否包含期望文本，不能等同完整标注下的 Recall@5，也不代表真实问答准确率 100%。

平台支持保存评测历史，并对 BM25、向量、融合结果比较。真实 Qwen＋ES 效果、独立人工验收集和引用支持率还需补验。当前尚未接 reranker；要先判断是召回遗漏还是排序问题，再决定是否引入。

## 十四、实时桌位预约与库存一致性（新增）

### 1. 这次新增的餐厅预约和原到家预约有什么区别？

原到家预约围绕服务时间、地址与服务状态；新餐厅预约需要解决实际桌位占用。首期采用固定且不重叠的时段，清场时间计入占用区间，每笔预约一张桌，1～6 人，系统自动选择最小适配桌。

实体桌 `dining_table` 保存桌号与容量，`dining_slot` 保存具体日期时段，`table_inventory` 保存“桌位×时段”的库存，`restaurant_reservation` 保存已确认预约快照。当前使用线上专用桌，线下占桌还没有接入。

### 2. “提交即确认”怎样实现？

确认接口同步执行数据库事务：校验用户、幂等键和草稿 → 锁餐厅与时段 → 检查开售、截止时间和人数 → 锁合适库存 → 写 CONFIRMED 预约 → 占用库存 → 标记草稿消费 → 写状态记录与 Outbox。

事务提交成功后才返回预约确认结果。通知可以异步发送，但本次分桌与确认不由 MQ 异步决定。模型回答“已经预约”不具备业务确认效力。

### 3. 最后一桌怎样避免被同时分给两笔预约？

当前通过餐厅/时段行锁协调并发，再锁定未占用的适配库存，最后执行条件更新：

```sql
UPDATE table_inventory
SET reservation_id = ?
WHERE id = ? AND reservation_id IS NULL;
```

影响行数必须为 1，否则抛业务异常并回滚订单和库存操作。`UNIQUE(table_id,slot_id)` 只防重复创建库存单元，不能单独保证不超卖，必须结合锁和同事务更新。

**已验证：** H2 环境创建 50 个竞争任务，由 16 个线程执行，最后只有一笔确认。这是并发正确性验证，不是生产 QPS 证明；真实 MySQL 版本已编写但尚待外部环境运行。

### 4. 为什么不用 Redis 预扣桌位？锁粒度有什么取舍？

餐厅预约希望成功响应时已确定具体桌位，库存与订单又在同一数据库，本地事务便于实现和核对。当前用户提交先锁用户，再按餐厅 → 时段 → 草稿/库存处理，取消和关售遵守兼容的餐厅/时段锁顺序。

餐厅行锁较保守，会串行化同店不同时间段；它简化了关售和确认的竞争规则，但限制吞吐。后续根据真实 MySQL 的锁等待和吞吐数据，再细化到时段级锁。统一锁顺序只能降低死锁风险，不能保证绝无死锁。

### 5. 草稿版本、有效期和幂等键各解决什么？

- **草稿不占库存：** 只保存待确认信息，10 分钟有效；提交时再次查询分桌。
- **version：** 用户修改人数/时段，或导购条件变化、会话删除时，使旧确认卡失效。
- **Idempotency-Key：** 同用户同 key 重试时核对 draftId/version 摘要，返回原预约；内容不同则拒绝。
- **consumed_id 与唯一约束：** `(draft_id,draft_version)` 防止换 key 重复消费同一草稿；用户新建不同草稿属于不同意图。

HTTP 响应丢失时使用原 key 查询/重试，不应立即新建草稿重下单。预约售罄时保留已填信息，由用户选择其他时段，不擅自更换餐厅或增加预算。

### 6. 取消为什么不能只按库存 ID 释放？

旧取消请求可能延迟到达，此时同一库存已被另一笔预约占用。如果只按 inventory_id 清空，会误释放新订单。当前校验状态，重复取消直接返回既有结果；真正释放时要求库存仍指向本预约：

```sql
UPDATE table_inventory
SET reservation_id = NULL
WHERE id = ? AND reservation_id = ?;
```

取消状态与库存释放在同一事务中，影响行数异常不能悄悄忽略。

### 7. 关售、签到与未到店怎么保证规则一致？

关售与确认使用同一餐厅/时段锁协议。确认先完成则保留预约，关售只停止后续新预订；关售先完成则确认读取最新状态并拒绝。关售不会隐式取消已确认订单。

```text
CONFIRMED → CHECKED_IN → COMPLETED
     ├──→ CANCELLED_BY_USER
     ├──→ CANCELLED_BY_MERCHANT
     └──→ NO_SHOW
```

用户取消要求开始前；签到核验到店码并限开始前后 15 分钟；完成要求已签到；未到店要求超过宽限期；商家取消必填原因。修改时锁定并检查最新状态，相同目标可幂等返回，不允许终态恢复为确认。

## 十五、商家后台、知识版本与可靠任务（新增）

### 1. 新增后台有哪些实际功能？

商家端维护资料、真实桌位、固定时段模板和每日排期，可批量生成时段、停止新预订，按日期/状态查看预约，完成签到、服务完成和取消。平台端管理账号与店铺归属、知识审核、会话记录、反馈、索引失败任务及评测历史。

店铺关闭和时段关售控制新请求，不能改写已确认预约快照。模板重复生成不创建重复库存，现有实例和订单不随模板被静默覆盖。

### 2. 怎么防止商家通过修改 shopId 访问别人的数据？

Spring Security 先校验 MERCHANT/ADMIN 角色，业务层再通过当前 Actor 与 merchant_member 核验店铺归属。处理预约时使用数据库记录的 restaurant_id 重新授权，不能相信用户传入的身份字段。

普通用户仅能访问自己的会话、草稿和预约。履约期间商家可查看完整联系方式，但需要店铺权限并记录审计；常规列表脱敏。当前运营与管理员合并为 ADMIN，未实现更细的店内岗位权限。

### 3. 知识审核通过后为什么还要等待索引？

知识按 document/version/chunk 拆分。审核通过后进入 INDEXING，后台生成向量、写 ES 并等待可检索，再通过数据库事务切换 `published_version`；失败保留旧版供线上使用。

ES 写入使用 `refresh=wait_for`，片段全部完成后调用 `publishReady`。发布时锁文档/版本，防止较旧任务覆盖更新的已发布版本。当前按创建时间比较顺序，严格递增版本号和相同时间戳顺序还可继续完善。

### 4. 文档撤回后，ES 向量还没删完怎么办？

先在数据库事务内清空发布指针并标记撤回，再通过 Outbox 异步清理索引。检索只允许当前有效版本，即使旧向量仍存在，也不能通过发布资格校验。正在索引的任务在发布前再次检查状态，撤回版本不能自动重新生效。

历史已显示的文字无法收回。当前有响应前复核，但数据库校验与网络发送并非一个原子操作；严格撤销所有在途回答还需要额外协调。

### 5. 为什么使用事务 Outbox？

数据库提交后直接发 MQ，进程可能在发送前宕机，导致业务成功但通知丢失；先发 MQ 再提交，消费者可能处理最终回滚的业务。Outbox 将业务与待处理事件写入同一个数据库事务，再由后台扫描投递。

因此，预约已提交但 MQ 暂时不可用时，用户仍能查询预约，通知任务等待恢复。Outbox 保证有可恢复的任务记录，消息仍可能重复，消费端必须幂等。旧秒杀 Redis 预扣记录与新平台数据库 Outbox 不是同一个实现。

### 6. Outbox 怎么重试？是不是都用手动 ACK 和死信队列？

发送端等待 Publisher Confirm，并检查 mandatory Return；扫描 PENDING/SENT 到期任务，消费完成标记 DONE，异常记录次数与错误类型，达到 5 次标记 FAILED，由平台手工重试。退避是 `min(300,5×attempts²)` 秒，属于二次增长。

新平台监听器使用容器 AUTO ACK。普通业务异常在消费函数内落为 Outbox 重试状态后返回，后续由数据库任务再次投递。DLQ 已声明，但业务重试耗尽主要保存在 Outbox FAILED，不能说所有失败都自动进入 DLQ。

通知通过 `(user_id,event_id)` 唯一约束和事务避免重复；索引用稳定片段 ID，商家索引通过 revision 与 external_gte 限制旧版本覆盖。多实例仍可能重复计算向量，Outbox 租约领取与批任务隔离是后续改进。

### 7. 会话管理、反馈和删除如何闭环？

平台可查看脱敏问题、约束、检索来源、执行事件、错误、总耗时及 Token；用户可点赞/点踩，运营记录处理状态，反馈不会直接变成线上知识。预约保存 source_request_id，方便追溯导购来源。

用户删除会话后清理可见对话和执行内容，并使关联未消费草稿失效；已确认预约继续保留履约记录。当前默认会话内容保留 30 天，统计、反馈、业务记录和备份属于不同保留域，不能把会话删除称为全系统永久擦除。
