## 1. 项目定位

### Q1：一句话介绍这个项目

这是一个以 Qwen3-VL 系列模型作为决策层的多任务医学视觉 Agent。它把分类、检测和交互式分割封装成工具，让模型根据任务指令、当前视觉状态和工具反馈决定下一步动作、是否复用中间结果以及何时停止。

### Q2：为什么这算 Agent，而不是普通多模型串联？

固定流水线会预先写死顺序，例如 `detect → segment → classify`。当前系统由 VLM 生成工具调用，Agent loop 执行工具，再把文本、检测 overlay 或 mask overlay 回灌给模型。模型可以根据反馈继续修正、跳过不需要的工具或结束任务，因此核心是“感知—决策—执行—反馈”闭环。

## 2. 架构与工具

### Q3：三个后端服务分别做什么？

- `segmentation_api.py`：封装 IMISNet/MedSAM2，支持 bbox、点提示和会话式交互分割；
- `detection_api.py`：封装 Grounding DINO，接收目标描述并返回候选框；
- `classification_api.py`：封装 BioMedCLIP，支持全图或指定 ROI 的文本引导分类。

当前默认端口为：分割 `8265`、检测 `8266`、分类 `8267`。

### Q4：当前工具名和反馈形式是什么？

```text
classify          → 文本分类结果
detect            → 检测框、文本和 overlay
add_bbox         → 分割 mask、文本和 overlay
add_point        → 更新后的分割 mask、文本和 overlay
finish_instance  → 完成一个候选实例
stop_action      → 结束整张图像的 episode
```

`finish_instance` 是当前多实例工作树新增的工具。它只结束一个候选病灶；只有所有待处理实例完成后，才允许调用图像级 `stop_action`。

### Q5：单病灶和多病灶流程有什么区别？

单病灶任务可以表示为：

```text
classify → detect → add_bbox → add_point* → stop_action
```

多病灶任务会先从检测结果注册 `candidate_0`、`candidate_1` 等实例，随后对每个实例独立维护 `instance_id` 和分割状态：

```text
detect → candidate_i → add_bbox → add_point* → finish_instance
                                      ↓
                         全部实例完成后 stop_action
```

这部分代码已经进入当前工作树，但应在完整回归和合并后再作为稳定版本能力对外承诺。

### Q6：为什么拆成三个 API？

分类、检测和分割的依赖、显存需求和故障模式不同。独立服务有三个好处：模型可以单独替换和升级，资源可以独立分配，单个服务故障时 Agent 能收到错误反馈并决定重试、换工具或结束当前路径。

## 3. 数据工程

### Q7：项目支持哪些数据？

工程预处理链路兼容 BUSI、Kvasir-SEG、COVID-19、TN3K、AbdomenCT 和 AbdomenMR。当前多病灶 SFT/RL/评估主要使用 BUSI、Kvasir-SEG 和 TN3K；其余数据集属于工程支持或后续扩展范围，不能直接说已经完成同等规模的 RL 对比实验。

### Q8：CT/MR 如何接入当前流程？

工程上支持把 3D NIfTI 转成代表性 2D 切片，再生成器官 mask、bbox 和 parquet 字段，从而复用现有 2D VLM 和工具接口。当前主实验仍以 BUSI、Kvasir-SEG 和 TN3K 为主，不能把 2D 切片流程表述成原生 3D Agent 已完成。

### Q9：SFT 和 RL 为什么使用不同数据格式？

SFT 更关注图像、多轮对话和工具调用格式，使用 ShareGPT 风格数据更直接；RL 更依赖统一字段、批量采样和多数据集合并，因此使用 parquet。两条链路共享任务语义和标注来源，但数据组织方式不同。

## 4. Agent loop 与训练

### Q10：多任务 Agent loop 如何工作？

模型先生成工具调用；Agent loop 校验并执行；工具结果根据类型转换为文本或视觉状态；模型再基于更新后的状态生成下一步调用，直到调用 `stop_action` 或达到 episode 限制。

### Q11：什么是工具实例持久化复用？

一个 episode 内，Agent 为工具维护持久化实例 ID，不会每轮重新初始化。交互式分割会持续复用同一 session，结束时统一释放资源。多实例场景还会为不同候选病灶维护独立 `instance_id`。

### Q12：SFT 和 RL 分别解决什么问题？

SFT 主要让模型学会工具 schema、参数格式、多轮反馈结构和基本调用先验；RL/GRPO 用于优化工具选择、结果复用、错误恢复、交互成本和停止时机。当前仓库已经具备数据、Agent loop、奖励和训练入口，但完整稳定 GRPO 收敛仍在验证。

### Q13：为什么用 GRPO？

GRPO 可以对同一输入采样多条轨迹，根据组内相对奖励优化策略，不需要额外训练 value/critic 网络，适合多轮工具调用和可验证规则奖励场景。它是当前训练方案，不等于已经完成最终性能证明。

## 5. CPR v2

### Q14：奖励函数怎么设计？

当前实现的是规则版 CPR v2，不是独立训练的 Clinical Judge。复合任务主要包含：终局任务质量、事件级状态增益、筛查—检测—分割—ROI 分类的信息流协同、任务条件化策略、格式约束、动作成本和规则式安全惩罚。奖励最终裁剪到 `[-1, 1]`。

### Q15：CPR v2 如何衡量过程？

分割动作记录 `mask_before` 和 `mask_after`，用 IoU/Dice 综合质量的变化衡量事件增益；检测框到 `add_bbox` 的复用用框 IoU 衡量；分割到 ROI 分类的复用用 ROI 对最终 mask 的覆盖率衡量。工具失败、重复调用和无效细化会产生成本或负向反馈。

### Q16：Clinical Judge 是否已经实现？

没有。Clinical Judge、推理文本合理性、logit entropy 置信度和医生一致性评价都是后续方向。当前 CPR v2 使用结构化工具事件、GT 和视觉状态变化，不能说已经使用学习式临床判官。
