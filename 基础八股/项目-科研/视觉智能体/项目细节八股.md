> 更新时间：2026-10-21  
> 事实基准：`D:\AIPro\MedSAM-Agent` 当前仓库与局部测试。  
> 统一原则：区分“已实现”“局部验证”“实验中”和“规划中”，不要把工程入口或设计目标写成最终实验结论。

## 1. 项目定位

### Q1：一句话介绍这个项目

这是一个以 Qwen3-VL 系列模型作为决策层的多任务医学视觉 Agent。它把分类、检测和交互式分割封装成工具，让模型根据任务指令、当前视觉状态和工具反馈决定下一步动作、是否复用中间结果以及何时停止。

### Q2：为什么这算 Agent，而不是普通多模型串联？

固定流水线会预先写死顺序，例如 `detect → segment → classify`。当前系统由 VLM 生成工具调用，Agent loop 执行工具，再把文本、检测 overlay 或 mask overlay 回灌给模型。模型可以根据反馈继续修正、跳过不需要的工具或结束任务，因此核心是“感知—决策—执行—反馈”闭环。

## 2. 架构与工具

### Q3：三个后端服务分别做什么？

- `segmentation_api.py`：封装 IMISNet/MedSAM2，支持 bbox、点提示和会话式交互分割；
- `detection_api.py`：封装 Grounding DINO，接收目标描述并返回候选框；
- `classification_api.py`：封装 BioMedCLIP，支持全图或指定 ROI 的文本引导分类。

当前默认端口为：分割 `8265`、检测 `8266`、分类 `8267`。

### Q4：当前工具名和反馈形式是什么？

```text
classify          → 文本分类结果
detect            → 检测框、文本和 overlay
add_bbox         → 分割 mask、文本和 overlay
add_point        → 更新后的分割 mask、文本和 overlay
finish_instance  → 完成一个候选实例
stop_action      → 结束整张图像的 episode
```

`finish_instance` 是当前多实例工作树新增的工具。它只结束一个候选病灶；只有所有待处理实例完成后，才允许调用图像级 `stop_action`。

### Q5：单病灶和多病灶流程有什么区别？

单病灶任务可以表示为：

```text
classify → detect → add_bbox → add_point* → stop_action
```

多病灶任务会先从检测结果注册 `candidate_0`、`candidate_1` 等实例，随后对每个实例独立维护 `instance_id` 和分割状态：

```text
detect → candidate_i → add_bbox → add_point* → finish_instance
                                      ↓
                         全部实例完成后 stop_action
```

这部分代码已经进入当前工作树，但应在完整回归和合并后再作为稳定版本能力对外承诺。

### Q6：为什么拆成三个 API？

分类、检测和分割的依赖、显存需求和故障模式不同。独立服务有三个好处：模型可以单独替换和升级，资源可以独立分配，单个服务故障时 Agent 能收到错误反馈并决定重试、换工具或结束当前路径。

## 3. 数据工程

### Q7：项目支持哪些数据？

工程预处理链路兼容 BUSI、Kvasir-SEG、COVID-19、TN3K、AbdomenCT 和 AbdomenMR。当前多病灶 SFT/RL/评估主要使用 BUSI、Kvasir-SEG 和 TN3K；其余数据集属于工程支持或后续扩展范围，不能直接说已经完成同等规模的 RL 对比实验。

### Q8：CT/MR 如何接入当前流程？

工程上支持把 3D NIfTI 转成代表性 2D 切片，再生成器官 mask、bbox 和 parquet 字段，从而复用现有 2D VLM 和工具接口。当前主实验仍以 BUSI、Kvasir-SEG 和 TN3K 为主，不能把 2D 切片流程表述成原生 3D Agent 已完成。

### Q9：SFT 和 RL 为什么使用不同数据格式？

SFT 更关注图像、多轮对话和工具调用格式，使用 ShareGPT 风格数据更直接；RL 更依赖统一字段、批量采样和多数据集合并，因此使用 parquet。两条链路共享任务语义和标注来源，但数据组织方式不同。

## 4. Agent loop 与训练

### Q10：多任务 Agent loop 如何工作？

模型先生成工具调用；Agent loop 校验并执行；工具结果根据类型转换为文本或视觉状态；模型再基于更新后的状态生成下一步调用，直到调用 `stop_action` 或达到 episode 限制。

### Q11：什么是工具实例持久化复用？

一个 episode 内，Agent 为工具维护持久化实例 ID，不会每轮重新初始化。交互式分割会持续复用同一 session，结束时统一释放资源。多实例场景还会为不同候选病灶维护独立 `instance_id`。

### Q12：SFT 和 RL 分别解决什么问题？

SFT 主要让模型学会工具 schema、参数格式、多轮反馈结构和基本调用先验；RL/GRPO 用于优化工具选择、结果复用、错误恢复、交互成本和停止时机。当前仓库已经具备数据、Agent loop、奖励和训练入口，但完整稳定 GRPO 收敛仍在验证。

### Q13：为什么用 GRPO？

GRPO 可以对同一输入采样多条轨迹，根据组内相对奖励优化策略，不需要额外训练 value/critic 网络，适合多轮工具调用和可验证规则奖励场景。它是当前训练方案，不等于已经完成最终性能证明。

## 5. CPR v2

### Q14：奖励函数怎么设计？

当前实现的是规则版 CPR v2，不是独立训练的 Clinical Judge。复合任务主要包含：终局任务质量、事件级状态增益、筛查—检测—分割—ROI 分类的信息流协同、任务条件化策略、格式约束、动作成本和规则式安全惩罚。奖励最终裁剪到 `[-1, 1]`。

### Q15：CPR v2 如何衡量过程？

分割动作记录 `mask_before` 和 `mask_after`，用 IoU/Dice 综合质量的变化衡量事件增益；检测框到 `add_bbox` 的复用用框 IoU 衡量；分割到 ROI 分类的复用用 ROI 对最终 mask 的覆盖率衡量。工具失败、重复调用和无效细化会产生成本或负向反馈。

### Q16：Clinical Judge 是否已经实现？

没有。Clinical Judge、推理文本合理性、logit entropy 置信度和医生一致性评价都是后续方向。当前 CPR v2 使用结构化工具事件、GT 和视觉状态变化，不能说已经使用学习式临床判官。

## 7. 创新点与代码实现（面试深挖版）

### Q20：怎样用一条主线讲清三个创新点？

**回答框架：问题 → 方法 → 训练 → 验证边界。** 原始 MedSAM-Agent 已经把框、点提示的交互式分割做成多步决策；本项目进一步处理分类、检测、分割和区域表征组成的复合任务。为此，先扩展统一多工具 Agent，再从已有分割标注自动生成多任务工具轨迹用于 SFT，最后用 CPR v2 衡量多轮动作的结果、过程和风险。这三点分别回答“如何决策”“如何获得训练轨迹”“如何优化决策”。

**归属边界：** 框/点交互分割、SFT 加多轮 RL 的基础范式来自上游 MedSAM-Agent；Grounding DINO、BioMedCLIP、IMISNet/MedSAM2 是已有视觉后端。我们的增量是任务条件化的工具编排、标注复用与多任务轨迹构建，以及规则版 CPR v2。不能把视觉后端本身或原始分割 Agent 说成独立原创。

### Q21：创新一“多工具 Agent”具体怎样运行？代码在哪？

上层 VLM 根据图像、自然语言任务与上一轮反馈生成 `<tool_call>`；`MultiTaskAgentLoop` 解析参数、执行工具、记录状态和事件，再把结果回灌给 VLM。`classify` 回文本，`detect` 回候选框及 overlay，`add_bbox` / `add_point` 回分割 mask overlay；`stop_action` 结束 episode。典型复合任务是“全图筛查 → 候选定位 → 用检测框初始化分割 → 点提示修正 → ROI 分类 → 停止”，但纯分类、纯检测和正常筛查样本不必走完这条链。

**对应代码：** `RL-verl/recipe/medsam_agent/multi_task_agent_loop.py` 中，`run()` 初始化 episode 状态并将 `pred_mask`、`detection_boxes`、`classification_result`、`tool_trace` 等写入 `extra_fields`；`_execute_single_tool_call()` 路由工具并复用实例；`_handle_processing_tools_state()` 生成不同反馈、记录每轮调用；`_cleanup()` 释放会话。三类后端分别在 `RL-verl/api_server/detection_api.py`、`classification_api.py`、`segmentation_api.py`。这些后端可以替换，训练重点在上层的工具选择、参数、信息复用与停止策略。

**追问“为什么是 Agent”：** 答“模型生成下一步工具调用，工具结果作为新状态返回，模型再决策”；不要只答“用了三个模型”。复合流程是监督轨迹中的策略先验，不代表推理代码把每个样本的动作硬编码成同一条固定流水线。

### Q22：创新二“标注复用与自动轨迹”具体怎样做？

从已有 mask 计算目标 bbox 与中心点，结合原有类别或器官标签，派生分类、检测、分割和复合任务样本。`data/prepare_sharegpt.py` 的 `build_classify()`、`build_detect()`、`build_segment()`、`build_composite()` 分别生成 `classify → stop`、`detect → stop`、`add_bbox → add_point → stop`、`全图 classify → detect → add_bbox → add_point → ROI classify → stop` 的 ShareGPT 对话。CT/MR 由 `data/extract_3d_slices.py` 做 3D NIfTI 到 2D 切片，再生成器官级 mask/bbox；RL 数据由 `data/prepare_all_datasets.py` 和 `data/combine_parquet.py` 整理为统一 parquet。

**准确口径：** 这是“从现有标注自动构造训练轨迹”，减少额外标注需求；当前 SFT 工具反馈主要由规则模板生成，代码中也有固定示例置信度，不能称为医生真实操作轨迹或完整在线工具回放。SFT 主要教会模型工具 schema、参数和基本顺序；策略优劣仍需后续 RL 和实验检验。

### Q23：创新三 CPR v2 相比只看最终 Dice/IoU 改了什么？

终局奖励只能说“最后结果好不好”，不能判断哪次调用真正改善了结果、检测框是否被分割利用、是否出现多余步骤或高风险漏诊。CPR v2 将 rollout 记录为 `tool_trace` 事件序列，每个事件含工具名、参数、成功状态、结果和局部奖励；分割事件还记录 `mask_before` 与 `mask_after`。`cpr_reward.py::compute_score()` 读取任务类型、GT、最终结果和轨迹，计算任务条件化总分：

```text
单任务 R = clip(0.70 Q_terminal + 0.20 Q_process
              + 0.05 Q_policy + 0.05 Q_format
              - C_action - P_safety, -1, 1)

复合任务 R = clip(0.60 Q_terminal + 0.20 Q_process
              + 0.10 Q_synergy + 0.05 Q_policy + 0.05 Q_format
              - C_action - P_safety, -1, 1)

复合任务 Q_terminal = 0.25 Q_detection
                      + 0.45 Q_segmentation
                      + 0.30 Q_classification
```

这组权重是当前代码中的规则配置，不是临床验证过的最优权重。**实现细节：** 事件先计算增益，再聚合成一条 rollout 的奖励交给 GRPO；目前不是对每个动作分别执行一次强化学习参数更新。

### Q24：过程增益与跨工具协同如何落到代码？

`compute_process_score()` 对分割动作计算 `gain_t = quality(mask_after_t) - quality(mask_before_t)`，其中 `quality = 0.5 × IoU + 0.5 × Dice`；检测、分类将各自质量映射到 `[-1, 1]`，工具失败给直接负反馈，`stop_action` 根据当前终局质量评价停止时机。事件分取平均形成 `Q_process`。

`compute_synergy_score()` 只对复合任务计算三类可测量的信息流：① 全图筛查发生在检测前时，使用其筛查质量；② 计算检测框与后续 `add_bbox` 参数的 IoU；③ 计算 ROI 分类区域对最终分割 mask 的覆盖率。当前代码对**实际存在的协同分量**取均值；缺失必要步骤另由策略项惩罚。这里的“协同”衡量结构化输出和调用参数的一致性，不能直接等同于证明模型在因果意义上利用了前一步信息。

### Q25：动作成本和临床安全项具体惩罚什么？

`compute_action_cost()` 计入非停止调用的基础成本，以及连续重复相同参数、当前任务无关的调用、失败调用、分割质量已高时的继续细化。`compute_policy_score()` / `compute_format_reward()` 根据 `task_type` 检查需要的工具、调用顺序和结束格式，避免纯分类任务因未检测或未分割而被错误扣分。

`compute_safety_penalty()` 采用规则式非对称惩罚：例如恶性判正常比良性判恶性扣分更高；有目标却漏检、分割质量过低，以及正常样本检出目标也会扣分。它是**启发式临床风险代理**，尚未经过医生一致性或真实临床效用验证；不能称为学习式 Clinical Judge。

### Q26：多病灶扩展的实现逻辑和当前边界是什么？

检测输出会在 `MultiInstanceState.register_detections()` 中注册为 `candidate_0`、`candidate_1` 等；`multi_task_agent_loop.py::_execute_segmentation_tool()` 按 `instance_id` 为每个候选维护独立分割 session，避免不同病灶的点和 mask 混在一起。每个候选通过 `finish_instance` 标记完成；存在 `pending_ids()` 时，图像级 `stop_action` 会被拒绝。`cpr_reward.py` 还包含实例 mask 匹配、漏实例与多余实例统计。

**当前边界：** 多实例代码和局部测试已在工作树中，但完整多实例 RL 尚未验证。现有 `cpr_reward.py` 的通用动作集合未包含 `finish_instance`，该动作可能被过程/策略/成本项当作未知或无关动作；正式训练前需要对齐奖励规则。面试时可以讲状态设计和已实现逻辑，不要声称多病灶 GRPO 已稳定提升。

### Q27：SFT → GRPO 的训练链路怎样解释？

SFT 阶段用 ShareGPT 风格工具轨迹和 LlamaFactory/LoRA 教模型“会按格式调用工具”。RL 阶段用统一 parquet 提供任务、图像与 GT；`run_multi_task.sh` 接入 `multi_task_dataset.py`、`multi_task_agent_loop.py` 和 `cpr_reward.py`，在 verl 中打开多轮 rollout 并设置 `algorithm.adv_estimator=grpo`。同一输入采样多条轨迹，比较组内奖励后优化策略，目标是让模型选更有价值的动作并及时停止。

**配置核对点：** 当前 `run_multi_task.sh` 设 `max_assistant_turns=5`，而标准复合 SFT 轨迹包含筛查、检测、框、点、ROI 分类、停止共 6 次工具调用；若实验要完整覆盖该轨迹，需要调整轮数配置或缩短策略。配置文件中的轮数与脚本覆盖值也不同，应以实际启动命令和日志为准。当前不声称完整 GRPO 已稳定收敛。

### Q28：如何用实验支撑“创新有效”？

先固定数据划分、checkpoint、随机种子、工具版本和评估脚本；在相同动作空间与训练预算下，对比 SFT、终局奖励 GRPO 和 CPR v2 GRPO。报告分类指标、检测质量、分割 Dice/IoU、平均有效交互和总工具调用数、正常样本假阳性、高风险漏诊，以及失败/重复调用比例。再分别去掉过程增益、信息流协同、动作成本和安全项做消融，并检查跨数据集表现。当前局部测试只证明奖励函数在构造样例上的行为符合预期，不能替代端到端性能结论。

### Q29：90 秒口述版

> 我们在 MedSAM-Agent 的交互式分割基础上，研究多工具医学视觉任务中的决策问题。原始方法主要让模型自主选择框和点完成分割；我们把全图分类、文本驱动检测、交互式分割和 ROI 分类接到统一 Agent loop，由视觉语言模型依据任务和工具反馈选择下一步并决定何时停止。第一个增量是任务条件化的多工具编排。第二个增量是复用现有分割标注，自动派生检测框、类别和交互提示，构造多任务 SFT 轨迹，降低训练数据构建成本。第三个也是算法重点，是规则版 CPR v2：它不只看最终 Dice 或分类结果，还根据分割前后质量变化评价单步增益，根据框 IoU 和 ROI 覆盖率评价跨工具信息复用，再扣除无效调用成本与高风险误判。现在系统、轨迹和奖励代码已实现并有局部测试；完整 GRPO 收敛、消融及最终性能提升仍需正式实验验证。

## 8. 全流程八股：数据来源、预处理、训练、推理、评估

> 本节以代码实际行为为准。回答时先说“现有入口做了什么”，再说“正式实验还需补什么”。项目研究对象是调度医学视觉工具的 VLM Agent；BioMedCLIP、Grounding DINO、IMISNet/MedSAM2 在当前方案中主要作为预训练后端，并非本项目重新训练的三个视觉模型。

### Q30：从原始数据到最终结果，完整链路是什么？

```text
原始图像/标注
  ├─ SFT：扫描图像与 mask → 派生类别、bbox、点 → ShareGPT 多轮工具轨迹
  │       → LlamaFactory 微调 VLM → 合并/加载策略模型
  └─ RL：统一样本元数据 → parquet；CT/MR 先由 NIfTI 转 2D
          → 转成 MultiTaskDataset 所需的图像 bytes/任务/GT schema
          → verl 多轮 Agent rollout → 工具反馈和 tool_trace → CPR v2 → GRPO

推理：图像 + 任务 → VLM 选工具 → 分类/检测/分割服务 → 结果回灌
      → 继续调用或停止 → 输出分类、候选框、mask、实例与轨迹

评估：固定 test split 与模型/工具版本 → 分任务质量 + 过程效率 + 安全错误
      → 与固定流水线、单工具和终局奖励基线比较
```

**关键事实：** 上述 RL schema 转换和统一离线评估是闭环中的必要环节；当前仓库有元数据 parquet 生成脚本、`MultiTaskDataset` 和奖励入口，但它们的数据字段尚未直接对齐，不能声称“把当前 combined parquet 路径传给训练脚本就能完整训练”。

### Q31：数据从哪里来？各数据集提供什么监督？

| 数据源 | 模态与目标 | 代码读取的标注/目录 | 可派生的任务 |
| --- | --- | --- | --- |
| BUSI | 乳腺超声，benign/malignant/normal | 类别文件夹中的图像及 `_mask*.png`，同图可有多个 mask | 分类；有 mask 时检测、分割及复合任务 |
| Kvasir-SEG | 内镜息肉 | `images/`、`masks/` 和 `kavsir_bboxes.json` | 息肉检测、分割、复合任务 |
| COVID-19 | 胸部 X-ray，COVID、肺部浑浊、正常、病毒性肺炎 | 类别目录中的图像及可选 mask | 分类；有对应 mask 时可做 mask 任务 |
| TN3K | 甲状腺超声结节 | 原始 `trainval-image/mask`、`test-image/mask`，或预导出 `manifest.jsonl` 子集 | 结节检测、分割、复合任务 |
| AbdomenCT / AbdomenMR | 腹部 CT/MR 多器官 | NIfTI 影像/标签体与 `dataset.json` 器官映射 | 切片后的器官分类、定位、分割 |

### Q32：原始图像如何统一成训练样本？

`prepare_all_datasets.py` 为 2D 样本整理 `image_path`、`mask_path`、`bbox`、`instances`、`label`、`modality`、`anatomy`、`sample_id` 等字段。非空 mask 先转灰度、以 `>127` 二值化，再取前景像素的 `xmin/ymin/xmax/ymax` 作为 bbox；空 mask 不生成有效目标框。BUSI 的多个 mask 分别进入 `instances[]`，同时把首个实例放到顶层 `mask_path/bbox`，兼容原有单目标链路。若类别正常或缺少有效标注，应按任务过滤，不能把无 GT 的样本直接计入分割质量。

**面试回答：** “我们先统一样本语义，再分别构造 SFT 对话和 RL 样本。`sample_id` 用于回溯来源，`instances[]` 保留同图多目标，顶层 mask/bbox 维持单目标兼容。”注意 parquet 当前主要记录文件路径，训练机必须能访问相同路径；它不自动包含图像字节。

### Q33：CT/MR 的 3D 数据怎样变成可用的 2D 样本？

`prepare_all_datasets.py::scan_abdomen_ct/mr()` 先匹配 NIfTI 影像体、标签体和 `dataset.json` 中的器官 ID。`extract_3d_slices.py` 再读取体数据，选择标签前景像素较多的切片（默认每体最多 5 张），跳过空切片，按器官 ID 为同一切片生成独立的 PNG mask、bbox 和样本记录。CT 使用腹部窗宽 400、窗位 40 映射到 0–255；MR 使用单切片 1%–99% 分位数截断并映射到 0–255。

完整切片模式是**先在体数据级切 train/val/test，再在各 split 内切片**，同一体的切片因此保持在同一集合。`--parquet-only` 重建模式按 2D 图像路径分组再划分，可避免同一切片不同器官跨集合，但不能仅凭这个分组保证同一原始体的不同切片不跨集合。切片轴由形状最小维度启发式推断，并非通用医学影像方向标准；正式实验应核对方向、spacing、体 ID 和切片选择偏倚。该路径是 2D 适配，不能说成原生 3D 建模。

### Q34：数据怎样切分？如何防止泄漏？

通用扫描器 `split_samples()` 用 seed 42 对样本随机打散，再按 70%/15%/15% 分为 train/val/test；这不是严格的分层或病人级切分。原始 TN3K 路径还会合并已有 trainval/test 后重新切分。新增 TN3K 子集通过 `prepare_tn3k_subset.py` 按 case 整体划分；Group Breast 原始视频帧按视频/病例组划分，子集布局直接读取固定 manifest；CT/MR 完整切片模式按体数据划分。

**必须说明的风险：** `prepare_sharegpt.py::scan_abdomen_2d()` 读取切片 parquet 时只读取找到的第一个 split，再统一重切；若改用扫描 PNG 的回退路径，逐器官样本也可能被独立切分。因此正式评估应统一保存不可变的患者/病例/体数据 ID 与 split manifest，并检查同一来源是否跨集合。SFT 的 `--merge-splits` 会合并 train/val/test 训练，若随后仍用这些样本作测试，就会发生评估泄漏；正式对比实验应关闭该选项并保持与 RL 相同的隔离测试集。

### Q35：为什么 SFT 和 RL 用两套数据形式？

SFT 学的是多轮对话及 `<tool_call>` 序列，因此 `prepare_sharegpt.py` 直接从图片和标注生成 ShareGPT JSON：每条包含 `conversations`、`images`、`system`，只在首轮用户消息放 `<image>` 占位符。默认分别输出训练、验证、测试 JSON，并有 `max_per_task`、`per_modality` 等采样参数；实际任务分布以生成日志和 JSON 统计为准。RL 需要按样本取任务类型、图像、GT 和工具环境，parquet 更便于混合采样及批量读取。`combine_parquet.py --include ...` 用白名单合并指定数据集，避免把历史目录中的旧 parquet 混入。

**需要讲清的接口差异：** 当前 `prepare_all_datasets.py` 记录的是 `image_path/mask_path/...`；`multi_task_dataset.py` 却读取 `images=[{"bytes": ...}]`、`extra_info.task_type/target_description/...`、`reward_model.ground_truth/gt_bbox/gt_label`。若没有这些字段，它会退回默认分割任务、默认目标描述，图像缺失时甚至创建空白图。正式 GRPO 前必须增加并验证转换步骤，检查图像 bytes、GT、任务类型、路径和 split，而非仅检查 parquet 文件存在。

### Q36：SFT 专家轨迹如何生成？它教会模型什么？

`prepare_sharegpt.py` 的四类构造函数分别生成分类、检测、分割和复合轨迹：`classify→stop`、`detect→stop`、`add_bbox→add_point→stop`、`全图筛查→检测→框→点→ROI 分类→stop`。框从 GT mask 派生并映射到 `[0,999]` 工具坐标；正点取 mask 内像素位置。多实例样本还可额外生成逐候选 `add_bbox/add_point/finish_instance`、最后图像级停止的轨迹。

**作用与局限：** SFT 让 VLM 学会任务提示、工具名、JSON 参数、调用顺序及接收反馈的基本模式；它不证明模型已经学会最优策略。当前工具反馈中的部分文本与置信度由模板合成，生成轨迹也使用 GT 派生提示，不等于真实后端在线产生的医生操作序列。不能用训练轨迹中的 GT 提示作为公平推理输入。

### Q37：VLM 如何训练？三个视觉后端需要一起反向传播吗？

当前设计固定或独立部署 Grounding DINO、BioMedCLIP、IMISNet/MedSAM2 权重，策略学习主要发生在 Qwen-VL 系列 VLM。SFT 在 LlamaFactory 中使用多模态 ShareGPT 格式；LoRA 配置通过 `data/sft_train.py --use-lora` 生成，模板为 `qwen3_vl_nothink`，示例 LoRA rank 8、target 为 all、cutoff 8192、bf16、每卡 batch 1、梯度累积 8、3 epoch。该脚本**不传 `--use-lora` 时生成的是 full fine-tuning 配置**，面试中不要把两种配置混为一谈。完成 SFT 后，可导出/合并适配器，再作为 RL 策略模型起点。

三个后端通过 API 提供观测和任务结果；GRPO 优化的是 VLM 的工具调用策略，不通过这些 HTTP 服务对后端权重端到端反传。具体模型大小、checkpoint、学习率和有效 batch 应以实际运行配置与日志为准，不能把模板默认值说成最终实验设置。

### Q38：GRPO 多轮训练时一条样本怎样流动？

`MultiTaskDataset.__getitem__()` 应读取图像、任务类型、目标描述和 GT，构造 system/user prompt、`tools_kwargs` 与 `extra_info`；VLM 在 `multi_task_agent_loop.py` 中生成动作，工具执行结果回灌，直至停止或达到轮数限制。Agent loop 将 `pred_mask`、`pred_instances`、`detection_boxes`、`classification_result`、`tool_trace` 和动作次数回传。`cpr_reward.py::compute_score()` 利用 GT 与这些字段计算一条 rollout 的奖励，verl 用同一 prompt 下多条轨迹的组内相对奖励估计优势并更新 VLM。

`run_multi_task.sh` 目前设置 `algorithm.adv_estimator=grpo`、多轮工具调用、`ROLLOUT_N` 默认 4、`TRAIN_BATCH` 默认 4，输入默认指向 `data/datasets/subset/*.parquet`。README 中的 combined parquet 是数据合并入口，实际训练脚本默认读取 subset，须以启动参数为准。脚本把 `max_assistant_turns` 设为 5，而标准复合 SFT 轨迹需要 6 次工具调用；正式复合训练前需核对轮数与停止动作是否能被执行。当前还缺少可复核的完整稳定收敛日志和 CPR 相对基线的最终增益证据。

### Q39：CPR v2 在训练中如何使用 GT？推理时还需要 GT 吗？

GT 只用于训练奖励和离线评估。奖励计算读取真实类别、真实 bbox/mask，评价分类、检测、分割终局质量，分割前后质量变化，跨工具输出的一致性，以及漏诊/假阳性等风险。它把事件级得分汇总为 rollout 分数交给 GRPO。真实推理时 Agent 只能看到图像、用户任务和工具反馈；不能用 GT 算 IoU 决定是否停止。停止是 VLM 基于可观测反馈学习到的策略，而非在线访问真实标签。

### Q40：多工具推理的输入、状态与输出是什么？

输入为医学图像和任务描述，例如“判断是否有异常并分割可疑病灶”。策略层解析任务并输出 `classify`、`detect`、`add_bbox`、`add_point`、`finish_instance` 或 `stop_action`。Agent loop 在一个 episode 内保存原图、检测结果、分类结果、mask 历史和 `tool_trace`；分类反馈是文本，检测和分割还回传 overlay 图。检测框在工具层由像素转换为 `[0,999]`，分割框/点再由工具层转回图像坐标；ROI 分类的 `region` 同样从 `[0,999]` 映射回像素坐标。`instance_id` 为多个候选维护各自 session，完成所有候选后才允许图像级停止；最后释放会话资源。

最终可得到类别/置信度、检测框、分割 mask、实例状态和调用轨迹；具体哪些输出存在取决于用户任务及实际动作。推理时对失败工具调用应记录失败并给模型可处理的错误反馈；当前分割无 mask 返回时部分路径可能直接结束，不能笼统声称所有失败都会自动重试恢复。

### Q41：三个工具各自做了什么预处理与输出？

`DetectTool` 把目标文本作为 caption 传给 Grounding DINO 服务，后端输出像素框和得分，工具返回归一化框及 overlay；阈值可由参数给出，默认工具阈值为 0.25。BioMedCLIP 服务接收全图或 ROI，并要求调用方提供至少两条候选 `text_prompts`，返回标签、置信度与候选类别分数；零样本分类效果受候选集和文本表述影响。`AddBboxTool` / `AddPointTool` 把归一化框或点映射到原图像素，调用 IMISNet/MedSAM2 的 session API，返回更新 mask，支持多轮累积提示。

**当前接口缺口：** `RL-verl/verl/tools/classification_tool.py::execute()` 目前只向 `/classify` 或 `/classify/region` 发送图像与可选 bbox，没有发送 API 必填的 `text_prompts`；分类 API 因此会拒绝该请求。正式使用多工具 Agent 前，需要让任务侧给出候选描述与标签，并由工具层传到 API，再做端到端验证。现阶段不能宣称 Agent 内的分类调用已稳定运行。

推理讨论中要分清三个坐标/图像层：VLM 输入可能被缩放，工具服务持有原图，提示与奖励必须统一坐标语义。不能把正常的 `[0,999]` 工具坐标直接当成像素框，也不能把分类分数当作已校准的临床概率。

### Q42：`infer/run_single_inference.py` 与多工具 Agent 推理是什么关系？

`infer/run_single_inference.py` 是上游风格的**单图交互分割**入口：按图像和目标描述加载 grounding 模型与分割模型，循环生成框/点和 mask，并保存推理记录。它不走当前的 BioMedCLIP＋Grounding DINO＋CPR v2 多任务 Agent loop，也不能用它的单图输出证明复合任务已经完成端到端评估。多任务训练/rollout 的入口在 `RL-verl/recipe/medsam_agent/`；若要做正式离线推理，需要用同一套 Agent loop、工具配置和停止规则实现批量 test 执行器。

### Q43：现在已经实现了哪些评估？哪些还只是目标指标？

| 层次 | 仓库已有的实现 | 不能据此宣称的内容 |
| --- | --- | --- |
| SFT 首轮格式检查 | `data/eval_sft.py` 在 test 样本上检查 `classify/detect/add_bbox` 首轮工具名、JSON 解析和分割框坐标范围，输出逐样本 JSON | 它不执行完整多轮工具链，也不计算真正的分类准确率、检测 mAP 或分割 Dice |
| 旧分割推理评估 | `infer/unibiomed_inference_toolusing.py` 可在有 GT 时记录逐轮及最终 IoU/Dice，并保存推理记录 | 不代表多任务 Agent 的分类、检测、ROI 与安全指标 |
| 奖励局部测试 | `test_cpr_reward_v2.py` 等验证奖励排序、坐标一致性、信息复用和风险惩罚 | 不能替代真实测试集上的收敛、消融和显著性结果 |
| 正式多任务评估 | 方案在 `PLAN_MULTIAGENT.md` 中列出 | 当前尚需统一批量推理与指标汇总脚本、固定实验记录 |

因此“评估已完成”的准确说法是：**格式检查、旧分割指标计算和奖励局部测试有代码；完整多任务端到端评估尚待实现与运行。**

### Q44：正式测试集应该报告哪些指标？怎么计算？

分类报告混淆矩阵、Accuracy、每类 Precision/Recall/F1；异常筛查尤其关注敏感度、特异度及“异常判正常”率。检测在固定匹配规则、IoU 阈值和置信度阈值下统计 recall、precision、mAP@0.5，也可报告框 IoU；多目标须一对一匹配并记录漏检和多余框。分割报告逐病例 Dice、IoU，必要时 HD95；HD95 需确定像素 spacing、空 mask 和边界异常时的处理规则。多实例报告每图实例召回、误检及匹配后的实例 Dice/IoU。策略报告成功完成率、平均总工具调用数、有效分割交互数、重复/失败调用率和停止时机；安全性报告恶性→正常、目标漏检、正常样本假阳性等分项。

这些是**正式实验应计算的指标**，并非都已由当前 `eval_sft.py` 实现。CPR 奖励里的质量分和安全惩罚用于训练，不宜直接替代独立测试集的原始指标。报告均值时还应给每数据集、每模态、每类别样本数及置信区间，避免数据量大的类别掩盖少数高风险病例。

### Q45：怎样设计对比和消融，才能证明创新点？

固定相同数据划分、VLM 初始 checkpoint、视觉后端、可用动作集合、最大轮数、算力预算及测试脚本，比较：① 单后端模型/固定流程；② SFT Agent；③ SFT＋只用终局质量的 GRPO；④ SFT＋CPR v2 的 GRPO。这样可以分别看工具调度与过程奖励的贡献。CPR 消融依次去掉事件增益、跨工具协同、动作成本、安全项，并观察任务质量、调用数和高风险错误是否变化。再做跨数据集/模态测试与多实例子集分析。

**面试答法：** “我不会只报一项总分；我要同时验证质量、效率和安全，并确保对比组使用相同动作空间。当前仓库已有奖励与数据入口，但上述完整对照、消融和统计还需正式实验支持。”

### Q46：复现实验前必须核对的五个接口问题是什么？

1. **RL schema：** 路径型 parquet 与 `MultiTaskDataset` 要求的图像 bytes、`extra_info`、`reward_model` 未直接对齐；无图像时存在空白图回退，必须以 schema 校验阻止静默训练。
2. **分类 API：** `/classify` 必须接收至少两个 `text_prompts`，当前 `ClassifyTool` 未传该字段，Agent 分类调用需要先对齐任务候选集和 HTTP 参数。
3. **split 一致性：** SFT、RL、CT/MR 切片和子集 manifest 要共享不可变的病例级测试划分；`--merge-splits` 或二次随机切分不能进入正式评估。
4. **动作与轮数：** 多实例 `finish_instance` 已进入 Agent loop 和工具配置，但 CPR v2 通用动作集合尚未把它作为正常动作完整处理；最大 rollout 轮数也要覆盖全部实例和停止。
5. **评估入口：** `eval_sft.py` 只做首轮格式检查；必须增加完整多轮批量推理与逐病例指标，再保存模型、数据、后端和代码版本。

这些是从代码核对出的当前边界，也是面试中体现工程判断的地方。回答时可说“我发现并正在对齐这些接口”，不要说“全流程已稳定验证”。

### Q47：两分钟完整口述版

> 这个项目的目标是让视觉语言模型自主调度医学影像分类、检测和交互式分割工具。数据层我们接入 BUSI、TN3K、Kvasir、COVID-19 以及腹部 CT/MR 等来源，统一记录图像、类别、mask、框和实例信息。对于 CT/MR，先在体数据级划分，再把 NIfTI 转成 2D 切片；CT 做窗宽窗位映射，MR 做分位数归一化，再按器官生成 mask 和框。训练分两步：SFT 使用从标注自动生成的 ShareGPT 工具轨迹，让 VLM 学会调用格式与基本顺序；随后计划在 verl 中用多轮 GRPO 和 CPR v2 优化实际工具选择、信息复用与停止。推理设计是 VLM 看到图像和任务，选择分类、检测或框点分割，工具结果回灌后继续决策，直到停止；GT 只用于训练奖励和离线评估，不会出现在推理输入中。评估要同时看分类、检测、分割质量，工具调用效率与高风险错误，并和固定流程、SFT 及终局奖励 GRPO 比较。目前多工具代码、数据生成、奖励和局部测试已具备；RL 数据 schema、分类工具与 API 参数、完整多轮评估和稳定增益仍需做正式闭环验证。
