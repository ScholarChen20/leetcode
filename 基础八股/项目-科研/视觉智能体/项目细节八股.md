# 多任务医学视觉 Agent — 工程实现与面试问答（当前进度版）

> 更新时间：2026-10-21  
> 事实基准：`D:\AIPro\MedSAM-Agent` 当前仓库与局部测试。  
> 统一原则：区分“已实现”“局部验证”“实验中”和“规划中”，不要把工程入口或设计目标写成最终实验结论。

## 1. 项目定位

### Q1：一句话介绍这个项目

这是一个以 Qwen3-VL 系列模型作为决策层的多任务医学视觉 Agent。它把分类、检测和交互式分割封装成工具，让模型根据任务指令、当前视觉状态和工具反馈决定下一步动作、是否复用中间结果以及何时停止。

### Q2：为什么这算 Agent，而不是普通多模型串联？

固定流水线会预先写死顺序，例如 `detect → segment → classify`。当前系统由 VLM 生成工具调用，Agent loop 执行工具，再把文本、检测 overlay 或 mask overlay 回灌给模型。模型可以根据反馈继续修正、跳过不需要的工具或结束任务，因此核心是“感知—决策—执行—反馈”闭环。

## 2. 架构与工具

### Q3：三个后端服务分别做什么？

- `segmentation_api.py`：封装 IMISNet/MedSAM2，支持 bbox、点提示和会话式交互分割；
- `detection_api.py`：封装 Grounding DINO，接收目标描述并返回候选框；
- `classification_api.py`：封装 BioMedCLIP，支持全图或指定 ROI 的文本引导分类。

当前默认端口为：分割 `8265`、检测 `8266`、分类 `8267`。

### Q4：当前工具名和反馈形式是什么？

```text
classify          → 文本分类结果
detect            → 检测框、文本和 overlay
add_bbox         → 分割 mask、文本和 overlay
add_point        → 更新后的分割 mask、文本和 overlay
finish_instance  → 完成一个候选实例
stop_action      → 结束整张图像的 episode
```

`finish_instance` 是当前多实例工作树新增的工具。它只结束一个候选病灶；只有所有待处理实例完成后，才允许调用图像级 `stop_action`。

### Q5：单病灶和多病灶流程有什么区别？

单病灶任务可以表示为：

```text
classify → detect → add_bbox → add_point* → stop_action
```

多病灶任务会先从检测结果注册 `candidate_0`、`candidate_1` 等实例，随后对每个实例独立维护 `instance_id` 和分割状态：

```text
detect → candidate_i → add_bbox → add_point* → finish_instance
                                      ↓
                         全部实例完成后 stop_action
```

这部分代码已经进入当前工作树，但应在完整回归和合并后再作为稳定版本能力对外承诺。

### Q6：为什么拆成三个 API？

分类、检测和分割的依赖、显存需求和故障模式不同。独立服务有三个好处：模型可以单独替换和升级，资源可以独立分配，单个服务故障时 Agent 能收到错误反馈并决定重试、换工具或结束当前路径。

## 3. 数据工程

### Q7：项目支持哪些数据？

工程预处理链路兼容 BUSI、Kvasir-SEG、COVID-19、TN3K、AbdomenCT 和 AbdomenMR。当前多病灶 SFT/RL/评估主要使用 BUSI、Kvasir-SEG 和 TN3K；其余数据集属于工程支持或后续扩展范围，不能直接说已经完成同等规模的 RL 对比实验。

### Q8：CT/MR 如何接入当前流程？

工程上支持把 3D NIfTI 转成代表性 2D 切片，再生成器官 mask、bbox 和 parquet 字段，从而复用现有 2D VLM 和工具接口。当前主实验仍以 BUSI、Kvasir-SEG 和 TN3K 为主，不能把 2D 切片流程表述成原生 3D Agent 已完成。

### Q9：SFT 和 RL 为什么使用不同数据格式？

SFT 更关注图像、多轮对话和工具调用格式，使用 ShareGPT 风格数据更直接；RL 更依赖统一字段、批量采样和多数据集合并，因此使用 parquet。两条链路共享任务语义和标注来源，但数据组织方式不同。

## 4. Agent loop 与训练

### Q10：多任务 Agent loop 如何工作？

模型先生成工具调用；Agent loop 校验并执行；工具结果根据类型转换为文本或视觉状态；模型再基于更新后的状态生成下一步调用，直到调用 `stop_action` 或达到 episode 限制。

### Q11：什么是工具实例持久化复用？

一个 episode 内，Agent 为工具维护持久化实例 ID，不会每轮重新初始化。交互式分割会持续复用同一 session，结束时统一释放资源。多实例场景还会为不同候选病灶维护独立 `instance_id`。

### Q12：SFT 和 RL 分别解决什么问题？

SFT 主要让模型学会工具 schema、参数格式、多轮反馈结构和基本调用先验；RL/GRPO 用于优化工具选择、结果复用、错误恢复、交互成本和停止时机。当前仓库已经具备数据、Agent loop、奖励和训练入口，但完整稳定 GRPO 收敛仍在验证。

### Q13：为什么用 GRPO？

GRPO 可以对同一输入采样多条轨迹，根据组内相对奖励优化策略，不需要额外训练 value/critic 网络，适合多轮工具调用和可验证规则奖励场景。它是当前训练方案，不等于已经完成最终性能证明。

## 5. CPR v2

### Q14：奖励函数怎么设计？

当前实现的是规则版 CPR v2，不是独立训练的 Clinical Judge。复合任务主要包含：终局任务质量、事件级状态增益、筛查—检测—分割—ROI 分类的信息流协同、任务条件化策略、格式约束、动作成本和规则式安全惩罚。奖励最终裁剪到 `[-1, 1]`。

### Q15：CPR v2 如何衡量过程？

分割动作记录 `mask_before` 和 `mask_after`，用 IoU/Dice 综合质量的变化衡量事件增益；检测框到 `add_bbox` 的复用用框 IoU 衡量；分割到 ROI 分类的复用用 ROI 对最终 mask 的覆盖率衡量。工具失败、重复调用和无效细化会产生成本或负向反馈。

### Q16：Clinical Judge 是否已经实现？

没有。Clinical Judge、推理文本合理性、logit entropy 置信度和医生一致性评价都是后续方向。当前 CPR v2 使用结构化工具事件、GT 和视觉状态变化，不能说已经使用学习式临床判官。

## 7. 创新点与代码实现（面试深挖版）

### Q20：怎样用一条主线讲清三个创新点？

**回答框架：问题 → 方法 → 训练 → 验证边界。** 原始 MedSAM-Agent 已经把框、点提示的交互式分割做成多步决策；本项目进一步处理分类、检测、分割和区域表征组成的复合任务。为此，先扩展统一多工具 Agent，再从已有分割标注自动生成多任务工具轨迹用于 SFT，最后用 CPR v2 衡量多轮动作的结果、过程和风险。这三点分别回答“如何决策”“如何获得训练轨迹”“如何优化决策”。

**归属边界：** 框/点交互分割、SFT 加多轮 RL 的基础范式来自上游 MedSAM-Agent；Grounding DINO、BioMedCLIP、IMISNet/MedSAM2 是已有视觉后端。我们的增量是任务条件化的工具编排、标注复用与多任务轨迹构建，以及规则版 CPR v2。不能把视觉后端本身或原始分割 Agent 说成独立原创。

### Q21：创新一“多工具 Agent”具体怎样运行？代码在哪？

上层 VLM 根据图像、自然语言任务与上一轮反馈生成 `<tool_call>`；`MultiTaskAgentLoop` 解析参数、执行工具、记录状态和事件，再把结果回灌给 VLM。`classify` 回文本，`detect` 回候选框及 overlay，`add_bbox` / `add_point` 回分割 mask overlay；`stop_action` 结束 episode。典型复合任务是“全图筛查 → 候选定位 → 用检测框初始化分割 → 点提示修正 → ROI 分类 → 停止”，但纯分类、纯检测和正常筛查样本不必走完这条链。

**对应代码：** `RL-verl/recipe/medsam_agent/multi_task_agent_loop.py` 中，`run()` 初始化 episode 状态并将 `pred_mask`、`detection_boxes`、`classification_result`、`tool_trace` 等写入 `extra_fields`；`_execute_single_tool_call()` 路由工具并复用实例；`_handle_processing_tools_state()` 生成不同反馈、记录每轮调用；`_cleanup()` 释放会话。三类后端分别在 `RL-verl/api_server/detection_api.py`、`classification_api.py`、`segmentation_api.py`。这些后端可以替换，训练重点在上层的工具选择、参数、信息复用与停止策略。

**追问“为什么是 Agent”：** 答“模型生成下一步工具调用，工具结果作为新状态返回，模型再决策”；不要只答“用了三个模型”。复合流程是监督轨迹中的策略先验，不代表推理代码把每个样本的动作硬编码成同一条固定流水线。

### Q22：创新二“标注复用与自动轨迹”具体怎样做？

从已有 mask 计算目标 bbox 与中心点，结合原有类别或器官标签，派生分类、检测、分割和复合任务样本。`data/prepare_sharegpt.py` 的 `build_classify()`、`build_detect()`、`build_segment()`、`build_composite()` 分别生成 `classify → stop`、`detect → stop`、`add_bbox → add_point → stop`、`全图 classify → detect → add_bbox → add_point → ROI classify → stop` 的 ShareGPT 对话。CT/MR 由 `data/extract_3d_slices.py` 做 3D NIfTI 到 2D 切片，再生成器官级 mask/bbox；RL 数据由 `data/prepare_all_datasets.py` 和 `data/combine_parquet.py` 整理为统一 parquet。

**准确口径：** 这是“从现有标注自动构造训练轨迹”，减少额外标注需求；当前 SFT 工具反馈主要由规则模板生成，代码中也有固定示例置信度，不能称为医生真实操作轨迹或完整在线工具回放。SFT 主要教会模型工具 schema、参数和基本顺序；策略优劣仍需后续 RL 和实验检验。

### Q23：创新三 CPR v2 相比只看最终 Dice/IoU 改了什么？

终局奖励只能说“最后结果好不好”，不能判断哪次调用真正改善了结果、检测框是否被分割利用、是否出现多余步骤或高风险漏诊。CPR v2 将 rollout 记录为 `tool_trace` 事件序列，每个事件含工具名、参数、成功状态、结果和局部奖励；分割事件还记录 `mask_before` 与 `mask_after`。`cpr_reward.py::compute_score()` 读取任务类型、GT、最终结果和轨迹，计算任务条件化总分：

```text
单任务 R = clip(0.70 Q_terminal + 0.20 Q_process
              + 0.05 Q_policy + 0.05 Q_format
              - C_action - P_safety, -1, 1)

复合任务 R = clip(0.60 Q_terminal + 0.20 Q_process
              + 0.10 Q_synergy + 0.05 Q_policy + 0.05 Q_format
              - C_action - P_safety, -1, 1)

复合任务 Q_terminal = 0.25 Q_detection
                      + 0.45 Q_segmentation
                      + 0.30 Q_classification
```

这组权重是当前代码中的规则配置，不是临床验证过的最优权重。**实现细节：** 事件先计算增益，再聚合成一条 rollout 的奖励交给 GRPO；目前不是对每个动作分别执行一次强化学习参数更新。

### Q24：过程增益与跨工具协同如何落到代码？

`compute_process_score()` 对分割动作计算 `gain_t = quality(mask_after_t) - quality(mask_before_t)`，其中 `quality = 0.5 × IoU + 0.5 × Dice`；检测、分类将各自质量映射到 `[-1, 1]`，工具失败给直接负反馈，`stop_action` 根据当前终局质量评价停止时机。事件分取平均形成 `Q_process`。

`compute_synergy_score()` 只对复合任务计算三类可测量的信息流：① 全图筛查发生在检测前时，使用其筛查质量；② 计算检测框与后续 `add_bbox` 参数的 IoU；③ 计算 ROI 分类区域对最终分割 mask 的覆盖率。当前代码对**实际存在的协同分量**取均值；缺失必要步骤另由策略项惩罚。这里的“协同”衡量结构化输出和调用参数的一致性，不能直接等同于证明模型在因果意义上利用了前一步信息。

### Q25：动作成本和临床安全项具体惩罚什么？

`compute_action_cost()` 计入非停止调用的基础成本，以及连续重复相同参数、当前任务无关的调用、失败调用、分割质量已高时的继续细化。`compute_policy_score()` / `compute_format_reward()` 根据 `task_type` 检查需要的工具、调用顺序和结束格式，避免纯分类任务因未检测或未分割而被错误扣分。

`compute_safety_penalty()` 采用规则式非对称惩罚：例如恶性判正常比良性判恶性扣分更高；有目标却漏检、分割质量过低，以及正常样本检出目标也会扣分。它是**启发式临床风险代理**，尚未经过医生一致性或真实临床效用验证；不能称为学习式 Clinical Judge。

### Q26：多病灶扩展的实现逻辑和当前边界是什么？

检测输出会在 `MultiInstanceState.register_detections()` 中注册为 `candidate_0`、`candidate_1` 等；`multi_task_agent_loop.py::_execute_segmentation_tool()` 按 `instance_id` 为每个候选维护独立分割 session，避免不同病灶的点和 mask 混在一起。每个候选通过 `finish_instance` 标记完成；存在 `pending_ids()` 时，图像级 `stop_action` 会被拒绝。`cpr_reward.py` 还包含实例 mask 匹配、漏实例与多余实例统计。

**当前边界：** 多实例代码和局部测试已在工作树中，但完整多实例 RL 尚未验证。现有 `cpr_reward.py` 的通用动作集合未包含 `finish_instance`，该动作可能被过程/策略/成本项当作未知或无关动作；正式训练前需要对齐奖励规则。面试时可以讲状态设计和已实现逻辑，不要声称多病灶 GRPO 已稳定提升。

### Q27：SFT → GRPO 的训练链路怎样解释？

SFT 阶段用 ShareGPT 风格工具轨迹和 LlamaFactory/LoRA 教模型“会按格式调用工具”。RL 阶段用统一 parquet 提供任务、图像与 GT；`run_multi_task.sh` 接入 `multi_task_dataset.py`、`multi_task_agent_loop.py` 和 `cpr_reward.py`，在 verl 中打开多轮 rollout 并设置 `algorithm.adv_estimator=grpo`。同一输入采样多条轨迹，比较组内奖励后优化策略，目标是让模型选更有价值的动作并及时停止。

**配置核对点：** 当前 `run_multi_task.sh` 设 `max_assistant_turns=5`，而标准复合 SFT 轨迹包含筛查、检测、框、点、ROI 分类、停止共 6 次工具调用；若实验要完整覆盖该轨迹，需要调整轮数配置或缩短策略。配置文件中的轮数与脚本覆盖值也不同，应以实际启动命令和日志为准。当前不声称完整 GRPO 已稳定收敛。

### Q28：如何用实验支撑“创新有效”？

先固定数据划分、checkpoint、随机种子、工具版本和评估脚本；在相同动作空间与训练预算下，对比 SFT、终局奖励 GRPO 和 CPR v2 GRPO。报告分类指标、检测质量、分割 Dice/IoU、平均有效交互和总工具调用数、正常样本假阳性、高风险漏诊，以及失败/重复调用比例。再分别去掉过程增益、信息流协同、动作成本和安全项做消融，并检查跨数据集表现。当前局部测试只证明奖励函数在构造样例上的行为符合预期，不能替代端到端性能结论。

### Q29：90 秒口述版

> 我们在 MedSAM-Agent 的交互式分割基础上，研究多工具医学视觉任务中的决策问题。原始方法主要让模型自主选择框和点完成分割；我们把全图分类、文本驱动检测、交互式分割和 ROI 分类接到统一 Agent loop，由视觉语言模型依据任务和工具反馈选择下一步并决定何时停止。第一个增量是任务条件化的多工具编排。第二个增量是复用现有分割标注，自动派生检测框、类别和交互提示，构造多任务 SFT 轨迹，降低训练数据构建成本。第三个也是算法重点，是规则版 CPR v2：它不只看最终 Dice 或分类结果，还根据分割前后质量变化评价单步增益，根据框 IoU 和 ROI 覆盖率评价跨工具信息复用，再扣除无效调用成本与高风险误判。现在系统、轨迹和奖励代码已实现并有局部测试；完整 GRPO 收敛、消融及最终性能提升仍需正式实验验证。
