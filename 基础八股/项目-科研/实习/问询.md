## 1. 智能问询平台：代码核实与面试问答

本章以 `telephone-customer-service` 当前源码为准。三个容易混淆的边界先记住：

1. 知识检索的当前主实现为 ES `DisMax` 融合关键词和向量评分，**不是 RRF**。若简历中保留 RRF，需另有可展示的实验或版本证据。
2. Badcase 是“自动采集和归因 + 人工审核修复 + 回测”的闭环，不是完全自动修复上线。
3. `/api/ai/speechToTicket` 生成待确认的 AI 草稿；坐席确认后进入工单列表的草稿态，不能等同于直接提交正式工单。

### 1.1 语音转工单接口：代码逻辑与技术实现

#### 1. 接口定位与请求契约

`AIController` 暴露 `POST /api/ai/speechToTicket`，接收 JSON 格式的 `SpeechToTicketDTO`，返回 `ResponseInfo<AITicketSummaryResultDTO>`。它是**同步接口**：本次请求等待录音获取、ASR、LLM 抽取和后处理结束后，直接返回 `sessionId`、`qaCount`、`qaList`、`fromCache=false`。这里没有提供直接接收 `MultipartFile` 的上传接口，也没有像在线会话 `POST /api/ai/ticketSummary` 那样返回异步任务 ID 供轮询。

| 请求字段 | 当前行为 |
| --- | --- |
| `sessionId` | 可按该 ID 从 `ServiceRecord` 找电话录音；若没有上传音频，则必需。 |
| `audioBase64` | 直接上传音频 Base64。若它和 `sessionId` 同时有值，**音频内容以 `audioBase64` 为准**，但后续仍使用传入的 `sessionId`。 |
| `audioFormat` | 直接上传时默认 `wav`；按会话获取录音时先按 `mp3` 处理。配置 `voiceTranscribeProperties.asrVoiceFormat` 非空时会覆盖这两者。 |

Controller 只校验 `sessionId` 和 `audioBase64` 不能同时为空。只传 Base64 时，Service 生成 `speech_` 加短 UUID 作为会话 ID。该模式可返回 QA，但如果没有关联的 `ServiceRecord`，可能无法推导渠道语料库；后续确认单条工单还要求 `callRecordId`。因此“可转写并生成草稿”和“可在现有电话服务记录下确认工单”需要分开验证。

```text
POST /api/ai/speechToTicket
  ├─ JSON: {"sessionId":"已有通话会话ID"}
  └─ JSON: {"audioBase64":"...","audioFormat":"wav"}
                  ↓ 同步执行
             返回 QA 列表与待确认草稿
                  ↓ 坐席核对
POST /api/ticketInfo/confirmAiTicket
或 POST /api/ticketInfo/confirmAllAiTickets
                  ↓
             常规工单列表中的草稿态
```

#### 2. 获取录音：ServiceRecord → COS → AICC

`AIServiceImpl.speechToTicket` 首先选定音频来源。直接上传时使用请求体内的 Base64；否则根据 `sessionId` 查询 `ServiceRecord` 和其中的 `ServiceRecordInfo`。有 `recordFileId` 时先通过 COS 文件地址下载；下载失败、状态异常或内容为空时，尝试 AICC 录音接口。AICC 回退需要服务记录里有 `recordId` 和 `recordLocationId`；仍拿不到字节时返回“未找到录音文件”。成功读取的字节被 Base64 编码后送到 ASR。

这层的工程意义是复用既有录音存储，避免要求坐席重新上传。面试追问时应讲清“COS 优先、AICC 回退”的触发条件，以及两者都失败时不会继续调用 LLM。

#### 3. ASR 适配：输入校验、协议兼容和文本兜底

`callAsrTranscribe` 先使用 `llm.asr-endpoint`，未配置时回退 `llm.asr-speaker-endpoint`。调用前去掉 Data URI 前缀并校验 Base64，构造的请求体为：

```json
{"voice_format":"mp3","voice_b64":["<音频Base64>"]}
```

`voice_b64` 是**数组**，字段名是 `voice_format`。代码通过 `RestTemplate.postForEntity` 同步请求 ASR，检查空响应和 `success=false`。返回文本优先取 `data.voice_text`，其次取顶层 `text`；两者为空时，才把 `data.speaker_segments` 或顶层 `segments` 按 `[speaker] text` 拼起来。文本仍为空则视为转写失败。

**容易讲错的细节：**如果 ASR 同时返回了 `voice_text` 和带说话人标签的分段，本接口优先使用全文，**不会把分段的说话人标签稳定地传给 QA 抽取**。这和标注表中已出现说话人混淆的风险直接相关。`asr-speaker-endpoint` 是地址回退，不等于下游一定采用说话人分离结果。

#### 4. LLM 抽取 QA：无工具调用，结果由后端解析

`buildSpeechToTicketMessages` 从提示词配置读取 `ai_ticket_summary` 系统提示词，并把会话 ID 与转写全文放入用户消息。提示词说明输入是电话录音转写、客服与用户交替发言且无角色标记，要求模型自行判断说话人。`TicketSummaryToolCallLoop` 复用了 `AbstractToolCallLoop` 骨架，但本场景的 `toolNames()` 返回空列表，**没有给模型开放检索工具或 Function Calling 工具**。代码中“构建工具定义”的注释不能当作功能实现。

模型输出经 `LlmJsonExtractUtil` 提取 JSON 数组，再用 Jackson 解析为 `AITicketSummaryItemDTO` 列表，字段包括提问人、标题、问题、原问题、回答、改写回答、话题批次和升级意图等。首次解析失败会尝试修复未转义引号后再解析；解析仍失败时返回空列表。因此现有实现是“提示词约定 JSON + 后端解析修复”，不宜称作严格 JSON Schema 强约束。`qaList == null` 会返回失败，但**空列表可继续走到成功响应**，这也是面试可主动提到的边界。

#### 5. 后处理：原文清洗、语料匹配、预检与拆合

电话录音没有在线会话的消息编号，`resolveAnswersByRef` 因而把模型摘录的 `answer` 保存为 `answerRaw`，做最小清洗后作为回答。相比之下，在线会话可按模型给出的消息编号从原始消息中回填坐席答复，并排除用户消息引用；两条链路在回答可信度上的差异需要说明。

后续处理顺序是：

1. 由 `ServiceRecord` 的渠道推导语料库编码；推导不到时跳过语料检索，不做全库兜底，避免跨库误挂。
2. 以清洗后的**客服回答**批量检索该语料库的候选语料。检索分低于配置阈值时不采纳；默认 `knowledgeMinScore=0`，实际粗筛强度要看配置。
3. 用 `knowledgeCode + libraryCode` 回查 MongoDB 语料分类，防止不同库同码造成错配。
4. 用一次 LLM 预检比较回答和候选语料是否一致。预检未通过时，默认 `knowledgeKeepOnUngrounded=true`：保留候选编码与分类，但置 `knowledgeConfirmed=false` 供坐席确认；配置为 false 时才清空。预检调用失败或输出无法解析时，当前代码沿用检索结果。
5. 根据客服回答补充升级意图；未命中语料时可采用模型改写的回答；然后由 `TicketSummarySplitMerger` 依据话题批次、延伸关系、分类和问题相似度决定合单或拆单。

检索、预检与拆合是**后台后处理**，不能说成 LLM 在抽取时自行调用了知识库。尤其是录音链路里的客服回答本身来自模型摘录，若说话人识别错，后端检索也可能建立在错误回答上。

#### 6. 草稿持久化与坐席确认

每条最终 QA 生成 `draftId`，写入 `libraryCode`。`saveAiTicketDrafts` 尝试在 MySQL `ai_ticket` 表逐条插入 `PENDING` 记录，记录 AI 原始产出用于追溯；同时 Redis `AI_TICKET_DRAFT + sessionId` 缓存 QA 列表供前端展示。坐席可以修改后调用单条或批量确认接口，确认逻辑填充员工、坐席、渠道等服务记录字段，将工单标记为草稿态和 `ticketSourceCode=AI`，并用 `aiTicketId` 关联 AI 草稿。确认时通过 Redis 锁与 `RMap` 中的工单 ID 避免重复确认。

**一致性边界：**录音接口的 `ai_ticket` 插入失败会记录日志并继续；Redis 草稿写入失败也只记警告，接口仍可能返回成功。录音接口本身没有在线会话总结那套 `RUNNING` 状态抢占与会话分布式锁，重复请求可再次执行 ASR/LLM 并产生新 `draftId`。这属于当前实现的可改进点，面试时可以作为“如果重新设计，我会如何补齐幂等与状态一致性”来回答，不应说成已有保证。

#### 7. 故障与质量风险清单

| 环节 | 当前处理 | 面试中可提出的改进 |
| --- | --- | --- |
| 录音不存在 | 返回失败；COS 失败尝试 AICC。 | 记录来源与错误码，支持可观测的补偿任务。 |
| Base64 非法或 ASR 空结果 | 调用前校验，响应为空时报错。 | 限制音频体积、格式和时长；长录音异步处理。 |
| 说话人错位、多人重叠 | 主要依赖 LLM 从无角色全文判断。 | 传入分段时间戳及角色置信度；重叠片段标记待核验。 |
| 漏句或专有名词错误 | 当前无字段级音频证据对齐。 | 对姓名、邮箱、日期、处理动作回听并做结构校验。 |
| LLM 输出非法 JSON | 提取 JSON 数组，有限修复；仍失败则空列表。 | 增加字段 Schema、必填校验和空结果原因码。 |
| 草稿持久化部分失败 | MySQL 插入与 Redis 缓存异常可被吞掉。 | 定义主存储和结果状态，以事务或补偿保证前端看到的草稿可追溯。 |
| 同一录音重复提交 | 当前录音接口缺少按会话的任务抢占。 | 用 `sessionId + 音频摘要` 建幂等键，并维护运行与终态。 |

#### 标注结论与样本概况

这批样本的转写**可用性较好**：55 条会话中，54 条状态为“成功”，1 条因检测出超过 2 位说话人而失败。多数会话已生成摘要、角色化对话明细和关键问答对，适合给坐席提供工单草稿参考。

主要风险集中在**说话人归属和业务关键信息**，而不只是普通字词错误。标注中可见说话人串位、两人同段讲话、短句遗漏，以及英文名、英文术语、邮箱和人名的误识别。这类错误会继续传导到 QA 抽取：把用户的话写成坐席答复、漏掉处理承诺，或将错误的专有名词写入工单。生成结果因此应经过坐席核对。

##### 四类问题与工单影响

还有一个**跨层错误**值得在面试中主动指出：标注不仅修订了 ASR 文本，也修订了会话摘要和关键问答对。例如某些问答对把员工陈述写成坐席回答。评估时应拆成三层：①转写文本是否正确；②说话人与话轮是否正确；③工单字段是否正确。否则容易把下游 LLM 的归因错误全部算到 ASR 上。

##### 建议的下一轮评估口径

1. **抽样方法：**按业务领域、录音时长、是否重试、说话人数、是否中英混说分层抽样，保留随机样本和困难样本两组。
2. **人工真值：**对抽样音频逐段标注文字、起止时间、说话人及重叠区域；双人复核有争议的片段。
3. **分层指标：**转写用 CER/WER；说话人用 DER 或话轮归属准确率；重叠讲话单独计算召回；工单用标题、问题、回复、处理动作、联系方式等字段准确率及人工修改率。
4. **业务权重：**姓名、邮箱、日期、金额、承诺动作和说话人归属单列“关键错误率”，避免大量正确寒暄掩盖少量高影响错误。
5. **效率指标：**记录草稿生成耗时、坐席确认耗时、每单编辑次数，以及与纯手工建单的同口径对照。简历中的“建单效率提升 50%”应能追溯到这一口径。

#### 面试问答：语音转工单与 AI 工单

##### Q1. 请你完整介绍电话录音生成工单的后台流程。

**答：**我按“取录音 → ASR 转写 → LLM 抽取 QA → 后端匹配语料并拆合话题 → 生成待确认草稿 → 坐席确认”介绍主线。可传音频 Base64，也可按会话从 COS 获取录音、失败时回退 AICC。面试中重点讲清两个边界：当前接口同步等待结果；模型生成草稿后仍需坐席核对，确认后才进入常规工单草稿流程。各步骤的字段和失败分支见 1.1。

##### Q2. ASR 接口的请求和返回如何适配？

**答：**我把 ASR 适配分成输入校验、协议映射和响应兜底三层：先验证音频编码，按服务要求提交 `voice_format` 与数组形式的 `voice_b64`；取不到正文时再尝试分段文本，两者都没有就判失败。排障时分别看音频格式、请求字段和下游状态，避免把协议错误当成识别效果问题。具体取值顺序见 1.1。

##### Q3. 你们如何处理说话人识别错误？

**答：**现有录音建单链路把转写全文交给 LLM，由提示词要求它判断双方角色；标注显示该做法在说话人串位、单一说话人标签混入双方语句时存在风险。我的处理原则是将说话人归属作为独立质量门槛：保留 ASR 分段和时间戳，用客服开场自报、提问与答复行为做一致性校验；无法可靠判定时不自动写入确定性的客服答复，由坐席核对。面试中应明确区分**当前实现**和这套**改进方案**。

##### Q4. 两个人同时讲话时，为什么比普通错字更难处理？

**答：**重叠讲话会同时影响语音识别和说话人聚类：一个分段可能包含两人的词，强制给一个 `SPEAKER` 标签会把双方语义混在一起。下游 LLM 即使拿到看似流畅的文本，也可能错误归因。可先检测重叠时间区间，保留 `overlap/unknown` 标记，再对片段单独处理；对影响工单结论的重叠片段安排人工复核。不要把“模型已分成两个说话人”误当作重叠问题已解决。

##### Q5. 漏字和漏句会怎样影响工单？如何检测？

**答：**漏掉普通语气词影响有限，漏掉日期、金额、否定词、处理动作和“我会再反馈”之类承诺会改变工单含义。检查时应将抽取字段与带时间戳的原始转写证据对齐：每个关键字段能追溯到哪段音频；没有证据的字段不让 LLM 补写，而是标成待确认。评估时另算关键字段遗漏率，不只看整体 CER/WER。

##### Q6. 英文名、邮箱和业务缩写为什么容易错？怎么优化？

**答：**电话音质、拼读方式和中英切换会让通用 ASR 把英文音节映射成中文或相近英文。业务侧可以维护招聘、HR 系统等领域热词，但邮箱和英文名不能单靠词表猜测；对邮箱做结构校验，对账号和人名保留逐字拼读证据，并在坐席确认页展示待核实字段。对标注集做中英混说的独立评估，避免总体准确率掩盖专有名词问题。

##### Q7. 表里 54/55 成功，能说 ASR 准确率达到 98.2% 吗？

**答：**不能。98.2% 是转写链路返回“成功”的比例，并未比较音频与人工标准文本。两条成功记录甚至只识别出一个说话人标签，却包含双方话轮。要说文字准确率，应建立人工真值后计算 CER/WER；要说角色质量，应计算 DER 或话轮归属准确率；要说业务效果，还要看工单字段准确率和人工修改成本。

##### Q8. 当前录音转工单与在线会话总结有什么技术差异？

**答：**关键差异是回答能否回到原始证据：在线会话有角色和消息编号，可以按编号回填客服原文；电话录音当前只把无角色标记的转写全文交给模型，回答沿用模型摘录，更依赖 ASR 和角色判断质量。因此录音草稿需要重点核对说话人和关键答复。录音接口同步返回，在线总结采用异步任务与轮询。

##### Q9. LLM 输出非法 JSON 或抽错字段怎么办？

**答：**先区分格式错误和内容错误。现有代码对 JSON 做提取、解析和有限修复；修复失败返回空 QA 列表，而空列表仍可能走到成功响应，这是要补齐的结果校验。即使解析成功，说话人和业务字段仍可能错，应结合原文证据、语料预检和坐席确认核查，不能把“合法 JSON”当成“内容正确”。

##### Q10. 为什么不让 LLM 直接给工单挂语料编码？

**答：**LLM 擅长抽取和概括，但直接猜语料编码容易出现“看起来相关、实际并非客服引用”的错误。当前实现使用客服回答字段批量检索语料（录音链路中的回答来自模型摘录），限定到会话渠道对应的语料库，再结合检索分和回答与语料的一致性预检决定是否采纳或标记待确认。语料库编码与语料编码要一起使用，因为不同库可能有同码语料。

##### Q11. 一段对话出现多个问题，怎么决定生成几张草稿？

**答：**LLM 提取话题批次、提问引用和是否为前一问题的延伸；后端完成语料与业务分类回填后，再按首问批、延伸关系及分类进行拆合。比如先问年假又追问年假余额，多半合并；后来转到社保，应拆成另一条。最终仍由坐席确认，避免把多诉求压成一单或拆得过细。

##### Q12. 为什么在线会话总结采用异步任务？如何防重复？

**答：**LLM 调用及后处理耗时不稳定，同步等待会拉长接口时间。提交时先检查已有结果缓存，再使用 Redis `trySet` 原子抢占运行态；多个实例收到同一会话请求时，未抢到的一方返回在途任务状态。终态重建使用 CAS，执行阶段还按会话加锁；线程池拒绝时回滚运行态。前端按会话轮询结果。这里要分别解释“接口提交幂等”和“后台执行互斥”。

##### Q13. AI 草稿与正式工单的边界是什么？

**答：**模型生成成功只表示已有待确认 QA 和 AI 草稿；坐席确认后才补齐服务记录信息，进入常规工单列表的草稿态。对外表述应分开“生成待确认草稿”“坐席确认”“正式提交或流转”三个阶段。确认接口有锁和工单 ID 的重复确认保护，但录音生成接口本身没有同等的会话级任务抢占。

##### Q14. “建单效率提升 50%”该如何证明？

**答：**先固定口径，例如同类型电话会话中，从通话结束到坐席完成工单草稿的中位耗时；对比纯手工与 AI 辅助两组，并统计坐席修改时间、生成失败率和字段正确率。若原来中位数 4 分钟、现在 2 分钟，可说耗时下降 50%；若用“效率提升 50%”则要说明效率定义。当前标注表没有手工建单对照数据，不能单独证明这一数字。

#### Badcase 流入决策：NeoHorse-Jev-4B 实现核实

**定位与链路。**NeoHorse-Jev-4B 用于判断智能体对话是否自动流入 Badcase，以及命中哪些采集来源；它不是记录创建后的 AI 根因归因模型。定时同步任务每小时拉取对话，也可手动触发；每条新对话先写入 `agent_bot_log_info`，再执行 `checkAndCollectBadcase → detectBadcaseSources → BadcaseJevInflowDecider.decide`。重复 `msg_id` 在插入失败后直接跳过。只有命中来源且 `staffId > 0` 才调用 `BadcaseCollectService.collect`，创建 `pending_confirm` 记录并写采集流水；随后通过事务提交后事件异步归因。

**请求与路由。**主链路先排除空白、纯标点、系统占位符等结构性无意义问题；点踩 `feedback_type=2` 先记作候选来源 `THUMBS_DOWN`，仍受后续“非知识寻求”判断约束。调用方查出会话内是否有真实问询、是否曾要求转人工，并与当前 `query`、`answer` 一起放进 `state`。一次 `LlmGateway.decide("badcase_decision", request)` 把三个 `noul` 问题放入 `questions` 映射，请求 `POST /v1/systemone`；模型返回各命题为真的概率，不走聊天接口的 `messages` 协议。网关按 `ai_model_channel_config.scene_code` 取模型、地址和限流参数，注入 `model_name`，获取令牌后发请求。`badcase_decision` 与后续 `badcase_attribution` 是不同场景和限流组。

| 决策问题 | 概率与实际效力 |
| --- | --- |
| `has_knowledge_intent`：是否有明确、实质性的 HR 知识寻求诉求 | 概率 `< 0.35` 时整条跳过，已命中的点踩也不采集；阈值偏低，减少误排除。 |
| `is_fallback_answer`：AI 是否给出兜底话术、空答或任务异常提示 | 概率 `≥ 0.5` 时增加 `FALLBACK`；转人工触发消息不加，若用户在当前回答后 10 秒内快速追问则移除此来源。 |
| `is_transfer_human_intent`：用户是否因 AI 未解决问题而希望转人工 | 概率 `≥ 0.5` 时可增加 `TRANSFER_HUMAN`；另有会话强规则：存在真实问询，且当前问答发生在首次转人工诉求之前或同时，也增加此来源。 |

**失败兜底与时延。**JEV 抛异常、响应为空或缺少任一概率字段时，整组三项判定退回旧规则：`shouldSkipFromBadcase` 过滤无价值问题，正则/空答/任务异常判断兜底回复，会话布尔信号判断转人工。HTTP 层最多尝试 3 次，并把 529“模型忙”按过载处理。初始化 SQL 将该场景设为每 60 秒 2 次、取令牌最多等 60 秒、`request_timeout_ms=90000`；但当前 `LlmHttpExecutor` 没有使用这个超时字段，实际 HTTP 读超时来自共享 `llmRestTemplate` 的 `llm.timeout`（未配置时默认 500 秒）。因此不能把“90 秒”说成实际调用或整条同步的耗时上限。

**面试时应说明的边界。**`ai_model_channel_config` 本地缓存 60 秒；SQL 初始化脚本重复执行时不会更新已有行的 `model_name` 和 `base_url`，后台现值须查库确认。会话级转人工规则只看判定当时已经入库的消息；前面问答先处理、转人工诉求后入库时，前面问答不会自动重算。模型的概率和阈值是工程判据，不等于已验证的准确率；应按误排除、误采集、降级比例与人工确认结果做离线评测。

#### 面试问答：Badcase 治理

##### Q15. Badcase 如何自动采集？如何避免误采集？

**答：**新对话入库后先过滤结构性无意义问题，点踩记为确定性候选来源；再用 NeoHorse-Jev-4B 一次判断“是否知识寻求、AI 回复是否兜底、是否有转人工意图”。知识寻求概率低于 0.35 时整条不采集；另两项达到 0.5 才新增来源，并结合快速追问过滤及首次转人工时间的会话规则。模型失败时退回旧确定性规则。命中后创建待确认 Badcase，再异步归因，人工复核后进入修复流程。这里是同步运营对话时的自动识别，不是用户问答请求中的实时判定。

##### Q16. 为什么归因放在事务提交之后异步执行？

**答：**采集记录必须先提交，归因线程才能稳定读取该记录及上下文；LLM 与检索耗时也不应拖慢采集接口。代码通过事务提交后事件和独立线程池触发归因。失败时保留 Badcase，标记归因失败并记录错误，不把采集事务一起回滚。

##### Q17. 归因是不是直接把问题交给 LLM 分类？

**答：**不是。当前顺序包括历史相似案例复用、意图判断、原问题及标准问的多轮检索诊断、预判、规则归因、必要时 LLM 归因，以及后置校验。检索诊断比较带用户标签的结果和宽召回结果，用来区分“知识缺失”和“知识存在但被标签或渠道挡住”等情况。LLM 处理规则无法确定的复杂问题，输出仍要接受合法根因和关联语料校验。

##### Q18. Badcase 治理为什么还需要人工？闭环终点是什么？

**答：**AI 给出的是归因和修复建议，运营人员需要认领或分发、核对证据、修复语料并提交。状态从待确认进入修复，采纳后进入待回测；回测通过才完成，失败则退回修复。操作流水留存谁在何时作了什么处理。由于有人工审核和回测，简历应写“自动归因与人工审核结合的闭环”，而不是“全自动化修复上线”。

##### Q19. 两人同时认领、修改或回测同一个 Badcase，如何保证状态正确？

**答：**状态机定义允许的 `fromStatus + action → toStatus`；实际更新还携带原状态、处理人等条件，影响行数为零则说明状态已变化，返回刷新重试。状态变更与操作日志在事务内处理，既防止覆盖，也保留审计证据。

##### Q20. 如何证明治理周期从周级缩短到天级、归因效率提升 35%？

**答：**治理周期应统一从采集时间算到回测通过时间，报告中位数或分位数，并按业务领域及根因分组，排除尚未完成的记录或单列处理。归因效率可用单条人工归因耗时、单位时间处理量或自动归因被人工采纳比例，但必须事先选定口径。仅有系统代码不足以证明这些数字，面试时应准备上线前后数据、样本量和统计 SQL。

#### 面试问答：知识语料检索

##### Q21. 当前检索如何结合关键词和语义向量？

**答：**知识编码符合格式时走编码精确查询；普通问题先做关键词 `multi_match`，同时计算标题、正文和相似问向量相似度，向量侧做权重组合与分数量级调整，最终用 ES `DisMax` 融合评分。还会按语料库、上架状态、分类和用户标签过滤。关键词适合专有词和精确名称，向量帮助召回不同表述的同义问题。

##### Q22. 你简历写 RRF，但代码里是 DisMax，面试时怎么答？

**答：**要按实际负责的版本说明。当前仓库的主查询是 `DisMax`，`tieBreaker=0.3`，不是 RRF。RRF 是根据两路结果名次计算倒数排名分后合并，适合分数难统一时使用；如果没有独立的 RRF 实验、分支和效果数据，就把简历改为“关键词与向量混合检索及业务过滤优化”，不要将 DisMax 说成 RRF。

##### Q23. 库里明明有语料，用户为什么仍搜不到？

**答：**按层排查：语料是否已发布；会话渠道是否映射到正确语料库；员工的管理主体、工作地、员工类型等标签是否匹配；ES 索引是否同步；关键词、相似问和向量是否覆盖用户说法。Badcase 诊断会同时跑带标签查询和宽召回：宽召回有结果、精确查询没有结果时，应优先查过滤条件，而不是直接补一条重复语料。

##### Q24. 为什么检索命中第一名，也不能直接挂到 AI 工单？

**答：**第一名只表示它在当前候选中得分最高，不代表确实是坐席回答所用的语料。工单链路限定语料库后，先按检索分粗筛，再用回答与候选语料的一致性预检。预检未通过时可依配置保留候选编码并标记待人工确认，或清空语料。这里既要避免误挂，也要考虑坐席重新找语料的成本。

##### Q25. “检索准确率提升 25%”应如何定义和验证？

**答：**先说明是 Precision@1、Recall@K、人工判定的有效命中率，还是问答最终解决率；定义分母、测试集与人工标注规则，再在相同样本上比较改造前后。还要说明“相对提升 25%”还是“提升 25 个百分点”，并按同义问、专有词、标签过滤等场景拆分。不要用一次线上主观感受代替可复现评测。

## 3. 运维闭环（原备考提纲）

### Q29. 为什么用 FastGPT 工作流而不是让 LLM 自由发挥（ReAct）？

**参考回答框架：**

```text
场景：网络/磁盘故障的检测→诊断→修复→工单，链路固定
固定流程用 Workflow：
- 每个节点的输入输出可预期、可校验
- 节点失败可单独重试，不用整条重跑
- 合规性：修复动作必须按固定步骤走

ReAct 适用：目标不明确、需要动态决策的场景
```

### Q30. "闭环状态机"怎么设计的？节点失败怎么办？

**参考回答框架：**

```text
状态：检测 → 诊断 → 修复 → 工单，每阶段状态机驱动
状态集：PENDING/RUNNING/SUCCESS/FAILED/WAITING_CONFIRM

失败处理：
- 可重试节点：限次重试
- 不可自动恢复：状态挂起 + 人工介入
- 状态持久化：服务重启后从断点恢复，不整条重跑

效果：工单创建 3 分钟 → 15 秒【需核实：口径是人工建单时长 vs 全流程时长】
```

**追问预判：**
- 修复动作是自动执行还是人工确认？→ 涉及生产环境变更必须确认【需核实】
- 状态机是自研还是框架？→ 自研，因为需要和工单系统耦合

## 5. 通用 Agent 工程追问

### Q34. 如果 Agent 工具调用失败，你的健全运行体系是什么？

```text
1. 调用前：参数 Schema 校验 + 权限确认 + 超时上限
2. 调用中：区分错误类型——参数错（反馈给 LLM 修正）vs 网络抖动（限次重试）vs 持续故障（熔断降级）
3. 调用后：写操作结果未知时禁止自动重试，转人工对账
4. 全局：最大步数/重复调用检测/统一 traceId 日志
```

### Q35. Workflow 和 ReAct 怎么选？

```text
Workflow：链路固定、需要可预期性和合规性（你的深信服场景）
ReAct：任务开放、需要动态决策
工程上：主干 Workflow + 节点内嵌 LLM 小步决策，是常见折中
```

### Q36. 上下文过长怎么处理？

```text
1. 预算控制：Token 计数 + 超限截断策略
2. 历史压缩：旧轮次摘要化（LLM 摘要/结构化提取）
3. 记忆分层：短期（最近几轮原文）+ 长期（向量库/用户偏好 KV）
4. 效果验证：压缩后任务完成率、关键信息保留率
```

### Q37. 评测怎么做才可信？

```text
- 评测集来源：线上 badcase + 人工标注 + 历史抽样
- 分层指标：召回（Recall@K/MRR）→ 生成（准确率/相关性）→ 业务（建单时长/命中率）
- 可靠性：固定测试集版本、回归跑批、A/B 灰度
- 你简历里的每个提升数字，面试官都会问"在什么评测集上测的"【需核实全部口径】
```

### Q38. Skill 渐进式加载了解吗？

```text
Skill = 可复用的能力包（指令 + 工具 + 示例）
渐进式加载：不在系统提示词里塞全部 Skill，而是：
- 一级：Skill 清单（名称+一句话描述）供 LLM 选择
- 二级：选定后动态注入完整指令
好处：省 Token、减少指令混淆、可扩展
```

## 6. 大模型与智能体评测

### 先背这一句

> 大模型评测重点看“回答好不好”；智能体评测重点看“任务是否可靠完成”。后者除最终答案外，还必须评估规划轨迹、工具调用、成本时延、异常恢复和安全边界。

### Q39. 如何搭建一套大模型评测体系？

```text
先定义任务和验收标准，再构建评测集；离线评测用于快速迭代，线上 A/B 验证真实业务收益，最后通过 badcase 回流形成闭环。

典型分层：
1. 基础能力：指令遵循、格式正确、拒答安全
2. 业务答案：正确性、相关性、完整性、事实一致性
3. RAG 链路：召回、重排、生成分别评测
4. 线上业务：任务完成率、人工介入率、满意度、成本和延迟
```

### Q40. 大模型常用评测指标有哪些？

| 维度 | 常见指标 | 说明 |
|---|---|---|
| 正确性 | Accuracy、EM、F1、人工通过率 | 有标准答案的任务优先用确定性指标 |
| 相关性 | Relevance Score | 回答是否切中用户问题 |
| 完整性 | Completeness Score | 是否遗漏关键条件、步骤或限制 |
| 事实一致性 | Faithfulness / Groundedness | 回答是否能被给定上下文或证据支撑 |
| 幻觉 | Hallucination Rate | 无依据编造、事实错误的比例 |
| 指令遵循 | Format / Constraint Pass Rate | JSON、字段、长度、禁用项等是否符合要求 |
| 安全性 | Unsafe Output Rate、Attack Success Rate | 越权、泄露、提示注入等风险比例 |
| 性能成本 | P50/P95 延迟、Token、单任务成本 | 生产环境必须纳入选型 |

**回答要点：** 开放式生成不适合只看 BLEU、ROUGE；它们更适合文本与参考答案表面重合度高的场景。业务问答更应看正确性、事实一致性和人工/LLM Judge 评分。

### Q41. 评测集如何构建，怎样保证可信？

```text
来源分三类：
- 真实线上问题和 badcase：代表真实分布
- 领域专家/运营人工构造：覆盖关键业务规则
- 对抗和边界样本：歧义问题、长文本、注入攻击、工具故障等

保证可信：
1. 明确题目、参考答案、证据和评分标准
2. 训练集、调参集、测试集严格隔离，防止评测泄漏
3. 按场景分桶：高频、长尾、高风险、不同用户群体分别看
4. 固化版本和数据快照，每次变更跑同一套回归集
5. 关键样本双人标注或专家复核，记录标注一致性
```

### Q42. LLM-as-a-Judge 是什么？如何避免它不可靠？

```text
LLM-as-a-Judge 是让一个评审模型按预设 Rubric 对回答打分或做两两比较。

正确用法：
- 先定义清晰 Rubric，例如正确性/完整性/事实一致性各 1~5 分
- 给评审模型问题、上下文、标准答案和待评答案，不只给待评答案
- 优先做盲评和两两比较，并随机交换 A/B 顺序
- 抽样由人工专家复核，与人工结果计算一致性
- 对关键结论同时报告自动评测和人工评测

常见偏差：偏好更长答案、位置偏差、偏好同源模型、自信但错误的评分。因此 LLM Judge 不能替代人工，只能提高评测吞吐。
```

### Q43. RAG 应该怎样分层评测？

```text
不能只看最终答案，要拆成三层：

1. 召回层：Recall@K、MRR、nDCG
   看正确文档是否进入 TopK、排位是否靠前。
2. 重排层：Precision@K、nDCG
   看相关文档是否被排到前面。
3. 生成层：Answer Correctness、Faithfulness、Citation Correctness
   看答案是否正确、是否依据召回内容、引用是否准确。

如果最终答案差，先定位是“没召回”“排得靠后”还是“召回了但模型没用好”，再决定调整对应环节。这里是通用 RAG 评测方法，不能直接当作本项目已上线的 Reranker 或 Chunk 策略。
```

### Q44. 如何评估幻觉？

```text
先定义幻觉：回答中的关键事实无法被给定上下文、可信工具结果或标准答案支持。

方法：
1. 把回答拆成原子事实（claim）
2. 对每条事实判断“有证据支持 / 无证据支持 / 与证据矛盾”
3. 计算无支持或矛盾事实占比，即幻觉率

生产上还要区分：
- 有知识但没引用：证据使用问题
- 知识库没有但模型编造：应明确说“资料不足”
- 工具结果过期：数据时效性问题
```

### Q45. 智能体评测和普通大模型评测的核心区别？

| 维度 | 大模型评测 | 智能体评测 |
|---|---|---|
| 关注对象 | 单次输入到输出的质量 | 多步任务是否完成及执行过程 |
| 输入 | Prompt、上下文 | Prompt、状态、工具、环境反馈 |
| 关键指标 | 正确性、相关性、事实性 | 任务成功率、工具成功率、轨迹质量、恢复能力、安全性 |
| 难点 | 开放式答案主观 | 环境不稳定、工具有副作用、轨迹可多解 |
| 典型方法 | 金标答案、人工/LLM Judge | 沙箱回放、轨迹评分、端到端验收、故障注入 |

### Q46. Agent 的核心评测指标是什么？

| 层级 | 指标 | 说明 |
|---|---|---|
| 结果 | Task Success Rate | 是否达到预定义验收条件，而非“回答看起来合理” |
| 规划 | Plan Validity、Subgoal Completion | 计划是否可执行，各子任务是否完成 |
| 工具 | Tool Selection Accuracy、Argument Validity、Tool Success Rate | 工具选得对不对、参数是否合法、调用是否成功 |
| 效率 | 平均步骤数、重复调用率、Token、单任务成本、P95 延迟 | 同样成功前提下越短、越稳、越省越好 |
| 稳定性 | Retry Success Rate、Recovery Rate、Loop Rate | 工具失败后能否恢复，是否陷入循环 |
| 安全 | Permission Compliance、Unsafe Action Rate、Prompt Injection ASR | 是否越权、危险操作是否拦截、注入攻击是否得逞 |

**最关键的口径：**

```text
Task Success Rate = 通过验收的任务数 / 总任务数

验收条件必须事先写清，例如：
“成功创建工单”不等于 Agent 说“已创建”，而是工单系统中存在唯一且字段正确的工单记录。
```

### Q47. 为什么 Agent 不能只评最终答案？

```text
因为最终答案正确，过程也可能有风险：
- 调错工具后碰巧得到正确结果
- 重复调用导致成本过高
- 对写操作没有权限确认
- 先泄露敏感信息再完成任务

所以 Agent 至少同时评“结果正确性 + 轨迹合理性 + 安全边界 + 效率”。
```

### Q48. Agent 轨迹怎么评测？

```text
轨迹并不要求和参考轨迹完全一致，因为同一任务可能有多条正确路径。

评测方式：
1. 硬规则：工具白名单、参数 Schema、权限、最大步数、禁止危险动作
2. 过程检查点：关键子目标是否完成，例如“先查询订单再退款”
3. 结果验收：外部环境状态是否正确
4. LLM/人工 Judge：对开放式规划评估是否合理、是否存在明显冗余

原则：优先评“是否满足约束并完成目标”，不要机械要求与单一路径逐 token 一致。
```

### Q49. Agent 工具故障、环境波动如何评测？

```text
要做故障注入，而不是只测 Happy Path：
- 工具超时、5xx、限流
- 参数缺失或返回空结果
- 工具返回过期/冲突数据
- 用户中途补充或修改目标
- 写操作结果未知

关注：
1. 是否区分可重试和不可重试错误
2. 是否有限次数重试并避免死循环
3. 是否走备用工具、降级或转人工
4. 写操作不确定时是否先查状态，而不是盲目重试
```

### Q50. Agent 评测如何保证可复现？

```text
1. 固定模型版本、Prompt、工具版本、评测集和环境快照
2. 外部 API 用 Mock/Sandbox 或录制回放，避免线上数据变化干扰
3. 控制随机性：固定 temperature/seed；对随机任务多次运行，报告均值和方差
4. 每条任务保存 traceId、输入、工具调用轨迹、最终环境状态
5. 指标同时看总体和分桶，不只报一个平均分
```

### Q51. 多 Agent 如何评测？

```text
先看团队最终 Task Success Rate，再额外看协作成本：
- 任务分配是否正确
- Agent 间信息传递是否遗漏或冲突
- 是否发生重复工作
- 总 Token、总耗时是否比单 Agent 有收益
- 关键决策是否有统一的最终裁决者

多 Agent 不是 Agent 越多越好。如果任务本身简单，协作通信成本可能超过收益。
```

### Q52. 离线评测很好，为什么还要线上 A/B？

```text
离线集只能代表历史和构造场景，无法完整覆盖真实用户表达、流量分布和业务流程。

线上 A/B 主要验证：
- 用户任务完成率、满意度、转人工率
- 实际延迟和成本
- 新版本是否引入新的 badcase 或安全风险

上线方式：灰度 → 监控 → 抽检 → badcase 回流，不应只凭离线分数直接全量发布。
```

### Q53. 如果模型分数提升，但业务指标没提升，怎么排查？

```text
先检查三件事：
1. 离线指标和业务目标是否一致，例如通用问答分数不等于工单完成率
2. 评测集是否过于简单或与线上分布脱节
3. 是否优化了某一环但瓶颈在别处，例如召回提升但工具执行仍失败

然后按漏斗拆解：输入理解 → 检索 → 生成/规划 → 工具执行 → 最终业务状态。
```

### 高频易踩坑

```text
1. 只报“准确率提升”，不说明任务定义、样本规模、基线和置信区间
2. 只用 LLM Judge，不做人工校准
3. RAG 只看最终答案，不拆召回、重排、生成
4. Agent 只跑正常路径，不做工具超时/失败注入
5. 把“工具调用成功”当成“业务任务完成”
6. 测试集参与 Prompt 调优，导致评测泄漏
7. 只看平均值，不看高风险场景、长尾样本和 P95 延迟
```

### 面试万能回答模板

```text
我会先把业务目标转成可验收的任务定义，再用真实线上样本、人工构造样本和对抗样本建立分层评测集。

离线阶段会拆链路评测：RAG 看召回/重排/生成，Agent 看结果、工具、轨迹、效率和安全；开放式答案通过明确 Rubric 的 LLM Judge 加人工抽检评估。

上线前做固定回归集和故障注入，上线后通过灰度 A/B 观察任务完成率、人工介入率、成本和 badcase，并把 badcase 回流到下一轮优化。
```
