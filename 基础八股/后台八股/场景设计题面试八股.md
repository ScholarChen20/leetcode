```text
1. 澄清需求：先问清楚量级、延迟要求、一致性要求
```

## 二、防止短信注册爆刷

### 需求分析

```text
攻击场景：
- 用脚本批量调用注册接口，刷短信验证码
- 消耗短信费用
- 骚扰用户手机

防护目标：
- 限制同一手机号发送频率
- 限制同一 IP 发送频率
- 识别恶意刷接口
```

### 分层防护设计

```text
第一层：图形验证码
- 发送短信前必须先通过图形验证码（滑块/点选）
- 拦截脚本化攻击（机器人识别图形码成本高）

第二层：频率限制（Redis）
- 同一手机号：60 秒内只能发 1 次，1 天最多 5 次
- 同一 IP：1 小时最多 10 次
- 同一设备/用户：限制每日发送上限

第三层：IP 黑名单
- 超过阈值直接封 IP 一段时间
- 配合风控系统

第四层：业务校验
- 手机号格式校验
- 是否已注册（注册场景）
- 是否存在异常设备指纹
```

### Redis 限流实现

```text
方案 1：计数器 + 过期时间
SET sms:phone:138xxxx 1 EX 60 NX
存在则拒绝，实现 60 秒 1 次

方案 2：滑动窗口（Lua 脚本）
ZSet 记录时间戳，窗口内计数超限则拒绝
```

### 面试话术

```text
"短信防刷的核心是分层限流：
1. 图形验证码挡机器
2. Redis 计数器限制手机号/IP 频率
3. 风控识别异常行为封 IP
4. 短信平台侧做最后兜底（供应商也有防刷机制）"
```

## 三、秒杀系统设计

### 核心挑战

```text
1. 高并发：瞬间百万级请求
2. 超卖问题：库存扣减一致性
3. 恶意请求：脚本刷单
4. 流量冲击：击垮正常业务
```

### 架构设计

```text
用户 → CDN/静态化 → 网关限流 → 秒杀服务 → Redis 库存 → MQ → 订单服务 → DB
```

### 关键设计点

```text
1. 前端：秒杀按钮防重复点击、倒计时
2. 网关：限流、拦截非法请求
3. 库存预扣：Redis 预扣减，防止超卖
   - Lua 脚本原子扣减
   - stock < 0 直接失败
4. 异步下单：Redis 扣减成功后发 MQ，异步创建订单
5. 缓存预热：秒杀开始前把库存加载到 Redis
6. 服务降级：秒杀期间关闭非核心功能
```

### 防超卖方案

```text
方案 1：Redis Lua 原子扣减
if stock > 0 then decr stock

方案 2：DB 乐观锁
UPDATE stock SET count = count - 1
WHERE id = ? AND count > 0

方案 3：DB 悲观锁（性能差，不推荐）
```

### 面试话术

```text
"秒杀核心是削峰 + 防超卖：
- 削峰：网关限流 + 验证码 + 异步化
- 防超卖：Redis Lua 原子预扣 + 数据库兜底
- 高性能：库存放 Redis，订单异步落库"
```

## 四、短链系统设计

### 核心问题

```text
1. 长 URL → 短码生成
2. 短码唯一性
3. 访问短码 → 302 跳转长 URL
```

### 短码生成方案

```text
方案 1：哈希 + 冲突处理
- MD5/SHA 后取前 6-8 位
- 冲突时重新哈希或加盐

方案 2：数据库自增 ID 转 62 进制
- 自增 ID 保证唯一
- 10 进制 → 62 进制（0-9 a-z A-Z）
- 如 1000000000 → 15ftgG
```

### 架构设计

```text
生成短链：
用户 → 短链服务 → DB 存储（短码、长 URL、过期时间）

访问短链：
用户 → 短链服务 → 查缓存（Redis）→ 302 跳转
```

### 关键点

```text
- 缓存：热门短链放 Redis
- 发号器：自增 ID 用号段模式或雪花算法
- 存储：短码 → 长 URL 映射表
- 302 临时重定向，便于统计
```

## 五、排行榜设计

### 需求

```text
实时排行榜：按分数排序，支持查看 Top N、查询个人排名
```

### 方案：Redis ZSet

```text
加分：ZINCRBY rank:game 10 user:1
Top10：ZREVRANGE rank:game 0 9 WITHSCORES
个人排名：ZREVRANK rank:game user:1
分数：ZSCORE rank:game user:1
```

### 大数据量优化

```text
- 按小时/天分桶，先找桶再算排名
- 定期把冷数据归档
- 多级榜单：日榜、周榜、总榜
```

## 六、点赞系统设计

### 核心挑战

```text
高并发点赞、点赞数实时性、用户点赞状态记录
```

### 方案

```text
点赞：Redis Set 存储点赞用户
SADD like:article:1 user:10

取消点赞：
SREM like:article:1 user:10

点赞数：
SCARD like:article:1

是否点过赞：
SISMEMBER like:article:1 user:10

持久化：定时任务把 Set 同步到 DB
```

### 扩展问题

```text
Q: 数据量太大怎么办？
A: 分片存储，按文章 ID 哈希

Q: 是否需要实时同步 DB？
A: 点赞是弱一致场景，异步批量同步即可
```

## 七、限流器设计

### 需求

```text
接口 QPS 限制，超限拒绝或排队
```

### 四种算法

| 算法 | 原理 | 特点 |
|---|---|---|
| 计数器 | 固定窗口计数 | 边界突刺 |
| 滑动窗口 | 窗口滑动计数 | 更平滑 |
| 漏桶 | 固定速率流出 | 绝对平滑 |
| 令牌桶 | 固定速率放令牌，允许突发 | 最常用 |

### Redis 实现令牌桶/计数器

```text
简单计数器（固定窗口）：
INCR key + EXPIRE 或 Lua 原子执行
超过阈值直接拒绝

生产方案：
- 网关层：Sentinel、Nginx limit_req
- 应用层：Sentinel、Guava RateLimiter
```

```text
方案：
```

## 附：场景题高频追问

| 追问 | 答案要点 |
|---|---|
| 秒杀为什么不用 DB 直接扣 | DB 扛不住高并发，Redis 单机 10w QPS |
| Redis 扣减成功但订单失败怎么办 | 回补库存 + 对账补偿 |
| 短链过期怎么办 | 设置过期时间，定时清理 |
| 排行榜同分怎么排 | ZSet 分数相同按 member 字典序，业务可加时间戳排序 |
| 短信防刷的极端情况 | 多维度联合限流 + 风控机器学习识别 |
| 秒杀超卖的根本原因 | 并发读写无原子性，需原子操作或锁 |
