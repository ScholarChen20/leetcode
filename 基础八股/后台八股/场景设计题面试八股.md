## 一、答题框架

```text
1. 澄清需求：先问清楚量级、延迟要求、一致性要求
2. 整体架构：画出分层结构
3. 核心设计：数据模型 + 接口设计

5. 扩展性：水平扩展、瓶颈分析
```

## 二、防止短信注册爆刷

### 需求分析

```text
攻击场景：
- 用脚本批量调用注册接口，刷短信验证码
- 消耗短信费用
- 骚扰用户手机

防护目标：
- 限制同一手机号发送频率
- 限制同一 IP 发送频率
- 识别恶意刷接口
```

### 分层防护设计

```text
第一层：图形验证码
- 发送短信前必须先通过图形验证码（滑块/点选）
- 拦截脚本化攻击（机器人识别图形码成本高）

第二层：频率限制（Redis）
- 同一手机号：60 秒内只能发 1 次，1 天最多 5 次
- 同一 IP：1 小时最多 10 次
- 同一设备/用户：限制每日发送上限

第三层：IP 黑名单
- 超过阈值直接封 IP 一段时间
- 配合风控系统

第四层：业务校验
- 手机号格式校验
- 是否已注册（注册场景）
- 是否存在异常设备指纹
```

### Redis 限流实现

```text
方案 1：计数器 + 过期时间
SET sms:phone:138xxxx 1 EX 60 NX
存在则拒绝，实现 60 秒 1 次

方案 2：滑动窗口（Lua 脚本）
ZSet 记录时间戳，窗口内计数超限则拒绝
```

### 面试话术

```text
"短信防刷的核心是分层限流：
1. 图形验证码挡机器
2. Redis 计数器限制手机号/IP 频率
3. 风控识别异常行为封 IP
4. 短信平台侧做最后兜底（供应商也有防刷机制）"
```

## 三、秒杀系统设计

### 核心挑战

```text
1. 高并发：瞬间百万级请求
2. 超卖问题：库存扣减一致性
3. 恶意请求：脚本刷单
4. 流量冲击：击垮正常业务
```

### 架构设计

```text
用户 → CDN/静态化 → 网关限流 → 秒杀服务 → Redis 库存 → MQ → 订单服务 → DB
```

### 关键设计点

```text
1. 前端：秒杀按钮防重复点击、倒计时
2. 网关：限流、拦截非法请求
3. 库存预扣：Redis 预扣减，防止超卖
   - Lua 脚本原子扣减
   - stock < 0 直接失败
4. 异步下单：Redis 扣减成功后发 MQ，异步创建订单
5. 缓存预热：秒杀开始前把库存加载到 Redis
6. 服务降级：秒杀期间关闭非核心功能
```

### 防超卖方案

```text
方案 1：Redis Lua 原子扣减
if stock > 0 then decr stock

方案 2：DB 乐观锁
UPDATE stock SET count = count - 1
WHERE id = ? AND count > 0

方案 3：DB 悲观锁（性能差，不推荐）
```

### 面试话术

```text
"秒杀核心是削峰 + 防超卖：
- 削峰：网关限流 + 验证码 + 异步化
- 防超卖：Redis Lua 原子预扣 + 数据库兜底
- 高性能：库存放 Redis，订单异步落库"
```

## 四、短链系统设计

### 核心问题

```text
1. 长 URL → 短码生成
2. 短码唯一性
3. 访问短码 → 302 跳转长 URL
```

### 短码生成方案

```text
方案 1：哈希 + 冲突处理
- MD5/SHA 后取前 6-8 位
- 冲突时重新哈希或加盐

方案 2：数据库自增 ID 转 62 进制
- 自增 ID 保证唯一
- 10 进制 → 62 进制（0-9 a-z A-Z）
- 如 1000000000 → 15ftgG
```

### 架构设计

```text
生成短链：
用户 → 短链服务 → DB 存储（短码、长 URL、过期时间）

访问短链：
用户 → 短链服务 → 查缓存（Redis）→ 302 跳转
```

### 关键点

```text
- 缓存：热门短链放 Redis
- 发号器：自增 ID 用号段模式或雪花算法
- 存储：短码 → 长 URL 映射表
- 302 临时重定向，便于统计
```

## 五、排行榜设计

### 需求

```text
实时排行榜：按分数排序，支持查看 Top N、查询个人排名
```

### 方案：Redis ZSet

```text
加分：ZINCRBY rank:game 10 user:1
Top10：ZREVRANGE rank:game 0 9 WITHSCORES
个人排名：ZREVRANK rank:game user:1
分数：ZSCORE rank:game user:1
```

### 大数据量优化

```text
- 按小时/天分桶，先找桶再算排名
- 定期把冷数据归档
- 多级榜单：日榜、周榜、总榜
```

### 核心挑战

```text

```

### 方案

```text
点赞：Redis Set 存储点赞用户

取消点赞：
SREM like:article:1 user:10

点赞数：
SCARD like:article:1

SISMEMBER like:article:1 user:10

持久化：定时任务把 Set 同步到 DB
```

## 七、限流器设计

### 需求

```text
接口 QPS 限制，超限拒绝或排队
```

### 四种算法

| 算法 | 原理 | 特点 |
|---|---|---|
| 计数器 | 固定窗口计数 | 边界突刺 |
| 滑动窗口 | 窗口滑动计数 | 更平滑 |
| 漏桶 | 固定速率流出 | 绝对平滑 |
| 令牌桶 | 固定速率放令牌，允许突发 | 最常用 |

### Redis 实现令牌桶/计数器

```text
简单计数器（固定窗口）：
INCR key + EXPIRE 或 Lua 原子执行
超过阈值直接拒绝

生产方案：
- 网关层：Sentinel、Nginx limit_req
- 应用层：Sentinel、Guava RateLimiter
```

## 九、截图中的后台高频场景题参考方案

> 说明：截图中的秒杀、短链、排行榜，前文已经有完整方案；下面补充其余题目，并统一采用“目标 → 方案 → 关键兜底”的面试表达方式。

### Q1. 如何自己实现一个 RPC 框架？

**参考回答：**

```text
核心链路：客户端代理 → 序列化 → 网络传输 → 服务端反序列化 → 方法分发 → 返回结果。

主要模块：
1. 注册中心：维护服务名、地址和版本。
2. 动态代理：调用远程方法时自动封装请求。
3. 通信层：可使用 Netty，支持连接复用。
4. 序列化：选择 Protobuf、Kryo 等高效格式。
5. 治理能力：超时、重试、负载均衡、熔断和监控。

关键点：请求要带 requestId；重试前要判断接口是否幂等，避免重复写入。
```

### Q2. 如何设计一个动态线程池？

**参考回答：**

```text
线程池参数包括核心线程数、最大线程数、队列容量、空闲时间和拒绝策略。

动态配置：把参数放到配置中心，监听变更后安全更新线程池；不能直接替换正在执行的线程池。

运行监控：记录活跃线程数、队列长度、任务耗时、拒绝次数和异常数。

更新时要校验参数范围，并支持回滚。线程数不能只看 CPU，还要结合任务是 CPU 密集还是 IO 密集。
```

### Q3. 如何设计一个站内消息系统？

**参考回答：**

```text
消息先写入数据库保证可靠，再通过 MQ 或事件通知异步推送。

核心数据：消息表、会话/接收人关系表、已读状态或已读游标。

Redis 保存未读数，WebSocket/SSE 做实时通知；用户离线后再次登录，从数据库或消息游标补拉。

每条消息使用唯一 messageId，消费端幂等；消息按会话或用户分区，尽量保证同一会话有序。
```

### Q4. 如何设计微博 Feed 流/信息流系统？

**参考回答：**

```text
常见方案是“推模式 + 拉模式”结合：
- 普通用户发微博时，把消息推送到粉丝 Feed 列表。
- 大 V 粉丝很多，不直接全量推送，用户读取时再拉取大 V 的内容。

Feed 列表可以用 Redis ZSet，按时间或游标分页；不能使用深分页 offset。

写入和推送通过 MQ 异步完成，读取时合并多路内容、去重、排序。热点内容放缓存，并设置过期时间。
```

### Q5. 订单超时自动取消如何实现？

**参考回答：**

```text
创建订单时写入过期时间，同时投递延迟消息或写入 Redis ZSet。

任务到期后，消费者先查询订单状态，只有状态仍为“待支付”且版本未变化时，才执行取消。

数据库使用条件更新：UPDATE ... WHERE status = WAIT_PAY，保证支付和取消并发时只有一个成功。

取消操作要幂等；消息重复、消费失败时可以重试，超过次数进入死信队列或人工补偿。
```

### Q6. 如何基于 Redis 实现延时任务？

**参考回答：**

```text
使用 Redis ZSet：score 存执行时间，member 存任务 ID。

生产者用 ZADD 写入任务；消费者定期查询 score 小于当前时间的任务，再用 Lua 脚本原子地“取出并删除”，避免多个实例重复消费。

任务执行失败时重新设置下一次执行时间；超过重试次数进入失败队列。生产环境还要持久化任务状态，Redis 只做调度加速，避免任务丢失。
```

也可以使用 Redisson `DelayedQueue`，但仍要补充幂等、重试和持久化兜底。

### Q7. 如何解决大文件上传问题？

**参考回答：**

```text
采用分片、断点续传和对象存储直传：
1. 服务端生成 uploadId 和分片地址。
2. 客户端把文件切成多个分片并并行上传。
3. 每个分片带序号和 checksum，失败只重传该分片。
4. 所有分片完成后调用合并接口。
5. 合并后异步做病毒扫描、格式校验和转码。

上传状态放 Redis/数据库；超时未完成的分片定时清理。服务端不直接承载整个文件流，避免占满应用服务器带宽和内存。
```

### Q8. 如何实现归属地功能？

**参考回答：**

```text
先明确是手机号归属地还是 IP 归属地。

手机号：维护号段到省市、运营商的映射表；按前缀查询。
IP：使用 IP 段到地区的数据库或本地 Trie/二分查找结构。

热点查询放 Redis，本地维护数据版本并定期更新。查询结果只作为展示或风控辅助，不能把归属地当作精确定位；同时注意隐私和数据合规。
```

### Q9. 如何统计网站 UV？

**参考回答：**

```text
UV 是指定时间范围内的去重访客数。

数据量较小时，用 Redis Set 保存 userId 或 deviceId，SCARD 得到精确 UV。

数据量很大时，用 HyperLogLog：PFADD 写入访客，PFCOUNT 统计数量，空间占用很小但有约 0.81% 的估算误差。

按天建立 Key，月底可用 PFMERGE 合并。计费等必须精确的场景不能只依赖 HyperLogLog。
```

### Q10. 项目中的敏感词脱敏如何实现？

**参考回答：**

```text
敏感词不只在前端处理，服务端入参、日志、接口响应都要处理。

词库使用 Trie 或 Aho-Corasick 自动机匹配，支持批量扫描和最长匹配；命中后按规则替换为 ***、部分掩码或哈希。

手机号、身份证等结构化敏感信息使用正则或字段级脱敏。原始数据如果必须保存，应加密存储、限制权限，日志禁止打印明文。

词库更新需要版本化和灰度，避免热更新导致服务异常。
```

### Q11. 如何安全传输和存储密码？

**参考回答：**

```text
传输使用 HTTPS/TLS，不能依赖前端加密替代 HTTPS。

服务端不保存明文密码，也不使用简单 MD5。使用 Argon2、bcrypt、scrypt 或 PBKDF2 加随机盐做单向哈希，登录时重新计算并比较。

密码、密钥放配置中心或 Secret，不写入代码和日志；登录接口增加限流、验证码和多次失败锁定。
```

### Q12. 如何实现第三方授权登录？

**参考回答：**

```text
采用 OAuth2/OIDC 授权码模式，Web 场景使用 PKCE。

流程：用户跳转第三方授权 → 回调拿 code → 服务端用 code 换 token → 校验身份信息 → 用 provider + openId 绑定本地账号。

state 用于防 CSRF，code 只使用一次且设置短过期时间；第三方 token 加密保存并限制权限范围。

绑定关系使用唯一索引，避免重复创建账号；解绑前要确认用户还有其他登录方式。
```

### Q13. 验证码登录场景怎么设计？

**参考回答：**

```text
发送验证码时生成安全随机码，写入 Redis，Key 绑定手机号、业务类型和场景，并设置短 TTL。

发送接口按手机号、IP、设备和账号多维度限流；验证码只能使用一次，并限制错误次数。

校验时使用 Lua 或原子删除，保证“校验成功 + 删除验证码”不会被并发重复使用。

登录成功后签发 Session/JWT。返回错误时不要暴露手机号是否注册，避免账号枚举。
```

### Q14. 多次输错密码后，如何限制一段时间内不能登录？

**参考回答：**

```text
按账号维度记录失败次数，按 IP 和设备维度做辅助限流，计数放 Redis 并设置过期时间。

达到阈值后写入锁定 Key，登录前先检查锁定状态；锁定时间到期自动恢复，也可以支持人工解锁。

计数和判断用 Lua 保证原子性。为了避免攻击者恶意锁定他人，不能只按账号永久封禁，还要结合验证码、二次验证和风险识别。
```

### Q15. 40 亿个 QQ 号，限制 1G 内存，如何去重？

**参考回答：**

```text
如果 QQ 号能映射到有限整数范围，使用 Bitmap：一个号码对应一个 bit，读到号码时判断 bit，未出现就输出并置 1。

若号码范围不超过 2^32，Bitmap 只需要 2^32 bit，约 512MB，满足 1G 限制。

如果号码是大范围 64 位整数，改用外部排序或按 Hash 分桶落盘后分块去重。Bloom Filter 只能近似判断，不能用于要求绝对准确的去重。
```

### Q16. 日活上亿，如何保证推荐视频不重复？

**参考回答：**

```text
先定义“不重复”的时间范围，例如最近 7 天或最近 N 条，而不是永久不重复。

为用户维护已看视频集合：规模可控时用 Redis Set，规模很大时用 Bitmap 或 Bloom Filter；推荐召回后先过滤已看内容，再排序和补充候选。

Bloom Filter 有误判，可能少推荐但不会漏掉已记录的重复判断；关键业务可以用 Set/数据库记录做精确校验。

用户看完视频后异步记录，记录失败要有补偿任务。
```

### Q17. 大数据 Top K 问题怎么解决？

**参考回答：**

```text
数据无法全部放内存时，使用大小为 K 的小顶堆，逐条读取数据：
- 堆未满就加入；
- 新数据大于堆顶，就替换堆顶。

时间复杂度 O(N log K)，空间复杂度 O(K)。

分布式场景先让每个节点计算本地 Top K，再汇总所有节点的候选继续计算 Top K。若是高频词统计，先做计数；数据特别大时可使用 Space-Saving 做近似统计。
```

### Q18. 多位骑手抢一个外卖订单，如何保证只有一个人抢到？

**参考回答：**

```text
最终以数据库条件更新作为成功依据：
UPDATE order SET rider_id = ?, status = GRABBED
WHERE id = ? AND status = WAITING;

只有 affected rows = 1 的请求抢单成功，其他请求失败。这个操作由数据库保证原子性，不建议只依赖应用层判断或分布式锁。

高并发时可以先用 Redis Lua 做预抢，再由数据库做最终确认；抢单接口需要幂等，订单取消、超时和重复回调也要做状态校验。
```

### Q19. 发生提现失败或退单时怎么处理？

**参考回答：**

```text
不能直接把余额重复加回，而要用状态机和资金流水保证一致性。

提现流程：可用余额扣减并冻结 → 创建提现流水 → 调用第三方 → 成功扣除冻结金额，失败解冻并退回余额。

状态至少有 INIT、PROCESSING、SUCCESS、FAIL；每次请求带唯一业务单号，第三方回调幂等处理。

结果未知时先查询第三方状态再决定是否重试，不能盲目重复提现。失败消息通过 MQ 重试，最终对账任务和人工补偿兜底。
```

### Q20. 秒杀、短链和排行榜题如何快速回答？

**参考回答：**

```text
秒杀：网关限流和验证码削峰，Redis Lua 原子预扣库存，MQ 异步下单，数据库做最终校验和补偿。

短链：用自增 ID 或号段生成唯一短码，Redis 缓存短码映射，访问时 302 跳转，过期数据定期清理。

排行榜：Redis ZSet 按分数排序，ZINCRBY 更新分数，ZREVRANK 查排名，数据量大时按时间分桶和归档。
```

| 追问 | 答案要点 |
|---|---|
| 秒杀为什么不用 DB 直接扣 | DB 扛不住高并发，Redis 单机 10w QPS |
| Redis 扣减成功但订单失败怎么办 | 回补库存 + 对账补偿 |
| 短链过期怎么办 | 设置过期时间，定时清理 |
| 排行榜同分怎么排 | ZSet 分数相同按 member 字典序，业务可加时间戳排序 |
| 短信防刷的极端情况 | 多维度联合限流 + 风控机器学习识别 |
| 秒杀超卖的根本原因 | 并发读写无原子性，需原子操作或锁 |
