## 一、Java 基础

### 1. 如何创建线程池？线程池常见参数？

**创建方式：** 优先用 `new ThreadPoolExecutor(...)` 显式构造；避免用 `Executors` 工具类（其队列默认无界，有 OOM 风险）。

**7 大参数：**

```text
corePoolSize        核心线程数（常驻）
maximumPoolSize     最大线程数（扩容上限）
keepAliveTime       非核心线程空闲存活时间
unit                时间单位
workQueue           任务队列（满后扩容线程）
threadFactory       线程工厂（命名）
handler             拒绝策略（线程+队列都满时）
```

**执行流程：** 核心线程 → 队列 → 非核心线程 → 拒绝策略。

**4 种拒绝策略：**

| 策略 | 行为 | 场景 |
|---|---|---|
| AbortPolicy（默认） | 抛异常 | 快速失败 |
| CallerRunsPolicy | 提交者线程自己执行 | 可降级 |
| DiscardPolicy | 静默丢弃 | 可容忍丢失 |
| DiscardOldestPolicy | 丢队列头部任务 | 优先新任务 |

### 3. JVM 垃圾回收算法

```text
标记-清除：产生内存碎片
复制算法：适合新生代（存活少）
标记-整理：适合老年代（无碎片）

现代 JVM 采用分代收集：新生代用复制，老年代用标记-清除/整理。
G1 等垃圾收集器引入 Region 分区 + 并发回收，进一步降低停顿时间。
```

### 4. HashMap 底层原理和扩容机制

```text
结构：数组 + 链表 + 红黑树（JDK 8+）
哈希定位：hash(key) & (n-1) 计算数组下标
冲突处理：链地址法，链表尾插

扩容：
- 默认容量 16，负载因子 0.75
- 元素数 > 容量 × 0.75 时扩容为 2 倍
- JDK 8 迁移只需判断高位 bit，无需重新 hash
- 链表长度 ≥ 8 且数组 ≥ 64 时转红黑树
```

## 二、Redis

### 2. Redis 的数据类型

| 类型 | 结构 | 场景 |
|---|---|---|
| String | SDS | 缓存、计数、分布式锁 |
| List | 双向链表 | 队列、栈、时间线 |
| Hash | 字段-值映射 | 对象存储 |
| Set | 无序唯一集合 | 去重、交并差 |
| ZSet | 跳表 + 哈希 | 排行榜、延迟队列 |

扩展类型：Bitmaps（签到）、HyperLogLog（UV 统计）、GEO（地理位置）、Stream（消息队列）。

---

### 5. Redis 持久化策略

```text
RDB：定时生成全量快照
  - 优点：文件紧凑、恢复快
  - 缺点：两次快照间可能丢数据

AOF：记录每条写命令
  - 优点：数据更完整（everysec 最多丢 1 秒）
  - 缺点：文件大、恢复慢

混合持久化（4.0+）：RDB 快照 + AOF 增量
  - 生产环境主流选择
```

---

### 6. Redis 与数据库双写一致性

```text
核心方案：
1. Cache Aside：写时先更新 DB 再删缓存（最常用）
2. 延迟双删：删缓存 → 更新 DB → 延迟再删一次
3. binlog 异步同步：Canal 监听变更，异步更新缓存
4. 过期时间兜底：所有方案都设置 TTL
```

| 方案 | 一致性 | 场景 |
|---|---|---|
| Cache Aside | 最终一致 | 通用读多写少 |
| 延迟双删 | 最终一致 | 高并发热点数据 |
| MQ 异步同步 | 最终一致 | 高吞吐容忍延迟 |
| 分布式锁 | 强一致 | 串行更新场景 |
| TCC | 强一致 | 金融级 |

### 8. Redis ZSet 怎么实现？

```text
跳表（skiplist）+ 哈希表：
- 哈希表：member → score，O(1) 查分
- 跳表：按 score 排序，O(logN) 范围/排行操作
- 元素少时用压缩列表（ziplist）省内存
```

## 四、消息队列

### 9. 消息队列如何保证消息不丢？

| 环节 | 策略 | 实现 |
|---|---|---|
| 生产者 | 同步确认 + 重试 + 事务 | ACK、本地消息表 |
| Broker | 持久化 + 多副本 | 同步刷盘、ISR、Raft |
| 消费者 | 手动 ACK + 幂等 + 死信 | basicAck、唯一 ID、DLQ |

```text
核心要点：
- 生产端：确认机制保证发送成功
- Broker：刷盘 + 副本同步
- 消费端：先处理业务，成功后手动提交，失败重试
- 兜底：死信队列 + 告警
```

## 五、MySQL

### 10. 为什么 MySQL 用 B+ 树作为索引？

```text
1. 矮：非叶子节点不存数据，3-4 层可存千万级数据，减少磁盘 IO
2. 有序：叶子节点按键排序且用双向链表连接，天然支持范围查询
3. 稳定：查询路径长度一致，适合磁盘按页读取
```

### 11. 如何判断索引是否生效？常见失效场景？

**判断三看：**

```text
1. EXPLAIN 看 type、key 是否命中
2. 看 rows 扫描行数是否骤降
3. 看查询耗时是否明显缩短
```

**常见失效场景：**

```text
- 索引列使用函数或计算：where year(create_time) = 2024
- 隐式类型转换：字符串列用数字查询
- 前导通配符：like '%xx'
- 联合索引不满足最左前缀
- OR 连接非索引列
- 索引列使用 !=、not in
```

### 12. 如何监控并优化慢 SQL？

```text
定位：慢查询日志 → EXPLAIN 分析

优化层次：
1. 索引层：为 where/join 字段建索引、避免失效、删冗余索引
2. SQL 层：避免 select *、减少排序分组、优化子查询

5. 硬件层：提升配置
```

### 13. 事务隔离级别有哪些？

| 级别 | 脏读 | 不可重复读 | 幻读 | 场景 |
|---|---|---|---|---|
| Read Uncommitted | ✗ | ✗ | ✗ | 日志 |
| Read Committed | ✓ | ✗ | ✗ | 多数 OLTP |
| Repeatable Read（默认） | ✓ | ✓ | 基本解决 | 通用（电商） |
| Serializable | ✓ | ✓ | ✓ | 强一致（金融） |

```text
✓ 表示已解决，✗ 表示可能发生
```

#### 三种并发问题示例

**1. 脏读（读到未提交数据）**

```sql
-- 初始余额：100

事务 A：                     事务 B：
BEGIN;                       BEGIN;
UPDATE account
SET balance = 200            读取 balance → 得到 200（脏数据！）
WHERE id = 1;
ROLLBACK;  -- 回滚，真实余额还是 100
```

**2. 不可重复读（同一事务两次读，结果不同）**

```sql
-- 事务 A 内两次读取

事务 A：                     事务 B：
BEGIN;
SELECT balance               BEGIN;
FROM account                UPDATE account
WHERE id = 1;                SET balance = 200
→ 100                        WHERE id = 1;
                            COMMIT;

SELECT balance
FROM account
WHERE id = 1;
→ 200  -- 同一事务两次读到不同值
```

**3. 幻读（同一事务两次查询，行数不同）**

```sql
-- 事务 A 内两次范围查询

事务 A：                     事务 B：
BEGIN;
SELECT COUNT(*)             BEGIN;
FROM orders                 INSERT INTO orders
WHERE amount > 100;         VALUES (150);
→ 3 行                      COMMIT;

SELECT COUNT(*)
FROM orders
WHERE amount > 100;
→ 4 行  -- 多出来一行"幻影"
```

#### 隔离级别选择建议

```text
- Read Uncommitted：基本不用，脏读不可接受
- Read Committed：读已提交，可能出现不可重复读，适合多数 OLTP
- Repeatable Read：MVCC 快照读 + 间隙锁基本解决幻读，MySQL 默认
- Serializable：全隔离，性能最差，仅金融等高要求场景

关键理解：
- 不可重复读针对"单行数据被修改"
- 幻读针对"新增/删除行导致行数变化"
```
