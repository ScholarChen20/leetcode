## 一、设计模式六大原则（SOLID）

| 原则 | 含义 |
|---|---|
| 单一职责（SRP） | 一个类只负责一件事 |
| 开闭原则（OCP） | 对扩展开放，对修改关闭 |
| 里氏替换（LSP） | 子类可以替换父类而不出错 |
| 依赖倒置（DIP） | 依赖抽象而非具体实现 |
| 接口隔离（ISP） | 接口最小化，不强迫实现不需要的方法 |
| 迪米特法则（LoD） | 最少知道，减少对象间耦合 |

**面试说法：** "设计模式的核心是**面向抽象编程**和**高内聚低耦合**，六大原则是设计模式的指导思想。"

## 二、创建型模式

### Q1. 单例模式

**作用：** 保证一个类只有一个实例，提供全局访问点。

**饿汉式：**

```java
public class Singleton {
    private static final Singleton INSTANCE = new Singleton();
    private Singleton() {}
    public static Singleton getInstance() { return INSTANCE; }
}
```

**双重检查锁（DCL）：**

```java
public class Singleton {
    private static volatile Singleton instance;
    private Singleton() {}
    public static Singleton getInstance() {
        if (instance == null) {
            synchronized (Singleton.class) {
                if (instance == null) {
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
```

**枚举式（推荐）：**

```java
public enum Singleton {
    INSTANCE;
}
```

**高频追问：**

```text
Q: DCL 为什么要 volatile？
A: 防止指令重排序。new 对象分三步（分配内存、初始化、赋值引用），
   重排序后其他线程可能拿到未初始化的对象。

Q: 饿汉 vs 懒汉？
A: 饿汉类加载即创建（简单、安全、可能浪费内存）；
   懒汉用时才创建（DCL、静态内部类实现延迟加载）。

Q: 如何破坏单例？
A: 反射、反序列化。枚举单例天然防止两者。
```

### Q2. 工厂模式三兄弟

| 模式 | 结构 | 场景 |
|---|---|---|
| 简单工厂 | 一个工厂类，switch 创建 | 类型少、简单 |
| 工厂方法 | 每个产品一个工厂类 | 产品种类多、需要扩展 |
| 抽象工厂 | 一组相关产品的工厂 | 产品族场景 |

**简单工厂示例：**

```java
public class ShapeFactory {
    public static Shape create(String type) {
        if ("circle".equals(type)) return new Circle();
        if ("square".equals(type)) return new Square();
        throw new IllegalArgumentException("unknown type");
    }
}
```

**区别一句话：**

```text
简单工厂：一个工厂造所有产品（if/else 分支）
工厂方法：一个产品对应一个工厂（符合开闭原则）
抽象工厂：一个工厂造一族产品（如不同品牌的手机+耳机）
```

**Spring 中的体现：** `BeanFactory`、`FactoryBean`。

### Q3. 建造者模式（Builder）

**作用：** 分离复杂对象的构建过程和表示。

```java
User user = User.builder()
    .name("张三")
    .age(18)
    .build();
```

**适用场景：**

```text
- 构造参数多（超过 4 个）
- 参数可选、有默认值
- 避免构造函数重载爆炸
```

**实际应用：** Lombok `@Builder`、`HttpClient` 构建、链式查询构造器。

## 三、结构型模式

### Q4. 代理模式

**作用：** 为对象提供代理，控制访问。

| 类型 | 特点 | 实现 |
|---|---|---|
| 静态代理 | 手动编写代理类 | 接口 + 代理类 |
| JDK 动态代理 | 基于接口 | `InvocationHandler` |
| CGLIB 代理 | 基于继承（类） | 字节码生成 |

**JDK 动态代理 vs CGLIB：**

```text
JDK 代理：目标类必须实现接口，通过 InvocationHandler 拦截
CGLIB：无需接口，通过继承 + 方法拦截

Spring AOP 默认策略：
- 有接口 → JDK 动态代理
- 无接口 → CGLIB
```

**实际应用：**

```text
Spring AOP（事务、日志）、MyBatis Mapper 代理、RPC 远程调用
```

---

### Q5. 装饰器模式 vs 代理模式

| 对比 | 装饰器 | 代理 |
|---|---|---|
| 目的 | 增强功能 | 控制访问 |
| 关注点 | 叠加能力 | 拦截控制 |
| 典型场景 | Java IO（BufferedReader）、HttpClient 拦截器链 | Spring AOP |

**Java IO 典型装饰器链：**

```java
new BufferedReader(new FileReader("file.txt"))
// BufferedReader 装饰 FileReader，叠加缓冲能力
```

---

### Q6. 适配器模式

**作用：** 把不兼容的接口转换为客户端期望的接口。

```text
场景：
- 对接第三方接口，格式不兼容
- 新旧系统过渡
- 统一多个实现类接口

实际应用：
- Spring MVC 的 HandlerAdapter
- 日志框架 SLF4J（统一 Log4j、Logback 接口）
```

## 四、行为型模式

### Q7. 策略模式

**作用：** 定义一组算法，让它们可互相替换，算法变化不影响使用方。

```java
// 支付方式：支付宝、微信、银联
public interface PayStrategy {
    void pay(BigDecimal amount);
}
```

**使用场景：**

```text
- 多种支付方式
- 多种优惠券计算规则
- 多种导出格式
```

**关键点：** 消除 `if-else` 分支，通过 Map 注册策略。

```java
Map<String, PayStrategy> strategies = new HashMap<>();
strategies.put("alipay", new AlipayStrategy());
strategies.put("wechat", new WechatStrategy());
```

**策略模式 vs 工厂模式：** 工厂关心"创建哪个对象"，策略关心"执行哪种行为"。

---

### Q8. 模板方法模式

**作用：** 定义算法骨架，子类实现具体步骤。

```java
public abstract class AbstractTemplate {
    public final void process() {  // 骨架方法 final
        step1();
        step2();  // 抽象方法，子类实现
        step3();
    }
    protected abstract void step2();
}
```

**实际应用：**

```text
Spring JdbcTemplate、AbstractApplicationContext.refresh()
RabbitTemplate 的消息发送模板
```

**模板方法 vs 策略：**

```text
模板方法：继承实现，固定流程 + 可变步骤
策略模式：组合实现，整体算法可替换
```

---

### Q9. 观察者模式

**作用：** 一对多依赖，一个对象变化通知所有依赖者。

```text
角色：
Subject（被观察者）：维护观察者列表，状态变化时通知
Observer（观察者）：接收通知，更新自身
```

**实际应用：**

```text
Spring 事件机制（ApplicationEvent + @EventListener）
MQ 发布订阅模式
Redis 的 Pub/Sub
```

**观察者 vs 发布订阅：**

```text
观察者：观察者直接注册到被观察者，耦合较紧
发布订阅：通过中间件（Broker/EventBus）解耦，双方互不知道
```

---

### Q10. 责任链模式

**作用：** 请求沿链传递，每个处理器决定处理或传递。

```text
场景：
- 审批流（经理 → 总监 → 老板）
- 过滤器链（Servlet Filter）
- 参数校验链
- 网关过滤器（Gateway Filter）
```

**实际应用：** Spring Security 过滤器链、Servlet FilterChain。

| 模式 | Spring 中的应用 |

## 六、项目实战追问

### Q11. 你在项目中用过哪些设计模式？

**推荐回答框架：**

```text
策略模式 + 工厂模式：多渠道支付/推送，替代 if-else
模板方法：消息处理流程（校验 → 落库 → 发送 → 更新状态）
责任链：请求校验链（参数校验 → 权限校验 → 风控校验）
观察者：订单事件发布（下单成功 → 发券、积分、通知）
建造者：复杂查询条件构造
单例：配置管理、连接池
```

**追问：为什么这样用？**

```text
- 满足开闭原则：新增支付渠道只需加类，不改原有代码
- 消除 if-else 分支，代码可读性和可维护性提升
- 单一职责：每个策略类只处理一种业务
```

## 附：高频追问速答

| 追问 | 答案要点 |
|---|---|
| 单例 DCL 为什么两次判空 | 外层判空避免加锁开销，内层判空防止重复创建 |
| 饿汉式有什么缺点 | 类加载即创建，可能浪费内存 |
| 动态代理底层原理 | 反射 + InvocationHandler 拦截方法调用 |
| 装饰器和代理怎么区分 | 装饰器增强功能，代理控制访问 |
| 策略模式怎么消除 if-else | Map 注册策略，按 key 获取执行 |
| 观察者模式缺点 | 通知顺序不可控，可能引发级联问题 |
| 设计模式是越多越好吗 | 不是，过度设计增加复杂度，按需使用 |
| 模板方法为什么用 final | 防止子类修改算法骨架 |
