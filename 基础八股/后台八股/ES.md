# ES（Elasticsearch）面试八股

> 定位：**搜索引擎与检索领域**。回答时先给一句话结论，再展开对比。
> 主线：ES = Lucene（单机检索引擎）+ 分布式封装（分片、副本、集群协调）。

---

## 一、基础概念

### 1. ES 是什么
一句话：**分布式的实时搜索与分析引擎**，底层是 Lucene，在上面加了分布式分片、副本、集群管理和 REST API。

核心能力：全文检索、结构化查询、聚合分析、近实时（1 秒内可见）。

### 2. ES vs MySQL 的检索差异
| | MySQL | ES |
|---|---|---|
| 索引结构 | B+Tree | **倒排索引**（+ Doc Values） |
| 擅长 | 事务、精确查询、JOIN | 全文检索、模糊匹配、多维聚合 |
| 模糊查询 | `LIKE '%xx%'` 全表扫，索引失效 | 走倒排索引，毫秒级 |
| 事务 | 完整 ACID | 无事务，最终一致 |

> **经典问法**：为什么 `LIKE '%关键词%'` 慢而 ES 快？—— B+Tree 的最左前缀匹配对前置通配符无能为力，只能全表扫；倒排索引是"词 → 文档列表"的直接映射。

### 3. ES vs Lucene
Lucene 是单机检索引擎库，只管索引和检索；ES 在 Lucene 之上解决了分布式问题：分片路由、副本同步、集群发现、故障转移、RESTful 接口。

### 4. 核心术语对照
| ES | MySQL | 说明 |
|---|---|---|
| Index（索引） | 表 | 7.x 起 type 被废弃，一个 index 就是一类数据 |
| Document（文档） | 一行记录 | JSON 格式 |
| Field（字段） | 列 | |
| Mapping | 表结构 | 定义字段类型和分析器 |
| DSL | SQL | JSON 格式的查询语言 |
| Shard | 分表 | 一个 index 拆成多个分片 |

## 二、text vs keyword

一句话：**text 用于全文检索（要分词），keyword 用于精确匹配、排序和聚合（不分词）**。

| 特性 | text | keyword |
|---|---|---|
| 核心用途 | 全文检索 (Full-text search) | 精确匹配 (Exact-value search) |
| 是否分词 | 是 | 否 |
| 倒排索引 | 对分词后的词条建立索引 | 对整个字符串建立索引 |
| 排序/聚合 | 不适用 | 适用 |
| 典型场景 | 邮件正文、商品描述、日志正文 | 国家码、标签、状态码、邮编、枚举值 |

**补充**：ES 动态映射会给字符串字段同时生成 `text` 主字段 + `keyword` 子字段（`字段名.keyword`），兼顾两种用途。聚合/排序时用 `title.keyword`。

**追问：为什么 keyword 能聚合而 text 不能？**
聚合和排序依赖 **Doc Values**（列式存储，构建时把 field 值按 doc 展开）。`text` 字段默认关闭 Doc Values（分词后列存没有意义且极占空间）；强行对 text 聚合要开 `fielddata`，会把倒排索引反向加载到堆内存，极易 OOM —— **生产禁用**。

## 三、Query vs Filter

一句话：**Query 算分（"匹配得多好"），Filter 只判是否匹配（"匹配不匹配"），且更快**。

| | Query（query context） | Filter（filter context） |
|---|---|---|
| 关注点 | 相关度 | 是否匹配 |
| 结果 | 计算 `_score` 并排序 | 二元 是/否 |
| 缓存 | 不缓存 | **结果缓存到 BitSet**，重复查询直接命中 |
| 开销 | 高（BM25 计算） | 低 |

**工程要点**：不关心相关度的条件（时间范围、状态码、租户 ID、类目）一律放 `filter`，既能利用缓存又不干扰打分。

```json
{ "query": { "bool": {
    "must":   [ { "match": { "title": "无线耳机" } } ],      // 算分
    "filter": [ { "term":  { "status": 1 } },                 // 不扣分、可缓存
                { "range": { "price": { "lte": 100 } } } ]
} } }
```

## 四、倒排索引（Inverted Index）

一句话：**记录每个"词条"出现在哪些"文档"中**，而不是记录文档包含哪些内容。这是毫秒级全文检索的秘密武器。

类比：书末的索引目录 —— 通过关键词直接翻到页码，而不是逐页扫描。

### 结构
```
Term Dictionary（词条字典）  →  Postings List（倒排列表）
"手机" → [doc1, doc3, doc7]     每个 doc 还带词频 TF、位置 offset
```

### 实现细节（加分）
- **Term Index**：字典前缀用 **FST**（Finite State Transducer）压缩放内存，快速定位词条在磁盘的位置
- **Postings List**：用 **Frame of Reference** 差分压缩 + Roaring Bitmap 压缩整数列表
- **不可变性**：段（Segment）一旦生成不可修改 —— 这是 ES 能做到免锁高并发读的根本原因

### 构建过程
分词 → 建立「词条 → 文档ID 列表」映射表

### 优缺点
- ✅ 查询极快，尤其全文检索和模糊匹配
- ❌ 写入/更新成本高（要重建索引）、占用存储比原数据大

## 五、分词器 Analyzer

一句话：**分词器 = Character Filter → Tokenizer → Token Filter** 三段流水线。

| 段 | 作用 | 例子 |
|---|---|---|
| Character Filter | 文本预处理 | 去 HTML 标签、替换字符 |
| Tokenizer | 按规则切分为词条 | 空格切分、中文分词 |
| Token Filter | 词条加工 | 转小写、停用词过滤、同义词、词干还原 |

**写入时和查询时用同一个分析器**（否则索引里存的和查询时切的对不上，搜不到）。

### IK 分词器两种模式
- `ik_smart`：**智能分词**，粒度粗。"中华人民共和国" → `[中华人民共和国]`
- `ik_max_word`：**最细粒度**，尽可能多切。"中华人民共和国" → `[中华, 中华人民, 人民, 共和国, 中华人民共和国...]`

> **实践**：索引用 `ik_max_word`（提高召回），查询用 `ik_smart`（提高准确，减少噪声得分）。可通过 `ik` 的扩展词典/停用词典自定义词库。

## 六、分片与路由

### 1. Shard / Replica
- **主分片（Primary Shard）**：数据的最小单元，负责写入。**创建索引时指定，之后不可改**
- **副本分片（Replica）**：主分片的拷贝，负责读负载均衡和故障转移，可动态调整

### 2. 路由公式
```
shard = hash(routing) % number_of_primary_shards
```
`routing` 默认是文档 `_id`，可自定义（如按 `user_id` 路由，让同一用户的数据落在同一分片，提升查询效率）。

> **为什么主分片数不能改？** 路由公式里分母就是主分片数 —— 改了它，所有已存文档算出来的分片号全变，历史数据就找不到了。要扩容只能用**重建索引（reindex）**或 **shrink/split** API。

### 3. 分片怎么定（实践）
- 单分片控制在 **30~50GB**
- 分片数 ≈ `ceil(预计数据量 / 30GB)`
- 分片不是越多越好：每个分片是一个 Lucene 实例，有独立的文件句柄、内存、线程池；分片过多会拖垮集群、放大查询扇出成本

## 七、写入流程（超高频）

一句话：**先写 buffer + translog，再异步 refresh 变可搜，最后 flush 落盘 + merge 整理**。

```
客户端 → 协调节点（按 _id 路由）→ 主分片
   1. 写内存 Buffer（Indexing Buffer）
   2. 追加 Translog（WAL，防宕机丢数据）
   3. 并行转发给所有副本分片，副本同样写 buffer + translog 后回 ACK
   4. 所有副本确认 → 主分片返回成功
   5. 后台异步：Refresh → Flush → Merge
```

### 三个核心动作（必背对比）

| 动作 | 触发时机 | 做了什么 | 目的 |
|---|---|---|---|
| **Refresh** | 默认 **每 1 秒** | buffer → 新 Segment（进 OS Cache），可被搜索 | **近实时搜索** |
| **Flush** | translog 达 512MB 或 **每 30 分钟** | Segment fsync 落盘 + 写 Commit Point + 清空 translog | **持久化** |
| **Merge** | 后台自动 | 多个小 Segment 合并成大 Segment，清理已删除文档 | **提查询性能、回收空间** |

### Translog 的作用
WAL（Write-Ahead Log）。宕机时内存 buffer 里没 flush 的数据丢了，重启后**重放 translog** 恢复。ES 7+ 默认 `index.translog.durability: request`（每次请求都 fsync）。

### 删除与更新怎么做的
**Segment 不可变**，所以删除不是在原地改：
- 删除：在 `.del` 文件里给文档**打删除标记**，查询时过滤掉
- 更新：旧文档打标记 + 新版本写入新 Segment
- 真正物理删除发生在 **Merge** 阶段

## 八、近实时（NRT）搜索

一句话：**ES 是"近实时"而非"实时"，因为文档要等下一次 Refresh（默认 1 秒）生成 Segment 后才可被搜索**。

**为什么写入返回成功了却搜不到？**
返回成功只代表写进了 buffer + translog，**还没 Refresh 生成可搜索的 Segment**。

**三个补充点**：
1. `GET /index/_doc/{id}`（按 ID 取）是**实时**的，可以直接读 translog 里未刷新的数据，不受 Refresh 影响
2. `?refresh=true` 可强制立即刷新，但会生成大量小 Segment，极大增加 Merge 压力，**生产慎用**
3. 批量导入时可临时把 `refresh_interval` 设为 `-1`，导完再改回

## 九、查询流程（Query Then Fetch）

一句话：**两阶段的 scatter-gather（分散-收集）**。

**Query 阶段**：
1. 协调节点把请求广播到相关分片（主分片或副本选一个）
2. 每个分片**本地执行**查询，算出 Top N，**只返回 doc id + score**
3. 协调节点合并成全局 Top N

**Fetch 阶段**：
4. 协调节点按最终 Top N 的 id，去对应分片拉取完整 `_source`
5. 汇总返回客户端

> 为什么分两阶段？"先窄后宽" —— 只传 id 和分值时数据量极小，最终只拉 N 条完整文档，大幅降低网络和序列化开销。

## 十、相关性评分 BM25

一句话：**ES 5.0 起默认用 BM25，是 TF-IDF 的改进版**。

**BM25 比 TF-IDF 强在哪**（加分）：
1. **词频饱和**：TF-IDF 里词频越高分越高，没有上限，容易被关键词堆砌刷分；BM25 引入饱和参数 `k1`，词频到一定程度后**增益迅速收敛**
2. **文档长度归一化**：用参数 `b` 惩罚过长文档（长文档里出现某词的概率天然更高）

$$
score = \sum_i IDF(q_i) \cdot \frac{f(q_i,D)\cdot(k_1+1)}{f(q_i,D) + k_1 \cdot \left(1 - b + b \cdot \frac{|D|}{avgdl}\right)}
$$

三个可调因子：`k1`（词频饱和，默认 1.2）、`b`（长度归一，默认 0.75）、`boost`（字段权重）。

> 如果答出"ES 5 之前是 TF-IDF，之后是 BM25"，面试官会觉得你真看过版本演进。

## 十一、深度分页问题（高频）

### 问题
`from + size` 深翻页时，每个分片都要算出 `from + size` 条，协调节点要合并 `分片数 × (from + size)` 条再排序裁剪 —— **内存和 CPU 随深度线性暴涨**，会触发熔断。默认 `max_result_window = 10000`，超过直接报错。

### 三种解法

| 方案 | 原理 | 适用 |
|---|---|---|
| **search_after**（推荐） | 用上一页最后一条的排序值做游标，无状态 | 实时深翻页 |
| **scroll** | 创建快照游标，批量拉取 | 全量导出/离线处理，**不反映实时变更** |
| **PIT + search_after** | Point-in-Time 保证翻页期间视图一致 | ES 7.10+，最稳 |

```json
// search_after：排序必须唯一，末尾加 _id 兜底
{ "size": 20,
  "sort": [{ "created_at": "desc" }, { "_id": "asc" }],
  "search_after": ["2026-03-20T10:00:00", "abc123"] }
```

**业务层的兜底**：直接限制前端最多翻多少页（很多产品根本不需要深翻页）。

## 十二、聚合 Aggregation

一句话：**聚合靠 Doc Values（列式存储），在写入时构建，不占堆内存**。

### 三类聚合
- **Bucket 分桶**：`terms`、`range`、`date_histogram`（按时间直方图，日志分析常用）
- **Metric 指标**：`avg`、`sum`、`max`、`min`
- **Pipeline 管道**：对聚合结果再聚合（如求移动平均）

### terms 聚合的两个坑（加分）
1. **结果不精确**：每个分片只返回自己的 Top N，协调节点合并 —— 高基数字段会**丢桶**。解决：调大 `shard_size`（分片返回候选数，默认 `size * 1.5 + 10`）
2. **深分页**：terms 桶很多时翻页同样慢。解决：**Composite Aggregation**（用 `after` 游标翻页，支持多维度）

### cardinality：去重计数
基于 **HyperLogLog（HLL）**，是**近似算法**。特点：
- 内存占用只与配置的精度有关，**与数据量无关**（数千还是数十亿都一样）
- 小数据集精度很高；默认误差约 5%，可用 `precision_threshold` 调（上限 40000）

> 追问："要绝对精确的去重数怎么办？" —— 用 `terms` 聚合数桶数，或用 `precision_threshold` 拉满后再二次校验，代价是内存。

## 十三、集群与高可用

### 1. 节点角色
| 角色 | 职责 |
|---|---|
| **Master** | 集群管理、分片分配、元数据更新。**不处理数据读写** |
| **Data** | 存储数据、执行读写和聚合 |
| **Coordinating** | 接收请求、路由、结果合并（默认每个节点都是） |
| **Ingest** | 写入前的数据预处理管道（grok、date 解析等） |

**最佳实践**：Master 与 Data 角色分离（`node.master: true, node.data: false`），避免 Master 被数据压力拖垮。

### 2. Master 选举
1. 只有 `node.master: true` 的候选节点能参选
2. 对候选节点按 nodeId 字典排序，每个节点投自己知道的"第 0 位"
3. 某节点得票 ≥ `minimum_master_nodes` 且自己也投自己 → 成为 Master

### 3. 脑裂（Split Brain）
**是什么**：网络分区导致集群裂成两半，各自选出 Master，数据出现两份不一致的元数据。

**成因**：网络抖动 / Master 节点兼任 Data 被压垮 / Data 节点 GC 停顿导致误判 Master 下线。

**三种解法**：
1. **角色分离**：Master 不存数据，Data 不参与选举
2. **最小主节点数**：`minimum_master_nodes = (master_eligible / 2) + 1`，保证多数派
3. **心跳调优**：调大 `ping_timeout`（默认 3s）避免 GC 误判

> **版本演进**：ES 7.x 起用 **Zen2**（基于 Raft 类协议），自动管理投票配置，不再需要手动配 `minimum_master_nodes`，但仍建议 **至少 3 个 master-eligible 节点**。

### 4. 集群健康状态
| 颜色 | 含义 |
|---|---|
| 🟢 Green | 主分片和副本分片全部正常 |
| 🟡 Yellow | 主分片正常，**副本未分配**（单节点集群的正常状态） |
| 🔴 Red | **有主分片未分配**，该部分数据不可读写 |

**磁盘爆满**：临时清过期索引 / 关分片自动分配 / 调高水位线；根治用 **ILM（索引生命周期管理）** 自动滚动和删除过期索引。

## 十四、性能优化

### 写入优化
1. **批量写 bulk**，单次 1000~5000 条最合适
2. 调大 `refresh_interval`（3s~10s），批量导入时设 `-1`
3. **大批量初始化时临时把副本数设为 0**，写完再恢复
4. 关闭动态映射，**提前定义好静态 mapping**（避免字段爆炸）
5. 用自动生成的 ID（自定义 ID 要先查一次是否存在）
6. 单分片控制 50GB 内

### 查询优化
1. 能 `filter` 就不 `must`（减少算分 + 命中缓存）
2. 精确匹配字段用 **keyword**，避免对 text 做分词查询
3. 用 `_source` 过滤掉不需要的返回字段
4. **避免深分页**，改用 `search_after`
5. **禁用 wildcard 前缀通配**（`*abc`）—— 会全量扫倒排列表
6. 分片数合理，避免过多分片放大扇出成本
7. 用 `routing` 把查询打到固定分片

### JVM 与系统
- **堆内存 = Min(节点内存/2, 32GB)**（超过 32GB 会失去指针压缩，反而更浪费）
- **关闭 swap**（避免 Lucene 的段被换出，查询会暴慢）
- 调大文件句柄数，SSD，有条件 RAID10

## 十五、ES 在检索/RAG 场景（与 Agent 关联）

> 这一块是现在 Agent 岗爱追问的方向。

**ES 在 RAG 里的角色**：做**关键词/稀疏检索**通道，和向量库的稠密检索组成**混合检索**。

- **BM25 稀疏检索的优势**：精确匹配专有名词、型号、代码标识符、人名 —— 这些恰恰是向量检索容易糊掉的地方
- **混合检索（Hybrid Search）**：ES 8.x 原生支持 `dense_vector` 字段 + kNN 检索，可以在一次查询里同时跑 BM25 和 kNN，再用 **RRF（Reciprocal Rank Fusion）** 融合排序
- **ES vs 向量库**：ES 胜在**已有基础设施、支持复杂过滤 + 关键词 + 向量的混合查询、运维成熟**；专用向量库（Milvus、Pinecone）胜在**纯向量场景下的规模和性能**
