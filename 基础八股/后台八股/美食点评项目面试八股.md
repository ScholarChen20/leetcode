# 美食点评项目面试八股

> 项目技术栈：Spring Boot、MySQL、MyBatis-Plus、Redis、Caffeine、RabbitMQ、Redisson、Qwen、LangChain4j
>
> 使用方式：先准备项目概述，再按“问题—回答—项目结合”展开。面试时不要只背概念，要结合自己的代码和业务场景说明为什么这样设计。

## 一、项目概述

### 1. 请介绍一下这个项目

这是一个面向用户的美食点评平台，主要功能包括商家查询、附近商家、优惠券秒杀、探店笔记、关注点赞、签到统计和智能客服等。

项目使用 MySQL 保存用户、商家、优惠券、订单和笔记等核心业务数据；使用 Redis 处理商家缓存、登录 Session、秒杀库存、分布式锁、附近商家和社交关系等高频场景；使用 RabbitMQ 对秒杀订单进行异步削峰；使用 Caffeine 和 Redis 构建多级缓存。

新增的智能客服基于 Qwen 大模型和 LangChain4j 实现，使用 Redis 保存会话记忆，通过 Function Calling 查询真实商家信息和创建到家服务预约。

### 2. 项目中最有挑战的地方是什么

主要有三类：

1. 秒杀场景下如何防止库存超卖和一人多单。
2. 商家缓存如何提高性能，同时尽量保证缓存和数据库的一致性。
3. 大模型如何安全调用真实业务能力，而不是只生成一段可能不准确的文字。

可以概括为：Redis 负责高并发和热点数据，RabbitMQ 负责异步削峰和解耦，MySQL 负责最终持久化和一致性兜底，大模型负责理解意图，后端工具负责真正执行操作。

## 二、Spring Boot 与项目架构

### 1. 项目采用什么分层结构

整体采用 Controller、Service、Mapper、Entity 分层：

- Controller：接收请求、参数校验和返回统一结果。
- Service：编排业务流程，处理事务和业务规则。
- Mapper：通过 MyBatis-Plus 访问数据库。
- Entity/DTO：分别表示数据库实体和接口传输对象。
- Config/Interceptor：处理 Redis、RabbitMQ、鉴权和 Web 配置。

面试中可以强调，业务逻辑尽量放在 Service 层，Controller 不直接操作数据库，依赖注入优先使用构造器注入。

### 2. 为什么使用统一的 Result 返回结果

统一返回结构可以让前端稳定处理接口结果，通常包含成功标识、错误信息、业务数据和总数等字段。这样可以减少不同接口返回格式不一致的问题，也方便统一异常处理和接口文档维护。

### 3. Spring 事务主要用在哪些地方

事务主要用于涉及多步数据库操作、且必须保证原子性的业务，例如创建秒杀订单、更新业务数据后处理关联记录等。

需要注意：Spring 事务默认基于代理实现，同一个类内部直接调用另一个事务方法时，可能不会经过代理，导致事务注解不生效。事务边界应该尽量放在 Service 对外方法上。

## 三、商家缓存与一致性

### 1. 商家详情使用什么缓存策略

使用 Cache Aside，也叫旁路缓存：

1. 查询时先查 Redis。
2. Redis 命中则直接返回。
3. Redis 未命中时查询 MySQL。
4. 查询到数据后写入 Redis。
5. 更新时先更新 MySQL，成功后删除 Redis 缓存。

数据库是最终数据源，缓存只是加速访问。

### 2. 为什么更新时选择“先更新数据库，再删除缓存”

因为数据库保存的是最终数据。更新数据库成功后删除缓存，下一次请求会重新从数据库加载最新值。

如果采用“更新数据库后更新缓存”，并发场景下可能发生旧数据覆盖新数据：一个线程读取旧数据后，另一个线程更新数据库并写入新缓存，前一个线程又把旧数据写回缓存，最终缓存反而变旧。

“先删缓存再更新数据库”也存在问题：删除缓存后，其他线程可能在数据库更新完成前读到旧数据，并把旧数据重新写入缓存。

### 3. 什么是缓存穿透、缓存击穿和缓存雪崩

缓存穿透：请求的数据缓存和数据库中都不存在，请求每次都打到数据库。

常见解决方案：缓存空对象、布隆过滤器、参数校验、接口限流。

缓存击穿：一个热点 Key 在某一时刻过期，大量请求同时访问数据库。

常见解决方案：互斥锁、逻辑过期、热点数据不过期、后台异步重建。

缓存雪崩：大量 Key 在同一时间集中失效，导致大量请求同时访问数据库。

常见解决方案：TTL 增加随机值、热点数据不过期、限流熔断、多级缓存和 Redis 高可用。

### 4. 项目中如何解决缓存穿透

当数据库查询不到商家时，在 Redis 中缓存一个空字符串，并设置较短的过期时间。后续相同的非法请求命中空值后直接返回，不再反复访问数据库。

需要注意空值 TTL 不能设置太长，否则商家刚新增时可能因为缓存空值而短时间查不到；同时还要限制非法参数，避免大量随机 ID 请求。

### 5. 互斥锁和逻辑过期有什么区别

互斥锁是在缓存重建期间只允许一个线程查询数据库，其他线程等待或重试，数据一致性相对更好，但可能增加响应时间。

逻辑过期是在缓存中保存数据和逻辑过期时间。数据逻辑过期后，先返回旧数据，再由后台线程异步重建缓存，性能更好，但允许短时间返回旧数据。

### 6. Caffeine 和 Redis 如何构建二级缓存

查询顺序是 Caffeine、Redis、MySQL：

1. 先查本机 Caffeine，速度最快。
2. Caffeine 未命中再查 Redis。
3. Redis 未命中查询 MySQL。
4. 查询到数据后回填 Redis 和 Caffeine。

更新时先更新数据库，再删除 Redis 和 Caffeine。多实例部署时，本地 Caffeine 之间可能短暂不一致，可以通过 Redis 发布订阅、MQ 消息或统一失效通知清理各实例的本地缓存。

### 7. 缓存一致性是否能做到绝对一致

通常只能做到最终一致，而不是严格强一致。项目中通过“先更新数据库，再删除缓存”降低不一致窗口；对一致性要求更高的场景，可以使用延迟双删、消息通知、Binlog 订阅或缓存更新重试。

## 四、Redis 高频场景

### 1. 为什么登录信息放到 Redis

如果 Session 只保存在单机内存中，请求被负载均衡到其他实例后可能无法识别用户。将 Token 对应的用户信息存入 Redis，可以让多个实例共享登录状态，并通过 TTL 控制登录有效期。

项目中的 RefreshTokenInterceptor 负责校验 Token 和刷新有效期，LoginInterceptor 负责判断接口是否需要登录。

### 2. 为什么使用 ThreadLocal 保存当前用户

请求经过鉴权后，将用户信息放入 ThreadLocal，Service 层可以直接获取当前用户，不需要每一层都传递 userId。

请求结束后必须调用 remove 清理，否则线程池复用时可能出现用户信息串号，也可能造成内存泄漏。

### 3. 附近商家为什么使用 Redis GEO

Redis GEO 适合根据经纬度查询附近数据。项目中可以只把商家 ID 和坐标放进 GEO，商家详情仍然保存于 MySQL 或 Redis：

1. 通过 GEO 查询附近商家 ID 和距离。
2. 根据 ID 批量查询商家详情。
3. 按 GEO 返回的顺序组装结果。

这样既能利用 Redis 的地理位置能力，也能避免把完整商家对象重复放到 GEO 中。

### 4. 用户签到为什么使用 Bitmap

签到只有“签了”和“没签”两种状态，非常适合用 Bitmap 表示。Key 可以设计为 `sign:{userId}:{yyyyMM}`，日期对应 Bit 的 offset。

- SETBIT：签到。
- GETBIT：判断当天是否签到。
- BITCOUNT：统计当月签到天数。
- 位运算：可以辅助计算连续签到。

Bitmap 占用空间小，一个用户一个月只需要几十个 Bit。

### 5. UV 统计为什么使用 HyperLogLog

HyperLogLog 适合统计独立访客数量，内存占用很小，适合大规模数据。缺点是结果是估算值，不能得到具体访问用户，也不能替代精确去重。

### 6. 关注关系为什么使用 Set

Set 适合保存关注用户 ID，支持快速判断是否关注、添加关注、取消关注和查询共同关注。共同关注可以通过两个用户关注集合的交集实现。

### 7. 点赞排行榜为什么使用 Sorted Set

Sorted Set 同时保存成员和分数，可以保存用户 ID 与点赞时间或点赞数量。这样既能判断用户是否点赞，也能按时间或热度排序。

## 五、优惠券秒杀

### 1. 秒杀场景的核心问题是什么

核心问题包括：

- 高并发请求瞬间涌入。
- 多线程同时扣库存导致超卖。
- 同一用户重复下单。
- 数据库和消息队列承受突发压力。

### 2. Redis Lua 脚本解决了什么问题

Lua 脚本可以把多个 Redis 操作合并成一个原子操作，项目中可以一次完成：

1. 判断库存是否大于 0。
2. 判断用户是否已经购买。
3. 扣减 Redis 库存。
4. 记录用户购买资格。
5. 返回执行结果。

这样可以避免“先查库存、再扣库存”之间被其他线程插入，降低超卖和一人多单风险。

### 3. 为什么不能先查询库存，再扣减库存

因为查询和扣减是两个独立操作。多个线程可能同时读到库存为 1，然后都执行扣减，最终库存可能变成负数或产生多笔订单。Lua 脚本可以保证判断和扣减整体执行。

### 4. 如何保证一人一单

Redis 层使用 Lua 脚本记录用户购买资格，快速拦截重复请求；MySQL 层建立 `(user_id, voucher_id)` 唯一索引作为最终兜底。即使因为重试或消息重复消费再次创建订单，唯一索引也能避免重复数据。

### 5. 为什么使用 RabbitMQ 异步下单

如果秒杀请求同步完成数据库扣库存、创建订单和事务提交，数据库会承受瞬时高并发压力。项目采用：

1. Redis Lua 脚本完成库存预扣和资格校验。
2. 生成订单 ID。
3. 发送秒杀订单消息到 RabbitMQ。
4. 接口快速返回。
5. 消费者异步创建数据库订单。

这样可以削峰填谷，缩短接口响应时间，也能将秒杀入口和订单创建解耦。

### 6. Redis 预扣库存后，消息发送失败怎么办

这是秒杀系统需要重点考虑的一致性问题。可以采用：

- 生产者 Confirm 确认机制。
- 发送失败重试。
- 本地消息表或补偿记录。
- 定时任务扫描未成功投递的订单并补发。
- 订单超时或创建失败时回补 Redis 库存。

实际方案需要明确“预扣库存”和“订单消息”之间的补偿关系，不能只依赖接口返回成功。

### 7. RabbitMQ 如何保证消息可靠性

生产者方面开启 Confirm，监听消息是否成功到达 Exchange；Exchange、Queue 和 Message 都设置持久化；消费者使用手动 ACK，只有业务处理成功后才确认。

如果消费失败，可以重试，超过重试次数后进入死信队列，由补偿任务或人工处理。

### 8. 如何保证消息幂等

RabbitMQ 可能因为消费者处理成功但 ACK 丢失而重复投递，所以消费端必须幂等：

- 订单 ID 或 `(user_id, voucher_id)` 建立唯一约束。
- 消费前查询订单是否已经创建。
- 通过业务状态判断是否已经处理。
- 重复消息直接确认并忽略。

幂等的关键不是保证消息只投递一次，而是保证消息重复处理也不会产生错误结果。

## 六、分布式锁与并发控制

### 1. 为什么需要分布式锁

Java 的 synchronized 或本地 Lock 只能锁住当前 JVM。服务部署多个实例后，同一个业务可能同时在不同机器执行，因此需要 Redis 或 Redisson 实现跨实例互斥。

常见场景包括缓存重建、同一用户重复下单、定时任务抢占和热点资源更新。

### 2. Redis 分布式锁如何实现

核心命令是：

```text
SET lockKey requestId NX EX 10
```

NX 表示只有 Key 不存在时才设置，EX 设置过期时间，requestId 用来标识锁的持有者。

释放锁时不能直接 DEL，因为锁可能已经过期并被其他线程重新获取。正确做法是通过 Lua 脚本判断 Value 是否等于自己的 requestId，只有相等时才删除。

### 3. Redisson 相比手写 Redis 锁有什么优势

Redisson 封装了可重入锁、自动续期 Watch Dog、公平锁、读写锁、信号量和闭锁等能力，可以减少手写锁时出现的误删、死锁和锁过期问题。

使用分布式锁时仍然要设置合理的锁粒度、超时时间和异常释放逻辑，不能因为用了 Redisson 就忽略业务幂等。

## 七、MySQL 与 MyBatis-Plus

### 1. 商家查询如何优化

- 商家类型、关联字段建立合适索引。
- 热门商家详情使用 Redis 缓存。
- 附近商家查询使用 Redis GEO。
- 分页查询限制单页数量。
- 只查询实际需要的字段。
- 避免大数据量下的深分页。
- 名称模糊搜索量大时考虑 Elasticsearch。

需要注意，`LIKE '%关键词%'` 通常无法使用普通 B+ Tree 索引。数据量较大时可以改为前缀匹配、全文搜索或接入 Elasticsearch。

### 2. MySQL 为什么使用 B+ Tree 索引

B+ Tree 的非叶子节点只保存索引，能容纳更多索引项，树高度较低；数据集中在叶子节点，叶子节点之间有链表连接，适合范围查询和排序。

### 3. 数据库如何防止秒杀库存变成负数

可以使用带条件的原子更新：

```sql
UPDATE tb_seckill_voucher
SET stock = stock - 1
WHERE voucher_id = ? AND stock > 0;
```

通过返回影响行数判断是否扣减成功。Redis 负责高并发快速拦截，数据库条件更新负责最终兜底。

### 4. MyBatis-Plus 的优点和局限是什么

优点是简化常见 CRUD，提供条件构造器、分页插件、逻辑删除和通用 Service，能够减少 Mapper 样板代码。

局限是复杂查询、聚合统计和性能敏感 SQL 仍然需要手写 SQL；不能因为使用 ORM 框架就忽略索引、执行计划和事务设计。

## 八、智能客服与大模型

### 1. 为什么使用 LangChain4j

LangChain4j 面向 Java 应用封装了 Chat Model、AI Service、会话记忆和 Function Calling 等能力，可以把大模型接入到已有 Spring Boot 业务中，减少手写 HTTP 调用和消息拼装代码。

### 2. Qwen 如何接入项目

可以通过 DashScope 的 OpenAI 兼容接口接入：配置 API Key、Base URL 和模型名称，使用 LangChain4j 的 OpenAI Chat Model 调用 Qwen。

API Key 不应写死在代码或提交到 Git，可以使用环境变量或配置中心注入。

### 3. Function Calling 是什么

Function Calling 的流程是：

1. 后端向模型声明可用工具和参数结构。
2. 用户提出问题。
3. 模型判断是否需要调用工具。
4. 模型返回工具名称和参数。
5. 后端校验参数并真正执行方法。
6. 后端把工具结果交给模型。
7. 模型根据真实结果组织自然语言回复。

模型只负责理解意图和生成参数，不能直接访问数据库。商家查询、预约创建等动作必须由后端工具执行。

### 4. 如何防止智能客服编造商家信息

不能让模型凭训练记忆回答商家地址、价格和营业时间。应通过 Function Calling 查询 MySQL 或缓存，并在系统提示词中要求只基于工具结果回答。

如果工具查询不到数据，要明确告诉用户没有找到，不能让模型自行补全。返回给模型的商家信息也应控制字段，避免暴露无关数据。

### 5. Redis 如何保存会话记忆

可以按用户或会话 ID 设计 Key，例如：

```text
chat:memory:{userId}
```

Value 保存最近一段对话消息，设置过期时间并限制最大消息数。每次请求读取历史消息，调用模型后再保存用户消息和 AI 回复。

生产环境需要考虑：

- 消息窗口限制，防止上下文无限增长。
- Redis TTL，避免长期占用内存。
- 多设备同时聊天时的并发更新。
- 敏感信息脱敏和会话清理。

### 6. Function Calling 如何保证安全

模型传入的参数不能直接信任，后端必须重新校验：

- 当前用户是否登录。
- 商家是否真实存在。
- 预约时间格式和时间范围是否合法。
- 联系电话和地址是否有效。
- 用户 ID 必须从登录上下文获取，不能由模型传入。
- 业务写操作是否需要幂等控制。

### 7. 大模型服务失败如何处理

- 设置连接、读取和整体调用超时。
- 捕获模型异常并返回友好提示。
- 对单用户和全局调用进行限流。
- 记录 traceId、模型名称和耗时。
- API Key 使用环境变量或密钥管理服务。
- 对模型不可用场景提供普通 FAQ 或人工客服降级。
- 对输入和输出进行敏感信息过滤。

## 九、常见追问与标准回答

### 1. Redis 和 MySQL 数据不一致怎么办

先明确一致性目标。一般缓存场景追求最终一致：更新时先提交数据库，再删除缓存；删除失败时通过重试、消息补偿或定时任务再次删除。对强一致要求高的业务，不能只依赖缓存，需要以数据库或事务消息为准。

### 2. Redis 挂了会怎样

需要区分业务：商家查询可以降级到数据库，但要限流，避免数据库被打垮；秒杀场景不能简单放行，应暂停秒杀或走保护逻辑；登录业务可以暂时不可用，避免把权限判断降级为默认放行。

生产环境还应使用 Redis 主从、哨兵或集群，并配置连接池、超时和监控。

### 3. RabbitMQ 消息积压怎么处理

先监控队列深度、消费者数量和消费耗时，判断是流量突增、消费者故障还是单条消息处理变慢。然后可以临时增加消费者、优化慢 SQL、拆分耗时任务或降低生产速度。不能直接无脑增加消费者，还要确认数据库和下游服务能够承受。

### 4. 接口重复提交怎么处理

读请求一般不需要特殊处理，写请求可以使用幂等 Token、业务唯一索引或状态机。秒杀订单通过 `(user_id, voucher_id)` 唯一约束和订单状态控制；预约等业务也应该设计业务幂等键。

### 5. 如何定位线上接口慢

先通过监控和链路追踪拆分耗时：网关、Controller、Redis、MySQL、第三方服务或消息队列。再查看慢 SQL、连接池、线程池、GC、Redis 命中率和外部服务响应时间。项目中可以用 traceId 串联请求日志和消息日志。

## 十、项目不足与可优化方向

面试官问“项目还有什么可以优化”时，可以从真实问题出发回答：

- 缓存 TTL 增加随机值，降低缓存雪崩风险。
- 多级缓存增加本地缓存失效广播。
- RabbitMQ 增加死信队列、重试队列和消息补偿任务。
- 秒杀增加库存回补和预扣超时处理。
- 商家搜索从 MySQL 模糊查询升级到 Elasticsearch。
- 智能客服增加限流、敏感词过滤、审计日志和降级 FAQ。
- 预约增加取消、确认、完成等状态流转。
- 增加链路追踪和业务监控，关注缓存命中率、秒杀成功率、消息积压量和模型调用失败率。
- 对所有重要写接口增加幂等设计。
- 增加单元测试、集成测试和高并发压测。

## 十一、面试速记版

### 缓存

Cache Aside：读缓存，未命中查库并回填；写库成功后删缓存。穿透用空值或布隆过滤器，击穿用互斥锁或逻辑过期，雪崩用随机 TTL 和限流。

### 秒杀

Lua 原子完成库存判断、扣减和一人一单校验；RabbitMQ 异步创建订单；MySQL 唯一索引和条件更新做最终兜底；消费者必须幂等。

### 分布式锁

`SET NX EX` 获取锁，Value 使用唯一请求 ID；释放锁要校验持有者，不能直接删除；复杂场景使用 Redisson。

### 登录

Redis 保存共享 Session；刷新 Token 有效期；ThreadLocal 保存当前用户，请求结束后清理。

### Redis 数据结构

GEO 做附近商家，Bitmap 做签到，Set 做关注关系，Sorted Set 做点赞排行，HyperLogLog 做 UV 估算。

### 智能客服

Qwen 负责理解和生成，LangChain4j 负责接入和工具编排，Redis 保存会话记忆，Function Calling 调用真实商家查询和预约服务，后端重新校验所有参数。

### 最后一句总结

> 这个项目的核心思路是：用 MySQL 保证业务数据可靠，用 Redis 承接高频访问和并发控制，用 RabbitMQ 做异步削峰和解耦，再通过大模型和后端工具把自然语言交互接入真实业务流程。
