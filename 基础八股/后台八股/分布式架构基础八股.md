# 分布式架构基础八股（微服务 / 分布式）

> 整理日期：2026-09-08
> 方向：后台开发 / 分布式 / 微服务

---

## 一、基础概念

### Q1. 分布式系统和微服务有什么区别？

**一句话结论：** 分布式描述的是系统的部署和协作方式，微服务描述的是应用的架构拆分方式；微服务通常是分布式的，但分布式系统不一定是微服务。

| 对比 | 分布式系统 | 微服务架构 |
|---|---|---|
| 关注点 | 多个节点如何协作 | 如何按业务拆分应用 |
| 核心目标 | 提高可用性、性能和扩展性 | 独立开发、部署和扩展服务 |
| 典型组成 | 集群、分布式数据库、缓存、MQ | 用户服务、订单服务、支付服务 |
| 关系 | 范围更大 | 是分布式系统的一种常见应用方式 |

**举例：**

- 一套单体应用部署在多台机器上，属于分布式部署，但不一定是微服务；
- 一个订单系统拆成订单、库存、支付多个独立服务，通常就是微服务架构。

### Q2. 单体架构、SOA 和微服务有什么区别？

- **单体架构：** 所有业务模块部署在一个应用中，开发和部署简单，但模块耦合较高；
- **SOA：** 按业务能力拆成较粗粒度服务，通常强调企业级服务复用和统一治理；
- **微服务：** 服务粒度更细，强调独立部署、独立扩展、服务自治和故障隔离。

**面试结论：** 微服务可以看作 SOA 思想的一种更轻量、更细粒度的实践，但二者不是完全等价的概念。

### Q3. 分布式系统有哪些典型问题？

分布式系统最大的难点是：网络不可靠，而且节点可能部分失败。

常见问题包括：

- 网络延迟、丢包、超时和重试；
- 数据一致性和并发冲突；
- 消息重复、乱序和丢失；
- 服务雪崩和级联故障；
- 分布式事务和分布式锁；
- 时钟不一致、故障定位困难；
- 链路变长后，监控和排查更复杂。

因此通常需要幂等、超时、重试、限流、熔断、降级、监控和链路追踪等机制。

### Q4. 微服务拆分有哪些原则？

**参考答案：**

1. 按业务边界拆分，优先参考领域模型和团队职责；
2. 服务内部高内聚，服务之间低耦合；
3. 每个服务尽量拥有自己的数据和核心业务规则；
4. 服务需要能够独立开发、测试、部署和扩展；
5. 避免拆分过细，防止调用链过长和分布式事务复杂化；
6. 拆分前评估团队规模、业务复杂度、部署和运维能力。

**面试结论：** 微服务不是拆得越细越好，核心是边界清晰、自治能力强、通信成本可控。

## 二、分布式理论

### Q5. CAP 理论

```text
C（Consistency）一致性：所有节点同一时刻数据相同
A（Availability）可用性：每个请求都能得到响应
P（Partition tolerance）分区容错性：网络分区时系统仍能运行

结论：三者不可兼得，最多同时满足两个
- P 是分布式系统的必然要求，只能在 C 和 A 之间取舍
- CP：保证一致性，牺牲可用性（Zookeeper）
- AP：保证可用性，牺牲一致性（Eureka）
```

### Q6. BASE 理论

```text
BA（Basically Available）：基本可用
S（Soft State）：软状态，允许中间状态
E（Eventually Consistent）：最终一致性

核心思想：牺牲强一致性，换取可用性和性能
```

### Q7. 一致性协议

| 协议 | 类型 | 代表 |
|---|---|---|
| 2PC | 两阶段提交，同步阻塞 | XA 事务 |
| 3PC | 三阶段提交，加超时机制 | 较少使用 |
| Paxos | 共识算法，理论完备 | 基础理论 |
| Raft | 易理解的共识算法 | etcd、Redis Sentinel |
| TCC | 业务层两阶段 | 分布式事务 |

**Raft 核心流程：**

```text
Leader 选举 → 日志复制 → 提交
- 节点三种角色：Leader / Follower / Candidate
- 任期（term）递增
- 多数派确认即提交
```

## 三、微服务架构

### Q8. 微服务架构的组件

```text
1. 注册中心：服务发现（Nacos、Eureka、Zookeeper、Consul）
2. 配置中心：集中配置管理（Nacos、Apollo）
3. 网关：统一入口、路由、鉴权（Gateway、Zuul）
4. 服务调用：RPC/HTTP（Feign、Dubbo）
5. 熔断降级：故障隔离（Sentinel、Hystrix）
6. 负载均衡：请求分发（Ribbon、Nginx）
7. 链路追踪：调用链监控（SkyWalking、Zipkin）
8. 消息队列：异步解耦（Kafka、RocketMQ）
```

### Q9. 注册中心原理

```text
作用：
- 服务注册：服务启动时注册自身地址
- 服务发现：调用方获取服务地址列表
- 健康检查：心跳检测，剔除故障节点

选型对比：
Nacos：功能全（注册+配置），AP/CP 可切换，主流
Eureka：AP 模型，简单，已停止维护
Zookeeper：CP 模型，强一致，性能一般
```

### Q10. 网关的作用

```text
- 统一入口：客户端只访问网关
- 路由转发：按路径转发到对应服务
- 鉴权：统一认证和权限校验
- 限流：保护后端服务
- 熔断：后端异常时快速失败
- 日志与监控：统一记录请求日志
```

### Q11. 服务调用方式

| 方式 | 代表 | 特点 |
|---|---|---|
| HTTP REST | Feign、RestTemplate | 简单、通用 |
| RPC | Dubbo、gRPC | 高性能、强类型 |

**Feign 原理：** 声明式接口 + 动态代理，底层封装 HTTP 调用。

**Dubbo 原理：** Netty 传输 + 自定义协议，支持多种序列化。

## 四、容错与治理

### Q12. 熔断、降级、限流

| 机制 | 作用 | 实现 |
|---|---|---|
| 熔断 | 下游故障时快速失败，防止级联故障 | Sentinel、Hystrix |
| 降级 | 异常时返回兜底数据 | 配置降级规则 |
| 限流 | 控制请求速率，保护系统 | 令牌桶、漏桶 |

**熔断器状态机：**

```text
Closed（正常）→ 失败次数达阈值 → Open（熔断）
Open → 等待冷却时间 → Half-Open（试探）
Half-Open：成功 → Closed；失败 → Open
```

**常见限流算法：**

```text
1. 计数器：固定窗口计数，简单但边界突刺问题
2. 滑动窗口：解决边界问题，统计更平滑
3. 漏桶：恒定速率流出，平滑流量
4. 令牌桶：允许突发，恒定速率生成令牌（最常用）
```

## 五、分布式事务

### Q13. 分布式事务方案

| 方案 | 原理 | 优缺点 |
|---|---|---|
| 2PC | 两阶段提交 | 强一致，阻塞性能差 |
| TCC | Try-Confirm-Cancel | 强一致，侵入业务 |
| 本地消息表 | 本地事务+消息表 | 最终一致，实现简单 |
| 事务消息 | RocketMQ 半消息 | 最终一致，需 MQ 支持 |
| Saga | 长事务补偿 | 最终一致，无锁 |
| 最大努力通知 | 通知+重试 | 简单，适合外部对接 |

**本地消息表方案流程：**

```text
1. 业务操作 + 写消息表，同一本地事务
2. 定时任务扫消息表，发送 MQ
3. 消费方处理，回调确认
4. 超时重试保证最终一致
```

**TCC 三阶段：**

```text
Try：预留资源（冻结库存）
Confirm：确认执行（扣减冻结库存）
Cancel：回滚释放（解冻库存）
```

### Q14. 分布式 ID 方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| UUID | 简单、无中心 | 无序、过长、索引性能差 |
| 数据库自增 | 简单 | 单点瓶颈 |
| 号段模式 | 批量取号、性能好 | 依赖 DB |
| Redis 自增 | 高性能 | 持久化可靠性问题 |
| 雪花算法 | 高性能、趋势递增 | 时钟回拨问题 |

**雪花算法（Snowflake）结构：**

```text
1 bit 符号位 + 41 bit 时间戳 + 10 bit 机器 ID + 12 bit 序列号
共 64 位，毫秒级可生成百万级 ID
时钟回拨处理：等待或备用机器 ID
```

## 六、分布式锁与幂等

### Q15. 分布式锁实现对比

| 方案 | 优点 | 缺点 |
|---|---|---|
| Redis（SET NX EX） | 性能高 | 主从切换可能丢锁 |
| Zookeeper | 强一致、有顺序性 | 性能一般 |
| 数据库 | 实现简单 | 性能差 |

**Redis 分布式锁要点：**

```text
SET key value NX EX seconds   -- 原子加锁+过期
value 用唯一标识，Lua 脚本判断后删除，防止误删他人锁
Redisson 看门狗自动续期
```

### Q16. 幂等性设计

```text
场景：网络重试、消息重复消费、用户重复点击

方案：
1. 唯一索引：数据库唯一约束天然防重
2. 唯一 ID 去重：请求带 requestId，Redis/DB 记录
3. 状态机：仅允许合法状态流转（如待支付→已支付）
4. Token 机制：页面 token 一次性消费
5. 乐观锁：版本号控制并发更新
```

## 七、数据一致性

### Q17. 缓存与数据库一致性

```text
方案：
1. Cache Aside + 删除缓存（最常用）
2. 延迟双删
3. binlog 异步同步（Canal）
4. 过期时间兜底

本质：分布式场景只能追求最终一致性
```

### Q18. 数据一致性方案总结

| 场景 | 方案 |
|---|---|
| 缓存一致性 | 删缓存 + 延迟双删 + binlog |
| 跨服务数据一致 | 分布式事务（TCC/Saga） |
| 消息一致性 | 事务消息 / 本地消息表 |
| 主从延迟 | 强制读主 / 半同步复制 |
| 多机房 | 双活、数据同步工具 |

## 八、高可用与高并发

### Q19. 高并发系统设计思路

```text
1. 分层架构：接入层 → 应用层 → 服务层 → 数据层
2. 水平扩展：无状态服务多实例部署
3. 缓存：多级缓存（本地+分布式）
4. 异步：MQ 削峰填谷
5. 限流降级：保护核心链路
6. 读写分离：主库写、从库读
7. 分库分表：数据层水平扩展
8. CDN + 静态化：减少源站压力
```

### Q20. 高可用设计

```text
- 集群部署：多实例避免单点
- 故障转移：主从切换、Sentinel
- 熔断降级：故障隔离
- 异地多活：机房级容灾
- 监控告警：及时发现故障
- 灰度发布：降低发布风险
```

## 九、分库分表

### Q21. 分库分表

```text
何时需要：
- 单表数据量大（千万级+）
- 单库写入瓶颈
- 单机磁盘/连接数上限

拆分方式：
- 垂直拆分：按业务拆库（用户库、订单库）
- 水平拆分：按数据行拆分（订单表分 16 张）

分片策略：
1. 哈希取模：均匀分布，扩容困难
2. 范围分片：按时间/ID 范围，易扩容但分布不均
3. 一致性哈希：扩容影响小

工具：ShardingSphere、MyCat
```

### Q22. 分库分表带来的问题

```text
1. 跨库 join 不可用 → 冗余字段、应用层聚合
2. 分布式事务 → TCC、最终一致
3. 全局 ID → 雪花算法
4. 排序分页复杂 → 应用层合并排序
5. 扩容迁移 → 双写、渐进迁移
```

## 附：高频追问速答

| 追问 | 答案要点 |
|---|---|
| CAP 到底怎么选 | P 必须选，CP/AP 按业务取舍 |
| 熔断和降级区别 | 熔断保护调用方（快速失败），降级保护服务方（兜底） |
| 为什么选 Nacos | 注册+配置一体，AP/CP 可切换，社区活跃 |
| 雪花算法为什么有序 | 时间戳在高位，趋势递增利于索引 |
| 本地消息表 vs 事务消息 | 本地消息表无 MQ 依赖，事务消息更可靠 |
| 分布式锁为什么不用 Redis 单机 | 主从切换可能丢锁，高要求用 ZK |
| 限流和熔断区别 | 限流控流入，熔断隔离故障 |
| 如何保证消息不重复消费 | 业务幂等：唯一 ID + 状态表 |
