# 水滴 AI 智能体 / 大模型质量工程师面试复盘面经

> 面试岗位：AI 智能体 / 大模型质量工程师  
> 面试形式：技术单面（因外部打断中途结束）  
> 候选人背景：27 届硕士，具备腾讯 AI Agent 业务实习、深信服工单编排优化项目经验，熟悉大模型归因、Skill 编排、ES 多路检索、AI 辅助编码与业务流程优化。

## 一、面试概况

本次面试重点围绕以下方向展开：

- 大模型在业务文本归因场景中的选型与落地
- AI Agent 的 Skill 设计与完整调用链路
- ES 关键词检索与向量检索的多路召回优化
- 工单自动化编排、异常处理与性能优化
- 测试设计、压力测试和系统稳定性保障
- AI Coding 工具的使用边界与工程实践

整体面试偏工程落地，面试官不仅关注“用了什么技术”，也重点追问了性能数据、异常场景、状态一致性和高并发下的稳定性。

## 二、核心技术面试问答

### 1. 腾讯项目：大模型选型与 AI 归因方案

#### 1.1 业务场景

项目主要面向客服业务中的用户文本问答和问题归因，输入以自然语言文本为主，图文交互场景较少。因此，方案重点围绕大语言模型的文本理解、分类归因和结构化输出展开。

#### 1.2 模型选型

业务侧没有直接引入多模态视觉模型，主要原因包括：

- 当前业务输入以文本为主，多模态能力的实际收益有限；
- 独立引入视觉模型会增加系统复杂度、推理成本和维护成本；
- 图片与多模态识别由算法团队负责，属于后续可能接入的独立能力模块；
- 当前阶段优先保障文本归因链路的准确性、稳定性和响应效率。

实际使用的模型包括：

- 内部部署的腾讯混元 3；
- 千问 3-235B 的业务适配及微调版本。

#### 1.3 方案回答要点

在文本归因场景中，模型选型应综合考虑以下因素：

1. **业务输入类型**：以文本为主时，优先选择语言理解和指令遵循能力较强的大语言模型。
2. **部署方式**：内部部署有利于满足数据安全、权限隔离和业务定制要求。
3. **模型效果**：重点关注归因准确率、复杂问题理解能力、结构化输出稳定性和 badcase 表现。
4. **工程成本**：综合评估推理延迟、并发能力、资源占用和后续运维成本。
5. **扩展能力**：为后续接入图片、多模态识别或其他 Agent 工具预留接口。

### 2. AI Coding 工具使用：CoCoding

#### 2.1 使用情况

项目中使用过内部 AI Coding 工具 CoCoding。早期为内部无限额度，后续转为限额模式，个人额度折合约 2000 元；额度不足时可以向 Leader 申请追加。

#### 2.2 个人使用策略

AI 主要用于标准化、重复性的开发工作，核心业务逻辑仍由人工设计和审查。具体使用方式包括：

- 拆分小模块，辅助生成脚本；
- 生成提示词模板和基础代码；
- 生成测试代码和边界用例初稿；
- 辅助整理重复性配置和样板代码。

以下部分坚持人工编写和把控：

- 归因规则；
- 检索融合逻辑；
- 核心业务流程；
- 异常处理与降级策略；
- 关键数据结构和状态流转。

#### 2.3 工程实践中的边界

AI Coding 可以提高编码效率，但不能替代对业务逻辑的理解。使用生成代码后，需要重点检查：

- 是否符合现有代码规范和接口约定；
- 是否遗漏异常分支和边界条件；
- 是否存在重复请求、状态覆盖或资源泄漏；
- 是否引入不必要的依赖和隐性性能问题；
- 测试是否真正覆盖了业务风险，而不是只验证 happy path。

### 3. 腾讯项目：Agent Skill 与业务链路

#### 3.1 Skill 的整体结构

Skill 可以理解为智能体的最小可调用能力单元，通常由以下部分组成：

- Skill 文档：描述能力边界、适用场景、输入输出和调用约束；
- 执行脚本：负责具体业务逻辑、工具调用或数据处理；
- 样例提示词：帮助模型理解如何识别意图并正确调用 Skill。

一个设计良好的 Skill 应具备清晰的职责边界，输入输出尽量结构化，并能够独立测试和监控。

#### 3.2 完整调用链路

```text
用户文本输入
    ↓
意图识别
    ↓
匹配已注册 Skill
    ↓
加载业务提示词
    ↓
调用工具接口 / 检索能力
    ↓
结果处理与校验
    ↓
结构化结果返回
```

链路中需要重点关注：

- 意图识别错误导致的 Skill 误调用；
- Skill 参数缺失、格式错误或类型不匹配；
- 工具调用超时、重试和幂等问题；
- 模型输出不符合结构化协议；
- 多个 Skill 之间的上下文传递和状态一致性。

### 4. 腾讯项目：ES 多路召回工程优化

#### 4.1 召回架构

项目采用关键词召回与向量检索结合的多路召回方案：

- ES BM25 关键词召回：适合命中明确关键词、专有名词和精确业务表达；
- 向量检索：适合处理语义相近但字面表达不同的问题；
- 多路融合：综合利用关键词匹配能力和语义泛化能力。

#### 4.2 结果处理流程

多路召回后的结果主要经过以下处理：

1. 对不同路径返回的文档进行 ID 去重；
2. 根据召回路径和匹配结果计算或调整排序分数；
3. 合并多路结果；
4. 按最终分数排序并截取 Top K；
5. 将结果交给后续归因或生成模块使用。

#### 4.3 稳定性保障

针对多路检索可能带来的延迟放大和单点故障，采用了以下措施：

- 单路检索设置超时控制；
- 对可重试异常进行重试，最大重试 3 次；
- 单路超时或异常时触发熔断；
- 失败路径降级到 BM25 关键词检索；
- 通过监控观测整体链路健康度。

重点监控指标包括：

- P95 / P99 延迟；
- 整体响应时间（RT）；
- 单路检索超时率；
- 召回成功率；
- 降级触发次数；
- 多路结果融合后的有效命中率。

#### 4.4 可进一步补充的测试点

如果面试官继续深挖，可以从以下角度展开：

- BM25 与向量检索分别不可用时，系统是否仍能返回结果；
- 重试是否存在请求放大和雪崩风险；
- 同一文档被多路召回时，去重是否稳定；
- 不同召回路径的分数是否可直接比较；
- 降级后结果质量是否明显下降；
- 低置信度召回时，是否需要转人工或返回兜底提示。

### 5. 深信服项目：工单编排优化

这是本次面试中被重点深挖的项目。

#### 5.1 项目成果

优化前人工创建工单约需 3 分钟，优化后自动化流程稳定在约 15 秒，极少数跨网段重试场景会出现小幅上浮，整体性能保持稳定。

#### 5.2 核心工作流

```text
输入系统名称 / IP
    ↓
自动解析 IP
    ↓
双 IP 连通性 Ping 检测 + 磁盘资源检测
    ↓
结果判别
    ├─ 可自动修复：执行端口开放、网络修复等后台策略
    └─ 不可修复：提取报错信息 → 填充工单表单 → 生成工单草稿 → 人工审核流转
```

#### 5.3 自动修复与人工兜底

对于能够通过预置策略处理的问题，后台自动执行修复操作，例如：

- 端口开放；
- 网络连接修复；
- 其他经过安全评估的标准化操作。

对于无法自动修复的问题，流程不会直接失败，而是进入人工兜底：

1. 结构化提取错误信息；
2. 自动填充工单表单；
3. 生成工单草稿；
4. 提交人工审核；
5. 由人工确认后继续流转。

这种设计兼顾了自动化效率与操作安全，避免模型或流程引擎在不确定情况下直接执行高风险操作。

#### 5.4 测试设计

测试按照业务场景拆分，覆盖正常链路、异常链路和边界条件。主要场景包括：

- 直接输入 IP 进行检测；
- 输入系统名称并解析 IP；
- 网络异常或两端断连；
- 磁盘空间满载或接近阈值；
- 自动修复成功；
- 自动修复失败并转人工提单；
- 跨网段请求和重试；
- 接口超时、返回空值或返回格式异常。

每个场景设计十余条核心用例，重点验证：

- 流程能够正常结束；
- 异常情况下不会卡死；
- 工单状态不会错乱；
- 同一异常不会重复创建工单；
- 自动修复失败后能正确进入人工审核链路；
- 重试过程中不会重复执行不可幂等操作。

#### 5.5 压力测试思路

压力测试不采用笼统地增加并发量的方式，而是按照业务场景拆分并逐步提升压力。

具体步骤如下：

1. **按场景单独压测**：分别压测 IP 解析、网络检测、自动修复失败并提单等场景。
2. **梯度提升并发**：逐步增加并发请求数，观察系统从低负载到高负载的性能变化。
3. **关注关键资源**：重点观察接口连接池、工作流调度能力、线程池、下游依赖和数据库资源。
4. **验证保护机制**：检查超时、重试、熔断和降级是否按照预期生效。
5. **验证业务正确性**：除吞吐量和响应时间外，重点检查工单状态一致性、无重复创建和无流程阻塞。

建议记录的指标包括：

- 吞吐量和成功率；
- 平均 RT、P95、P99 RT；
- 接口超时率和重试率；
- 连接池、线程池和队列使用率；
- 工作流任务堆积量；
- 重复工单数量；
- 状态不一致和异常终止数量。

## 五、面试短板与优化方向

### 1. 测试样本量级偏小

当前测试以小场景精准测试为主，每个场景覆盖十余条核心用例，能够验证主要业务链路，但在样本规模和数据分布方面仍有提升空间。

后续可以补充：

- 批量历史工单样本；
- 不同系统、网段和设备类型的数据分层；
- 正常样本、异常样本和边界样本的比例分析；
- 自动化回归集和线上 badcase 回流集；
- 基于真实流量分布的压测数据。

### 2. 熔断降级自主实现经验偏少

当前项目中的熔断和降级更多依赖现有组件提供的能力，自己从零设计和实现降级逻辑的经验相对有限。

可以进一步准备以下内容：

- 超时、重试、熔断、限流、舱壁隔离之间的关系；
- 重试次数、退避策略和请求幂等性设计；
- 不同依赖服务的降级优先级；
- 降级结果的质量监控；
- 熔断恢复、半开状态和故障演练。

### 3. 大模型质量工程知识需要体系化

针对 AI 智能体 / 大模型质量工程岗位，还应重点补强：

- 大模型评测指标体系；
- Agent 任务成功率、工具调用成功率和流程完成率；
- 事实性、相关性、完整性和安全性评估；
- badcase 分类、归因、修复、回归和效果验证闭环；
- Prompt、模型、检索、工具和工作流的分层定位方法；
- 越权调用、敏感信息泄露和高风险工具调用测试；
- 线上监控、样本采集和评测集版本管理。

## 七、可直接复述的项目总结

### 腾讯 AI Agent 项目

我在腾讯 AI Agent 业务中主要参与文本归因、Skill 编排和检索链路优化。由于业务输入以用户文本为主，因此方案使用内部部署的大语言模型，没有在当前客服链路中直接引入多模态视觉模型。Agent 链路大致是用户输入、意图识别、匹配 Skill、加载提示词、调用工具或检索能力，最后返回结构化结果。检索侧采用 ES BM25 和向量检索多路召回，并做 ID 去重、分数融合和结果排序。为保证稳定性，对单路检索设置超时、重试和熔断，异常时降级到 BM25，重点监控 P95/P99 延迟、整体 RT、超时率和召回成功率。

### 深信服工单编排项目

我参与了工单自动化编排优化，将人工创建工单约 3 分钟缩短到稳定约 15 秒。流程从系统名称或 IP 输入开始，自动解析 IP，执行双 IP 连通性检测和磁盘资源检测，再根据结果决定是否自动修复。能够修复的问题由后台执行端口开放或网络修复策略；无法修复的问题则提取报错信息、自动填充工单表单、生成草稿并转人工审核。测试按照 IP 直测、系统名解析、异常断连、磁盘满载和自动修复失败等场景拆分，重点验证异常不阻塞、状态一致和不重复创建工单。压测时也按业务场景分开进行，逐步提升并发，观察连接池、工作流调度、超时熔断和高并发下的状态一致性。

## 八、复习建议

建议面试前重点准备以下三类内容：

1. **项目细节**：每个项目都要能讲清背景、个人职责、技术方案、难点、指标和最终收益。
2. **质量体系**：准备大模型评测指标、Agent 评测方法、badcase 闭环和线上质量监控的完整回答。
3. **稳定性与测试**：重点掌握超时、重试、熔断、降级、限流、幂等、状态一致性以及场景化压测方法。

面试回答建议遵循“业务背景 → 方案设计 → 个人工作 → 测试验证 → 数据结果 → 风险与改进”的顺序，既能体现技术深度，也能突出实际落地能力。
