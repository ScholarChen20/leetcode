### 实习经历
1) 智能客服项目做了多久，整个流程说下
> 答：先说时长和你的角色（做了多久、几个人、你负责哪块），再讲链路：用户接入（多渠道/工单）→ 意图识别与分流 → RAG 检索 + LLM 生成 → 兜底转人工 → 会话质检与 badcase 回流。每一环补一句"我们是怎么做的、瓶颈在哪"，比如意图识别用规则 + 小模型双路、检索用混合召回 + rerank、转人工率靠置信度阈值控制。

2) 广告投放平台使用的是什么AI架构
> 答：整体是"Workflow 主干 + 单点 ReAct + RAG"：外层用 DAG 编排（素材生成 → 文案 → 建计划 → 数据回收），固定步骤不浪费 LLM 推理；需要探索的节点（选人群、定出价、异常归因）用 ReAct 让模型自己决定调哪些工具；素材规范和投放知识用 RAG 注入；工具层封装投放平台 API。强调"为什么不全用 Agent"——成本、可控性和可审计。

3) ReAct原理讲下
> 答：Reasoning + Acting 交替：把任务和工具列表放进 system prompt，模型先输出 Thought 分析当前状态，再输出 Action（工具名 + 参数），框架执行工具拿到 Observation，把 Observation 追加回上下文进入下一轮，直到模型输出 Final Answer。生产的三个加固点：用原生 Function Call 替代文本解析、设最大步数防死循环、对工具结果做长度裁剪防上下文爆炸。

4) 工具调用流程
> 答：模型输出结构化调用意图（tool_name + arguments）→ 框架按 schema 校验参数（类型、必填、枚举）→ 不合法则回填默认值或让模型重填 → 鉴权与配额检查 → 执行（带超时、重试、熔断）→ 结果序列化并裁剪 → 追加到上下文 → 模型继续推理。失败要区分可重试（网络超时）与不可重试（参数错误、无权限），后者直接把错误信息回给模型让它改。

5) 工具调用过程中大模型和智能体分别做了什么
> 答：大模型负责"决策"——判断要不要调、调哪个、参数填什么、拿到结果后怎么推理下一步；智能体（框架）负责"执行与治理"——解析校验参数、真正发请求、处理超时重试熔断、维护上下文与状态、记录链路、做权限与幂等。一句话：模型出主意，框架干活并兜底。

6) 上下文工程有哪些
> 上下文工程对进入上下文窗口的信息做全生命周期管理，主要包括：检索筛选（RAG+重排）、上下文压缩（滑动窗口、摘要、结构化抽取）、分层记忆（短期/工作/长期记忆）
> 、上下文编排、工具返回值裁剪、任务隔离拆分；目标是控制token开销，减少无关噪声，缓解窗口溢出和幻觉问题

### 项目经历
1. 美食点评中的数据一致性如何保证
> 答：分场景给方案——①同一库多表：本地事务 + 合理隔离级别，注意 @Transactional 的失效场景（自调用、异常被吞、非 public）；②跨服务：最终一致，用本地消息表或事务消息 + 消费端幂等 + 定时重试补偿；③缓存与 DB：Cache Aside + 延迟双删 + 过期时间兜底；④兜底：定时对账任务比对差异并修正。答题时一定要说"不一致的窗口有多长、能容忍什么程度"，这是加分点。

2. 为什么要先更新数据库再删缓存
> 答：如果先删缓存再更新 DB，删除之后到更新提交之间若有读请求，会把**旧值**重新加载进缓存，等 DB 更新完成后，缓存里就是长期脏数据。先更新 DB 再删缓存虽然理论上也有极小概率脏读（读请求刚好在删之前回填），但概率低得多，再叠加延迟双删（更新后延迟 N 毫秒再删一次）和过期时间兜底，工程上够用。另外"更新缓存"不如"删缓存"，因为并发更新时写入顺序不可控。

3. 本地缓存和redis缓存多实例情况下同步如何保证一致（短TTL兜底+MQ广播清除本地缓存）
> 答：短 TTL 兜底 + MQ 广播失效：数据变更时先改 DB、再删 Redis，然后发 MQ 广播消息，各实例订阅后删除自己 JVM 里的本地缓存 key，靠广播延迟内的短 TTL 兜住不一致窗口。本地缓存只放能容忍秒级不一致的数据（配置、字典、类目），资金与库存类不放。极端场景再用版本号或时间戳校验，发现版本落后就回源。

4. 优惠券防止超卖如何实现（lua脚本校验购买资格和库存预扣，MQ异步下单）
> 答：Redis 层用 Lua 脚本原子完成"校验资格 + 预扣库存"，避免"先查再扣"的竞态；扣减成功才发 MQ 异步落库下单，快速返回用户；消费端按唯一键幂等（同一用户同一券只处理一次），DB 层再加 where stock > 0 的乐观扣减兜底，防止 Redis 与 DB 不一致。失败或超时要有补偿：定时核对 Redis 预扣量与 DB 实扣量，差异回滚库存。

5. lua脚本实现库存预扣和购买校验使用什么数据结构（hash+set去重）
> 答：hash 存活动维度的库存与配置（field 如 total/remain，value 数值），set 存已领用户做去重（SISMEMBER 判断资格）。两个 key 放在同一个 slot（用 hash tag）保证 Lua 脚本能原子操作。

6. 购买人员多set集合不高效怎么办（全塞进hash实现，但是查询用户下单效果较低）
> 答：先判断瓶颈是内存还是查询。方案：①把用户集合按活动/分片拆成多个小 set（或用 hash tag 分桶），单 key 元素数下降，SISMEMBER 和内存都改善；②用 bitmap 按用户 ID 位映射（连续 ID 场景省内存），或布隆过滤器做前置判断（有误判，最终靠 DB 唯一索引兜底）；③热窗口放 Redis、全量落 DB，靠唯一索引保证不重复。全塞 hash 的问题是查询退化成遍历，不推荐。

7. 多维度滑动窗口限流怎么实现
> （用户、IP、全局各一个 Key，zset实现，score是时间戳，member 是“时间戳 + 唯一请求 ID”，避免同一毫秒内请求相互覆盖)
> 补充：一次请求要依次校验多个维度的 key，任一超限即拒绝（注意顺序：先查全局再查细粒度，减少无效写入）；用 Lua 把 ZREMRANGEBYSCORE 清理、ZCARD 判断、ZADD 写入合成原子操作；key 设过期时间自动清理冷数据；阈值可按接口分级配置。
8. Java中链表是哪个类，是否是线程安全，为什么不安全？
> LinkedList：底层是双向链表，非线程安全；因为多线程并发修改有并发问题；想要线程安全，可以用Collections.synchronizedList包装；
> 或者并发场景优先用CAS无锁的ConcurrentLinkedQueue/ConcurrentLinkedDeque
9. Java中队列有哪些？
> LinkedList(单线程使用)；ConcurrentLinkedQueue(并发无锁队列,CAS无所非阻塞)；
> 阻塞队列：LinkedBlockingQueue、ArrayBlockingQueue、PriorityBlockingQueue、DelayQueue（订单超时使用）、SynchronousQueue
10. hashmap的put操作流程
> 答：①算扰动后的 hash（h ^ (h >>> 16)）；②(table 为空先初始化) 用 (n-1) & hash 定位桶；③桶空则直接放新节点；④是树节点走红黑树插入；⑤否则遍历链表，key 相同则覆盖 value 并返回旧值，否则尾插；⑥插入后若链表长度 ≥8 且容量 ≥64 则树化（容量不足优先扩容）；⑦++size > threshold 则扩容（容量翻倍 + 高低位拆分迁移）。
11. hashmap和concurrentHashMap区别
> 后者线程安全；jdk7分段锁segment（把哈希表分为多段，不同段可以并发操作）；jdk8使用synchronized+CAS实现线程安全，链表转红黑树优化查询性能
12. currentHashMap能不能存null,为什么？
> 不能存null，key和value都不能为null；因为get方法返回null；get(key)返回为null分不清是不存还是值本身为null,并发场景下容易有歧义
13. redis挂了怎么办
> 最大风险是缓存失效，流量全部达到DB造成数据库雪崩；
> 第一部署高可用：哨兵或者集群，自动主从切换
> 第二熔断降级和限流，异常时挡住流量
> 第三是搭配本地二级缓存兜底。同时开启RDB+AOF持久化，方便故障恢复
14. redis的主从同步原理
> 主从同步分为全量同步和增量同步；全量同步：主节点生成快照文件RDB，传给从节点，从节点加载RDB文件；增量同步：主节点将写命令发送给从节点，从节点执行命令
> 补充：首次同步或 offset 差距超出 replication backlog 才走全量；全量期间主节点把新写命令缓存（repl buffer）后补发；之后靠 backlog + offset 续传增量。还有 repl-diskless 无盘复制，避免落地大 RDB。
15. 主从模式中从节点选为主节点的策略是什么
> 主从模式没有自动选主机制，需要人工接入（执行replicaof no one)；人工挑选从节点时优先replica-priority,相同情况下选复制偏移量最大、数据最新的从）
16. 哨兵模式选主节点的策略
> 哨兵先判断主客观下线，Raft协议集群投票选出领头哨兵；领头哨兵按照从节点优先级、复制偏移量、runid的顺序选出最优从节点提升为新主）
17. MVCC是什么（并发多版本控制靠undo log保存数据多版本、ReadView控制可见性，实现普通select的无锁快照读；写操作依然会加行锁）
> 只在RC(读已提交)、RR(可重复读)隔离级别生效
> 补充两者差异：RC 每次 SELECT 都新建 ReadView（所以能读到别人已提交的新数据），RR 在事务内复用第一次的 ReadView（所以可重复读）。串行化不走 MVCC。
19. 快照读和当前读区别
> 快照读：普通select,不加锁，读历史版本；
> 当前读：update/delete/insert/select for update/lock in share mode，加锁，读最新版本
20. select 和select for update区别
> 普通select是快照读，走MVCC,不加锁，读快照数据；select for update当前读，加排他锁，读最新数据，防止其他事务修改这条数据；
> 都是行级锁：共享锁是读锁，读读可以并发，读写互斥；排他锁是写锁，读写、写写都互斥，同一行只能有一个排他锁
> 补一句关键：for update 必须命中索引，否则 InnoDB 会退化成锁范围甚至锁表；业务上用于"读-改-写"必须互斥的场景，如扣库存、改状态机。
21. synchronized和ReentrantLock区别
> synchronized是JVM内置锁，自动释放，只能阻塞等待，不支持公平锁、超时、中断；
> ReentrantLock基于AQS的API锁，手动释放锁，支持非阻塞加锁、超时、可中断、公平锁。二者都是可重入锁
22. 线程池有哪些参数？（核心线程数、最大线程数、空闲存活时间、时间单位、阻塞任务队列、线程工厂、拒绝策略）
> 答：七个，按提交顺序串起来讲：核心线程未满就新建核心线程；满了进工作队列；队列满才新建非核心线程直到 max；再满就触发拒绝策略。线程工厂用于命名便于排查，空闲存活时间只对非核心线程生效（除非 allowCoreThreadTimeOut）。
23. 当任务大于最大线程数怎么办
> 超过最大线程数时，执行拒绝策略；
> 追问：任务数大于核心数小于最大线程数：核心线程已满，进阻塞队列，队列满了，新建非核心线程数）
24. 为什么不推荐Executors快捷创建线程池（默认队列无界或最大线程无限，容易报OOM，生产手动new ThreadPoolExecutor)
> 答：newFixedThreadPool / newSingleThreadExecutor 用无界 LinkedBlockingQueue，任务堆积不会拒绝，直接 OOM；newCachedThreadPool / newScheduledThreadPool 最大线程数是 Integer.MAX_VALUE，线程数失控同样 OOM。所以生产上手动 new ThreadPoolExecutor，显式指定有界队列、线程数上限和拒绝策略，并给线程命名。
25. 拒绝策略有哪些（抛异常；直接丢掉任务，不报错；丢掉队列最老任务，尝试提交当前任务；交给提交任务的调用线程自己执行）
> 答：AbortPolicy（抛 RejectedExecutionException，默认）、DiscardPolicy（静默丢弃）、DiscardOldestPolicy（丢队列最老的再重试提交）、CallerRunsPolicy（交给提交线程执行，天然形成反压，不丢任务但会拖慢上游）。自定义策略常见做法是落库/写 MQ 稍后重试。
26. 阻塞队列有哪些
> ArrayBlockingQueue（有界数据、单锁）\LinkedBlockingQueue（链表，无界）\SynchronousQueue\PriorityBlockingQueue(优先级）\DelayQueue（延迟）
> 补充：LinkedBlockingQueue 默认容量是 Integer.MAX_VALUE 才叫"名义无界"，可传容量变有界；SynchronousQueue 不存元素、直接移交，配合 CachedThreadPool 使用；DelayQueue 元素需实现 Delayed，适合订单超时关闭。
27. volatile了解吗
> 是java关键字，不能保证原子性（count++这种读改写复合操作，拦不住并发问题，需要锁）；1.保证可见性（一个线程修改volatile变量，会立刻刷回主内存；其他线程读取时，直接从主内存读，而不是本地缓存，别的线程马上能看到新值）
> 2.禁止指令重排序（volatile可以加内存品屏障，阻止特定重排序）
28. 和synchronized区别
> volatile轻量，无锁，只能修饰变量；synchronized保证可见性、有序性、原子性，会阻塞；
> 典型用法：状态标志位（while(!stop)）、双重检查锁的单例（instance 必须 volatile 防重排序）、一次性安全发布。

### 手撕
> 实现一个链表. 按下面类实现相关方法.
```text
/**
     * Your MyLinkedList object will be instantiated and called as such:
     * MyLinkedList obj = new MyLinkedList();
     * int param_1 = obj.get(index);
     * obj.addAtHead(val);
     * obj.addAtTail(val);
     * obj.addAtIndex(index,val);
     * obj.deleteAtIndex(index);
*/
```
> 答：核心是**双哨兵（dummyHead + dummyTail）+ size**，所有操作先统一做 index 合法性校验，再走"找前驱 → 插/删"的同一套模板，头尾插入天然统一，能省掉大量空指针判断。各操作查找 O(n)、改链 O(1)。
>
> ```python
> class MyLinkedList:
>     def __init__(self):
>         self.head = Node(0)          # 哨兵头
>         self.tail = Node(0)          # 哨兵尾
>         self.head.next, self.tail.prev = self.tail, self.head
>         self.size = 0
>
>     def _node(self, index):          # 返回下标 index 的节点；index==size 时返回 tail
>         if index < self.size // 2:
>             cur = self.head.next
>             for _ in range(index):
>                 cur = cur.next
>         else:
>             cur = self.tail
>             for _ in range(self.size - index):
>                 cur = cur.prev
>         return cur
>
>     def get(self, index):
>         if index < 0 or index >= self.size:
>             return -1
>         return self._node(index).val
>
>     def addAtHead(self, val):
>         self.addAtIndex(0, val)
>
>     def addAtTail(self, val):
>         self.addAtIndex(self.size, val)
>
>     def addAtIndex(self, index, val):
>         if index > self.size:            # 超过长度直接忽略（LeetCode 语义）
>             return
>         index = max(index, 0)
>         nxt = self._node(index)          # 插在 nxt 之前
>         prev = nxt.prev
>         node = Node(val)
>         prev.next, node.prev = node, prev
>         node.next, nxt.prev = nxt, node
>         self.size += 1
>
>     def deleteAtIndex(self, index):
>         if index < 0 or index >= self.size:
>             return
>         cur = self._node(index)
>         cur.prev.next, cur.next.prev = cur.next, cur.prev
>         self.size -= 1
> ```
>
> 易错点：①index 越界到处都要判；②addAtIndex 的 index == size 是合法的（追加到尾部），index > size 才忽略；③双哨兵后 `_node(size)` 返回 tail 正好用于尾插；④按 index 从近的一端遍历，把查找降到 O(n/2)。
