> **答题公式**：一句话结论 → 分点展开（2~4 点，带对比）→ 工程落地/坑 → 主动挂一句"我项目里是怎么用的"。

## 1. 多线程和多进程的区别

**一句话**：进程是**资源分配**的基本单位，线程是 **CPU 调度**的基本单位；进程有独立地址空间，同一进程内的线程共享地址空间。

| 维度 | 多进程 | 多线程 |
|---|---|---|
| 地址空间 | 独立，互不影响 | 共享代码段/数据段/堆/文件描述符 |
| 私有部分 | 全部私有 | 栈、寄存器、PC、errno、信号屏蔽字 |
| 通信方式 | IPC：管道/共享内存/消息队列/socket | 直接读写共享变量（但要加锁） |
| 创建/切换开销 | 大（切页表 CR3、TLB 失效） | 小（共享页表，只切栈和寄存器） |
| 容错 | 一个进程崩了不拖累别人 | 一个线程段错误整进程挂 |
| 调试 | 相对容易 | 竞态、死锁、难复现 |

**怎么选（这才是面试官想听的）**
- **CPU 密集** → 多进程，能吃满多核；
- **IO 密集** → 多线程/协程，等待期间切换出去；
- **Python 特有**：GIL 让同一时刻只有一个线程执行字节码，多线程**无法并行计算**，CPU 密集必须用 `multiprocessing`（或 C 扩展/numpy 里 `release GIL` 的部分）；IO 密集用线程/`asyncio` 反而更快，因为 IO 时会释放 GIL。

**加分**：真正的开销差在**切换成本**——线程切换要陷入内核保存上下文，但 TLB 和 Cache 还有局部性；进程切换还要换页表，TLB 直接 flush，缓存全凉；协程是用户态切换，最轻，适合十万级并发连接。

**易错**：别说"线程比进程快"，要说"线程通信和切换更便宜，但没有隔离性"。

## 2. Java 中的 GC 是什么

**一句话**：GC 是 JVM 自动回收**堆上不可达对象**内存的机制，核心是**可达性分析**判断存活 + **分代收集**降低开销，代价是 STW 停顿。

**① 怎么判断对象死了**
- 引用计数：实现简单，但**解决不了循环引用**（Python 是引用计数 + 标记清除补漏），Java 不用它当主算法；
- **可达性分析（Java 采用）**：从 **GC Roots** 出发做图遍历，走不到的对象即可回收。GC Roots 包括：虚拟机栈中局部变量表引用的对象、方法区静态属性/常量引用的对象、JNI 引用的对象、活跃线程、锁对象等。
- 四种引用：强（不回收）、软（内存不足才回收，做缓存）、弱（下次 GC 必回收，ThreadLocalMap/WeakHashMap）、虚（回收时收到通知，管直接内存）。

**② 分代假说与内存布局**
- 假说：绝大多数对象朝生夕死，熬过越多次 GC 的对象越难死；
- **新生代**（Eden : S0 : S1 = 8:1:1）用**复制算法**，只牺牲 10% 空间，无碎片；对象优先分配在 Eden，Minor GC 后存活对象在 S0/S1 间来回复制，**年龄到阈值（默认 15）晋升老年代**，大对象直接进老年代避免反复复制；
- **老年代**对象存活率高，复制不划算，用**标记-清除**（有碎片）或**标记-整理**（要移动对象）。

**③ 收集器演进（能报出名字 + 一句特点就够）**
Serial / ParNew（新生代，复制）→ Parallel Scavenge（吞吐优先）→ CMS（老年代并发标记清除，**初始标记、并发标记、重新标记、并发清除**，低停顿但有浮动垃圾和碎片）→ **G1**（堆切成 Region，按回收价值排序，"可预测停顿模型"，用 Remembered Set 解决跨 Region 引用、SATB 解决并发漏标）→ **ZGC**（染色指针 + 读屏障，停顿亚毫秒级，与堆大小基本无关）。

**④ 为什么必须 STW**
并发标记时用户线程还在改引用，会出现"**对象消失**"（三色标记的漏标：黑对象新增指向白对象的引用，且灰对象到白的路径被断开）。CMS 用增量更新（Incremental Update），G1 用原始快照（SATB）来修，但**初始标记和重新标记阶段必须停**。

**加分**：Java 调优的本质是"**在吞吐和停顿之间选点**"——堆大则 GC 次数少但单次停顿长；G1 的 `MaxGCPauseMillis` 就是给这个权衡设个目标值。

## 3. Agent 的 Memory 机制

**一句话**：Memory 是让 Agent **跨轮次、跨会话保留信息**的机制，本质是解决"上下文窗口有限 + LLM 无状态"这两件事。

**① 分层（按生命周期讲最清楚）**

| 层 | 存什么 | 载体 | 管理手段 |
|---|---|---|---|
| **工作记忆/短期** | 当前对话、任务中间状态、工具返回 | 直接放 context / LangGraph State | 滑窗、摘要压缩、token 预算、关键信息抽取 |
| **长期·情景记忆** | 发生过的事、历史会话摘要 | 文档库/DB + 向量索引 | 时间衰减、按会话归档 |
| **长期·语义记忆** | 用户画像、偏好、事实性知识 | 向量库 / KV / 知识图谱 | 去重、冲突时更新而非追加 |
| **程序记忆** | 成功的做法、工具用法、失败教训 | Prompt/Skill 库、few-shot 样例库 | 成功轨迹沉淀（Reflexion 式） |

**② 完整生命周期：写入 → 检索 → 更新/遗忘**
- **写入**：从对话里抽取结构化事实（LLM 抽取 → schema 校验），做**去重和冲突合并**，并打**重要度分**；
- **检索**：混合召回（向量 + 关键词/时间过滤），打分 = 相似度 × 时间衰减 × 重要度，取 top-k 注入 context；
- **遗忘**：TTL、LRU、低重要度淘汰、容量上限滚动淘汰——**不遗忘的记忆库就是垃圾场**。

**③ 工程实现**
- 框架自带：**LangGraph Checkpointer**（按 `thread_id` 持久化 State，支持中断/恢复/时间旅行）、LangChain 的 `ConversationSummaryBufferMemory`；
- 专用方案：**Mem0**（抽取-合并-检索的托管记忆层）、**MemGPT/Letta**（把 context 当"内存"、外部存储当"磁盘"，做分页换入换出）；
- 存储：Redis（短期 + 会话锁）、Postgres + pgvector（长期 + 元数据过滤）、Milvus/Qdrant（大规模向量）。

**④ 坑（务必说一条）**
- **记忆污染**：模型自己编的结论被写回记忆，之后越用越偏 → 加写入门控，只允许高置信度/用户显式确认的信息入库；
- **检索噪声**：召回不相关记忆反而带偏 → 门槛分 + rerank；
- **隔离**：多用户/多租户必须用 `user_id/session_id` 做 namespace，否则串数据是事故级 bug。

**加分**：Memory ≠ 把历史全塞进 context。判断标准是"**这条信息未来还会被用到吗**"，会→沉淀成结构化记忆，不会→摘要后丢弃。上下文工程（Context Engineering）比堆窗口更有效。

## 4. 多线程同步

**一句话**：同步就是保证并发访问共享可变状态时满足**原子性、可见性、有序性**这三个性质。

**① 手段清单（按顺序讲，从重到轻）**
- **互斥锁**：Java `synchronized`（对象头 Mark Word 指向 Monitor，锁升级：偏向→轻量级 CAS→重量级）；`ReentrantLock`（基于 AQS，支持可中断、超时、公平锁、多 Condition）；Python `threading.Lock/RLock`；
- **读写锁**：`ReentrantReadWriteLock`、`StampedLock`，读多写少场景吞吐提升明显；
- **条件变量**：`wait/notify`、`Condition`、Python `threading.Condition`——实现生产者-消费者，**wait 必须在 while 循环里判断条件**（防虚假唤醒）；
- **信号量**：`Semaphore`，本质是限流/控制并发度；
- **原子类/CAS**：`AtomicInteger`、`LongAdder`，无锁自旋，代价是 ABA 问题（用 `AtomicStampedReference` 加版本号解决）和 CPU 空转；
- **volatile**：保证可见性 + 禁止指令重排，**不保证原子性**（`i++` 仍然不安全），是**双重检查锁单例**能成立的关键；
- **并发容器与工具**：`ConcurrentHashMap`（CAS + 桶级 synchronized，读无锁）、`BlockingQueue`（天然的生产者-消费者）、`CountDownLatch/CyclicBarrier/CompletableFuture`。

**② 底层支撑**：Java 内存模型的 **happens-before** 规则（程序次序、锁、volatile、线程 start/join、传递性）——回答"为什么加了锁就可见了"用这个。

**③ 死锁**
- 四个必要条件：互斥、请求并保持、不可剥夺、循环等待；
- 破坏方式：**固定加锁顺序**（最实用）、`tryLock` 带超时、一次性申请全部资源、减少锁粒度/锁分离；
- 排查：`jstack` 直接打印死锁环、`pstack`、Python 用 `faulthandler`/超时。

**易错**：不要在锁里做 IO、RPC、日志刷盘（锁持有时间暴涨 QPS 腰斩）；锁要覆盖**整个临界区**，加锁粒度不是越小越好。

## 5. 多进程怎么同步

**一句话**：进程地址空间独立，所以同步必须**借助内核对象或共享介质**，本质就三类——共享内存 + 信号量、消息传递、文件/分布式锁。

**① 共享内存 + 信号量（性能最高）**
`mmap` / `multiprocessing.shared_memory` / `Value`、`Array` 拿到共享区域，再用 **POSIX 具名信号量**或互斥量做互斥。注意 Python 的 `multiprocessing.Lock/Semaphore` 底层就是 POSIX 信号量，可以跨进程用。坑：共享内存要自己管生命周期（不释放会泄漏到 `/dev/shm`），结构体对齐全靠自己保证。

**② 消息传递（最省心）**
- `pipe` 管道（父子进程、半双工）、`Queue`（multiprocessing.Queue，内部靠 feeder 线程 + 管道 + 锁，**天然串行化，不需要额外加锁**）；
- 消息队列（RabbitMQ/Kafka/Redis Stream）：解耦 + 削峰 + 可跨机器，代价是延迟和运维。
- 原则：**能用消息传递就别用共享内存**，共享状态是并发 bug 的温床。

**③ 文件锁 / 系统级**
`fcntl.flock`、`fcntl.lockf`（Windows 用 `msvcrt.locking`）做单机互斥；`signal` 做通知；`Manager()` 的 dict/list 看着像共享变量，实际是 **RPC 到 manager 进程**，每次读写都序列化，**慢一个数量级**，只适合小数据。

**④ 跨机器（分布式锁）**
Redis `SET key val NX PX 30000`（**必须带过期 + 唯一 value + Lua 脚本原子释放**，业务没执行完要续期），或 Redlock；更严谨用 **ZooKeeper 临时顺序节点**（会话断开自动删、天然避免惊群）或 etcd lease。坑：锁过期而业务还没跑完 → 需要 **fencing token**（带单调递增版本号，让存储端拒绝旧持有者）兜底。

**选型一句话**：大数据量共享 → 共享内存 + 信号量；控制流/任务分发 → 队列；单机文件互斥 → 文件锁；跨机 → 分布式锁。

## 6. 说说 RAG

**一句话**：RAG = 检索 + 生成，把"模型不知道的、最新的、私有的"知识**在推理时**检索出来塞进 prompt，让模型基于证据回答，而不是靠参数记忆。

**六步链路（按顺序讲，这是骨架）**

| 步骤 | 做什么 | 关键细节/坑 |
|---|---|---|
| 1. 索引 | 文档解析 → 分块 → embedding → 建索引 | 分块要带**重叠**和**标题/层级元数据**；表格、扫描件先做 OCR/结构化，直接切会碎 |
| 2. Query 预处理 | 改写、多角度扩写、HyDE、指代消解 | 多轮对话里"它"指谁，必须靠改写补全 |
| 3. 召回 | 向量（语义）+ BM25（关键词）双路 | **query 和建库必须用同一个 embedding 模型**，否则向量空间对不上 |
| 4. 融合 + 精排 | RRF 融合 → Cross-Encoder rerank | 向量分和 BM25 分**不可比**，不能加权平均；rerank 只留 Top-3~5 |
| 5. 拼 prompt | 上下文 + 约束指令 | 明确"只依据资料回答，资料不足就说不知道"；控制上下文长度防"中间遗忘" |
| 6. 生成 + 溯源 | 输出答案 + 引用编号 | 便于人工核验，也是降低幻觉的强约束 |

**优化按层说（面试官问"怎么优化"就按这五层背）**：索引层改分块/加元数据/多粒度父子块；查询层加改写与多 query；召回层混合检索 + 图检索 + 权限过滤；重排层加 rerank + MMR 去冗余；生成层加引用约束 + 拒答门控。

**加分**：RAG 的瓶颈**80% 在检索不在生成**。上线要看两个指标：`context recall`（该给的资料给到了吗）和 `faithfulness`（答案是否忠于资料），前者低是检索问题，后者低是 prompt/模型问题。

## 7. RAG 解决了什么问题

**一句话**：解决 LLM 的**三个固有短板**——知识过期、私域空白、无依据时爱编。

1. **时效性**：训练截止日之后的事模型不知道；RAG 换索引就能立刻更新，**不用重训**；
2. **私有知识**：公司文档、客服话术、内部规章从没进过训练集，对模型是完全空白；
3. **幻觉**：给证据后模型从"编"变成"读"，幻觉显著下降；
4. **可溯源**（常被忽略但 To B 刚需）：答案能标来源，金融/医疗/法务要合规审核；
5. **成本与权限**：比 SFT 便宜得多，且能复用文档 ACL 做**行级权限过滤**（不同角色召回不同内容）。

**边界也要说清（这是加分项）**：RAG 只能补**知识**，补不了**能力**——它不能让模型学会新的推理范式或表达风格，多跳推理、跨文档归纳仍然弱；这类需求要靠 SFT/RL 或 Agent 多步检索。

## 8. RAG 和 Agent 的记忆有什么区别

**一句话**：RAG 是"**查外部资料**"，只读、权威、共享；Memory 是"**记自己的经历**"，可读写、私有、会衰减。

| 维度 | RAG | Agent Memory |
|---|---|---|
| 数据来源 | 已有的静态文档/知识库 | Agent 与用户交互过程中**产生**的信息 |
| 写入 | 离线批处理建索引，运行时不写 | **在线实时写入**，边聊边存 |
| 读写 | 只读 | 读 + 写 + 改 + 删 |
| 内容性质 | 客观事实、权威知识 | 主观经历、用户偏好、任务状态、教训 |
| 生命周期 | 长期稳定，版本化管理 | 短期为主，带时间衰减和淘汰 |
| 正确性 | 相对可信 | **可能被模型自己污染**，需要写入门控 |
| 隔离粒度 | 按知识库/租户 | 按 `user_id` / `session_id` |
| 触发方式 | 每次提问必触发 | 按需触发（判断"要不要回忆"） |

**关系（一句话收尾）**：二者**技术栈复用但语义不同**——Memory 常用向量检索来实现，本质是"在 RAG 的基础上加了写入和更新"；工程上放在同一个向量库里、用 **collection/namespace 隔离**，检索时一路走知识、一路走记忆，最后按 token 预算分配给谁。

**加分**：真正的区别是**冲突处理**——RAG 里两份文档矛盾，可以让模型自己权衡并引用；记忆里新旧信息矛盾，必须**以新覆盖旧**（否则 Agent 会人格分裂）。所以 Memory 要有 `update` 语义，而不是只 append。

## 9. 平时用的多的 AI 工具是啥

**答题策略**：别报菜名，按"**场景 → 工具 → 为什么**"三层说，最后落到方法论，体现你是"有工作流的"，不是"跟风的"。

- **写代码**：**Claude Code / Codex** 做跨文件重构、写测试、读陌生仓库（它自己会 grep、跑测试、看报错再改）；IDE 内的 Copilot/Cursor 做行级补全和小函数；两者分工是"**大任务交给 agent，肌肉记忆交给补全**"；
- **日常问答与调研**：ChatGPT / Claude 做长文理解和方案对比，DeepSeek 做中文和数学题，Kimi 读长 PDF；
- **Agent 开发**：LangGraph（有状态图 + checkpoint，可控性最好）、LlamaIndex（RAG 全家桶）、AutoGen（多智能体）；
- **低代码验证**：Dify / Coze / n8n，用来半天内验证一个想法、或者做非技术同事能改的 demo；
- **RAG 基建**：RAGFlow（带版面解析，中文文档友好）、Milvus/Qdrant/pgvector、bge-m3 做 embedding、bge-reranker 做精排；
- **服务与评测**：vLLM 做推理加速（PagedAttention + 连续批处理）、Ragas / LangSmith / LangFuse 做链路追踪和效果评测；
- **本地**：Ollama 跑小模型做隐私数据。

**收尾一句**：工具选型我看三点——**能不能接进现有链路、出问题能不能观测、换模型成本高不高**，所以框架层我倾向薄的（LangGraph 而不是全家桶），避免被绑死。

## 10. Codex 和 Claude Code 的区别

**一句话**：都是"能自己改代码的 CLI Agent"，区别在**执行位置与信任模型**——Codex 偏"云端沙箱里跑任务"，Claude Code 偏"在你本地仓库里边读边改、每步向你报备"。

| 维度 | Codex（OpenAI） | Claude Code（Anthropic） |
|---|---|---|
| 形态 | CLI + IDE 插件 + 云端任务，可异步派发 | CLI（终端里跑）+ IDE 插件，本地进程为主 |
| 运行环境 | 强隔离沙箱，网络默认受限，适合"关起来跑" | 直接操作你的工作区，用 git 做安全网 |
| 交互风格 | **任务式**：给一个明确 issue，它跑完给 diff/PR | **对话式**：边探索边汇报，中途可打断、可纠正 |
| 上下文策略 | 仓库索引 + 精准取文件，偏"少而准" | 大量 grep/read 主动探索，偏"广而深"，会自己找证据 |
| 安全模型 | 沙箱 + 网络白名单，默认不信任代码 | 权限确认 + 可配置 allowlist，**信任靠审批** |
| 强项 | 并行派发多个任务、CI 里跑、批量化 | 大型陌生仓库的深度理解、长链路重构、debug 推理 |
| 弱项 | 交互性弱，环境不一致时容易跑偏 | token 消耗大、本地误改风险要靠 git 兜 |

**怎么用（加分）**：需求明确、可自动验证（跑测试就知道对错）→ 交给 Codex 异步跑；需要"想清楚再动手"、跨十几个文件的架构级改动 → Claude Code 带着我一步步来。共同点是**都要有测试和 git 兜底**，因为 agent 的自信心和正确率不成正比。

**易错**：不要背参数量、价格、版本号（一说错就露怯），讲**任务粒度、上下文策略、信任边界**这三个维度最稳。
