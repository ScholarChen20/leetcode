## AI算法
1. 自我介绍
> （略）30 秒：学校/专业 + 微调项目或 RAG 项目（你负责哪块、量化结果）+ 技术栈关键词 + 投递理由。

2. 日常八股
1) transformer架构
> 答：每层 = 多头自注意力 + FFN，外套残差与 LayerNorm，输入加位置编码。自注意力用 Q/K/V 的缩放点积算权重，多头是让不同头在不同子空间学不同关系；FFN 做逐位置非线性变换。Encoder 双向，Decoder 加因果掩码和交叉注意力；现在的大模型多是 Decoder-only。

2) attention注意力的复杂度
> 答：时间与空间都是 O(n²·d)：n 个 token 两两算相似度得到 n×n 注意力矩阵，每个元素做 d 维点积，所以是 O(n²d)；存注意力矩阵本身是 O(n²)。这就是长文本贵的根源。优化方向：FlashAttention（分块计算，不落显存，降的是显存不是复杂度）、稀疏/滑动窗口注意力、线性注意力、GQA/MQA 降 KV 头数。

3) 向量数据库你了解多少
> 答：专为高维向量相似检索设计的库，核心能力是索引（ANN 近似检索）+ 过滤（标量条件）+ 增删改。常见选型：Milvus（功能全、可分布式）、Qdrant、Weaviate、pgvector（复用 PG，运维简单）、FAISS（库不是服务）。关键参数：索引类型、距离度量（内积/余弦/L2）、Top-K 与 ef_search。

4) 常用的向量索引算法有哪些
> 答：四类——①Flat 暴力检索（准但不快，小数据集或评测基线）；②HNSW 分层可导航小世界图（工业界主流，查询快、召回高，代价是内存大、构建慢）；③IVF 系列（倒排聚类，先找簇再簇内搜，IVF-PQ 用乘积量化压内存）；④LSH 局部敏感哈希（快但精度一般）。选型看数据量、内存预算和召回要求。

3. 项目经历

一:微调项目

1) 微调的模型参数量多大、用了什么显卡
> 答：说清"模型 + 方式 + 显卡"三件套。例：Qwen2.5-7B 做 LoRA 微调（rank 8~16，只训 adapter），单卡 A100 80G 或 2×4090（配合 4bit QLoRA）。要能讲显存账：全参 7B 训练需 ~8 倍参数量的显存，LoRA/QLoRA 能把可训参数和优化器状态压到很小，所以消费级卡也能跑。

2) 微调数据集格式，如何构建的数据集
> 答：主流用对话格式（messages: [{role, content}]）或 instruction-input-output 三元组，导出为 JSONL，一条一行。构建流程：收集原始语料 → 清洗去重去噪 → 按模板套成指令格式 → 人工抽检质量 → 划分训练/验证集。要点：模板必须和推理时一致，否则训完效果打折。

3) 数据集来源及分布
> 答：来源如实说（业务日志脱敏、公开数据集、模型蒸馏生成、人工标注），分布按维度统计：类别占比、长度分布、难度分布、来源占比。要主动交代表达"哪些场景样本少"，因为这直接引出下一题的类别不均衡。

4) 数据类别不均衡怎么处理
> 答：三层手段——①数据层：过采样少数类（可加扰动/改写）、欠采样多数类、用 LLM 改写扩增少数类；②损失层：类别加权、focal loss、按类别重采样 batch；③策略层：把它拆成"分类先均衡、生成再补"，或对少数类单独加规则/检索兜底。最后一定要说"用 macro-F1 / 每类召回看效果，而不是只看总体准确率"。

5) 训练/测试集划分
> 答：按业务维度划分而不是随机划分——同一用户/同一文档/同一时间段的样本不能跨集，否则会数据泄漏导致指标虚高。比例常见 8:1:1；小数据用交叉验证；时间序列类按时间切（用过去训、未来测）。补充"验证集用于调参、测试集只在最后看一次"。

6) 训练参数，如使用LlamaFactory框架的epoch参数是多大
> 答：LoRA 微调常用 epoch 2~3（数据少时 3~5 但要看是否过拟合），学习率 1e-4 ~ 2e-4（LoRA 比全参大一个量级），batch size 用梯度累积凑到 32~64，warmup 3~5%，cosine 衰减，cutoff_len 按数据长度分布定（多数场景 1024~2048）。判断依据是验证集 loss 曲线：连续几个 epoch 不降就停。

7) 报告生成的评估指标有哪些（ROUGE/BELU），项目中说到的生成准确率是如何得出的
> 答：自动指标：ROUGE-1/2/L（看 n-gram 与最长公共子序列召回）、BLEU（看 n-gram 精确率，偏机器翻译）、BERTScore（语义相似）。生成类任务这些指标和人工感受相关性有限，所以通常再加：关键字段准确率（抽取的结构化信息是否全对）、事实一致性（有无编造，用 LLM-as-Judge 或规则校验）、人工评分（1~5 分抽检）。"生成准确率"必须能拆开讲——分子是什么、分母是什么、谁判定的。

二:智能体项目

1) 多智能体协同是怎么实现的
> 答：主 Agent 分解任务并分发给子 Agent（各自有专属 prompt + 工具），结果摘要回传主 Agent 汇总；并行任务用并发调度 + 合并节点，有依赖的用 pipeline 串联。关键设计：Agent 间只传结构化摘要不传全量上下文，避免上下文爆炸；失败时主 Agent 重试或换策略重新分配。

2) 多模态RAG是如何设计的
> 答：分三条线——①解析：PDF/图片走 OCR + 版面分析，还原标题层级、表格、图片区域；②索引：文本走文本 embedding，图片走 CLIP 类视觉 embedding 或"图生文"后用文本 embedding，两者共用一套元数据（doc_id、页码、类型、bbox）；③检索与生成：查询同时打文本库和图库，融合后把图片以 URL/引用形式交给多模态模型看原图。要点是"图不要转成文本就丢了，得保留原图给模型看"。

3) 数据预处理是如何操作的，metadata有哪些字段数据
> 答：流程：格式解析（docx/pdf/html）→ 文本抽取与去噪（页眉页脚、乱码、重复段）→ 版面/表格处理 → 切块 → 打标 → 入库。metadata 常见字段：doc_id、doc_title、source（来源系统）、page_no、chunk_index、section_path（章节路径）、content_type（正文/表格/图片）、created_at、version、tenant_id/权限域、以及业务标签（产品线、地区）。metadata 的用处是过滤和引用溯源，不是摆设。

4) 你项目中的RAG是如何切块的
> 答：优先按结构切再按长度兜底：先按标题层级切成语义块，块过长再按句子/段落递归切，保留 overlap（10%~20%）防语义被切断；表格整表保留并附上表头与所属章节；每个 chunk 前置"文档标题 + 章节路径"作为上下文前缀（contextual header），显著提升召回准确率。参数：chunk_size 300~800 token，看文档密度调。

5) 固定token切块有哪些局限，解决策略有哪些
> 答：局限——①切断语义（一句话/一张表被劈两半）；②丢失结构（不知道属于哪一章）；③块大小一刀切，短问答块浪费、长论述块稀释。策略：语义/递归切分（按段落→句子→字符的顺序尝试）、结构感知切分（标题、表格、代码块单独处理）、滑动窗口 + overlap、小块检索大块召回（small-to-big：用小块做索引、命中后返回其父块）、给每块加标题路径前缀。

6) 项目使用的RAG召回策略是哪种
> 答：混合召回 + 重排：BM25 关键词与向量召回并行各取 Top-K，用 RRF 或加权融合，再交给 rerank 模型（bge-reranker）精排取 Top-N。加分项：query 改写/多查询扩展处理短查询，元数据过滤缩小范围，多模态场景再加图库一路。

7) RAG的实际指标是怎么计算出来的
> 答：分两段算——检索段：Recall@K（标注的标准答案文档有没有出现在 Top-K 里）、MRR / nDCG（排得靠不靠前）、命中率；生成段：答案正确率（人工或 LLM-Judge 对照标准答案）、忠实度/无编造率（答案是否都能被检索内容支撑）、引用准确率。做法是建 100~300 条带标注的评测集，跑批统计，改一次算一次，形成可比较的基线。
