## 二、技术面试问答

1. 智能问答项目使用了哪些模型？为什么没有使用多模态模型？

> 按分层选型答：Embedding 用 bge-m3，rerank 用 bge-reranker，生成用 Qwen2.5 / GLM 系列（或闭源 API），向量库 Milvus 或 pgvector。不用多模态要落到业务理由上：用户提问以纯文本为主，多模态会带来 3~5 倍的 token 成本和延迟、链路更复杂（OCR、版面还原、图文对齐）、评测集也缺，收益不匹配；但要补一句"如果出现图文工单场景，会先用 OCR/VLM 做前置结构化，而不是直接上网端到端多模态"，显得你考虑过而不是没想过。

2. 你在项目中如何使用 AI Coding 工具？

> 三档：全交给 AI 的是样板代码（CRUD、DTO、单测、正则、SQL、一次性脚本）；交给 AI 出初稿、自己改的是有明确规格的逻辑实现和重构；自己写、AI 只做 review 的是架构决策、核心链路和涉及资金安全的代码。交互原则：先对齐方案再让它写，给上下文和约束（用哪个库、不要新增依赖、保持签名不变），写完自己必读 diff，最后靠 lint 和单测兜底。

3. 什么是 Agent Skill？

> Skill 是封装了一类任务"怎么做"的能力包：包含若干工具 + prompt 指引 + 操作流程 + 参考资源，按需渐进加载（注册时只留名称和一句话描述，命中后才注入完整定义）。和 Tool 的区别是粒度：Tool 是单个原子函数，Skill 是一组能力加方法论；和 MCP 的区别是定位：MCP 是工具接入协议（解决"怎么接"），Skill 是能力封装（解决"怎么做"）。

4. 描述一下 Agent 的完整调用链路(Badcase闭环流程每个阶段的输入输出)

```text
用户输入 → 意图识别 → 匹配注册 Skill → 加载提示词
→ 调用工具或检索能力 → 结果校验 → 返回结构化结果
```

> 每段的输入输出：意图识别（输入原始 query + 会话上下文，输出意图标签与槽位）；Skill 匹配（输入意图与 Skill 描述表，输出候选 Skill 及置信度）；加载提示词（输入 Skill ID，输出 system prompt + 工具 schema）；工具/检索（输入结构化参数，输出 JSON 结果或 Top-K 文档）；结果校验（输入原始结果，输出通过/重试/降级三态）；返回（输入校验后内容，输出结构化响应 + 引用来源）。每一环都要有超时和兜底。

5. ES 多路召回是怎么做的？

> 一路 BM25 关键词（multi_match 打标题和正文，配同义词与分词优化），一路 kNN 向量（dense_vector + HNSW，先做 embedding 再检索），两路并行发起，各自取 Top-K，再用 RRF 融合排序，最后 rerank 取 Top-N 拼 prompt。可选第三路：字段精确匹配或标签过滤，用于兜住"型号、编号"这类关键词强场景。

6. 多路融合（RRF)的时间复杂度和空间复杂度如何估量
> RRF 本身不需要重新计算文档相似度，只需要遍历各路 Top K 结果，按照文档 rank 累加 \(1/(c+rank)\) 的分数。假设有 m 路召回、每路 K 条结果，去重后有 D 个文档，分数聚合是 \(O(mK)\)，如果对所有结果排序，整体复杂度是 \(O(mK+D\log D)\)。如果最终只取 Top N，可以用大小为 N 的小顶堆，把排序部分优化成 \(O(D\log N)\)。空间上主要是保存分数 Map 和召回结果，通常为 \(O(mK+D)\)，流式处理时可以降低到 \(O(D+N)\)。RRF 中的平滑常数 c 不影响复杂度。)

7. 如果双路召回的其中一路（关键词检索）响应慢，如何优化
> 双路召回应该并行执行，整体耗时接近两路中的最大值。如果关键词检索慢，我会先通过 ES 慢日志和链路监控定位是查询本身、分片、网络还是资源问题。查询侧可以优化 bool/filter、分词和 mapping，减少返回字段和 Top K，避免通配符及深分页，并通过合理分片和 routing 减少查询范围。架构侧给关键词路设置独立超时、重试上限和熔断，超时后允许仅使用向量召回继续返回，RRF 只对实际成功的召回路计算分数。同时监控降级后的召回质量，必要时增加热点查询缓存。这样既能降低关键词检索的长尾延迟，也能避免单路故障拖垮整体链路。

8. 多路检索如何保证稳定性？比如检索失败后如何处理？
> 向量召回慢时，我会先拆分 Embedding 生成、向量索引查询、网络传输和结果处理的耗时，确认瓶颈所在。如果是向量生成慢，可以使用轻量模型、缩短输入、模型量化、Batch 推理和查询向量缓存；如果是向量检索慢，可以使用 HNSW 等近似索引，调小 k、ef_search 或 num_candidates，减少返回字段，并通过过滤、routing 和合理分片缩小查询范围。架构上两路召回并行执行，并给向量路设置独立超时和熔断，超时后降级为 BM25，RRF 只融合成功返回的召回路。最后需要同时监控 P95/P99 延迟、超时率和降级后的召回质量，不能只追求速度而导致效果明显下降。

9. 工单编排项目的效果是什么？

人工创建工单约 3 分钟，优化后自动流程稳定在 15 秒左右。极少数跨网段重试场景耗时会小幅上浮，但整体性能稳定。

10. 详细说一下工单自动化流程。

```text
输入系统名称 / IP → 解析 IP → 双 IP 连通性 Ping 检测 + 磁盘资源检测 → 判断处理结果
```

11. 这个项目设计了哪些测试场景？

- IP 直接检测；
- 系统名称解析 IP；
- 网络异常或两端断连；
- 磁盘满载及阈值边界；
- 自动修复成功；
- 自动修复失败并转人工提单；
- 跨网段重试、接口超时和异常返回。

每个场景设计十余条核心用例，覆盖正常、异常和边界链路，重点验证流程不死循环、状态不错误、工单不重复创建。

12. 如果让你做压力测试，会怎么设计？

不做笼统压测，而是按业务场景拆分：

1. 分别压测 IP 解析、网络检测、自动修复失败提单等场景；
2. 梯度增加并发请求数，观察系统性能变化；
3. 重点观察连接池、线程池、工作流调度和下游依赖；
4. 验证超时、重试、熔断和降级是否生效；
5. 检查高并发下工单状态一致、无重复创建、无流程阻塞。

**关注指标：**吞吐量、成功率、平均 RT、P95/P99 RT、超时率、重试率、任务堆积量和重复工单数量。


## 三、业务与协作问题

1. 需求通常如何推进？

```text
业务对齐 → 需求评审 → 可行性与风险评估 → 方案定稿
→ 开发落地 → 测试验收 → 上线迭代
```
参与角色包括开发、产品和业务方。测试验收除功能外，还需要关注性能、异常处理、权限和数据一致性。

2. 这段项目经历最大的收获是什么？

> 三点：①从"写功能"变成"对效果负责"——学会用指标证明改动有效，而不是凭感觉；②建立了质量意识，badcase 必须闭环成回归用例，否则同一个坑会踩第二次；③做自动化时想清楚了"宁可少修一步，不能误操作生产"，学会在效率和安全之间划线。

3. 是否有和第三方交接的经历

> 有，按五件事讲：接口契约（文档 + 请求示例 + 字段约束）→ 联调环境与测试数据 → 异常约定（错误码、超时时间、重试与幂等要求）→ 上线步骤与回滚方案 → 责任边界和对接人。强调"把口头约定写成文档"，后面出问题能对得上。
