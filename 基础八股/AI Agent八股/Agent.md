# AI Agent 面试八股速答手册

> **回答公式**：一句话结论 → 展开对比 → 工程要点/加分点。先抛结论，面试官 3 秒抓到重点。
> **一句话主线**：Agent = Model + Harness。模型负责"想"，Harness 负责"让它想得下去、干得成、不出事"。

---

## 一、Agent 基础

### 1. Agent 是什么
一句话：**能自己决定下一步做什么的 LLM 应用**。区别传统程序的是控制流由模型运行时决定，而不是代码写死。

工程化定义：`Agent = Model + Harness`
- **Model**：推理、生成、决策下一步
- **Harness**：系统提示词、工具注册、权限、沙箱、记忆、上下文压缩、编排循环、钩子、反馈回路

### 2. 三层形态对比（高频必考）

| 维度 | 传统 Workflow | Agentic Workflow | 自主 Agent |
|---|---|---|---|
| 控制流 | 代码硬编码 | LLM 运行时决定 | LLM 全权决定 |
| 流程图 | 固定 DAG | 无固定路径，边走边选 | 目标都可能自我调整 |
| LLM 角色 | 节点里的一个函数 | 决策主体 | 完全自治的"员工" |
| 任务边界 | 确定封闭 | 半开放 + 终止条件 | 开放式长期目标 |
| 时长 | 一次性 | 有界（秒~分钟） | 长期/无人值守 |
| 确定性 | 高、易调试 | 中，可观测可重放 | 低、风险高 |
| 代表 | LCEL、Dify、Airflow | ReAct、Function Calling | AutoGPT、Devin |

**加分**：没有谁更高级，只有匹不匹配。生产上多数是"Workflow 打底 + Agent 兜边角"的混合体。

### 3. Workflow / Graph / Loop 的关系
- **Workflow**：描述任务怎么完成
- **Graph**：用 Node / Edge / State 把过程变成可执行结构
- **Loop**：让节点按条件回退到前序步骤自我修正

**落地要点**：先定 State 的职责和更新规则，再写清条件边、退出条件、最大轮次、超时、Token 预算。所有进路由/数据库/工具的数据都要校验；重试、降级、人工中断、checkpoint 恢复都要进测试覆盖。

## 二、推理范式（CoT → ReAct → Plan-Execute → Reflection）

### 1. 四者递进关系
- **直接输出**：无中间推理
- **CoT**：先写推理过程再给答案，准确率更高
- **ReAct** = CoT + **行动**：交替输出「Thought → Action → Observation」，根据结果继续想
- **Plan-and-Execute**：先出全局计划，再逐步执行
- **Reflection**：加一层「生成 → 评估 → 改进」闭环

### 2. 三者取舍（必背）

| 范式 | 优势 | 代价 | 适合 |
|---|---|---|---|
| ReAct | 每步看最新情况，灵活 | 易漂移，历史全带上 token 线性增长 | 边界不明的探索型任务 |
| Plan-Execute | 全局视野，不跑偏 | 简单任务是多余开销 | 目标明确的多步复杂任务 |
| Reflection | 专治输出质量 | 额外 token 和延迟 | 对正确性要求高的场景 |

**加分 1**：工程上常混合 —— Plan-and-Execute 做全局规划，ReAct 做每步执行。
**加分 2**：**动态 Replan** —— 每步执行完把结果 + 剩余计划交给规划模块判断要不要改。
**加分 3**：**Reflexion** —— 不只检查对错，还把失败原因总结成"经验教训"存进记忆，下次遇到类似任务作为上下文传入。

## 三、记忆系统

### 1. 四层结构
| 层 | 存什么 | 生命周期 |
|---|---|---|
| **感知记忆** | 当前这次调用的原始输入（消息、截图、文档） | 一次调用，用完即弃 |
| **短期记忆** | context window 里的全部消息（输入/输出/系统提示） | 一次会话 |
| **长期记忆** | 跨任务信息，存外部 DB（向量/关系/KV） | 永久 |
| **实体记忆** | 从对话里提炼的结构化字段（"用户偏好 Python""预算 5 万"） | 永久 |

长期记忆再分三类：
- **情节记忆**：具体事件经历（上周二写爬虫遇到反爬，用 Selenium 解决）
- **语义记忆**：从多次经历提炼的通用规律（遇到 JS 动态渲染优先用 Playwright）
- **程序记忆**：可直接复用的操作 SOP（部署 Flask 的标准步骤）

### 2. 结构化工作记忆
给 context 这个"工作台"划固定区域：任务目标 / 已确认结论 / 待验证假设。每步执行完不是追加到末尾，而是**更新对应区域**——把过时结论替换掉、已验证的移入确认区。

### 3. 【回答核心】三个问题
1. **存什么**：只存对下次任务有价值的，过滤噪音
2. **怎么存**：语义内容 → 向量库；结构化偏好 → 关系库；**混合存储是主流**
3. **什么时候取**：任务开始前主动检索加载背景，执行中按需检索

### 4. 记忆压缩四法
摘要压缩（长对话总结）、滑动窗口（只留最近 N 轮）、重要性过滤（打分筛选）、结构化抽取（抽成结构化字段）。

## 四、上下文工程（Context Engineering）🔥 新热点

> 一句话：上下文窗口是**稀缺且有边际递减**的资源（n 个 token 有 n² 的关系要算），管理它 ≈ 操作系统管理内存。

### 1. 五大策略（Offload / Reduce / Retrieve / Isolate / Cache）

| 策略 | 解决什么 | 手段 |
|---|---|---|
| **Offload 卸载** | 上下文太挤 | 搬到文件系统/数据库，按需读回 |
| **Reduce 压缩** | 上下文太长 | 摘要、修剪、紧凑化 |
| **Retrieve 检索** | 需要的信息在窗口外 | RAG、glob/grep 即时检索 |
| **Isolate 隔离** | 一个窗口装不下 | 拆成多个子 Agent 独立上下文 |
| **Cache 缓存** | 重复计算 | KV cache / prompt cache 复用稳定前缀 |

### 2. Reduce 的两种做法（必会区分）
- **Compact 紧凑化**：把老的工具结果换成占位符，保留对话结构，信息损失小、可逆
- **Summarize 摘要化**：用一段总结替换整段历史，回收 token 多但**不可逆**、破坏结构

> 优先级：**先紧凑化，实在不行再摘要化。**

### 3. 五种上下文失败模式（加分）
- **Context Rot**：token 越多，整体表现越差
- **Context Poisoning**：幻觉/错误进入上下文并被放大
- **Context Distraction**：模型过度关注历史，忽略自身训练知识
- **Context Confusion**：冗余信息（如工具过多）干扰输出
- **Context Clash**：上下文各部分信息互相冲突

### 4. Manus 六条生产经验（加分）
1. KV-cache 命中率是核心指标（直接决定成本和延迟）
2. **mask 不 remove** 工具（删工具会破坏缓存前缀）
3. 文件系统是终极上下文
4. `todo.md` 复述目标，对抗长任务中的目标漂移
5. **把错误留在上下文里**（模型看到失败才会换路走）
6. 防止 few-shot 漂移（少样本例子重复多了会固化行为）

## 五、工具与 MCP

### 1. MCP 三层架构
- **Host**：用户直接交互的 AI 应用（Claude Desktop、Cursor）
- **Client**：负责与 Server 建连、管理通信
- **Server**：真正暴露工具能力的服务

**加分**：每接一个 MCP Server，工具定义约固定消耗 4000~6000 tokens，接 5 个就占 12% 上下文。**工具不是越多越好，每个都有认知成本**。

### 2. 工具设计原则
好的工具 = **边界清晰、输入稳定、输出可解释、结果可观察**。
太多会消耗上下文并增加误选率；太少完不成任务。解决矛盾的手段是 **Tool Search / 渐进式披露**：按需发现并加载工具。

**另一种思路（脚本化执行）**：只给少数原子工具（bash、文件、fetch），把复杂操作下沉到脚本，大幅减少工具描述的开销。

## 六、多 Agent 协作

### 1. 两种组织方式
- **中心化**：统一调度者分配任务、收集结果 —— **工程上主流**，调度清晰、责任明确、好排查
- **去中心化**：Agent 自行协商直接通信

### 2. 两种通信机制
| | 消息传递 | 共享状态 |
|---|---|---|
| 本质 | **解耦**，发送方不用知道接收方 | **直接**，所有 Agent 读写同一对象 |
| 适合 | Agent 需要独立运行 | 依赖明确的流水线（LangGraph 即此思路） |

### 3. 路由策略
- **静态路由**：稳定可预测，但覆盖不了边缘情况
- **动态路由**：灵活，但多一次 LLM 调用且行为不可预测
- ✅ **混合策略**：主流程用静态路由保底，边缘情况才交给 LLM 动态决策

### 4. 子 Agent 的真正价值（加分）
不只是并行提速，**核心是上下文隔离**。子 Agent 读一大堆文件、跑自己的循环，只把总结返回主 Agent，中间日志不污染主会话。

> 所以多 Agent 首先是**信息架构**问题，其次才是并发问题。没有清晰任务边界和汇总机制，加 Agent 只会增加协调成本。

### 5. 共享状态怎么传
Claude Code 的做法：**Scratchpad 目录** —— 子 Agent 把中间发现写入共享目录的文件，其他人读文件。用最古老的机制（磁盘）解决最前沿的问题。

## 七、容错与兜底（调用失败怎么办）⭐ 合并重点

> **核心思想**：不把异常当"停止信号"，而是当"反馈信息"喂回模型，让 Agent 自己调整修复。

### 1. 先分级，再处理
| 失败类型 | 例子 | 处理 |
|---|---|---|
| 瞬时错误 | 网络超时、限流 | 系统自动重试 |
| 模型可恢复 | 工具调用失败、解析出错 | 错误回灌，模型自行调整 |
| 用户可修复 | 信息缺失、指令不明 | `interrupt()` 暂停请求人工输入 |
| 服务中断 | 模型供应商挂了 | 自动切换备用模型 |
| 过度调用 | 陷入思考-行动死循环 | 硬性限制调用次数强行终止 |
| 意外错误 | 未预见的代码缺陷 | 任其抛出，开发者介入 |

### 2. 核心机制：错误注入与模型自修正
- **错误作为反馈**：捕获异常后不崩溃，封装成结构化 `ToolMessage`，连同历史轨迹一起回给 LLM —— 相当于告诉模型"你刚才失败了，原因是这个，反思并调整"
- **模型自主修复**：LLM 用推理能力分析并提替代方案 —— **不仅能修代码，还能修计划本身**

> 这就是为什么要把错误留在上下文里，而不是悄悄吞掉重试。

### 3. 多级防护
- **智能重试**：对瞬时故障自动重试，**指数退避**（1s / 2s / 4s）。模型调用与工具调用的重试可独立配置
- **熔断与降级**：连续失败超阈值触发熔断，暂时隔离避免无效重试污染上下文。降级手段：返回缓存/默认值、切换备用模型/简化工具、关闭工具只做概念性回答
- **失控循环防护**：监控重复失败操作，检测到就强制插入指令要求换路径或承认无法处理

### 4. 状态持久化与断点续跑
每步（如每次成功工具调用后）把完整状态（对话历史、中间结果）持久化到 DB 作为 **checkpoint**；中断后从最近检查点恢复，**不用从头跑**。

## 八、Harness 工程 🔥

### 1. Harness 是什么
不是框架，是**把不确定的模型推理约束成可执行流程的控制系统**。它必须回答六个问题：

1. 给模型看什么？（上下文）
2. 给模型哪些工具？
3. 工具在什么权限下跑？
4. 工具结果怎么回给模型？
5. 长任务怎么管上下文、状态、失败？
6. 系统怎么判断任务可以结束？

### 2. Agent Loop（最核心）
```
用户提出任务 → 模型分析并选择工具 → Harness 检查权限
  → 执行工具并返回结果 → 模型观察结果 → 继续或结束
```
**产品的差异全藏在这个循环的每个细节里**，而不是"模型多强"。

### 3. 九条 Harness 设计原则（超加分）
1. **模型负责决策，系统负责边界** —— 能力与授权必须分离，模型能请求工具，但执行与否由 Harness 裁决
2. **Agent 的核心不是 Prompt，是反馈闭环** —— 能"行动-观察-修正"才算 Agent
3. **不追求每步正确，追求错误可恢复**
4. **上下文是稀缺计算资源** —— 决定哪些常驻、按需加载、压缩、下放子 Agent
5. **确定性规则不能只写进 Prompt** —— 关键约束要用权限/沙箱/Hooks/状态机由代码强制执行
6. **工具质量 > 工具数量**
7. **多 Agent 首先是信息架构，其次才是并发架构**
8. **人是控制系统的一部分** —— Human-in-the-loop 是治理设计，不是"不够自动化"
9. **Harness 本身要持续评估** —— Agent 表现差不一定模型弱，可能是上下文错、工具描述差、压缩丢了目标

### 4. 通用七子系统（学术归纳，加分）
`Agent Loop` / `Tools & Actions` / `Memory & Context` / `Safety & Permissions` / `Orchestration` / `Extensibility` / `Observability`

## 九、Claude Code 内部机制 🔥

> 512,664 行 TypeScript，1332 个文件。核心是 `query.ts` 里一个 `while(true)` 循环，其余全是"安全带"。

### 1. 12 层 Harness 架构（分层记忆法）
| 层 | 解决什么 |
|---|---|
| L1 生成器查询循环 / L2 API 客户端与流式 / L3 重试与错误恢复 | **API 可靠性** |
| L4 系统提示词组装 / L5 工具注册中心 / L6 Bash AST 解析器 | **工具问题** |
| L7 工具沙盒 / L8 三层上下文压缩 / L9 权限与安全门 | **信任问题** |
| L10 会话记忆持久化 / L11 后台 Agent / L12 多智能体协调 | **自主问题** |

> 大多数同类只做到前六层。上面六层才是护城河 —— 处理"会话几小时、用户不在、多 Agent 共享状态"。

### 2. 系统提示词：动态装配 + 缓存友好
- **静态部分**（全员共享）：身份定义、安全准则、做事原则、工具规则、风格要求
- **动态部分**（每人不同）：CLAUDE.md、工作目录/OS、MCP 说明、自动记忆、Git 状态
- 用常量 `SYSTEM_PROMPT_DYNAMIC_BOUNDARY` 一刀切两段，**分界线上方共享缓存，命中时省约 90% 成本**
- 工具列表**按字母排序**保证缓存稳定

### 3. 流式工具执行 `StreamingToolExecutor`
不等所有 `tool_use` 到齐再执行，边收边跑。按工具的 `isConcurrencySafe` 标记调度：可并行的（Read、Grep）立即启动，必须串行的（Edit）排队。

### 4. 五步权限流水线
否决规则 → 询问规则 → 工具自身权限 → 模式决策 → **Hook 一票否决**

Bash 命令风险评估 = `shell-quote` 结构化解析 + **LLM 语义分析**，分低/中/高风险。不是静态白名单，而是完整 **Bash AST 解析器（2679 行 TS）** —— 避免正则被引号、变量展开、子 Shell 绕过。

### 5. 知识注入用 `tool_result` 而非 system prompt
把合成响应伪装成工具返回结果注入对话。**好处**：系统提示词保持精简，且知识恰好落在模型最关注的近期窗口。

### 6. 四层记忆
| 层 | 特点 |
|---|---|
| `CLAUDE.md` | 手动编写的项目规则，跨会话 |
| `MEMORY.md` | 模型自动维护，跨会话记忆 |
| Session Memory | 当前会话进度 |
| 上下文压缩 | token 接近上限（如 167k）触发，**优先复用 Session Memory 摘要省掉一次 API 调用** |

### 7. 子 Agent 与 Scratchpad
协调器管四阶段：**研究 → 综合 → 实现 → 验证**。
两种子 Agent：**进程内**（共享父进程，轻量，适合只读）/ **独立进程**（完全隔离，有自己上下文、工具、权限，适合修改型任务）。

### 8. 三个未发布功能（聊趋势用）
- **KAIROS**：自主守护进程，心跳唤醒检查 PR/CI/评论，自主行动并推送 —— 交互单元从"对话"变"订阅"
- **Dream**：后台记忆整合。三阶段门控（间隔够久 / 会话数达标 / 无锁）→ 四阶段流程（定向 → 收集 → 整合 → 修剪），**模拟人类睡眠期的记忆巩固**
- **BUDDY**：电子宠物，用可变比率强化做用户留存

### 9. 模型耦合问题（加分）
- **可移植层**：生成器循环、Bash AST、文件操作 —— 与模型无关
- **不可移植层**：权限分类器、Dream 提示词、压缩提示词 —— 高度依赖 Claude 的指令遵循能力和摘要能力

> **架构是开放的，调优才是壁垒。**

## 十、Codex 内部机制 🔥

> `codex-rs`，Rust workspace，60+ crates，约 55 万~110 万行。

### 1. 三层循环
1. **submission_loop**：最外层，等待 `Op`（UserInput / Shutdown / Cancel），贯穿整个会话
2. **Turn loop**：收到用户输入后启动，组装 prompt 调 Responses API，处理事件流
3. **Inner tool loop**：单次 turn 内，工具调用和结果追加进 prompt 反复回灌，直到 done

### 2. 队列对协议（Queue-Pair）
两个 tokio channel：
- **Submission channel（Op）**：客户端 → session
- **Event channel**：session → 所有客户端广播

**价值**：客户端永不阻塞在模型推理上，TUI 可以边渲染边收流式 token。

### 3. 三个会话原语
- **Thread**：SQLite 持久化的对话，可 resume / fork / archive / rollback
- **Turn**：一轮完整往返（输入 → 推理 → 工具 → 结果 → 响应）
- **Item**：turn 内的细粒度事件（单次工具调用、一段响应文本、一个推理步）

### 4. 性能两板斧
- **Prompt caching**：避免每轮重发完整历史导致的**二次方开销**
- **Compaction**：超阈值时用专用端点压缩历史（GPT-5.2-Codex 起支持模型原生 compaction）

> 踩过的坑：tool 枚举顺序不稳定导致 cache 失效退回二次方 —— **agent loop 里确定性状态管理极其关键**。

### 5. 四层权限栈（全场最强）
```
L1 执行策略（config.toml 规则）
L2 生命周期 Hooks（PreToolUse / PostToolUse / Interrupt）
L3 Guardian（LLM 审批子 Agent）
L4 OS 沙箱（AppContainer / macOS profile / seccomp+Landlock）
```
必须依次通过。这是**中间件式**设计：策略与执行分离（policy 和 enforcement 是不同 crate）。

### 6. 与 Claude Code 的差异（加分对比）
| | Claude Code | Codex CLI |
|---|---|---|
| 语言 | TypeScript | Rust |
| 工具调用 | 43 个 typed tools | **V8 执行的 JS**（可动态组合工具，独一份） |
| 命令分析 | 完整 Bash AST（2679 行） | execpolicy + OS 沙箱 |
| 审批 | LLM 分类器 + Hook | **Guardian 子 Agent** |
| 记忆 | 阈值触发压缩 | **Agent 自己写摘要并持久化** |
| 会话 | checkpoint | Thread 树，可 fork/resume/archive |
| 编排 | 协调器 + Scratchpad 目录 | Thread 树 fan-out |

## 十一、框架：LangChain / LangGraph

### 1. 生态定位
| 框架 | 定位 |
|---|---|
| **LangChain** | 高层 Agent 框架：模型、Prompt、工具、middleware，上手快 |
| **LangGraph** | 低层**编排框架与运行时**：直接控制 State、节点、边、路由、并行、子图、中断与恢复 |
| **LlamaIndex** | 数据接入、解析、索引、检索 —— 数据密集型 RAG |
| **OpenAI Agents SDK** | OpenAI 模型为主的轻量 Agent |
| **CrewAI** | 用角色和任务表达多 Agent 协作 |

> **LangChain 与 LangGraph 是上下层关系，不是竞争关系** —— LangChain v1 的 `create_agent` 本身就跑在 LangGraph 上。

**选型**：常见「模型判断 → 调工具 → 回模型」循环 → LangChain + middleware；需要显式多阶段、确定性步骤与 Agent 混排、复杂并行、长期暂停 → 直接 LangGraph。

### 2. Chain 的本质
一种**应用编排思路**：把 Prompt、模型、检索器、输出解析器按明确数据流串起来，上一步输出成为下一步输入。

技术基础是 **Runnable** —— 统一输入输出和执行接口，用 LCEL 的 `|` 串行组合，用字典/`RunnableParallel` 并行组合。组合后的整条 Chain 仍是 Runnable，可继续嵌套，统一支持 `invoke` / `ainvoke` / `batch` / `stream`。

### 3. 底层架构
- `langchain-core` 用 **Message / Model / Tool / Runnable** 标准协议隔离厂商差异
- 消息进 Agent State → 模型产出 `AIMessage` → 含工具调用则路由到工具节点 → 结果以**相同调用 ID** 的 `ToolMessage` 写回状态 → 模型继续判断，直至最终回答

**职责划分**：State 保存可变状态；Context 提供可信依赖；Store 保存跨线程数据；Middleware 负责权限、重试、摘要、人工审批；LangGraph 负责状态推进、路由、检查点与恢复。

### 4. 注册 Tool 的本质
**同时**向模型提供一份工具说明，向运行时提供一个可执行函数。说明含名称、用途、参数 Schema；模型据此选工具并生成参数，LangChain 执行对应函数。

四种方式（由简到繁）：
1. 已有函数 + 类型注解 + docstring 直接放入 `tools`
2. `@tool` 装饰器 —— 大多数业务工具，可自定义名称、描述、Schema
3. `StructuredTool` —— 运行时动态组装同步/异步函数和 Schema
4. 继承 `BaseTool` —— 需封装客户端、维护资源或定制执行过程

### 5. 记忆机制
- **短期**：属于当前会话线程。Agent State 存消息/当前步骤/中间结果；**Checkpointer** 按 `thread_id` 存快照，同 id 再调用可恢复
- **长期**：不绑线程，存到 **Store**，用 `namespace` + `key` 组织（namespace 常含租户/用户/记忆类型）。即使新建线程，只要用户身份和 namespace 相同仍可读取

### 6. 用不用框架？（开放式问题）
框架的三个坑：**抽象层太多不好调试**、**版本升级破坏性变更**、**通用设计与业务有偏差，定制反而更费劲**。

手搓的优势：可观测性好、好排查、方便做性能优化。

> **策略**：核心逻辑手写，只在边缘功能上用框架工具。

## 十二、反思机制专题（高频追问）

闭环结构：**评估 prompt**（专门找问题）+ **改进 prompt**（结合原始任务和批注定向修改），缺一失效。

四个必答要点：
1. **评估 prompt 的两个关键设计**：给出具体检查维度 + 设置「PASS」出口 —— 否则 LLM 要么流于表面，要么无限挑毛病
2. **步骤级 vs 任务级反思**：前者错误发现得早但开销大；后者能看整体但前期无效工作难挽回，按任务特点选
3. **防死循环（最易漏）**：必须硬性设最大轮次（2~3 轮），不能指望 LLM 自己停
4. **加分**：多 Agent 互评比自我反思效果好 —— 同一模型对自己的输出有**自洽偏见**
