## 知识地图（记住这张表就能答一半的题）

| 概念 | 一句话定位 | 解决的核心问题 |
| --- | --- | --- |
| **Function Calling** | 模型的「调用语言」 | 模型怎么表达"我要调哪个函数、参数是什么" |
| **MCP** | 工具的「生态协议」 | 工具怎么标准化打包、注册、被发现，一次实现到处复用 |

## 一、Function Calling

### Q1. 什么是 Function Calling？原理是什么？

开发者用 JSON Schema 把工具描述好传给模型，模型需要工具时不输出自然语言，而是输出一段结构化的 `tool_calls` JSON（函数名 + 参数）；应用代码解析后真正执行，把结果回灌进对话，模型再生成最终答案。

**运行时本质是「两轮对话 + 中间执行」的闭环：**

1. **第一轮**：工具列表 + 用户问题一起传给模型 → 模型返回 `finish_reason="tool_calls"`，意思是"我需要工具帮助，先不给最终答案"；
2. **中间执行**：你的代码解析 `tool_calls`，拿到函数名和参数，执行本地/远程函数；
3. **第二轮**：把结果以 `role="tool"` 的消息追加进历史，再次调用模型 → 这次模型有了数据，才输出自然语言答案。

> 模型支持一次返回多个 `tool_calls` 实现**并行调用**，但仅当多个调用之间无依赖时才适合并行。

### Q2. 工具 Schema 怎么写？（每个字段都有含义）

```python
tools = [{
    "type": "function",
    "function": {
        "name": "get_weather",          # 唯一标识，模型输出 tool_calls 时用它
        "description": "查询指定城市的实时天气，含气温、天气状况、风向风速，仅支持中国大陆城市",
        "parameters": {
            "type": "object",
            "properties": {
                "city": {"type": "string", "description": "城市名，如「北京」，不要带省份前缀"},
                "unit": {"type": "string", "enum": ["celsius", "fahrenheit"], "description": "温度单位，默认摄氏度"}
            },
            "required": ["city"]
        }
    }
}]
```

**写 Schema 的三条经验：**

- `description` 是模型选工具的唯一依据，写清**能力边界**（能干什么、不能干什么）；
- 参数描述里写**示例和反例**（"不要带省份前缀"），比写类型更能纠偏；
- `required` 只放真正必填的，可选参数给了默认值，模型才不会瞎编。

### Q3. 模型是怎么学会调工具的？（训练层面）

两个阶段解决两个不同的问题：

| 阶段 | 喂什么数据 | 解决什么问题 |
| --- | --- | --- |
| **SFT**（监督微调） | 大量「工具调用示范对话」：工具定义 → 结构化 JSON 调用 → 工具结果 → 最终答案 | 学会整套流程：看到工具描述 → 判断要不要调 → 输出合法 JSON |
| **RLHF**（人类反馈强化学习） | 人类标注「哪种回答更好」→ 训奖励模型 → 强化学习调主模型 | 学会**边界感**：能直接答的直接答，需要实时数据才调工具，别"学过头"遇事就想调 |

> **RLAIF** 是 RLHF 的变体，用另一个 AI 代替人类标注员打分，成本更低、速度更快。业界常见打法：**核心业务数据用 RLHF 保质量，量大面广的用 RLAIF 提效率**。

### Q4. 🆕 `tool_choice` 参数怎么控制调用行为？

它是控制「模型是否/如何调工具」的开关，四种取值：

| 取值 | 行为 | 典型场景 |
| --- | --- | --- |
| `auto`（默认） | 模型自己决定调不调 | 通用对话 |
| `none` | 强制不调工具，只输出文本 | 已知工具结果、走纯生成分支 |
| `required` | 必须调至少一个工具 | 强制走工具链的环节（如必须查库） |
| `{"type":"function","function":{"name":"xxx"}}` | 强制调指定函数 | 意图已确定，只差参数抽取（如信息抽取/填槽） |

### Q5. 🆕 Function Calling、JSON Mode、Structured Output 有什么区别？

三者都是"让模型输出结构化内容"，但约束强度递进：

| 方案 | 机制 | 强度 | 适用 |
| --- | --- | --- | --- |
| **JSON Mode** | 只约束"输出合法 JSON"，schema 靠 prompt 描述 | 弱，可能不合 schema | 简单解析场景 |
| **Structured Output** | 用 JSON Schema 约束解码（约束解码/受限采样） | 强，保证 schema 合法 | 结构化抽取、数据清洗 |
| **Function Calling** | 在 Structured Output 之上，额外表达"调用意图" | 最强，含语义（要调工具） | 需要触发外部执行 |

> 一句话：**只要 JSON 用 JSON Mode，要 schema 保证用 Structured Output，要触发动作才用 Function Calling。**

### Q6. 🆕 工程上 Function Calling 有哪些常见坑？

| 坑 | 表现 | 解法 |
| --- | --- | --- |
| **参数幻觉** | 编造不存在的城市 ID、订单号 | 参数校验 + 失败时把错误原样回灌给模型让它重试 |
| **必填参数缺失** | 漏传 `required` 字段 | 本地兜底校验，报错信息结构化返回 |
| **死循环** | 模型反复调同一个失败的工具 | 设最大轮数（`max_iterations`）、失败计数熔断 |
| **工具结果过长** | 一次返回几万 token，撑爆上下文 | 结果截断/摘要、只回灌关键字段 |
| **工具选错** | 几十个工具时选混 | 工具分组、按意图路由、只暴露相关子集 |
| **并发一致性** | 并行调用间存在依赖却并行了 | 依赖检测，有依赖则串行 |

## 二、MCP（Model Context Protocol）

### Q7. MCP 是什么？解决什么问题？

Anthropic 于 2024 年底推出的开放协议，解决的是**「模型接工具太碎片化」**：每个应用都要为每套工具手写一遍接入代码，M × N 的重复劳动。

MCP 的思路是把工具接入标准化：**工具提供方按协议实现一个 Server，任何支持 MCP 的 AI 客户端就能直接接进来，一次实现、到处复用**（M + N）。

### Q8. MCP 的组成（三层架构）

| 层 | 内容 | 要点 |
| --- | --- | --- |
| **角色层** | Host（AI 应用，如 Claude Desktop）、Client（Host 内负责通信的模块）、Server（工具提供方实现的独立进程） | 一个 Host 可同时连多个 Server，一个 Client 对应一个 Server 连接 |
| **能力层** | Tools、Resources、Prompts | 见 Q9 |
| **协议层** | 消息格式 JSON-RPC 2.0；传输 stdio / Streamable HTTP | 见 Q10 |

### Q9. MCP Server 暴露的三类能力（高频必背）

| 能力 | 性质 | 谁来控制 | 例子 |
| --- | --- | --- | --- |
| **Tools** | **有副作用**的操作，需用户授权 | 模型主动调用 | 创建文件、调 API、发消息 |
| **Resources** | **只读数据**，无副作用 | 应用/用户选择加载 | 读取文档、数据库快照 |
| **Prompts** | **可复用的提示词模板** | 用户主动触发 | "生成周报"模板、代码评审模板 |

> 面试官爱追问的区别点：**Tools 是模型驱动的（有副作用，要授权），Resources 和 Prompts 是用户/应用驱动的（只读、无副作用）**。

### Q10. MCP 的通信方式有哪些？怎么选？

消息格式与传输方式**解耦**：不管底层走什么传输，消息格式统一是 **JSON-RPC 2.0**，切换传输不影响上层逻辑。

| 传输 | 部署形态 | 优点 | 局限 |
| --- | --- | --- | --- |
| **stdio** | Server 作为本地子进程，管道通信 | 不走网络、延迟极低、生命周期随 Client 自动管理、无需鉴权 | 只能单机本地，无法共享 |
| **Streamable HTTP** | Server 作为 HTTP 服务部署，单端点处理请求与响应 | 多 Client 共享一个 Server，适合团队统一部署、支持远程 | 需考虑鉴权与网络延迟 |

> **版本演进（加分点）**：早期是「HTTP + SSE 双端点」方案，在 **2025-03 的规范更新里被标记为 deprecated**，推荐改用单端点的 **Streamable HTTP**。能说出这条，说明你跟进过协议演进，不是背的旧稿。

### Q11. MCP 和 Function Calling 有什么区别？

- **Function Calling 是「调用语言」**：定义模型怎么表达"我要调哪个函数、参数是什么"；
- **MCP 是「工具生态协议」**：定义工具怎么标准化打包、注册、被 AI 客户端发现。

**关键认知：MCP 底层其实仍然靠 Function Calling 来触发工具调用**，MCP 只是在它之上加了一套工具发现与管理的框架，让工具实现一次、到处复用。

### Q12. 什么时候用 Function Calling，什么时候用 MCP？

判断的核心问题只有一个：**这个工具会不会在这个应用之外被用到？**

| 场景 | 选择 | 理由 |
| --- | --- | --- |
| 单个应用、临时接一两个工具、不需要复用 | Function Calling | 简单直接，不引入额外进程和配置 |
| 工具要被多个应用/团队复用 | MCP Server | 一次实现到处复用 |
| 做 Agent 系统，工具来源多、数量大 | MCP | 手写 Function Calling 的维护成本会让代码失控 |

### Q13. 🆕 MCP 的安全机制有哪些？有什么风险？

**机制侧：**（2025-06 规范强化了授权）

- Server 被定位为 **OAuth 2.1 Resource Server**，Client 需持有合法 token 才能访问；
- Tools 有副作用的操作**必须经过用户授权/确认**；
- `roots` 机制限定 Server 可访问的目录边界，做最小权限隔离。

**风险侧（面试常问的"阴暗面"）：**

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| **工具投毒 / Prompt Injection** | 恶意工具描述或工具返回的外部数据里藏指令，劫持模型行为 | 工具来源白名单、返回内容做隔离与清洗 |
| ** rug pull（工具名变更）** | Server 更新后悄悄改工具语义 | 版本锁定、变更审计 |
| **越权访问** | Server 拿到过高权限读到本地敏感文件 | 最小权限 + roots + 沙箱运行 |

### Q14. 🆕 MCP 除了 Tools 还有哪些高级能力？

除三类基础能力外，规范还定义了几个双向交互能力（体现"Server 也能反过来用 Client"）：

- **Sampling**：Server 可以反过来请求 Client 侧的 LLM 做一次补全（让 Server 具备"智能"）；
- **Elicitation**：Server 执行过程中反过来向用户追问补充信息；
- **Roots**：Client 告知 Server 可操作的根目录边界。

## 三、Agent Skill

### Q15. Skill 是什么？

Agent Skill 是把「指令 + 脚本 + 模板」一体化打包成可复用能力包的机制。关键在于三件事：**Agent 能自动发现它、按需加载它、在需要时调用里面的脚本和资源**。

它不只是"存 prompt"，而是一份 Agent 能自己翻阅的**操作手册 + 工具箱**。每个 Skill 是一个文件夹，里面有 `SKILL.md` 指令文件，还可以带脚本、模板、参考文档。

### Q16. MCP 和 Agent Skill 的区别是什么？

- **MCP 解决「Agent 怎么获得外部能力」**：把数据库、API、文件系统标准化封装成服务，让 Agent 能查数据、调接口、读写文件；
- **Skill 解决「Agent 拿到能力之后按什么步骤、什么标准完成任务」**：把完成某类工作的知识和流程打包成可复用模块。

> 类比：MCP 是给 Agent 配齐**工具**（扳手、螺丝刀），Skill 是教它**怎么用这套工具按流程修好车**。

### Q17. Function Calling、MCP、Skill 三者有什么区别？（高频综合题）

| 层次 | 概念 | 解决的问题 |
| --- | --- | --- |
| 底层 | **Function Calling** | 模型怎么调函数 → 输出结构化 JSON |
| 中层 | **MCP** | 工具怎么暴露给模型 → 外部能力标准化封装，一次实现到处复用 |
| 上层 | **Agent Skill** | 拿到工具后按什么流程完成任务 → 执行步骤、标准、脚本、模板打包 |

## 四、A2A 协议

### Q18. A2A 是什么？和 MCP 什么关系？

A2A 是 Google 于 2025 年发起（后捐赠给 Linux Foundation）的开放协议，专门解决**多个 AI Agent 之间怎么通信协作**。

| 协议 | 方向 | 解决问题 |
| --- | --- | --- |
| **MCP** | 向下 | 单个 Agent 怎么连工具和数据 |
| **A2A** | 向上 | 多个 Agent 之间怎么分工协作 |

**两者互补不冲突**：一个 Agent 通过 A2A 把子任务委托给另一个专业 Agent，接收方按自己声明的 Skill 承接；被委派方内部再用 MCP 去调工具。复杂多 Agent 系统里两个都要用。

### Q19. A2A 的核心机制是什么？

- **Agent Card**：JSON 格式的能力声明（能干什么、怎么连、要不要鉴权），用于自动发现；
- **Task 状态机**：支持异步长任务，`submitted → working → input-required → completed/failed`，支持流式推送中间结果。

> 一句话总结：**A2A 本质就是 Agent 世界的微服务架构**——Agent Card 是服务注册中心里的服务描述，Task 是异步任务，A2A 是 RPC 调用协议。

## 五、通信协议（流式 / 实时）

### Q20. SSE 和 WebSocket 的区别和局限性？

- **SSE**：服务端**单向**推送，客户端只能收，想发消息只能另起一个 HTTP 请求；基于原生 HTTP，轻量、运维简单；
- **WebSocket**：**全双工**，双方随时可主动发消息，但需要独立的协议升级、连接管理和心跳。

**为什么 LLM 流式输出用 SSE 就够？** 模型一直在推 token、用户只是看，天然是单向流；复杂度和运维成本都更低。**OpenAI 和 Anthropic 的流式 API 用的都是 SSE。**

WebSocket 的复杂性只有在**真正需要双向实时交互**时才值得引入——比如用户要在模型说话过程中随时打断（barge-in）。

### Q21. 实时语音对话为什么要用 WebRTC，而不是 WebSocket？

核心原因：**WebSocket 基于 TCP，而 TCP 的可靠性设计在实时语音里反而是负担。**

| 维度 | WebSocket（TCP） | WebRTC（UDP） |
| --- | --- | --- |
| 丢包处理 | 等待重传，队头阻塞 → 延迟抖动 | 不重传，用插值/PLC 算法填补 → 延迟稳定 |
| 典型延迟 | 较高且不稳定 | **50 ~ 150 ms** |
| 音频能力 | 需自己实现 | **内置回声消除（AEC）、噪声抑制、抖动缓冲** |
| 适用场景 | 文本、控制信令 | 实时语音/视频 |

一句话：**用一点点音质损失，换来稳定的低延迟**，这是实时语音场景的正确取舍。

### Q22. 🆕 四种实时通信方式怎么选？

| 方式 | 方向 | 开销 | 适用 |
| --- | --- | --- | --- |
| 轮询 | 拉 | 高（大量空请求） | 几乎不用 |
| 长轮询 | 拉 | 中 | 兼容性兜底 |
| **SSE** | 单向推 | 低 | **LLM token 流式输出**（首选） |
| **WebSocket** | 全双工 | 中 | 需要打断、双向交互 |
| **WebRTC** | 全双工（UDP） | 中高 | 实时语音/视频 |

## 六、LLM 网关

### Q23. 为什么需要 LLM 网关？LiteLLM 解决了什么？

LiteLLM 是目前最活跃的开源 LLM 网关，核心价值四条：

1. **多模型统一接口**：业务代码只调一个地方，换模型只改网关配置，不动应用代码；
2. **API Key 集中管理**：不用每个服务都存一份 Key，降低泄漏风险；
3. **限流与配额**：给不同团队分设 token 预算，防止某个团队把公司额度打爆；
4. **成本追踪**：所有请求的 token 用量在网关统一记录，方便定位"哪个服务最烧钱"。

### Q24. LLM 网关区别于普通 API 网关的亮点功能？

**语义缓存**：用向量相似度匹配语义相近的问题，命中缓存直接返回历史答案，**跳过 LLM 调用**——省钱还降延迟。

（其他亮点：多模型 fallback 降级、请求级重试、按租户的成本归因。）

## 七、高频补充题（🆕 新增）

### Q25. 什么是 ReAct？它和 Function Calling 什么关系？

ReAct = **Reason（推理）+ Act（行动）**交替进行的范式：模型先输出"思考"（Thought），再输出"行动"（Action = 工具调用），拿到 Observation 后再进入下一轮思考，直到得出答案。

**关系**：ReAct 是**策略层**的方法论（决定"什么时候想、什么时候调"），Function Calling 是**执行层**的机制（决定"调用怎么表达"）。工程实现上，ReAct 的 Action 步骤通常就是用 Function Calling 落地的。

### Q26. 工具调用和 RAG 有什么区别？什么时候用哪个？

| 维度 | RAG | 工具调用 |
| --- | --- | --- |
| 拿到什么 | **静态知识**（文档、知识库） | **动态能力**（实时数据、执行动作） |
| 有无副作用 | 只读，无副作用 | 可能有副作用（下单、发邮件） |
| 典型问题 | "公司差旅报销标准是什么" | "帮我查一下明天北京的天气" |

**结论**：不是二选一。复杂 Agent 里二者并存——RAG 负责"知道"，工具调用负责"做到"。

### Q27. Agent 的工具调用循环怎么防止跑飞？

四道保险：

1. **最大轮数** `max_iterations`（如 10 轮），到点强制收敛输出；
2. **失败熔断**：同一工具连续失败 N 次，不再重试，转交兜底策略；
3. **超时控制**：单轮工具执行设超时，避免卡死；
4. **人工接管**：高风险操作（支付、删数据）走 human-in-the-loop 确认。

### Q28. 工具数量很多时（几十上百个）怎么保证选对？

- **意图路由**：先用一次轻量分类，把候选工具从 100 个缩小到 5~10 个再交给模型；
- **工具检索**：把工具描述向量化，用问题语义检索 Top-K 工具动态注入；
- **分层组织**：按域拆成多个 MCP Server，按需挂载而不是一次性全塞；
- **命名与描述规范**：描述里写清"什么时候用 / 什么时候不要用"。

> 经验值：单次请求暴露给模型的工具控制在 **20 个以内**，准确率明显更好。

### Q29. 🆕 为什么说推理模型（如 o1/R1 类）早期不支持 MCP / 工具调用？

推理模型在给答案前会先跑一段**完整的思维链（thinking）**，这个过程是一次性连续生成的，**不能中途打断**；而工具调用天然是多轮交互（输出请求 → 暂停等结果 → 拿到结果继续生成），两种模式不兼容——没法在思考链跑到一半时暂停去等工具结果，否则推理上下文就断了。

MCP 底层靠 Function Calling 驱动，**FC 支持不好，MCP 自然也用不了**。

> 补充（体现跟进）：这是早期状态，新一代推理模型已逐步支持"多轮思考 + 工具调用交替"，但**思考块不可回溯、思考内容不进下一轮上下文**仍是工程约束。

### Q30. 🆕 怎么评估一个模型的工具调用能力？

业界常用 **BFCL（Berkeley Function Calling Leaderboard）**，主要考察四个维度：

| 维度 | 考察点 |
| --- | --- |
| **简单调用** | 单工具、参数正确的 JSON 生成 |
| **多工具选择** | 从多个相似工具里选对 |
| **并行调用** | 无依赖关系时能否一次发多个调用 |
| **相关性判断** | 不需要工具时能否**不调**（不过度调用） |

> 除了公开榜单，落地时一定要建**自己的评测集**：用真实业务工具 + 真实 query，统计"选对工具率"和"参数正确率"两个指标。

## 附录：面试口述速记版（30 秒答完三件套）

> **Function Calling** 是模型表达调用意图的语言，运行时是"两轮对话 + 中间执行"的闭环；
> **MCP** 是工具生态协议，用 JSON-RPC 2.0 统一消息格式、stdio/Streamable HTTP 两种传输，把工具一次实现到处复用，底层仍靠 FC 触发；
> **Skill** 是上层的任务流程封装，教 Agent 拿到工具后怎么按标准干活；
> **A2A** 则更往上一层，解决 Agent 与 Agent 之间的协作。四者是逐层依赖的关系，不是竞争关系。
