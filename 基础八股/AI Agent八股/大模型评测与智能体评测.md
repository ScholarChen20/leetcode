## 知识地图：评测的三层金字塔

```
        ┌──────────────────────────────┐
        │  ③ Agent 系统评测             │  目标是否达成？轨迹是否合理？成本与安全？
        │     outcome / trajectory      │  难点：多步、有状态、非确定性、有副作用
        ├──────────────────────────────┤
        │  ② 应用 / 组件评测            │  RAG 召回与忠实度、工具调用准确率
        │     retrieval / tool calling   │  难点：必须分层归因才能定位问题
        ├──────────────────────────────┤
        │  ① LLM 能力评测              │  知识、推理、代码、指令遵循、安全
        │     capability benchmark       │  难点：数据污染、静态题被刷穿
        └──────────────────────────────┘
```

**一句话区分**：评测 LLM 问的是「它会不会」，评测 Agent 问的是「它能不能稳定办好一件事」。

## 一、评测基础方法论

### Q1. 为什么大模型评测这么难？

三个根本性难题，面试开场抛这个很加分：

1. **主观性**：开放式生成没有唯一标准答案，"好"难以量化；
2. **非确定性**：同一输入多次采样结果不同，单次评分不可靠，**必须多次采样看分布**；
3. **数据污染与饱和**：公开 benchmark 极易混入训练数据，且一经发布就开始衰减。

> 附加难题：**评测本身有成本**——大规模评估一次动辄几千元，导致很多团队用几十条样本仓促下结论。

### Q2. 评测应该分几层做？

| 层次 | 评什么 | 手段 | 何时用 |
| --- | --- | --- | --- |
| **能力层** | 模型本身的通识/推理/代码能力 | 公开 benchmark + 自建单选题 | **选模型**时 |
| **组件层** | RAG 召回、工具调用、Prompt 模板 | 分层指标（Hit@K、Faithfulness、参数正确率） | **优化单个环节**时 |
| **系统层** | 端到端任务是否达成 | 黄金数据集 + grader | **上线前 + 回归**时 |
| **在线层** | 真实用户是否满意 | 埋点、踩率、转人工率、A/B | **持续运营**时 |

> 核心原则：**越往上越贵越慢，但越接近真实价值**；层级越低越适合快速迭代。

### Q3. 评测数据从哪来？

| 来源 | 优点 | 缺点 | 用途 |
| --- | --- | --- | --- |
| **公开 Benchmark** | 免费、可比、有公信力 | 会污染、会饱和、与业务脱节 | 模型选型粗筛 |
| **自建黄金数据集** | 贴合业务、分布真实 | 构建成本高、需维护 | **核心资产** |
| **线上日志采样** | 真实分布、源源不断 | 有噪声、需脱敏 | 补充与刷新评测集 |
| **合成数据** | 量大、快、可控 | 分布偏移、继承生成模型的偏差 | 冷启动、扩充长尾 case |

> 实战打法：**公开 benchmark 粗筛 → 线上日志采样确定分布 → 人工精标 100~300 条建黄金集 → 合成数据扩充边缘 case**。

### Q4. 打分器（Grader）有哪几种？

评测系统的核心是 Grader，一共四类，**生产上必须组合使用**：

| Grader 类型 | 怎么打分 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| **代码型** | 规则 / 正则 / 单测 / SQL 校验 / 字符串匹配 | 100% 确定、零成本、可复现 | 只能判对错，判不了质量 | 客观题、代码执行、schema 校验 |
| **模型型**（LLM-as-Judge） | 让 LLM 按 rubric 打分 | 能评开放式质量、覆盖广 | 有偏差、有成本、不稳定 | 开放式生成、轨迹评审 |
| **人工型** | 专家按标注规范打分 | 最准，最终裁判 | 贵、慢、难规模化 | 校准 judge、关键业务抽检 |
| **环境型** | 真实执行 / 沙箱验证（跑测试、调 API） | 最客观，看真实结果 | 需可执行环境 | 代码 Agent、GUI / Web Agent |

> 关键认知：**LLM-as-Judge 必须用人工标注校准对齐，否则你只是在放大另一个模型的偏见。**

### Q5. 怎么判断差异是真提升还是随机波动？

答不出这点会显得没做过评测实操：

1. **多次采样**：同一条 case 至少跑 3~5 次取均值，单次结果没有意义；
2. **样本量要够**：几十条 case 的差异基本是噪声，正式对比通常要 ≥200 条；
3. **报告置信区间**：说「68.3% ± 2.1%」而不是孤零零一个点；
4. **配对检验**：同一批评测集做配对对比，比独立数据集更敏感；
5. **消除格式偏置**：选项顺序、答案格式都会影响分数，评测时要做位置打乱等去偏处理。

## 二、LLM 能力评测

### Q6. 主流 Benchmark 都有哪些？各自考什么？

**回答策略**：不要背全表，按能力维度分类说，说 8~10 个就够。

| 能力维度 | 代表 Benchmark | 备注 |
| --- | --- | --- |
| **综合知识** | MMLU、C-Eval / CMMLU（中文） | MMLU 已接近饱和，区分度下降 |
| **高阶推理** | MMLU-Pro（需 CoT）、GPQA Diamond（博士级）、HLE（极难） | 用于区分头部模型 |
| **数学** | GSM8K、MATH、AIME、FrontierMath | GSM8K 已饱和，现在看 AIME 及以上 |
| **代码** | HumanEval、MBPP、**SWE-bench Verified**、LiveCodeBench | SWE-bench 是最被认可的工程能力指标 |
| **指令遵循** | **IFEval**（可验证约束） | 比开放式打分客观得多 |
| **多轮对话** | MT-Bench、LiveBench | 多轮质量与角色扮演 |
| **竞技场** | **LMArena**（原 Chatbot Arena） | 人类盲测投票，最贴近主观感受 |
| **长上下文** | Needle in a Haystack、**RULER**、LongBench | 长文本能否找到并利用信息 |
| **幻觉** | TruthfulQA、HalluQA、FacTool | 编造倾向 |
| **安全对齐** | 各类红队集、TrustGPT | 拒答率与越狱防御 |
| **智能体能力** | GAIA、**τ-bench**、WebArena、**OSWorld**、**BFCL** | 见 Q22 |

> **加分点**：选 benchmark 的第一原则是**看它有没有饱和、裁决是否客观可验证**。近年趋势是从静态选择题转向**可执行验证（verify-based）**，例如 LiveCodeBench 按题目发布时间做时间切分来抗污染。

### Q7. 客观题常用的自动指标有哪些？

| 指标 | 计算 | 适用 | 坑 |
| --- | --- | --- | --- |
| **Accuracy** | 正确数 / 总数 | 选择题、分类 | 类别不平衡时失真 |
| **EM（Exact Match）** | 字符串完全命中 | 有唯一答案的抽取 / 短答 | 过严，同义答案判错 → 需先归一化 |
| **F1** | 精确率与召回率的调和平均 | 抽取式问答 | 对答案粒度敏感 |
| **pass@k** | 生成 k 个候选至少一个通过 | **代码、数学** | 必须标明 k |

> EM 的工程细节：计算前必须**归一化**（小写、去标点、去冠词、数字格式统一），否则系统性低估。

### Q8. pass@k 为什么不能简单相除？

朴素算法是「通过数 / 总数」，但只采 k 个样本会低估真实能力（没采到的样本里可能也有通过的）。Codex / HumanEval 论文用的是无偏估计：

```
pass@k = E[ 1 - C(n - c, k) / C(n, k) ]
```

其中 `n` 为总采样数、`c` 为通过数，含义是"从 n 个样本中抽 k 个，至少一个通过"的概率期望。

> 面试只要答出：**pass@k 需要采样 n ≥ k 并做组合数校正，不能简单相除**，并知道它衡量的是"模型在这道题上的能力上界"。

### Q9. BLEU / ROUGE / BERTScore 有什么区别？为什么不适合作开放式评测？

| 指标 | 原理 | 优点 | 致命缺陷 |
| --- | --- | --- | --- |
| **BLEU** | n-gram 精确率 + 长度惩罚 | 快、无模型依赖 | 只看字面重叠，**语义相反也能得分** |
| **ROUGE** | n-gram 召回率 | 适合摘要 | 同样不看正确性 |
| **BERTScore** | 用上下文 Embedding 算相似度 | 能识别同义改写 | 仍无法判断**事实正确性** |

> 结论：**三者衡量的都是"像不像参考答案"，而不是"答案对不对"**。开放式生成必须用 LLM-as-Judge 或人工。

### Q10. LLM-as-Judge 怎么做才靠谱？有什么偏差？

**基本流程**：构造 rubric（评分细则）→ 把待评答案 + 参考答案 + rubric 喂给 judge 模型 → 解析分数。

**五种已知偏差（背下来很有杀伤力）：**

| 偏差 | 表现 | 缓解 |
| --- | --- | --- |
| **位置偏差** | 偏爱第一个选项 | 交换顺序各评一次取平均 |
| **冗长偏好** | 越啰嗦分越高 | rubric 明确约束长度，或做长度归一 |
| **自我偏好** | 偏爱自家模型的输出 | 换厂商做 judge，或多 judge 投票 |
| **锚定效应** | 给了参考答案就被牵着走 | 无参考打分与有参考打分结合使用 |
| **分数聚集** | 分数挤在中间档不敢给极端值 | 先输出判断依据再打分，细化分档描述 |

**可靠性保障（工程必答）：**

1. 用**人工标注集**算 judge 与人的一致率（Cohen's kappa），低于 85% 就该重写 rubric；
2. **定期校准**：模型升级后重新校验 judge，防止 judge 漂移；
3. **成对比较比绝对打分稳定得多**——让 judge 判「A 和 B 谁更好」，比让它打 7 分可靠。

### Q11. 竞技场排名（Elo）是怎么出来的？

LMArena 这类平台用的是**人类盲测成对比较**：

1. 随机抽两个匿名模型回答同一问题 → 用户投票选哪个更好；
2. 用投票结果拟合 **Bradley-Terry 模型**（Elo 是其简化近似），得出隐含实力分；
3. 输出置信区间，并按题型分类排名。

**优点**：贴近真实主观感受，难以定向刷分（题目由用户现场产生）。
**缺点**：容易被"用户审美"（格式、长度）带偏；样本分布不均；覆盖不了垂直领域。

### Q12. 什么是数据污染？怎么检测和规避？

**定义**：评测集内容出现在训练数据中，导致分数虚高，无法反映真实泛化能力。

| 检测方法 | 思路 |
| --- | --- |
| **n-gram 重叠** | 用评测题的 n-gram 去训练集检索看命中率 |
| **困惑度法** | 污染样本的模型困惑度显著偏低 |
| **成员推断** | 让模型判断文本是否出现在训练集中 |
| **Canary 字符串** | 在评测集埋特殊标记串，检测是否被记住 |
| **时间切分法** | **最可靠**：只用训练截止之后发布的数据评测 |

**规避实践**：优先用带时间切分的 benchmark；用自建私有评测集；保留 heldout 集永不参与调参。

### Q13. 长上下文怎么评？

三种递进思路：

1. **Needle in a Haystack（大海捞针）**：在超长文本插入一句无关事实让模型捞出来 → 只考检索，现在经常全绿；
2. **RULER**（NVIDIA）：升级为多针、多跳、变量追踪、聚合，更接近真实使用；
3. **LongBench 等真实任务**：长文档 QA、总结、仓库级代码理解。

> **面试要点**：只报"大海捞针全绿"是不够的，那只是及格线；真实瓶颈是**多跳推理与中段信息利用（lost-in-the-middle）**。同时别忘了算**成本与延迟**。

### Q14. 幻觉怎么评测？

| 方法 | 思路 | 适用 |
| --- | --- | --- |
| **TruthfulQA / HalluQA** | 构造人类常见误解类问题 | 通用 / 中文对比 |
| **FacTool / FactScore** | 把答案拆成原子事实，逐条做外部核查 | 长文本生成（传记、摘要） |
| **SelfCheckGPT** | **不依赖外部知识**：多次采样，若互相矛盾则大概率幻觉 | 黑盒场景 |
| **引用核查** | 要求标注来源，逐条验证引用是否支持结论 | **RAG，最实用** |

> 工程结论：RAG 场景最有效的幻觉评测就是**引用核查**——把幻觉指标落地成对 chunk 的可验证性检查，成本低且全自动。

### Q15. 安全性评测怎么做？

三个核心动作：

1. **红队测试**：人工或自动化构造攻击，覆盖有害内容、越狱提示、隐私泄漏、提示注入；
2. **量化指标**：**ASR（攻击成功率）** 越低越好；同时统计**拒答率**；
3. **双向评测**：既评"该拒的是否拒了"，也评"不该拒的是否拒了"。

> **过度拒答（Over-refusal）** 是高频追问点：安全指标不能只看拒得多不多，正常请求被误拒同样是缺陷。安全与有用性是一对 trade-off，两条曲线必须同时看。

## 三、Agent 评测

### Q16. Agent 评测和 LLM 评测的本质区别是什么？

**一句话：LLM 评测的是「一次输出」，Agent 评测的是「一段有副作用的执行过程」。**

| 维度 | LLM 评测 | Agent 评测 |
| --- | --- | --- |
| 对象 | 单轮输入输出 | **多步轨迹 + 最终结果** |
| 状态 | 无状态 | **有状态**，上下文随步骤演化 |
| 副作用 | 无 | **有**（写文件、下单、调外部 API） |
| 不确定性来源 | 采样 | **更高**：模型 + 环境 + 工具 + 网络 |
| 能否重放 | 容易 | **难**，需环境快照 / 沙箱 / mock |
| 成本 | 次要指标 | **核心指标**：步数、token、耗时、钱 |

> 由此引出 Agent 评测的两项基础设施：**可观测（全量 trace 记录）** 与 **可重放（环境确定性：固定时间、mock 外部依赖、容器快照）**。没有这两样，评测结果不可信也不可回归。

### Q17. Agent 评测应该分哪几层？

| 层 | 评什么 | 代表指标 |
| --- | --- | --- |
| **Step（单步决策）** | 该调哪个工具、参数对不对 | 工具选择准确率、参数正确率 |
| **Trajectory（轨迹）** | 执行过程是否合理 | 步数、冗余调用率、是否陷循环、是否走回头路 |
| **Outcome（结果）** | 任务有没有办成 | 任务成功率、pass^k |
| **System（系统）** | 工程与治理质量 | 延迟 P95、单次成本、错误恢复率、安全违规率 |

> 高频追问：「端到端成功率掉了你怎么定位？」答：**从 step 层往上查**——先看工具选择与参数正确率（是不是换了模型版本导致 schema 理解退化），再看轨迹层（是不是多绕几步把上下文撑爆），最后看 outcome。这条归因链路详见 `智能体高频50.md` Q29。

### Q18. 轨迹（Trajectory）具体怎么打分？

四类做法，成本从低到高：

| 方法 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **精确匹配** | 与标注的标准步骤序列完全一致 | 严格、全自动 | 过苛，忽视殊途同归 |
| **关键步骤子集** | 只要求命中若干关键动作（must-include / must-not） | **性价比最高** | 需人工定义关键点 |
| **LLM-as-Judge 评审轨迹** | judge 按 rubric 评判过程合理性 | 灵活，能评开放式过程 | 有偏差、有成本 |
| **环境验证** | 检查执行后的环境终态（DB 记录、文件内容） | **最客观** | 需要可执行环境 |

> 推荐组合：**关键步骤 + 环境验证**为主，LLM-judge 兜住难判的部分。

### Q19. 什么是 pass^k？和 pass@k 有什么区别？

这是 Agent 评测里**最关键、也最容易被忽略**的一道题（由 τ-bench 等 Agent 基准提出）：

| 指标 | 含义 | 衡量的是 | 适用场景 |
| --- | --- | --- | --- |
| **pass@k** | k 次尝试中**至少一次成功** | **能力上界**：它能不能做到 | 探索型任务、辅助创作（用户自己挑最好的） |
| **pass^k** | k 次尝试**全部成功** | **可靠性**：能不能每次都稳 | 无人值守、自动化业务（客服、交易、运维） |

假设单次成功率 p = 0.7：

```
pass@3 = 1 - 0.3³ ≈ 97.3%     pass^3 = 0.7³ ≈ 34.3%
```

同一个模型：三次尝试里"至少成一次"高达 97%，但"次次都成"只剩 34%。

> **面试金句**：pass@k 回答的是「它能不能做到」，pass^k 回答的是「我能不能放心让它自动跑」。**做 Agent 产品，后者才是上线门槛。**

### Q20. Agent 的非确定性怎么量化？

同一任务跑多次结果不同，单点分数毫无意义。标准做法是采样 K 次后报告一组分布指标：

| 指标 | 含义 |
| --- | --- |
| **mean@K** | K 次平均成功率（期望表现） |
| **pass^K** | K 次全部成功的比例（一致性 / 可靠性） |
| **标准差** | 结果稳定程度 |
| **P50 / P95 步数与耗时** | 长尾风险（有的 case 会跑飞） |

> 还必须看 **worst case**：Agent 的失败常常是灾难性的（删错文件、下单金额错），所以除了均值还要判断"最坏情况是否可接受"——这正是 Human-in-the-loop 存在的理由。

### Q21. 工具调用能力怎么评测？

三个递进维度（也是 BFCL 等基准的考察点）：

1. **选择准确率**：该不该调、调哪个工具；
2. **参数正确率**：函数名对了，但参数值 / 类型 / 必填项是否合法（可用 schema 校验做**代码型 grader**）；
3. **克制能力**：不该调工具时能否不调（很多模型有过度调用倾向）；
4. **并行调用**：无依赖时能否并发，有依赖时能否正确串行。

> 落地建议：不要只依赖公开榜，**用业务里真实的工具定义和真实 query 建评测集**，统计「选对工具率」和「参数正确率」两个指标。这与 `LLM工具调用(整理版).md` Q30 呼应。

### Q22. 主流 Agent Benchmark 有哪些？

| Benchmark | 任务类型 | 特点 |
| --- | --- | --- |
| **GAIA** | 通用助手任务（需联网、多步推理） | 人类几乎满分、GPT-4 时代只有个位数，区分度好 |
| **AgentBench** | 多环境（OS、DB、Web、知识图） | 覆盖广，偏综合 |
| **WebArena** | 真实 Web 网站操作（自建站点） | 可复现、可执行，结果客观 |
| **OSWorld** | 真实操作系统 GUI 操作 | 最接近桌面 Agent 实战 |
| **τ-bench（tau-bench）** | 工具-用户-Agent 三方交互（客服场景） | **提出 pass^k**，强调可靠性 |
| **BFCL** | Function Calling 能力 | 单双调用、并行、相关性判断 |
| **SWE-bench Verified** | 真实 GitHub issue 修复 | 代码 Agent 事实标准 |
| **BrowseComp / HLE** | 高难信息检索 / 极难综合题 | 区分头部模型 |

> 一句话总结趋势：**从"能不能答对"走向"能不能在真实环境里把事办成"，并且裁决从人判转向可执行验证**。

### Q23. Agent 的成本与效率怎么评？

常被忽略但业务方最关心的一组指标：

| 指标 | 说明 | 为什么重要 |
| --- | --- | --- |
| **平均步数** | 完成任务用了几轮 tool loop | 步数与 token 消耗、失败率都正相关 |
| **单次任务成本** | token 费用 + 工具调用费用 | 决定毛利能不能覆盖 |
| **P95 延迟** | 长尾体验 | 用户感知的是慢的那一次 |
| **上下文膨胀率** | 终态上下文 / 初始上下文 | 反映是否需要引入压缩策略 |
| **冗余调用率** | 重复且无收益的调用占比 | 直接对应优化空间 |

> **优化闭环**：步数下降 → 上下文变短 → 延迟下降、成本下降、同时 pass^k 通常上升（每多一步就多一次失败机会）。

### Q24. Agent 的安全与可控性怎么评？

三条红线，缺一不可：

1. **越权控制**：是否执行了未被授权的操作（尤其写操作、支付、删除）→ 用 Harness 的权限层强制拦截，评测时统计"未授权执行次数"必须为 0；
2. **提示注入防护**：外部环境返回内容里藏指令时是否被劫持 → 构造注入用例，测被诱导执行率；
3. **不可逆操作管控**：高风险动作是否走了人工确认（human-in-the-loop）→ 统计绕过率。

> 补充一个常被问的点：**可观测性本身也是评测对象**。没有 trace（每步的输入、工具调用、耗时、token），前面所有指标都无从计算。生产上线前先问能不能把一次完整轨迹完整复盘出来。

## 四、搭建评测体系

### Q25. 从 0 到 1 怎么搭一套评测体系？

按顺序做这八步：

1. **先定义成功标准**：这个任务"做成"长什么样？写清楚可验证的判据；
2. **建黄金数据集**：线上日志 + 人工构造，100~300 条起步，覆盖典型 + 长尾；
3. **选 / 写 Grader**：能代码判的绝不交给模型；开放式部分用 judge，并用人工标注校准；
4. **定采样策略**：每条跑 K 次（K=3~5），同时输出 mean@K 和 pass^K；
5. **接可观测**：全量 trace 落库，字段至少包含输入、每步工具调用、耗时、token、最终状态；
6. **跑基线**：记录当前版本的全套指标作为 baseline；
7. **纳入 CI / 回归**：改 Prompt、换模型、加工具都必须跑一次评测集，设通过阈值卡住；
8. **线上闭环**：踩率、转人工、点赞点踩回流，失败的 case 沉淀进黄金集。

> 一句话：**评测体系不是一次性项目，而是一条"失败case → 进评测集 → 防回归"的自动迭代流水线。**

### Q26. 换模型时怎么做回归？

这是 LLM 应用最容易翻车的场景：

| 步骤 | 动作 |
| --- | --- |
| 1 | 固定**同一套评测集**，先跑旧版作为 baseline，再跑新版做**分维度对比**（不只看总分） |
| 2 | 重点看**分层指标**：工具选择准确率、参数正确率、格式合规率、拒答率 |
| 3 | 检查**格式与风格**是否变化（下游解析器、正则、JSON schema 是否被破坏） |
| 4 | 小流量灰度 + 线上 A/B，观察真实分布下的表现 |
| 5 | 保留快速回退开关 |

> 经验：换模型最常见的失败不是"能力下降"，而是**输出格式变了导致下游解析崩**——这类问题在总分指标上完全看不出来。

### Q27. 线上评估怎么做？

| 手段 | 做法 | 看什么 |
| --- | --- | --- |
| **A/B 测试** | 新旧版本分流 | 核心业务指标 + 满意度 |
| **灰度发布** | 小比例放量逐步扩大 | 错误率、回滚成本 |
| **隐式反馈** | 采纳率、修改率、重试率、会话时长 | 用户是否真的满意 |
| **显式反馈** | 点赞点踩、评分 | 主观质量 |
| **人工抽检** | 每日抽检 N 条 bad case | 发现指标体系盲区 |

> 踩率 / 转人工率是 To B 场景最诚实的指标：**离线指标全绿但线上踩率飙升，一定是评测集失真了。**

### Q28. RAG 的评测和 Agent 的评测怎么衔接？

两者不是两套体系，而是**同一套分层评测在不同系统上的投影**：

| 系统 | 组件层指标 | 系统层指标 |
| --- | --- | --- |
| **RAG** | Hit@K、MRR、Context Precision/Recall | Faithfulness、Answer Relevancy |
| **Agent** | 工具选择/参数准确率、单步决策准确率 | 任务成功率、pass^k、P95 延迟、单次成本 |
| **Agentic RAG** | 上面两行全部适用 + 检索触发时机是否正确 | 是否多轮补齐信息、是否过早/过晚停止 |

> 详细指标口径见 `RAG(整理版).md` Q28/Q29。

### Q29. 评测有哪些常见误区？

| 误区 | 后果 | 正解 |
| --- | --- | --- |
| **只看总分** | 掩盖分项退化 | 分层看指标 + 看题型分布 |
| **只跑一次** | 非确定性让结果失真 | 多次采样看均值与方差 |
| **只用公开榜选模型** | 与业务分布不符 | 自建业务评测集定生死 |
| **评测集参与调参** | 过拟合评测集 | 保留 heldout 集永不调参 |
| **judge 不校准** | 放大偏见 | 人工标注对齐，算一致率 |
| **不看成本/延迟** | 上线即破产 | 与效果指标同表汇报 |
| **只评 happy path** | 上线被边缘 case 打崩 | 专门建一类"对抗/异常"用例 |

### Q30. 推理模型（thinking 类）的评测有什么特殊性？

四点：

1. **要区分「思考预算」**：同一模型给不同 thinking token 预算，分数差异巨大，对比时必须对齐预算；
2. **答案抽取**：很多推理模型的输出混在 thinking 块里，评测脚本要正确解析最终答案，解析失败常被误判为答错；
3. **成本要单独计**：thinking token 计入输出成本，评测报告里必须单列；
4. **稳定性更值得关注**：长思考路径的方差通常更大，多跑几次看 pass^k。

### Q31. 评测在 CI 里怎么落地？

工程化 Checklist：

- 评测集**版本化**（像管理代码一样管理 case，改动需 review）；
- 每次 PR / Prompt 变更**自动跑核心集**（跑全量太贵，可分层：核心 50 条必跑，全量夜间跑）；
- 设置**阈值门禁**：核心指标下降超过 X% 直接阻断合并；
- **failure case 自动入库**：失败的样本自动生成 issue，人工确认后转成正例加入评测集；
- 结果**可对比可视化**：每次跑分入库，画趋势图。

### Q32. Agent 评测中最容易被追问的三个问题是什么？

提前准备这三个，命中率极高：

1. **「你怎么保证评测结果可复现？」** → 环境 mock、固定时间/随机种子、记录版本（模型版本号 + Prompt hash + 工具版本）。
2. **「端到端成功率掉了怎么定位？」** → 分层归因：step → trajectory → outcome → system，配合 trace 逐层排查。
3. **「上线了发现离线指标和线上感受不一致怎么办？」** → 评测集分布失真，从线上日志重新采样刷新评测集，并把线上失败 case 沉淀进来。

### Q33. 如果只能记住三个评测结论，是哪三个？

1. **LLM 评测看能力上界（pass@k），Agent 评测看可靠性（pass^k）**——后者才是上线门槛；
2. **必须先分层再归因**：没有分层指标的评测体系 = 只知道变差了，不知道为什么；
3. **评测体系是流水线不是项目**：坏 case 持续回流进评测集，才是它真正的价值。

## 附录：面试口述速记版（60 秒答完"你怎么给一个 Agent 做评测"）

> 我会分四层评：**单步层**看工具选择和参数正确率；**轨迹层**看步数、冗余调用和是否陷循环；**结果层**用**黄金数据集 + 多种 Grader**（能代码判的用代码，开放式用 LLM-judge，judge 再用人工标注校准）；**系统层**看 P95 延迟、单次成本和安全违规率。
> 因为 Agent 有非确定性，每条 case 会**采样 K 次同时报 mean@K 和 pass^K**——pass^k 衡量的是"能不能放心让它自动跑"，这才是上线门槛。
> 前置条件是**可观测和可重放**：全量 trace 记录，外部依赖 mock 掉，环境固定可复现。
> 最后接入 CI：改 Prompt、换模型自动跑核心集，指标退化卡住合并；线上失败 case 自动沉淀回评测集，形成闭环。
