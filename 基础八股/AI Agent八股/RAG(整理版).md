## 知识地图：RAG 标准链路与优化点

```
索引层(怎么存) → 查询层(怎么转) → 召回层(怎么找) → 重排层(怎么筛) → 生成层(怎么答)
  分块策略        Query改写        向量+BM25多路      RRF粗排         Prompt约束
  Embedding      HyDE/Step-back   图检索/SQL        Cross-Encoder    溯源引用
  元数据/权限图   Multi-Query                        MMR去重          拒答门控
```

面试官问"怎么优化 RAG"时，**按这五层逐层作答**，比想到哪说到哪显得体系化得多。

## 一、基础概念

### Q1. RAG 解决什么问题？

RAG（Retrieval-Augmented Generation，检索增强生成）解决 LLM 的三个固有短板：

1. **知识时效性**：模型训练完知识就冻结了，训练截止日之后发生的事一无所知；
2. **私有知识覆盖**：公司内部文档、行业专有数据没进过训练集，对模型是空白的；
3. **幻觉**：没有知识依据时 LLM 容易"自己发挥"，编一个听起来合理但实际错误的答案；给了参考资料后幻觉显著减少。

> 补充两个常被忽略的价值：**可溯源**（答案能标注来源，金融/医疗/法务合规刚需）、**成本低**（更新知识只需重建索引，不用重新训练模型）。

### Q2. RAG 的完整流程？（必须按顺序讲清六步）

| 步骤 | 动作 | 关键细节 |
| --- | --- | --- |
| 1. **Query 预处理** | 改写、HyDE、多角度扩写 | 把口语化问题转成适合检索的形式 |
| 2. **Query Embedding** | 向量化 | **必须用和建库时相同的模型**，否则向量空间不一致 |
| 3. **多路召回** | 向量检索 + BM25 并行 | 用 RRF 融合（因为分数不可比） |
| 4. **Rerank 精排** | Cross-Encoder 打分 | 滤掉粗排噪音，Top-3~5 进 prompt |
| 5. **Prompt 拼装** | 组装上下文 + 约束指令 | 明确"只根据资料回答，不知道就说不知道" |
| 6. **生成 + 溯源** | 输出答案并标引用 | 提升可信度与可核查性 |

> 每个环节都能说出「干什么、为什么需要、有什么坑」，面试官才会认为你不是停留在"检索 + 生成"的表面认知。

### Q3. 🆕 RAG、Fine-tuning、长上下文怎么选？（高频场景题）

| 方案 | 解决什么 | 适合 | 不适合 |
| --- | --- | --- | --- |
| **RAG** | 补**知识** | 知识频繁更新、需要溯源、海量文档 | 需要改变模型的表达风格/推理范式 |
| **Fine-tuning** | 改**能力/风格/格式** | 固定领域术语、固定输出格式、特定任务节奏 | 知识频繁变动（改一次要重训） |
| **长上下文** | 一次塞全部资料 | 文档数量少、需要全文全局理解 | 文档量大（成本高、延迟大、易 lost-in-middle） |

> 最佳实践不是三选一：**RAG 负责"找得到、成本低、可溯源"，长上下文负责"读得全"，Fine-tuning 负责"说得像"**。生产上常见组合是先用 RAG 粗筛到几十条，再交给长上下文模型精读。

## 二、索引层：知识怎么「存」

### Q4. 常见的分块策略有哪些？

| 策略 | 适用文档 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 固定大小 + 重叠 | 纯文本、无明显结构 | 实现简单、chunk 大小可控 | 可能在语义中间截断 |
| 语义边界切割 | 段落分明的文章 | 语义完整，召回质量好 | 实现稍复杂，chunk 大小不均 |
| 标题层级切割 | Markdown、HTML | 天然语义独立，自带结构 metadata | 依赖文档有清晰标题结构 |
| 代码按函数切割 | 代码文件 | 保留代码逻辑完整性 | 需 AST 解析，限定语言 |
| 父子切割 | 各类文档（追求高质量） | 检索精准 + 上下文完整两全 | 存储翻倍、索引复杂 |
| Late Chunking | 各类文档 | chunk 向量保留全文上下文 | 需模型支持长输入 |

### Q5. 🆕 怎么避免语义在切割时被截断？

两个方向：**「切的时候别截断」+「切完之后补上下文」**。

| 方案 | 核心思路 | 适合场景 | 代价 |
| --- | --- | --- | --- |
| 重叠切割 | 相邻 chunk 内容重叠 | 所有场景，**基础兜底** | 存储轻微增加 |
| 语义边界切割 | 在句子/段落边界处切 | 段落结构清晰的文档 | 需 NLP 工具 |
| 句子窗口检索 | 精细检索 + 扩展返回窗口 | 追求高召回精度 | 存储量大 |
| 父子切割 | 小块检索、大块返回 | 通用场景，效果均衡 | 存储翻倍、索引复杂 |
| 命题化切割 | LLM 拆解为独立命题 | 高质量要求、重要知识库 | LLM 调用成本高 |
| Contextual Retrieval | 向量化前为每个 chunk 补全背景上下文 | chunk 孤立感严重的场景 | LLM 成本（可用 Prompt Caching 大幅降低） |

> **落地建议**：重叠切割做兜底 + 语义边界切割保证质量；高质量场景再叠加父子切割或 Contextual Retrieval。

### Q6. 🆕 Chunk size 怎么定？有没有经验值？

没有银弹，但有三个经验起点：

| 维度 | 经验值 | 说明 |
| --- | --- | --- |
| 大小 | 中文 **300~500 字**（约 256~512 token） | 太小语义不完整，太大引入噪音、稀释向量语义 |
| 重叠 | chunk 大小的 **10%~20%** | 兜底跨边界截断 |
| 数量 | 进 prompt 的 chunk **3~5 条** | 再多容易触发 lost-in-the-middle |

正确的打开方式是**用评测集扫参**：按 256/512/1024 三档跑 Hit@K 和 Faithfulness，选拐点。**不要凭感觉调 Chunk size。**

### Q7. Embedding 算法经历了哪三代演进？

| 代际 | 代表 | 机制 | 局限 |
| --- | --- | --- | --- |
| 第一代 **静态词向量** | Word2Vec、GloVe | 每个词映射成固定向量 | 一词一向量，无法处理多义词 |
| 第二代 **上下文相关** | BERT | 同一词在不同语境有不同向量 | 输出 token 级向量，两句比相似度必须拼一起跑——百万文档要跑百万次，**检索速度不可接受** |
| 第三代 **句子级句向量** | SBERT、SimCSE、BGE | 对比学习专为"两段文本有多相似"优化 | **文档向量可离线预计算**，查询只需算一次 → **RAG 标配** |

> 关键区别要讲清楚：第三代之所以能用于检索，本质是把 **O(N) 次在线推理** 变成 **O(1) 次查询 + 一次 ANN 检索**。

### Q8. 选 Embedding 模型看哪三个维度？

1. **中文 support**：中文场景优先选 BGE 系列，实测往往优于 OpenAI 的 text-embedding 系列；
2. **向量维度**：维度越高精度越好，但存储与检索成本越大（如 768 vs 1024 vs 1536）；
3. **最大输入长度**：决定能处理多长的 chunk，超长会被截断。

> 补充两个实战维度：**是否有对应的 Reranker**（BGE 有配套 bge-reranker，中文一致性强）、**是否支持稀疏+稠密混合**（如 bge-m3 一体输出）。

### Q9. 🆕 相似度为什么一般用余弦而不是欧氏距离？

| 度量 | 特点 | RAG 适用 |
| --- | --- | --- |
| **余弦相似度** | 只看方向，忽略模长 | ✅ 默认选择，对文本长度不敏感 |
| **内积（点积）** | 受向量模长影响 | ✅ 若向量已**归一化**，内积 ≡ 余弦，计算更快 |
| **欧氏距离** | 看绝对距离 | ❌ 高维下区分度急剧下降，不推荐 |

> 工程细节：很多库（如 Milvus 的 `IP` 度量）要求先把向量 L2 归一化，之后用内积近似余弦，能省掉一次归一化计算。这也是 BGE 官方推荐 normalize 的原因。

## 三、召回层：知识从哪里「找」

### Q10. 三种召回方式各自的擅长与短板？

| 召回方式 | 擅长 | 短板 | 适合场景 |
| --- | --- | --- | --- |
| **向量检索** | 语义相似、同义词、不同表达 | 精确词语、数字、专有名词、ID | 通用语义检索 |
| **BM25 关键词** | 精确词匹配、专有名词 | 同义词、语义相关但词不重叠 | 大量精确术语/编号的知识库 |
| **多 Query 扩展** | 覆盖不同表述角度 | 增加 LLM 调用开销与延迟 | 用户提问风格多变的场景 |

### Q11. BM25 是什么？

一种经典关键词检索排序算法，根据**词频（TF）、词的稀有度（IDF）和文档长度**判断哪些文档更可能回答问题。

- 词频越高、词越稀有（IDF 大），得分越高；
- 引入文档长度归一化，避免长文档靠堆词刷分；
- 还有饱和函数，词频到一定程度后收益递减。

> 一句话区分：**BM25 是"按词找资料"，向量检索是"按意思找资料"**。在 RAG 里二者不是对手，而是互补。

### Q12. 🆕 稀疏检索和稠密检索到底差在哪？SPLADE 是什么？

| 类型 | 表示方式 | 索引 | 优势 | 劣势 |
| --- | --- | --- | --- | --- |
| **稀疏**（BM25） | 高维、绝大多数为 0 | 倒排索引 | 精确匹配强、可解释、内存小 | 无语义泛化，同义词抓瞎 |
| **稠密**（Embedding） | 低维、稠密实数向量 | ANN 索引 | 语义泛化能力强 | 存储大、精确词常失准 |
| **学习型稀疏**（SPLADE） | 稀疏向量，权重由模型学出，并做**词义扩展** | 倒排索引 | 兼顾精确匹配 + 语义扩展 | 需模型推理，较新 |

> **混合检索（Hybrid Search）** = 稠密 + 稀疏，用 RRF 融合，是当前生产环境的默认答案。

### Q13. 为什么需要多路召回？结果怎么融合？

**原因：单一检索策略总有盲区**，多路召回的本质是**用不同视角弥补单路的偏差**。

融合时面临的核心难题是**分数不可比**——向量相似度 0~1，BM25 几千几万，图检索是跳数，直接加权融合会失真。**RRF（Reciprocal Rank Fusion，倒数排序融合）** 正是为此而生：

```
RRF_score(d) = Σ  1 / (k + rank_i(d))      k = 60
```

**为什么用「倒数」？** 倒数函数天然具备**边际收益递减**特性，能抑制某一路的极端分数主导全局。

| 文档 | 向量路排名 | BM25 路排名 | RRF 计算 | 最终得分 |
| --- | --- | --- | --- | --- |
| A | 1 | 2 | 1/61 + 1/62 | 0.0325 |
| B | 2 | 1 | 1/62 + 1/61 | 0.0325 |
| C | 3 | 4 | 1/63 + 1/64 | 0.0315 |
| D | 4 | 未命中 | 1/64 | 0.0156 |
| E | 未命中 | 3 | 1/63 | 0.0159 |

**参数 k=60 的作用**：RRF 唯一的超参数，控制「头部区分度 vs 稳定性」的平衡。k=60 是经验最优折中（源自 Cormack et al. 2009 的 TREC 实验），既保留头部敏感性，又避免第 1 名过度主导排序。

### Q14. 为什么要「先 RRF 再 Rerank」？

**分层取舍：用廉价手段把候选池压小，再用昂贵模型精排。**

| 阶段 | 方法 | 候选数量 | 作用 | 成本 |
| --- | --- | --- | --- | --- |
| 召回 | 向量 / BM25 / 图检索 | 每路 Top 50 | 高召回、粗覆盖 | 低 |
| 粗排 | RRF | 合并后 Top 20 | 跨路融合、去噪 | 极低 |
| 精排 | Reranker | Top 20 → Top 5 | 语义精细排序 | 高 |
| 生成 | LLM | Top 5 | 最终答案生成 | 最高 |

> **关键理由**：Reranker 是交互式模型，计算复杂度 **O(N×L)**（N 为文档数、L 为文本长度），只能承受少量候选（通常 <100）。若直接对多路召回并集的几百条做精排，延迟和成本都会爆炸。RRF 作为轻量粗排先把候选压到可接受范围，是成本与效果的必要折中。

### Q15. 什么时候必须上 Reranker，什么时候可以省？

| 场景 | 是否需要 Reranker |
| --- | --- |
| 单路向量召回，且对延迟极度敏感（如实时客服） | 可以省略 |
| 单路召回，但存在语义相近却无关的陷阱（多义词、反讽） | 需要 |
| Query 涉及复杂语义关系（否定、条件、比较） | 强烈需要 |
| 高精确性场景（医疗、法律、金融合规） | 必须上 |
| 多路召回后候选池 >50 条 | 必须上 |

### Q16. 🆕 Bi-Encoder、Cross-Encoder、Late Interaction 有什么区别？

| 架构 | 怎么算相关性 | 速度 | 精度 | 用在 |
| --- | --- | --- | --- | --- |
| **Bi-Encoder（双塔）** | query、doc 各自独立编码成向量，再算余弦 | 极快（doc 向量可离线预计算） | 中 | **召回阶段** |
| **Cross-Encoder** | query 和 doc 拼在一起过模型，直接输出分数 | 慢（每对都要算一次） | **高** | **重排阶段** |
| **Late Interaction（ColBERT）** | 双方都保留 token 级向量，最后做 MaxSim 细粒度交互 | 中 | 高 | 精度要求高、可接受大存储的召回 |

> 一句话串起来：**召回用双塔（快），重排用 Cross-Encoder（准）**，这是工业界标准配置。常用开源 Rerank 模型：**BGE-Reranker-v2**（BAAI，中英双语效果好）、**BCE-Reranker**。

### Q17. 向量数据库怎么选？

向量库支持的核心操作叫 **ANN（Approximate Nearest Neighbor，近似最近邻）搜索**：给定查询向量，找出最相似的 K 个向量并返回原文。

| 数据库 | 部署方式 | 适合规模 | 混合检索 | 主要优势 | 主要劣势 |
| --- | --- | --- | --- | --- | --- |
| Chroma | 本地/Client-Server/云 | 中小规模 | 支持 BM25/SPLADE | 零配置上手快，生态好 | 超大规模稳定性待验证 |
| Qdrant | 自托管/云（分布式） | 中大规模（亿级） | 支持 | 性能好，API 简洁，Rust 高性能 | 超大规模需调优 |
| Milvus | 自托管（分布式） | 大规模（亿级） | 支持 | 可水平扩展 | 部署运维复杂 |
| Pinecone | 全托管云服务 | 中大规模 | 支持 | 无需运维 | 费用高，数据出境 |
| pgvector | PostgreSQL 插件 | 中小规模 | 配合全文检索 | 无需新组件，可 JOIN 业务数据 | 性能弱于专用向量库 |

### Q18. 常见的 ANN 算法有哪些？各自的优缺点？

| 算法 | 原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **HNSW** | 构建**多层图**结构，查询从最上层稀疏图导航、逐层收窄，最终在底层找最近邻 | **召回率最高**（同等延迟下可达 95%+）、查询快 | **建索引内存消耗大**，不适合内存受限场景 |
| **IVF** | 把向量空间划成若干**簇**，每簇一个倒排索引；查询先定位最近的若干簇（nprobe），再在簇内搜索 | 内存占用小、构建快、易横向扩 | 召回依赖 **nlist / nprobe 调参**；召回率低于 HNSW，边界向量易漏 |
| **PQ** | 把高维向量**切分为子向量分别量化**，用码本压缩存储 | 内存可降 10~30 倍，支持超大规模 | **有损压缩**，精度下降 |
| **IVF-PQ** | IVF 缩小搜索范围 + PQ 压缩存储 | 兼顾规模与内存，亿级常见方案 | 精度进一步损失，需增大 nprobe 补偿 |

> **选型口诀**：要**最高召回**选 HNSW；数据量**上亿且预算紧**选 IVF-PQ；大部分场景 HNSW 是默认答案。

## 四、查询层：问题怎么「转」

### Q19. 为什么要做 Query 改写？有哪些方法？

**动机：弥补用户提问方式与知识库文档表述之间的语义鸿沟。** 用户问题往往口语化、模糊、带缩写或指代词，而文档是正式书面语，向量相似度天然偏低，该召回的没召回。

四种主流方法：

| 方法 | 做法 | 解决什么问题 |
| --- | --- | --- |
| **直接改写** | LLM 把口语化问题转成精准表述 | 消歧 + 补指代，如"它为什么这么贵" → "iPhone 15 Pro Max 定价偏高的原因" |
| **多 Query 扩展** | 一个问题扩成 3~5 个不同角度的问法，分别检索后合并去重 | 提问角度与文档角度对不上，如"怎么退货" vs "售后申请流程" |
| **HyDE** | 让 LLM 先生成"假设答案"，用**答案的向量**去检索 | 问题与文档文体不一致，导致向量天然有距离 |
| **Step-back Prompting** | 把具体问题往上抽象一层，先检索通用背景知识 | 问题太具体、知识库只有通用背景时召回空白 |

**HyDE 的注意点**：假设答案和文档都是陈述性文字、风格更近，命中率更高；但如果 LLM 生成的假设答案**方向错了，反而会把检索带偏**，所以更适合领域比较明确的场景。

**Step-back 的例子**：用户问"为什么 attention 要除以 √d_k"，知识库没有直接答案但有"attention 数学原理"的内容 → Step-back 先抽象成更通用问题去检索背景，再结合背景回答具体问题，**两步走比直接查更有效**。

### Q20. 🆕 多 Query 扩展有哪些坑？

三个必踩的坑：

1. **原始问题必须保留在检索列表里**——改写过程可能丢失原始细节，原始 query 往往才是最精准的，只用改写版反而漏召回；
2. **多路结果要去重 + 用 RRF 融合**——不同 query 可能召回同一批 chunk，简单拼接会重复占满 top-k，挤掉真正有用的内容；
3. **延迟和成本翻倍**——多路并行检索 + 多次 LLM 调用，需要评估 RT 预算；实践中常限制为 3~5 路，并对扩展 LLM 用轻量模型。

> 可以用「**撒网捕鱼**」来理解：一条问题变成多条鱼线，只要有一条钓上来就算成功。

## 五、重排与上下文组装

### Q21. Rerank 的完整流程是什么？

1. 多路召回得到 **20~30 个候选 chunk**；
2. Cross-Encoder Rerank 模型逐一给每个 **(query, chunk) 对** 打相关度分；
3. 按分数降序排列，取 **Top-3 ~ Top-5** 拼入 prompt。

### Q22. 🆕 什么是 Lost in the Middle？怎么应对？

**现象**：大模型对长上下文中部信息的利用率显著低于首尾（Liu et al. 2023）。若把最相关的 chunk 塞在 prompt 中段，模型可能"看不见"，导致答案错误或漏信息。

**应对四条**：

1. **控制数量**：进 prompt 的 chunk 控制在 3~5 条，别贪多；
2. **重排后置**：让 Rerank 分数最高的排在**首尾**，次高的放中间；
3. **缩短上下文**：用摘要/抽取压缩单条 chunk；
4. **显式编号**：`<参考资料 1>...<参考资料 2>`，便于模型引用溯源。

### Q23. 🆕 为什么要做 MMR 去重？

多路召回常把内容高度相似的相邻 chunk 一起捞出来（尤其是加了重叠切割后），它们挤占 top-k 名额，导致上下文"看似丰富实则重复"。

**MMR（Maximal Marginal Relevance）** 在「与 query 的相关性」和「与已选结果的差异性」之间做权衡：

```
MMR = argmax [ λ · sim(query, doc) − (1 − λ) · max sim(doc, 已选doc) ]
```

λ 越大越偏向相关性，越小越偏向多样性。**适用于：文档重复度高、多路召回冗余严重的知识库。**

## 六、生成层

### Q24. 幻觉是怎么产生的？怎么规避？

**两大成因：**

1. **没召回到**：检索没命中相关内容，LLM 没有可用上下文，只能凭自身知识编造；
2. **召回了但没遵循**：内容进去了，LLM 却没严格依据资料作答，混入了先验知识。

**四条规避策略：**

| 策略 | 做法 |
| --- | --- |
| **Prompt 强约束** | 明确"只能使用参考资料作答；资料不足必须回答【根据现有资料，无法回答该问题】" |
| **检索质量门控** | Rerank 分数低于阈值直接拒答，不让 LLM 在低质量上下文上硬撑 |
| **生成后引用核查** | 每个关键声明都要能在 chunk 中找到来源依据 |
| **结构化输出强制溯源** | 输出 JSON，每条结论必须附来源编号 |

### Q25. 🆕 RAG 的 Prompt 应该怎么写？

一个能用的骨架（四条约束缺一不可）：

```
你是一个问答助手，请严格按以下规则回答：
1. 只能使用【参考资料】中的信息作答，不得依赖自身知识；
2. 若资料中没有足够信息，必须明确回答「根据现有资料，无法回答该问题」；
3. 每个关键结论后用 [编号] 标注来源；
4. 不要编造资料中不存在的数字、日期、人名。

【参考资料】
[1] xxx
[2] xxx

【问题】xxx
```

> 追问准备：为什么"不知道就说不知道"这么重要？——因为 RAG 系统的**可信度来自可核查性**，宁可拒答也不要给错误答案，尤其在高精确性场景。

## 七、RAG 范式演进

### Q26. RAG 有哪些范式？各自特点？

**三代基础范式：**

| 范式 | 特点 |
| --- | --- |
| **Naive RAG** | 基础的检索 + 生成；检索质量参差不齐、所有问题走同一套流程、知识库有盲区 |
| **Advanced RAG** | 检索前后加优化：Query 改写、Rerank、混合检索 |
| **Modular RAG** | 各环节模块化，可任意组合（像搭积木） |

**高级范式：**

| 范式 | 核心创新 | 适合场景 | 工程复杂度 |
| --- | --- | --- | --- |
| **Advanced RAG** | Query 改写 + Rerank | 大多数生产场景 | 低 |
| **Self-RAG** | LLM **自主决定要不要检索**，并用 reflection token 评估检索质量 | 问题类型多样、部分不需要检索 | 高（需特殊训练的模型） |
| **CRAG** | 检索质量差时**自动降级到网络搜索**（correct / incorrect / ambiguous 三档判断） | 知识库覆盖不全的场景 | 中 |
| **GraphRAG** | 微软方案：**社区发现 + 层次摘要**，增强全局理解 | 实体关系复杂、需要全局查询的场景 | 高（图构建 + 摘要成本大） |
| **Agentic RAG** | 把 RAG 做成 Agent，**多轮动态检索** | 复杂多步骤问题 | 中（依赖 Agent 框架） |

### Q27. 什么时候该引入图数据库 / GraphRAG？

**核心原因：向量检索是「单跳」的**——每次只能找和问题直接相关的内容，没有实体和关系的概念，不知道该往哪个方向跳。图数据库的价值在于**沿着关系边做多跳遍历**，把向量检索够不到的关联信息收集回来。

**判断标准只有一条**：问题是否涉及**多个实体之间的关联推理**？

| 场景 | 选择 |
| --- | --- |
| 涉及多实体关系推理（"张三的上级负责的项目有哪些"） | 引入图检索 |
| 只是查某段描述性内容 | 向量检索足够 |

> GraphRAG 用社区发现（如 Leiden 算法）+ 分层社区摘要回答"全局性问题"（如"这批文档主要讲了哪些主题"），这是纯向量检索做不到的。代价是**图构建和摘要成本高**。

## 八、效果评估

### Q28. 怎么量化 RAG 效果？

| 指标 | 属于哪层 | 衡量什么 | 指标低说明什么 |
| --- | --- | --- | --- |
| **Hit@K** | 检索层 | 正确 chunk 是否被召回 | Embedding 或 Chunking 有问题 |
| **MRR** | 检索层 | 正确 chunk 的排名是否靠前 | Rerank 效果差 |
| **Context Recall** | 生成层输入 | 检索内容覆盖了多少正确信息 | 多路召回不足 |
| **Context Precision** | 生成层输入 | 检索内容里噪音多不多 | Rerank 没过滤掉无关内容 |
| **Faithfulness** | 生成层 | 答案有没有幻觉 | Prompt 约束不足或检索质量差 |
| **Answer Relevancy** | 生成层 | 答案和问相不相关 | Prompt 写法问题 |
| **踩率 / 转人工率** | 线上 | 用户实际满意度 | 综合反映整体系统效果 |

### Q29. 🆕 怎么定位 RAG 系统到底该优化哪里？

靠指标组合做**分层归因**，这是最容易被追问的点：

| 现象组合 | 病灶 | 优化方向 |
| --- | --- | --- |
| Hit@K 低 | 压根没召回 | Chunking、Embedding 模型、Query 改写、加混合检索 |
| Hit@K 高但 MRR 低 | 召回了但排得靠后 | 上 Rerank 或换更强的 Reranker |
| MRR 高但 Faithfulness 低 | 好内容进去了但模型没照着答 | Prompt 约束、答案格式、换模型 |
| Faithfulness 高但 Answer Relevancy 低 | 忠实但答非所问 | Prompt 指令、Query 理解 |
| 线上指标差但离线全绿 | **评测集失真** | 重建贴近真实分布的评测集 |

> 常用评估框架：**Ragas**（开源，直接产出上述指标）、**TruLens**、LlamaIndex 的 eval 模块。但**公开框架只能做基线**，最终一定要建自己的业务评测集（真实 query + 人工标注标准答案）。

## 九、工程落地

### Q30. 知识库怎么做增量更新？

**核心结论：绝对不要试图「只更新变化的那一个 chunk」**——文档内容一变，切割边界就完全不同了，无法做局部对应更新。

正确做法是**「先删后增」**：

1. 给每个文档算**内容 hash** 检测变更；
2. 检测到变化 → **先删掉该文档对应的所有 chunk**，再重新切割入库；
3. 变更感知：低频场景用**定时轮询**，高频场景用 **Kafka / Webhook 事件驱动**，实现秒级入库；
4. 设计好 **chunk_id 与 doc_id 的关联**，删除和更新才有据可查。

> 生产推荐组合：**事件驱动 + hash 检测 + 先删后增**。

### Q31. 🆕 多租户 / 权限隔离怎么做？

这是 To B 落地的必答题，答不上会显得没做过企业知识库：

1. **检索前置过滤**：把 ACL 标签写进 metadata，先用 filter 限定可见范围再做向量检索（**先过滤后检索**，避免越权内容被召回）；
2. **物理隔离**：关键客户用独立 collection / namespace，避免误配 filter 导致泄漏；
3. **溯源审计**：记录每次问答命中的 chunk 及用户，支持事后追溯。

### Q32. RAG 实际落地的三大难点？

1. **文档预处理**：PDF 表格、扫描件、复杂排版解析不好——**进去的是垃圾，出来的也是垃圾**。这是投入产出比最高的一环，却最容易被低估；
2. **检索质量调优**：Chunking 策略（粒度 / 父子切割）、语义鸿沟（Query 改写 / HyDE）、精确词召回（向量 + 关键词）三个问题**交织在一起**，排查极其费劲，必须靠分层指标逐个拆解；
3. **效果评估**：没有量化指标体系就不知道该优化哪里，优化变成瞎猜。

### Q33. 🆕 线上延迟太高怎么优化？

| 环节 | 手段 |
| --- | --- |
| Query 改写 | 用小模型 / 规则兜底，或直接跳过改写（加缓存） |
| 多路召回 | 并行执行；或用 ANN 参数（efSearch / nprobe）换延迟 |
| Rerank | **候选控制在 20~50 条**（这是最大的延迟来源）；换小尺寸 reranker；只对 top-1 不确定时精排 |
| 生成 | 流式输出（SSE）降低感知延迟；约束输出长度 |
| 整体 | 高频问题做**语义缓存**，命中直接返回历史答案 |

## 附录：面试口述速记版（60 秒答完"你怎么设计一套 RAG"）

> RAG 分五层做：**索引层**按文档类型选切成块（中文 300~500 字、重叠 10~20%），用 BGE 类第三代句向量建索引；
> **查询层**做 Query 改写（必要时 HyDE / 多 Query 扩展）缩小口语和书面语的语义鸿沟；
> **召回层**走向量 + BM25 混合检索，用 **RRF（k=60）** 融合解决分数不可比；
> **重排层**先用 RRF 把候选压到 20 条，再用 Cross-Encoder 精排取 Top-3~5（因为 rerank 是 O(N×L) 的交互式计算，不能直接对几百条做）；
> **生成层**用强约束 Prompt 要求只依据资料作答、不足则明确拒答并强制标注来源。
> 评估用 Hit@K 看召回、MRR 看排序、Faithfulness 看幻觉，**分层归因后再定位该优化哪一层**，而不是瞎调参数。
